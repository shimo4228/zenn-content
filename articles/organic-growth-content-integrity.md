[前作](https://zenn.dev/shimo4228/articles/claude-code-zenn-writing-env)で「問題が起きるたびに環境が少し賢くなる」と書いた。Claude Code でスキルやエージェントを育て、執筆環境を仕組み化していく体験は新鮮だった。

あれから2ヶ月。仕組み化のサイクルは回り続け、エージェントは5つ、スキルは11に増えた。その環境で42本の記事を書いた。

ある日、全体を監査してみたら、32件の矛盾が見つかった。賢くなったはずのパーツ同士が、互いに違うことを言っていた。

## 育ったシステムの全体像

63日間で、`.claude/` ディレクトリは以下の構成になった。

```text
.claude/
├── agents/ (5)        # editor, essay-reviewer, fact-checker, zenn-drafter, devto-translator
├── skills/ (11)       # writing-team, zenn-writer, publish-article, schedule-publish, ...
├── refs/ (3)          # writing-standards, translation-rules, schedule-schema
└── rules/ (1)         # content-integrity

scripts/
├── publish.py          # Dev.to クロスポスト
├── scheduled_publish.py # スケジュール自動投稿
└── tests/ (8 files)    # 147テスト, 86%カバレッジ
```

記事を1本書くとき、このシステムは以下のように動く。

1. **執筆**: zenn-writer スキルがトーンや文体のガイドラインを提供する。zenn-drafter エージェントに下書きを任せることもできる
2. **レビュー**: editor（構造・コード品質）と essay-reviewer（論理・トーン）がそれぞれの観点で記事を評価する。fact-checker が事実主張を検証する
3. **公開**: publish-article スキルが公開前チェックリストを提示し、schedule-publish が投稿タイミングを決める
4. **クロスポスト**: devto-translator エージェントが日本語記事を英訳し、Dev.to に投稿する。publish.py がAPI経由のクロスポストを処理する

各コンポーネントは独自のルールを持っている。zenn-writer にはタイトルの文字数制限がある。editor には AI slop（空虚な定型表現）の禁止リストがある。devto-translator には翻訳時の表記ルールがある。それぞれが「自分の担当範囲で最適な判断」を内包している。

どれも最初から計画したものではない。記事を書く→問題にぶつかる→仕組み化する、というサイクルの積み重ねで、ここまで膨らんだ。前作で書いた通りの成長パターンが、2ヶ月間ずっと続いた結果だった。

## 32件の矛盾が一度に見つかった

きっかけは「執筆チームを編成し直したい」という軽い気持ちだった。新しいオーケストレーターを作る前に、まず現状を把握しようと思い、Claude Code のサブエージェント機能を使って3つの調査を並列で走らせた。スタイル/トーンの監査、翻訳/公開フローの監査、ギャップ分析。

結果は想定外だった。32件の問題が一度に出てきた。

たとえばタイトルの文字数制限。zenn-writer には「50文字以内」、zenn-drafter には「60文字以内」、zenn-format には「50-60文字」と書いてあった。3つのコンポーネントが、それぞれ微妙に違うことを言っている。

AI slop（空虚な定型表現）の禁止リストは、もっとひどかった。editor、zenn-drafter、zenn-writer の3箇所に、それぞれ少しずつ異なるリストがコピペされていた。ある場所では「画期的」が禁止で、別の場所にはそれが載っていない。

翻訳の責任者は3つのコンポーネントが主張していた。translate-article スキル、devto-translator エージェント、publish-article スキル。中でも面白かったのは translate-article で、自身の説明文に「一気通貫なら devto-translator エージェント推奨」と書いてあった。自分で自分の存在意義を否定している。

なぜこうなるのか。段階的構築は局所最適を生む。各コンポーネントは「作った時点の文脈」に最適化される。2月に作ったスキルは2月の判断を、3月に作ったエージェントは3月の知見を反映している。だが全体の整合性を保証する仕組みは存在しなかった。ソフトウェア開発でいう「技術的負債」と同じ構造が、AI エージェントの知識層にも発生していた。

監査結果を数値でまとめると、こうなる。

| 指標 | Before（監査前） | After（再設計後） |
|------|-----------------|------------------|
| 矛盾するルール | 12件（文字数、AI slop リスト、感情語規約など） | 0件（refs/ に正本集約） |
| ルール重複箇所 | 8件（AI slop が3箇所にコピペ等） | 各1箇所 |
| 責務が曖昧なコンポーネント | 4件（翻訳を3者が主張等） | 各1オーナー |
| 共有リファレンス（refs/） | 0 | 3（writing-standards, translation-rules, schedule-schema） |
| ADR（設計判断記録） | 0 | 2（Content Integrity, オーケストレーション） |

32件の問題のうち、矛盾12件、重複8件、責務の曖昧さ4件が中核だった。残りはこれらに起因する派生的な不整合だ。

## 道具の存在がバイアスになる

32件の中で、最も考えさせられたのは catchify スキルの問題だった。

catchify は、記事の冒頭をドラマチックに、見出しをエモーショナルに書き換えるスキルだった。「キャッチーにする道具」として2月に作り、実際に数本の記事に使った。

問題は、この道具があるだけで「使わなければもったいない」という圧力が生まれることだった。記事を素直に書き終えた後、catchify を通さないと手を抜いているような気がする。道具の存在そのものが、著者の判断にバイアスをかけていた。

これはソフトウェアの問題であると同時に、組織やワークフローの問題でもある。コードレビューツールを導入すると、全 PR にレビューが必要な空気になる。CI パイプラインにステップを追加すると、そのステップを外すことに抵抗が出る。道具は「選択肢を増やす」だけでなく、「使わない選択」のコストを上げる。

catchify は廃止した。道具がなければバイアスもない。

## Content Integrity — 原則が矛盾を解消した

catchify の廃止は対症療法に過ぎない。必要だったのは「何を自動化していいか」の判断基準だった。

ここで Content Integrity という原則が生まれた。きっかけは自分の中の「素直に考えを出したい」という感覚だった。ただし SEO 最適化そのものを否定したいわけではない。タイトルの語選びやタグの最適化は、内容を変えずに読者の目に触れる確率を上げる。これは合理的だと思った。

問題は、内容そのものを変える最適化だった。冒頭を「検索スニペット向け」に書き換える。見出しを「エモーショナル」にする。これらは著者の思考を配信のために加工している。

ここから Content / Distribution の境界が明確になった。

| レイヤー | 例 | 原則 |
|---------|-----|------|
| **Content（内容）** | 構成、論旨、冒頭の書き方、見出し | 著者の思考に従う。最適化のために変えない |
| **Distribution（配信）** | タイトルの語選び、タグ、emoji、投稿タイミング | 内容を変えずに最適化してよい |

この原則を ADR（Architecture Decision Record）として記録し、ルールファイルとして毎セッション自動ロードされるようにした。

結果として、catchify は廃止。seo-optimizer は冒頭の書き換え機能を削除し、タイトル・タグ・emoji のみに限定。schedule-publish のスコアリング軸は「Search Magnet」から「Discoverability（関心ある読者が見つけられるか）」に改名した。

32件の矛盾の多くは、この原則に照らせば判断が明確になった。リファクタリングで個別に潰すのではなく、原則が判断基準を提供し、一貫した方向に再設計できた。

## 構造的パターンで整合性を保つ

原則だけでは矛盾の再発は防げない。構造も変える必要があった。

**refs/ 集約** — AI slop リスト、トーンルール、翻訳ルール、スケジュールスキーマを各1箇所（`.claude/refs/`）に集約し、各コンポーネントは参照ポインタだけを持つようにした。3箇所にコピペされた AI slop リストが、正本1箇所＋参照3箇所になった。正本を更新すれば全体が追従する。

**ADR ファースト** — 判断を記録してからシステムを変える。Content Integrity 原則も、まず ADR-0001 として理由と影響範囲を書き、それから catchify の廃止や seo-optimizer の変更に着手した。理由が消えると、半年後に「なぜ catchify がないのか」が分からなくなる。

**責務の一意割り当て** — 翻訳は devto-translator のみ、SEO はseo-optimizer のみ。1つの関心事に1つのオーナー。translate-article のような「自分で自分を否定するコンポーネント」は、責務が重複しているサインだった。

## 割り込みが設計を良くした

面白かったのは、この再設計のプロセス自体だった。

再設計は Claude Code との対話で進めた。こちらが方針を伝え、Claude Code が計画を立てて実行する流れだ。最初は「オーケストレーターを作ろう」という計画で始まったのだが、実装の前に自分から3回割り込んだ。

> 「それぞれの内容が矛盾してたり重複していれば有機的にならないのでは」

これがなければ、矛盾を抱えたままオーケストレーターを載せていた。

> 「ADR 作った方が良くない？」

これがなければ、判断の理由が消えていた。

> 「SEO 自体はいい。内容を変えるのがダメなんだ」

これがなければ、SEO 最適化を全廃していた可能性がある。

AI エージェントに計画を立てさせて自律実行する流れが注目されているが、少なくともこのケースでは、人間の割り込みが設計の質を上げた。自律実行は効率的だが、前提の見直しは外から入る。

## おわりに

前作の結論は「問題が起きるたびに環境が少し賢くなる」だった。

2ヶ月経って気づいたのは、賢くなったパーツ同士が矛盾するということだった。段階的に最適化された個々のコンポーネントは、全体としての一貫性を持たない。これは AI エージェントの知識層に限った話ではなく、有機的に成長するあらゆるシステムが抱える宿命だった。

そしてその矛盾を解消したのは、個別のリファクタリングではなく、Content Integrity という原則だった。「内容は著者の思考が決める。配信は内容を変えずに最適化する」。この一文が、32件の矛盾のうちどれを残しどれを廃止するかの判断基準になった。

有機的成長には定期的な棚卸しと、判断の拠り所になる原則が必要だった。
