## 元はただのプロンプトだった

Chain-of-Thought (CoT) を覚えているだろうか。「Let's think step by step」と一文添えるだけで LLM の推論精度が上がる。初期のプロンプトエンジニアリングで発見されたテクニックだ。あれはもともとモデルの外にあった。ただの文字列に過ぎなかった。

今は違う。CoT の概念は現在の推論モデル（GPT-5、Claude の extended thinking、Gemini の thinking mode 等）の源流になっている。これらのモデルは、強化学習によって推論能力をトレーニング時に獲得した。推論の過程はモデルの中に入った。Claude の extended thinking のように思考過程を可視化するモデルもあるが、多くの場合、その詳細は外からは見えない。

Wharton GAIL の研究では、推論モデルに初期の CoT プロンプトを渡しても効果がほぼなく、むしろ冗長性を生じて逆効果になるケースが報告されている。外にあったものが中に入った結果、外から同じ型を注入しても効かなくなっている。

ここで用語を整理しておく。AI 安全性の文脈では、LLM の重みを変えず外側へ構築される構造を scaffolding（足場）と呼ぶ[^1]。system prompt、ツール定義、RAG パイプライン、エージェントループなどがこれにあたる。

AI エージェントのブラックボックスには、見えない**原因**が2つある。技術の限界と、ビジネスの都合だ。この2つは性質が異なるから、打ち手も異なる。

```text
■ 層1: モデル内部（weights）— 技術的に不可視
  例: 言語能力、常識推論、倫理判断、CoT（内在化後）
  見えない理由: 重みの中に溶け込んでおり、原理的に取り出せない

■ 層2: Scaffolding（足場）— 技術的には可視、商業的に秘匿
  モデルの外側で人間が構成する部分の総称[^1]
  見えない理由: 競争優位の源泉であり、公開するインセンティブがない

  例: system prompt、ペルソナ設定、ツール定義、RAG、
      エージェントループ、安全性ゲート、セッション管理、
      harness（実行時の制御層）
```

学術的には scaffolding（構築時）と harness（実行時）を区別する試みもあるが、この境界は急速に曖昧になっている。永続メモリ、スキルエコシステム。OpenClaw のようなモデル非依存のエージェント基盤は、Claude でも GPT でもローカルモデルでも交換可能に動く。Anthropic はサブスクリプション経由での利用をブロックしたが、scaffolding がモデルをコモディティ化する力学は止まらない。scaffolding の範囲はエージェント開発の盛り上がりに合わせて拡大し続けている。この記事では harness を含む広義の意味で scaffolding と呼ぶ。

自分のエージェントを運用してきた所感がある。scaffolding を適切にコンテキストマネジメントしていると、モデルはただの推論器で、エージェントの本質は scaffolding の側にあると感じるようになった。人格、能力、判断基準 — すべて scaffolding の中にある。モデルを差し替えても scaffolding が同じなら、エージェントは同じように振る舞う。以前「[エージェントの本質は記憶ではないか](https://zenn.dev/shimo4228/articles/agent-essence-is-memory)」と書いたことがある。あの記事での「記憶」— EpisodeLog、KnowledgeStore、Identity の3層 — は、今の用語で言えばすべて scaffolding だ。当時はまだこの区別を持っていなかったが、scaffolding という概念を得たことで、あの直感を構造的に説明できるようになった。

**scaffolding は技術的には見えるのに、実際には見えない。** この落差がどこから来るのかが、この記事の主題になる。

## ブラックボックスの二層構造

エージェントをスクラッチで組んだ経験から、ブラックボックスには2つの異なる層があると感じている。

**層1: モデル内部 — トレーニングによる内在化**

倫理、世界観、推論の型。これらは事前学習と強化学習の過程で重み（weights）に溶け込んでいる。一見すると技術的な必然に見える。しかし個人的には、この「内在化」の範囲は世間が思っているほど不可避ではないのではないか、と感じている。

前述の CoT がわかりやすい例だ。CoT はもともとモデルの外にあった。内在化されたのは、外部プロンプトでは達成できない性能向上 — 自己修正、バックトラック、推論時計算量のスケーリング — を得るためだった。膨大なコストを払ってでも内在化する価値がある、という性能優先の設計判断だ。技術的に不可避だったわけではなく、可視性とのトレードオフを含む選択だった。

もちろん、すべてを外に出せるわけではない。大規模な事前学習で獲得された暗黙知は、構造的に外在化しにくい。自分のエージェントでは、アイデンティティ・職業倫理・スキル・判断ログといった scaffolding の要素はすべてファイル化できた。一方、モデルが事前学習で獲得した言語能力や常識推論は外に出しようがなかった。「どこまでが不可避で、どこからが都合か」の線引きは、少なくとも自分の経験では scaffolding とモデル内部の境界に重なる。しかし、この線引きは現在の議論では曖昧なまま放置されている。

**層2: Scaffolding — 技術的には見えるが、秘匿されている**

モデルの外側にはもう1つの層がある。system prompt、ペルソナ設定、ルール、ツール定義 — scaffolding だ。この層は技術的には可視化できる。ファイルにして git で管理すれば、差分の追跡が可能だ。

しかし、多くの場合これは秘匿されている。理由は資本主義の競争原理にある。

プロンプトの設計やモデルの調整手法は、プロダクトの差別化要因になる。見せれば競合にコピーされる。この商業的合理性が、安全性の可視化との間にトレードオフを生んでいる。**見えるようにすべきだが、見えないようにしないと商売にならない。**

AI 安全性の研究では、scaffolding を含む post-training enhancements がベンチマーク性能を 5〜20倍増幅しうると指摘されている[^2]。つまりモデル単体の安全性評価では不十分で、scaffolding 込みの評価が必要になる。しかし scaffolding が秘匿されていれば、外部からの安全性評価は構造的に不可能だ。

2026年3月31日、Anthropic が Claude Code v2.1.88 のリリースミスで完全なソースコード（約51万行）を露出させる事故があった。npm パッケージにソースマップが含まれ、数時間で大量にミラー・fork された。象徴的なのは、AI 安全性を最も重視する企業の1つである Anthropic ですら、scaffolding を公開していなかったという事実だ。公開されれば外部から検査可能になり、安全性の議論は前進する。それでも公開できない。競争環境がそれを許さない。

## 見せたいが見せられない

AI の安全性議論の根底に、この矛盾がある。

安全性の観点からは、エージェントの振る舞いの因果を辿れるようにしたい。そのためには scaffolding の可視化が不可欠だ。しかしビジネスの観点からは、scaffolding は競争優位の源泉であり、公開するインセンティブがない。

自分が個人プロジェクトでエージェントの全構成要素をファイル化できたのは、この矛盾が存在しなかったからだ。秘匿する商業的理由がなかった。その代わりに、可視化の恩恵 — デバッグ可能性、変更追跡、因果の遡行 — だけが丸ごと残った。

逆に言えば、商業的な文脈でエージェントを作っている組織は、この矛盾を構造的に抱えている。安全のために可視化したいが、ビジネスのために秘匿したい。この2つの力が拮抗するところに、現在のブラックボックス問題がある。

注意しておきたいのは、これは「企業が悪い」という批判ではないということだ。競争環境で差別化要因を守ろうとするのは合理的な行動であり、その合理性を否定しても問題は解けない。問題は、その合理性と安全性要求が同じ地点で衝突している構造そのものにある。技術だけの話でも、倫理だけの話でもない。市場の力学と安全性要求が構造的に噛み合わない、というレイヤーの話だ。

この矛盾を解く方法があるとすれば、それは「全部見せろ」でも「全部隠していい」でもなく、**何を可視化すれば因果が辿れるか**の最小セットを定義する作業になるだろう。

自分のエージェントでは、全行動を append-only の JSONL ログに記録している。scaffolding の全構成要素（identity、constitution、スキル、ルール）は専用のログとして保存し、変更には人間の承認を必須にしている。設計判断は ADR として文書化した。事故が起きたとき「どのバージョンの scaffolding で、どの行動ログを経て、その出力に至ったか」を辿れる。scaffolding の全文を公開しなくても、因果追跡に必要な情報は開示できるはずだ。その線引きをどこに置くかが、次の議論の焦点になる。

## 技術と社会構造の時間軸

ここでもう1つ、見落とされがちな軸がある。時間だ。

技術と社会構造の関係を歴史に沿って眺めると、新しい技術が社会に広く受け入れられる過程は、多くの場合同じ順序を辿っている。

**技術側の変化 → 社会側の認知変化 → 構造の再編成 → 技術の本格普及**

わかりやすい例として印刷技術を挙げる。グーテンベルクの活版印刷(1440年代)から、印刷文化が知識の保存・標準化・普及を通じて社会を変容させるまでに数世紀を要した[^3]。電気やインターネットでも、技術の商用化から社会制度の再編成までには数十年単位の遅延が観察されている。少なくともこれらの事例では、技術の変化速度と社会構造の変化速度に大きな差があった。

そして、この不整合が大きすぎた技術は、どれだけ優れていても広く実務化できなかった。認知の変化が追いつく前に「便利さ」だけで押し切ろうとした技術は、一部のニッチで動くことはあっても、社会全体に広がらないまま停滞した。

AI エージェントも、この時間軸の中にいる。

現在の AI の技術変化の速度は、過去の技術革新と比べても際立って速い。一方で、社会構造 — 法制度、組織の意思決定プロセス、業界の規制枠組み、人々の働き方 — の変化速度は、過去とさほど変わらない。人間が新しい概念を受け入れ、制度として定着させるまでの時間は、技術の種類にあまり依存しない。認知の変化は、技術ではなく世代と経験の関数に近いからではないか。

この速度差が意味するのは、AI エージェントの技術側がどれだけ成熟しても、社会構造が追いつくまでの「ギャップ期間」は必ず存在する、ということだ。そしてこのギャップ期間こそが、エージェントが実際に社会で機能できるかどうかの試験場になる。

## 構造を変えるか、構造に合わせるか

「構造側がエージェントに合わせて変わるべきだ」という声がある。承認ゲートや監査証跡の要求水準が AI の速度に見合っていない、という主張だ。筋が通っている部分もあるし、構造側が変わるべき部分は確かに存在する。

問題は時間軸だ。前節で見た通り、社会構造の変化には技術の変化と比べて大きな遅延が伴う。「構造側が変わればいい」は長期的には正しい可能性がある。しかし、構造変革を待つ数十年の間にもエージェントは動く必要がある。既存の構造と整合を取りながら動くエージェントを先に作り、その実績の積み重ねで社会側の認知が変わる — 歴史的に見て、この順序を飛ばせた技術はほとんどなかった。この点は[前の記事](https://zenn.dev/shimo4228/articles/agent-causal-traceability-org-adoption)で具体的な設計判断として掘り下げた。

## 議論のプレイヤー構成

時間軸の問題を踏まえた上で、もう1つ気になっていることがある。なぜ「構造を壊せ」が支配的な声になっているのか。議論のプレイヤー構成に偏りがあるからではないか。

開発の最前線にいる人は「自分で因果を追える側」にいる。出力を見れば原因を推定できるし、プロンプトも自分で調整できる。この人たちにとって、承認ゲートや監査証跡は自分の能力で代替できる「非効率な儀式」に見える。一方、運用・監査・事故後処理の側にいる人たちの声は、技術カンファレンスのスピーカーリストにはあまり載らない。

開発者の視点から合理的に見える「構造を壊せ」は、運用者の視点からは「壊されたら困る」に映っている。これは善悪の話ではなく、視野の話だ。同じシステムの異なる断面を見ている。片方の断面だけで設計された技術は、もう片方の断面で拒絶される。

## 見えない理由を見る

ブラックボックスの中身を問うことは重要だ。しかしそれと同じくらい、**なぜ見えないのか — 技術の限界か、ビジネスの都合か、社会の速度か — を分けて見る**ことが次の議論の土台になる。この3つを混ぜたまま「ブラックボックスは危険だ」と言っても、打ち手が見えない。分けて見れば、少なくとも打てる場所と打てない場所の区別はつく。
