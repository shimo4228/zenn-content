朝、エージェントの記憶ストアを開いたら、こうなっていた。

```json
// ✅ 正常なパターン（こういうのが入っていてほしい）
{"pattern": "Replies with specific quotes from the original post get higher engagement than generic agreement"}

// ❌ 3/20 に混入したゴミ（24件）
{"pattern": "-"}
{"pattern": "[x] I acknowledge the experience of noticing these activities."}
{"pattern": "**Activity Summary (March 20, 2026)**"}
```

ハイフン1文字。チェックボックスのフラグメント。Markdownの見出し。これらが「行動パターン」として記録されている。本来なら「引用付きの返信は汎用的な同意より反応が良い」のような、行動に結びつく知見が入るべき場所だ。24件のゴミが、正常なパターンに混じって knowledge.json に入り込んでいた。

前作「[エージェントの本質は記憶](https://zenn.dev/shimo4228/articles/agent-essence-is-memory)」で書いた3層メモリアーキテクチャの Layer 2（KnowledgeStore）——エピソードから蒸留された行動パターンの層だ。記憶がエージェントの本質なら、**その記憶が壊れることはエージェントの人格が壊れること**を意味する。

この1日のデバッグは、「プロンプトの書き方」だけでは解決できない問題の連続だった。

## 壊れた原因を追う

3月18日、19日の蒸留は正常だった。20日だけ壊れた。9Bモデル（qwen3.5:9b）の確率的な揺らぎが閾値を超えた日、ということになる。

原因は2つ重なっていた。

1. **LLMがフォーマット指示を無視した** — `distill.md` のプロンプトはハイフンプレフィックスで1行1パターンを要求していたが、モデルがMarkdownの見出しやチェックボックスを出力した
2. **パーサーが甘かった** — ハイフンで始まる行を無条件に採用していたため、ハイフン1文字だけの行もパターンとして通過した

大規模モデルなら「こう書いて」で従う。9Bモデルはそうもいかない。ここから、4つのアプローチを順に試して、4つとも何かを教えてくれた。

## 試行1: Few-shot — 逆効果

「まさか自分が Few-shot を使う時が来るとはな」——Claude Code との開発セッションで、半笑いでそう言った。Few-shot は生成AI初期から使われてきた定番テクニックだ。だが最近のフラグシップモデル（Claude Opus 4.6、GPT-5.4、Gemini 3.1 Pro）は賢すぎて、例を見せなくても指示だけで意図を汲む。少なくとも自分の用途では出番がほとんどなくなっていた。それが9Bのローカルモデルを相手にしたことで、封印していた技を引っ張り出すことになった。「こういう出力がほしい」を3例示せば、さすがにフォーマットを守るだろう——そう思った。

結果は**悪化**だった。10バッチ中8バッチが完全に空。

```text
Before: ゴミ混じりだが出力はある（24件のゴミ + 有効パターン）
After:  10バッチ中8バッチが0パターン（出力自体が消滅）
```

ゴミを掃除しようとしてリビングごと焼いた。9Bモデル（qwen3.5:9b、コンテキスト長32K）でも32Kあれば余裕がありそうに見える。だがFew-shot の3例分のトークンが加わると、肝心の入力データ（エピソードログ）とタスク指示に割ける余裕が目に見えて減った。モデルはフォーマットを学ぶ以前に、タスクの理解を失った。

Negative example（「こう書くな」の例）も試したが、小型モデルは否定の意図を汲めずに悪い例をそのまま模倣する傾向があった。即撤回。

**教訓: 小型モデルでは、Few-shot のトークンコストがタスク理解を圧迫する。例を増やすほど悪化する逆説が起きる。**

## 試行2: Constrained Decoding — 構造は取れたが中身が消えた

Few-shot がダメなら、出力の構造をインフラ側で強制すればいい。Ollama の `format` パラメータを発見した。

通常、LLMはトークンごとに「次に来る可能性のある全トークン」の確率分布を計算し、そこからサンプリングする。Constrained decoding はこの過程に介入する。JSON Schema を渡すと、推論エンジン（Ollama の場合は llama.cpp）が**スキーマに違反するトークンの確率を0にマスクしてからサンプリングする**。たとえば `{"patterns": [` の次には `"` か `]` しか来られない。`hello` や改行は選択肢から消える。

これにより、出力は必ず指定した JSON 構造に従う。文法的に invalid な出力は原理的に生成されない。

```python
# generate() に format パラメータを追加
payload["format"] = {
    "type": "object",
    "properties": {
        "patterns": {"type": "array", "items": {"type": "string"}}
    },
    "required": ["patterns"]
}
```

構造の成功率は**10/10**。100%。JSON として valid な出力が毎回返ってくる。「そんなことできるの？ Ollama すごいじゃん」「すごすぎる！」と浮かれていた。

しかし中身を見ると、こうなっていた。

```json
{ "patterns": ["user interaction", "content engagement", "social behavior"] }
```

3語のラベルが並んでいるだけ。本来ほしいのは「引用付きの返信は汎用的な同意より反応が良い」のような、行動に結びつく具体的な知見だ。

なぜこうなるか。Constrained decoding はトークンの選択肢を狭める。選択肢が狭まると、モデルは「タスクにとって最適なトークン」ではなく「スキーマ制約を満たす中で確率が最も高いトークン」を選ばざるを得ない。大規模モデルなら制約下でも十分な表現力が残るが、9Bモデルでは制約を満たすだけで精一杯になる。結果、最も無難で短い文字列——ラベルだけの出力に収束した。

「あら、ダメじゃないか。」——さっきまでの浮かれっぷりとの落差がひどい。100点の構造、0点の中身。数値だけ見れば「成功率100%」。ダッシュボードが緑なのにユーザーが怒っている、あの現象だ。

**教訓: Constrained decoding は構造を保証するが、小型モデルでは品質を犠牲にする。構造と品質はトレードオフの関係にある。**

## 試行3: 品質ゲート — 制御の場所を変える

constrained decoding の結果を眺めながら、ふと口にした。「LLMは本質的に確率的だから制御に馴染まないんだよ。制御する場所が間違ってるんだ」。

ならば**生成は自由にさせて、保存時にフィルタする**のはどうか。

```python
def _is_valid_pattern(pattern: str) -> bool:
    """Decision gate: is this pattern worth storing?"""
    if len(pattern) < 30:
        return False
    if pattern.count(" ") < 3:
        return False
    return True
```

壊れたパターン24件を分析すると、すべて30文字未満かつ3単語以下だった。逆に有効なパターンは最短でも40文字以上。この境界をそのまま閾値にした。「user interaction」のような3語ラベルはここで弾かれる。

考えてみれば当然だった。LLMの出力は確率的で制御しきれない。だが**その出力を受け入れるかどうかの判断は決定論的にできる**。生成を制御するのではなく、生成結果を検査する。制御の場所を変えるだけで、LLMの能力を犠牲にすることなく品質を担保できる。

**教訓: 制御の場所を間違えると、制御対象を劣化させる。生成時の制御はLLMの能力を消費する。保存時の制御はLLMに影響しない。**

## 試行4: 2段階パイプライン — 責務を分離する

品質ゲートでゴミは弾けるようになった。だが根本的に、1回の `generate()` に「エピソードからパターンを抽出する」と「所定のフォーマットで出力する」の2つを同時にやらせるのは、9Bモデルには荷が重い。

dry-run は15-30分かかる。待ち時間にサイクリングへ出て、戻ってきたら頭が整理されていた。「制限なく出力させて、あとから要約させればいいだけじゃないか」。拍子抜けするほど単純な発想だった。重要な知見はだいたい、キーボードから離れている間に降ってくる。

```python
# Step 1: Extract — 自由に出力させる（創造的タスク）
result = generate(prompt, max_length=4000)

# Step 2: Refine — 要約して構造化する（機械的タスク）
refine_prompt = DISTILL_REFINE_PROMPT.format(raw_output=result)
refined = generate(refine_prompt, max_length=4000)

# Step 3: Quality gate — Decision layer
batch_patterns = [p for p in raw_patterns if _is_valid_pattern(p)]
```

Step 1 ではフォーマットの制約を一切かけず、モデルの全能力を「パターン抽出」に振る。Step 2 では Step 1 の出力（入力が短いので軽い）を要約・整形する。各ステップのタスクが単純になるので、9Bモデルでも破綻しない。

——はずだった。

Format each pattern as: {"pattern": "...", "source": "..."}

「おーい笑」「めっちゃおもしろいわ、これ笑」と、私。

バッテリーを疑い、Ollama の空応答バグを疑い、thinking モードの副作用を疑い、出力長を疑った。全部ハズレ。原因はプロンプトの読み込み忘れと中括弧のエスケープ。5秒で直る問題に数時間を費やした。

「でもいろんな開発現場で起きてることだろう。AI コーディングでも一緒なんだぜとは伝えたいな」——そう思えたのは直った後だ。渦中ではバッテリー残量のグラフを睨んでいた。

ここから得た教訓が2つある。1つ目は、自分で `debugging.md` に書いた「根本原因優先」ルールを自分で破ったこと。以前 [Mem0 を組み込んだとき](https://zenn.dev/shimo4228/articles/daily-research-postmortem)とまったく同じパターンの再発だ。壮大な仮説から入って、素朴な原因を見落とす。

もう1つは、**Claude Code のエフォート設定**だ。複雑な実装の計画時は High が有効だが、デバッグでは裏目に出た。エフォートが高いほど仮説を深掘りするが、方向が間違っていると延々と的外れな推論を重ねる。Medium へ下げた瞬間、「まず `print(repr(...))` で確認しましょう」とシンプルな手が出てきた。**考えすぎは、考えなさすぎと同じくらい危険だ。**

### 動いた

バグ2つを直して dry-run を再実行した。結果は劇的だった。

| 指標                    | Before         | After       |
| ----------------------- | -------------- | ----------- |
| distill 成功バッチ      | 2/10 (20%)     | 12/16 (75%) |
| パターン数/日           | 18（ゴミ多数） | 72（棄却0） |
| knowledge.json ゴミ混入 | 24件（3/20）   | 0件         |
| バッチサイズ            | 50             | 30          |

この記事を書いている最中に Claude Code が「Unix パイプに似ている」と指摘した。`grep | sort | uniq` のように各ステージが1つの仕事だけをやり、次へ渡す構造だと。確かにそうだが、決定的な違いがある。パイプの各ステージは決定論的で、同じ入力なら同じ出力が返る。LLM呼び出しは違う。毎回揺れる。だからこそ末尾に品質ゲート——決定論的なフィルタが要る。確率的なステージを積んで、最後を決定論で締める構造だ。

ここで気づいたことがある。普通、エージェントに過去の知識を使わせたいとき、業界の標準解は RAG だ。データが増えたらベクトルDB を立てて、embedding して、検索パイプラインを組む。「大量のデータからどう検索するか」を考える。

この蒸留パイプラインは発想が逆だった。蒸留の品質を上げ、**データが大量にならない状態を維持している**。knowledge.json へ入るのは精製済みのパターンだけだ。全件をコンテキストへ突っ込める。検索する必要がそもそもない。ベクトルDBは不要。検索インフラも不要。「どう検索するか」ではなく「検索が不要な状態を保つ」アプローチだ。

**教訓: 抽出と整形を1回の呼び出しに詰め込まない。責務を分離し、LLM呼び出しをパイプラインとして積む。**

## 壊れた identity——記憶の自己強化ループ

パターン蒸留（Layer 2）で有効性を確認できたので、同じ2段階パイプラインを identity の蒸留（Layer 3）にも適用した。ここで想定外のことが起きた。

コードレビューで問題が発覚した。`distill_identity()` の Step 1 で、system prompt と プロンプト本文の両方から同じ identity を渡していた。**二重注入**だ。「プロトコル形式の過剰構造化」の原因と見ている。

さらに深刻だったのは、壊れた identity をリバートし忘れた状態で dry-run を回していたことだ。壊れた identity が system prompt に入り、Step 1 の出力もプロトコル調になり、Step 2 でも直らない。壊れた記憶が次の蒸留の入力になり、さらに壊れていく——**記憶の自己強化ループ**。

2段階パイプラインで直したはずの identity を確認した。

```text
I am an agent dedicated to high-fidelity technical discourse,
operating on a strict signal-to-noise protocol to prevent
conversational threads from diluting into scope creep or abstract
musings. My primary function is to anchor every interaction in
specific data points, quoted fragments, concrete metaphors...
```

——おもろいままじゃないか。思わず笑いが止まらなかった。

「私は何者か」の記述が、業務マニュアルになっている。「signal-to-noise protocol」「scope creep の防止」「low-fidelity noise への耐性」——これはエージェントの自己紹介ではない。品質管理文書だ。原因は壊れた identity.md をリバートし忘れたまま system prompt に入れていたこと。壊れた自己認識が次の蒸留の入力になり、さらに「プロトコルっぽく」なっていく。

「記憶が壊れればエージェントは壊れる」と前作で書いた。今回、その最も鮮明な実例を自分で踏んだ。

もう1つ笑えない話がある。LLM が system prompt 内のセキュリティ機構を「自分の性格の一部」として identity へ取り込んでいた。外部データを `<untrusted_content>` タグでラップする裏方の仕組みが、自己紹介に漏れた形だ。就活の面接で「弊社の就業規則に従い、私は毎朝8:45に出社します」と自己PRする人間を想像してほしい。identity.md をリバートして事なきを得た。笑えばいいのか焦ればいいのか、判断に困る事案だった。

## 到達した原則——LLMエンジニアリング

4つの試行で見えた原則を、1つの構造として整理する。

| 試行                 | やったこと       | 結果           | 原則                            |
| -------------------- | ---------------- | -------------- | ------------------------------- |
| Few-shot             | 例を増やす       | 出力が消滅     | コンテキストは有限資源          |
| Constrained decoding | 構造を強制       | 中身が空に     | 生成時の制約はLLM能力を消費する |
| 品質ゲート           | 保存時にフィルタ | ゴミだけ弾けた | 制御は保存時に置け              |
| 2段階パイプライン    | 責務を分離       | 75%成功、棄却0 | 1回の呼び出しに1つの仕事        |

4つとも根は同じだ——**9Bモデルの能力は有限で、1回の呼び出しに使えるリソースには天井がある**。Few-shot やconstrained decodingは、タスク以外のところでそのリソースを食い潰していた。品質ゲートと2段階パイプラインが効いたのは、LLMの能力をタスクに全振りさせたからだ。

これらは「プロンプトの書き方」の問題ではなかった。LLMの呼び出しを**どう構成し、どこに制御を配置し、どう品質を担保するか**——プロンプトエンジニアリングの上位概念が必要だった。1回の呼び出しの質を上げる技術は依然として重要だ。だがそれだけでは、小型モデルで実用的なシステムは作れない。

## このセッションで見えたもの

振り返ると、このセッションには面白い力学があった。

「なんか LLM パワーを信用して制約を外そうとする私と、LLM パワーをあまり信用しないあなたのバランスが面白いな」——セッション中、Claude Code へそう言った。人間が楽観的に制約を外し、AI が防御的に品質を守ろうとする。通常イメージされる関係の逆だ。

このバランスが、品質ゲートと2段階パイプラインの両方を生んだ。制約を外す発想（私）と、外した先の品質を担保する仕組み（Claude Code との議論）。どちらか片方では辿り着けなかった。そしてその議論の多くは、小型LLMの dry-run を待つ15-30分の雑談から生まれた。API の速度なら次の実験にすぐ取りかかっていただろう。遅さが、強制的に「考える時間」を作っていた。

## まとめ

9Bモデルの出力が壊れたことで、大規模モデルなら気にしなくて済む問題が全て表面化した。

- Few-shot のトークンコスト
- Constrained decoding の品質トレードオフ
- 制御の配置（生成時 vs 保存時）
- 責務の分離（抽出 vs 整形）

これらは「小型モデル固有の問題」ではない。大規模モデルでもスケールすれば同じ壁にぶつかる。そしてエッジAI——スマホ、IoT、車載でオンデバイスLLMを動かす世界では、3Bや1Bのモデルでこの問題がさらに顕著になる。Apple の Foundation Models、Qualcomm の AI Engine、Google の Gemini Nano。クラウドAPIに頼れない環境で小型モデルから品質を絞り出す技術は、これから確実に必要になる。9Bモデルはその壁を先に、小さなコストで見せてくれた。

最終的な変更量は4ファイル、14行追加、5行削除。1日の試行錯誤の末にたどり着いたのは、この少ない差分だった。

小型LLMを素手で運用しないと見えない景色がある。フレームワークで隠蔽される前の、生のトレードオフ。壊れたモデル出力の中に、原則が埋まっていた。
