あるコミットの直前の状態を復元して、そのリポジトリが毎週回している未使用コード検出を走らせると、こう返ってきます。

```json
{
  "tool": "vulture",
  "report_prefixes": ["src/", "scripts/"],
  "count": 0,
  "candidates": [],
  "parsed_total": 149,
  "unparsed_lines": 0,
  "stderr_lines": 0
}
```

候補0件。健全に見えます。

その1分後のコミットで、4つのファイル（合計2,063行）が消えました。記録側のドキュメント更新を含めて、コミット全体の削除行数は2,065行です。

削除の理由はコミットメッセージに書いてあります。**zero consumers** —— 消費者がゼロだから、です。

検出器は0件と答え、人間は2,065行を消しました。両方とも正しい判断です。

この記事は、なぜ両方正しくなるのかと、それが分かったあとで何を変えたかの話です。

## 前日に上限を刈った。翌日も、コードは膨れていた

対象はContemplative Agent（私が開発している自律AIエージェント。Python）です。

2026年8月28日、私はこのリポジトリに関数の複雑度上限（Ruffの`C901`、`max-complexity = 15`）を入れ、その日のうちに超過13件を全部刈りました。経緯は[前編](https://zenn.dev/shimo4228/articles/lint-as-subtraction)に書いています。

翌29日の15時20分、私はエージェントにこう打ち込みました。

> ここ最近コードベースが、多重レビューの連鎖でかなり行数が増えてしまった。本来的にこのプロジェクトはそこまで行数を必要とするようなプロジェクトでない気がするが膨れ上がってしまった。本当に必要なコードだけを備えたシンプルなプロダクトでありたいのだが、それをここから実現するにはどうすればいいか？

前日に上限を入れて刈ったばかりです。それでも減った感触がありませんでした。

会話の途中で、私は自分でこう聞いています。

> Vultureとか入ってなかったっけ？これでは検出できない類なの？

Vultureは入っていました。しかも毎週自動で回っていました。それでも減っていませんでした。

## 前編で「機械へ」と振ったもの

前編で、私はチェック項目を3つに分類する表を出しました。

| 分類 | 判定の入力 | 行き先 |
|---|---|---|
| 決定論 | 構造・書式・実在・一致（複雑度、循環import、**未使用コード**、命名規則） | 機械 |
| 意味的 | 意図・妥当性・両面性 | LLMに残す |
| 混合 | 機械が数え、LLMが解釈する | 機械が値を出し、LLMが読む |

未使用コードは「決定論」に置きました。構造で決まるから機械へ、という判断です。

その翌日に消えた2,063行は、この分類のどこにも引っかかりませんでした。

## 削除の直前リビジョンで、3つの検査を回し直した

言葉で書くと弱いので、削除前の状態を復元して測りました。削除コミットの1つ前（`a06c6be^`）をworktreeに切り出し、3つ回しています。

```bash
CA=~/MyAI_Lab/contemplative-agent
git -C $CA worktree add --detach /tmp/ca-pre a06c6be^

# 1. リポジトリ自身の週次未使用コード検査
cd /tmp/ca-pre && uv run --with vulture==2.16 python scripts/dead_code_scan.py

# 2. Vultureの素の出力から、これから消える4ファイルに関する行だけ拾う
cd /tmp/ca-pre && uvx vulture@2.16 | grep -E 'coselection|sampling_probe|offwindow'

# 3. 複雑度上限を含むlint
cd /tmp/ca-pre && uvx ruff@0.16.0 check \
  scripts/coselection_families.py tests/test_coselection_families.py tests/sampling_probe.py
```

結果です。

| 検査 | 削除対象4ファイル（2,063行）に対する出力 |
|---|---|
| 週次未使用コード検査 | `"count": 0`（候補0件、パース総数149） |
| Vultureの素の出力 | `tests/sampling_probe.py:83: unused variable 'prompt_eval_count' (60% confidence)` の1件のみ |
| Ruff（`C901`込み） | `All checks passed!` |

912行のスクリプトと、その726行のテストについては、3つとも何も言いませんでした。唯一出た1件は、これから消える別ファイルの中の未使用ローカル変数で、しかも確度60%です。

そしてその1分後、この4ファイルが消えました。

```text
$ git show --stat a06c6be
 scripts/coselection_families.py    | 912 --------------------
 scripts/offwindow-run.sh           | 129 -------
 tests/sampling_probe.py            | 296 ---------------
 tests/test_coselection_families.py | 726 ------------------
 （残り6ファイルは記録側のドキュメント更新。省略）
 10 files changed, 22 insertions(+), 2065 deletions(-)
```

## 上限を刈ったら、行が増えた

もう1つ、測って初めて分かったことがあります。

前日に「複雑度上限の超過13件を全部刈った」と書きました。そのコミットのPythonの増減はこうです。

```text
$ git show --numstat --format= 009baee -- '*.py' | awk '{a+=$1; d+=$2} END {print "+"a, "-"d, "net", a-d}'
+1901 -1086 net 815
```

**刈ったのに815行増えています。**

考えてみれば当然でした。「1関数の分岐数を15以下にする」は、1つの関数を複数のヘルパーに割れば満たせます。関数あたりの複雑度は下がりますが、総行数は増えます。関数定義が増えるぶん、むしろ増えやすい。

複雑度上限は、私が減らしたかった量とは別の量を最適化していたわけです。効いていなかったのではなく、**効いている先が違った**。

ここまでで、検査を2つ疑いました。複雑度上限は指す先が違い、未使用コード検出は何も指しませんでした。前者は上限値の問題ですが、後者は違います。検出器そのものが何を測っているのかを見る必要がありました。

## 検出器は参照を測っていて、消費を測っていない

ここが機序です。

Vultureは名前の定義と利用を突き合わせ、`return`の後ろのコードや成立しない条件の下のコードも到達不能として拾います。つまり測っているのは、**コードの側に到達する道があるか**です。

- 関数が呼ばれていれば「使われている」
- CLIのエントリポイントがあれば「使われている」

一方、私が消したかったものの条件は**読み値に消費者がいるか**でした。そのスクリプトが出力する数字を、誰かが読んで、何かを決めているか。

この2つは別物です。そして後者は、どのシンボルにも現れません。「出力を読んだ人間が誰もいない」という事実は、コードのどこにも書かれていないからです。

前編の分類表を撤回する必要はありませんでした。Vultureが判定する「未使用コード」の定義の中では、あれは依然として機械の仕事です。ずれていたのは、**私が畳みたかったものが、その定義の外側にあった**ことでした。分類が間違っていたのではなく、分類する前の項目名が粗かったわけです。

もう1つ、テストを書くほど検出から外れやすくなる構造があります。このリポジトリの週次検査自身が、docstringでそれを宣言しています（該当部分のみ抜粋）。

```python
"""Weekly dead-code intake — the fifth deterministic intake.

Scan-wide, report-narrow: vulture's scan paths (pyproject [tool.vulture])
include tests/ and evals/ so that code used only by tests resolves as used,
but candidates are reported for src/ and scripts/ only.
"""
```

テストからしか呼ばれないコードを「使われている」と解決させるために、走査対象にテストを含めています。これは誤りではありません。含めなければ、テスト専用のヘルパーが全部候補に上がって使い物になりません。

ただし副作用として、**テストが参照しているシンボルは、それが1箇所であっても「使われている」に解決されます**。912行のスクリプトの内部関数を726行のテストが網羅的に呼んでいたので、候補に上がる余地のあるシンボルがほとんど残りませんでした。

ここで「計器」と呼んでいるのは、動かすためではなく**読むために書いたコード**です。読み値・分布・較正スケール・監査面。作用させるのが目的ではないので、消費者が消えても機能は壊れません。壊れないから、気づきません。

## 912行を生かしていたのは、一緒に消えた自分のテストだった

消えた4ファイルの内訳を、削除の根拠と一緒に並べます。それぞれ別の記録に、日付つきの理由が残っています。ここでADR（Architecture Decision Record）と呼んでいるのは、設計判断とその理由を1件1ファイルで残しているテキストのことです。

| 消えたもの | 消費者が消えた理由 | 記録先 |
|---|---|---|
| `coselection_families.py` 912行 + テスト726行 | 読み値の唯一の受け皿だった提案が2026-08-26に取り下げ（`withdrawn`）になった | ADR-0097の注記 |
| `tests/sampling_probe.py` 296行 | 対応するADRを書いた時点で用済み。その後の消費者もなし | ADR-0047の注記 |
| `scripts/offwindow-run.sh` 129行 | リポジトリ内に参照元が1つも無かった | 削除直前リビジョンのgrep |

1行目が、この記事で一番はっきりした例です。912行のスクリプトを実際にimportしているものを、削除直前の状態で探すとこうなります。

```bash
# 先ほど切り出した worktree をそのまま使う
$ cd /tmp/ca-pre && grep -rn 'coselection' --include='*.py' --include='*.sh' -l .
tests/test_coselection_families.py
tests/test_stats.py
scripts/_stats.py
scripts/coselection_families.py
```

4件のうち、実際のコード参照は1件だけです。`test_stats.py`と`_stats.py`のヒットはdocstringの中の言及で、依存の向きも逆でした（`coselection_families.py`のほうが`_stats.py`からヘルパーをimportしています）。

```python
# tests/test_coselection_families.py:25
import coselection_families as cf
```

**912行のスクリプトを生かしていた唯一のimportは、同じコミットで一緒に消えた726行のテストでした。** テストがスクリプトを呼び、スクリプトは他の誰からも呼ばれていない。この形は参照グラフの上では完全に健全です。外から誰も使っていなくても、そうなります。

3行目の`offwindow-run.sh`はもっと単純で、参照元が自分自身以外に1つもありませんでした。129行の孤児です。それでも検出器は何も言いません。**Vultureが解析するのはPythonの構文木だけで、シェルスクリプトは最初から検査対象に入っていない**からです。

もう1つ、`coselection_families.py`には特徴的な履歴がありました。この計器の出力は**ちょうど1回読まれ**、その数値はADRの注記に凍結されています。1回読まれて、役目が終わって、それから誰も読んでいない。それでもコードは残り続けました。

なお、3つとも「復元点は削除コミット。必要になったら書き直さずgit履歴から復元する」と記録に書いてあります。削除は不可逆ではありません。

## 建立は必須で、溶解は任意だった

なぜこうなるのかを、リポジトリの記録側で測りました。

このプロジェクトには「介入の前に測れ」という設計判断があります。何かを変える前に読み値を出せ、という規約です。良い規約だと今も思っています。ただ、**建てる側にだけ義務があって、畳む側には無かった**。

ADRには、失効条件を書く節（`## Review-when`）を置ける決まりがあります。削除の直前時点で数えました。

```bash
$ cd /tmp/ca-pre
$ ls docs/adr/*.md | grep -v ja.md | grep -v README | wc -l
     101
$ grep -l '^## Review-when' docs/adr/*.md | grep -v ja.md
docs/adr/0069-gemma-production-model-and-think-on-value-layer-pipelines.md
docs/adr/0097-consolidator-dissolution-and-skill-store-exit.md
docs/adr/0098-weekly-single-session-and-triage-delegation.md
docs/adr/0099-weekly-report-instrument-redesign.md
docs/adr/0100-retire-chaos-tdd-by-default-mandate.md
docs/adr/0101-instrument-dissolution-mandate.md
```

101本のうち6本。ただし末尾の0100と0101は、この日に私が書いたものです。それ以前で数えると**99本のうち4本**で、95本には、いつ効力を失うかが書かれていませんでした。

撤去の話がまったく書かれていなかったわけではありません。個別のADRの本文には「この計器は目的を果たしたら降ろす」と書いてあるものがありました。問題は、それが**どのゲートも読まない散文の中に散らばっていた**ことです。書かれていないのではなく、読まれていない。

こうなると、ローカルな判断がどれだけ良くても在庫は増えやすくなります。減ることはあります —— この記事の2,063行がまさにそれです。ただしそれは、誰かがある日思い立って数えたときにだけ起きます。1本ずつは全部正当化されていて、合計だけが誰の判断でもない、という状態です。

## 新設時に3つ書かせる

対処は、事後の検出をあきらめて、新設時のゲートに移すことでした。

新しい計器を建てるときは、その設計判断の記録に次の3つを書く。書けないものは受理しない。

- **(a) 誰が・いつ読むか** —— 名指しの消費者と、頻度または発火イベント。「必要になったとき」は不可
- **(b) 何回の読みで何を決めるか** —— 読み値が入力される判断と、それを閉じる読みの回数
- **(c) 満了時の撤去条件** —— 何をもって終わりになり、いつ降ろすか

(a)の「必要になったとき」を明示的に禁じているのが効きどころです。私が過去に書いた計器は、だいたいこれで通っていました。

(b)には例外を1つ置きました。探索的な計器 —— 読み値が存在するまで介入を選べないからこそ建てるもの —— は、回数の代わりに**日付つきの見直し時点**を書いてよい。読み手と日付は依然として名指しが要ります。免除されるのは回数だけです。

**3つに答えられないこと自体が、その計器に消費者が居ないという信号です。** これが捕まえたい失敗の形でした。

この3つを、以下では**消費計画**と呼びます。

置き場所も決めました。消費計画は、その計器を生んだADRの`## Review-when`節の中に、`### Consumption plan`という小見出しを立ててその下に書く。計器1つにつき1箇所、それを生んだ判断の隣です。

## 機構を作らないことが条件だった

ここが、前編・前々編と地続きの部分です。

対処を考えたとき、真っ先に浮かんだのは「消費計画の有無を検査するlintを書く」「計器の登録簿を作る」でした。両方やめました。

決めたのはこうです。**新しいコード・スケジューラ・lintゲート・登録簿ファイルを作らない。** 義務はすでに書いている文書に3文を足すことで果たされ、強制するのはその記録を受理するのと同じ人間のゲートです。

拒否のされ方も、新しい成果物を作らない形にしました。却下台帳は作りません。拒否は**「提案が理由1行つきで、未受理のまま留まること」**として記録されます。

登録簿を作らなかったのには、この記事の主題そのものの理由があります。**登録簿は、それ自体が保守対象の計器になる。** 誰が読むのか、何回読んだら判断が閉じるのか、いつ降ろすのかを、登録簿自身について答えられなければ、同じ問題を1階層足すだけです。

## 何行減ったのか

セッションの最後に、私はこう聞いています。

> 結局ビフォーアフターでどれくらいコードの行数は減ったの？

測り直した数字です。判断を始める直前のコミットから、翌日までを比べています。

| 指標 | Before | After | 差 |
|---|---|---|---|
| Pythonの総行数 | 94,882 | 92,723 | −2,159 |
| `.py`ファイル数 | 234 | 231 | −3 |
| `scripts/`（.py + .sh） | 9,544 | 8,503 | −1,041 |
| `tests/` | 52,170 | 51,021 | −1,149 |
| `src/` | 29,965 | 29,867 | −98 |

計測はコミット2点をそれぞれ展開して数える方式です（コミットごとの差分の総和ではありません）。

```bash
CA=~/MyAI_Lab/contemplative-agent
loc() { T=$(mktemp -d); git -C "$CA" archive "$1" | tar -x -C "$T"; \
        find "$T" -name '*.py' -exec cat {} + | wc -l; rm -rf "$T"; }
loc 64393cf   # 94882（判断を始める直前）
loc 6ce54d9   # 92723（翌朝）
```

減った分の大半が`tests/`と`scripts/`にあることに注目してください。減らせたのは製品の本体（`src/`は−98行）ではなく、**読むために建てた側**でした。

## この判断が効かない場合

弱いところを先に書きます。

**「原理的に検出できない」とは言えません。** ここで測ったのは、参照を測る検出器の死角です。実行時のトレースや、出力が実際に読まれたことを記録する利用ログを持っていれば、消費者の不在は測れる可能性があります。私はそれを持っていなかったし、そのために新しい計器を建てるのは本末転倒だと判断しました。持っている人には別の道があります。

**対処は「した」のではなく「書いた」段階です。** 消費計画の義務を決めたのは2026年8月29日で、既存の計器に対する遡及的な棚卸しはまだ1度も終わっていません。効果を語れるのは、少なくとも1周してからです。

**同じ罠に、この対処自身が落ちる可能性があります。** 実例があります。今回消した計器を生んだ先行の設計判断では、読み値を建てるのに`.py`で6,355行を足し、その読み値が導いた結論で消したのは5,672行でした。

```text
（.py のみ、各コミットの純増減）
建立: 186dee6 +2,816 / 8757683 +2,008 / c9a1df4 +1,531  → +6,355
退役: 47616da +841 −6,513                              → −5,672
```

**退役を正当化するために建てた行数のほうが、退役が消した行数より多かった**わけです。同じことが「消費計画」の節そのものに起きない保証は、まだありません。だから機構を作らない形に寄せました。

**計器が総量を支配していると主張するつもりはありません。** 2026年5月から8月末までの窓で、追跡下のPythonは29,079行から93,620行へ、+64,541行増えています。そのうち計器が占める割合は測っていません。今回の2,063行は、同定できた1つのスライスであって、成長の主因だと示したわけではありません。

## 自分の環境に移すなら

ADRやRFCの受理ゲートを持っていなくても、同じ判定は回せます。要るのは記録の形式ではなく、問いのほうです。

**1. 「動かすため」でなく「読むため」に書いたコードを列挙する。** メトリクス、分布の集計、監査スクリプト、ワンショットの計測ハーネス、ダッシュボード用のエクスポータ。動かしても製品の挙動が変わらないものが対象です。

**2. 1つずつ、読み手を名指しできるか試す。** 「必要になったとき誰かが」は名指しではありません。名指しできない時点で、それが消費者ゼロの信号です。

**3. 名指しできたものには、次の2つも書く。** 何回の読みで判断が閉じるか。閉じたらいつ降ろすか。探索的なものは回数の代わりに見直しの日付でも構いません。

**4. 書く場所は、その計器を生んだ判断の隣にする。** ADRを持っていないなら、ファイル先頭のdocstringでも、その計器を足したコミットのメッセージ1行でも足ります。大事なのは、次にそのファイルを触った人の目に入る場所であることです。別のドキュメントに集約すると、そのドキュメント自身が読み手のいない計器になります。

**5. 新設のときに聞く。** 既存分の棚卸しは重い作業です。新設時のほうは、私の環境では「すでに書いている文書に3項目を足す」で済みました。読み手を誰にするかの合意が要る場では、そこがコストになります。棚卸しは在庫を減らし、新設時のゲートは増分を止めます。止めないと、棚卸しは毎回同じ量に戻ります。

最後に、この記事の中にもう1つ入っている話を書きます。

912行の計器の消費者が消えた瞬間は、特定できます。読み値の唯一の受け皿だった提案が取り下げられた2026年8月26日です。取り下げの理由は提案自体の欠陥ではなく、上流の設計をやり直すほうが先だという判断でした。良い判断だと思います。

問題は、そこで**コードのほうは何も起きなかった**ことです。提案の状態は`withdrawn`になり、912行はそのまま残りました。両者をつなぐ仕組みは無く、つないだのは3日後に人間が別件で数え直した1回だけです。

台帳の状態遷移とコードの生死は、放っておくと連動しません。だから(c)の撤去条件が要ります。**「この読み値の行き先が消えたら、この計器も降ろす」と、消える側の隣に書いておかないと、消えたことに誰も気づけない。** 消費者がいるかどうかは、そのファイルの中には書かれていないからです。
