> **用語の更新 (2026-04-30):** [AAP repository](https://github.com/shimo4228/agent-attribution-practice) 側との整合のため、4 象限名のうち 2 つを改名した。(2) Algorithmic Search 象限 → (2) Algorithmic Search 象限、(4) Autonomous Agentic Loop 象限 → (4) Autonomous Agentic Loop 象限。スクリプト象限と LLM ワークフロー象限は維持。本文中で象限名として使われていた表記は新名前に置換しているが、ReAct パターン (Yao et al. 2022) や ReAct ループへの言及はそのまま。

## 前提

[前作](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant) で業務 AI を 4 象限に分けた。横軸が「決定論で書ける / 意味判断を要する」、縦軸が「ワークフロー定義可能 / 探索的」。本記事を通じて参照しやすいように、4 象限に短い名前を付ける。

- (1) **スクリプト象限** — 決定論 × 定義可。スクリプト / パイプラインで処理
- (2) **Algorithmic Search 象限** — 決定論 × 探索的。A* 探索 / 動的計画法 / MCTS / 強化学習 (本記事の射程外)
- (3) **LLM ワークフロー象限** — 意味判断 × 定義可。事前定義されたワークフローの中で LLM を呼ぶ。Anthropic の "Building Effective Agents" でいう workflow patterns (prompt chaining / routing / orchestrator-workers ほか) や、対話業務の専門 chat agent、バッチ業務の単機能 LLM 関数を含む
- (4) **Autonomous Agentic Loop 象限** — 意味判断 × 探索的。LLM 自身が次の行動を決める自律ループ

前作の主張は、ReAct エージェントが正当に必要なのは Autonomous Agentic Loop 象限だけで、業務の大半はスクリプト象限と LLM ワークフロー象限で済む、というものだった。

今回はその根本原因を書く。なぜエージェントベンダーは Autonomous Agentic Loop 象限のアーキテクチャを業務全体に被せたがるのか。なぜ LLM ワークフロー象限で済む業務まで自律ループで設計されるのか。

これは技術選択の問題というより、業界の語彙そのものに LLM ワークフロー象限が独立した呼び名を持っていない、という問題に見える。

## (3) LLM ワークフロー象限が語彙から脱落している

エージェント言説を読んでいると、業務の語り方は概ね 2 つに収束している。

- 決定論で書ける部分は古いやり方で残す
- それ以外は自律エージェントが処理する

この間に LLM ワークフロー象限が入る場所がない。「ワークフローは決定論で組み、その中の意味判断点だけ LLM を呼ぶ」というアーキテクチャを肯定形で名指しする語が、業界の標準語彙にない。前作で触れた Anthropic の "Building Effective Agents" や Thoughtworks の agentwashing 批判では同種の指摘が出ているが、いずれも「自律性が要らない場面ではエージェントを建てるな」という否定形での警告が中心となっている。LLM ワークフロー象限を独立した設計象限として肯定形で呼ぶ語は不在のままだ。

肯定形の語彙がないと何が起きるか。エージェント設計者は、決定論で書ける部分とそれ以外を切り分けたあと、後者をひとまとめに「LLM が自律的に判断する領域」として扱う。LLM ワークフロー象限と Autonomous Agentic Loop 象限を区別する切れ味のある名前を持たないので、Autonomous Agentic Loop 象限のアーキテクチャ — ReAct ループ — を LLM ワークフロー象限にも被せる消去法的選択になる。前作で「業務の大半は LLM ワークフロー象限のはずなのに、なぜか Autonomous Agentic Loop 象限で実装される」と書いたカテゴリエラーは、この語彙の不在の必然的な帰結に見える。

## (3) LLM ワークフロー象限を (4) Autonomous Agentic Loop 象限で扱った帰結

LLM ワークフロー象限を Autonomous Agentic Loop 象限のアーキテクチャで処理すると、独立した症候が下流で複数立ち上がる。観察してみると、それぞれ別の問題に見えて、根は同じだった。以下の 4 症候はいずれも、語彙の不在が生んだ人為的 redirect 不能性の別の現れ方として読める。

### RPA の例外処理ボトルネック

業務自動化の世界で長年知られている現象がある。決定論ルールで書ける部分を RPA で抜き取ると、残った例外処理がボトルネックとして立ち上がる。例外処理担当が増え、メンテナンスコストが膨らむ。前作で書いたとおり、業務には決定論で書ける部分と、そこに収まらない部分がある。後者が LLM ワークフロー象限であり、RPA は LLM ワークフロー象限を扱う語彙を持たないままスクリプト象限だけを抜き取った結果、LLM ワークフロー象限が現場に手作業として残された。

LLM が登場した今、LLM ワークフロー象限を単機能 LLM 関数や専門 chat agent として明示的に分離できるはずだ。だが業界の語彙に LLM ワークフロー象限がないので、結局 Autonomous Agentic Loop 象限の自律エージェントに丸投げされる。RPA 時代の例外処理ボトルネックが、エージェント時代に名前を変えて再発しているように見える。

### サンドボックスの強度要請

ReAct ループは「次に何を実行するか」を LLM が動的に決める。本番運用では、エージェントが何をするか事前に予測できない。被害を封じ込めるためにプロセス分離・microVM・WASM など、強度の高いサンドボックスが要請されるようになった。

サンドボックス技術それ自体は独立の合理性を持つ堅牢な技術であり、ここで否定する対象ではない。気になるのは、それが要請される強度だ。LLM ワークフロー象限が独立に概念化され、各 LLM 呼び出しが固定の役割を持つ部品として明示的に分離されていれば、各部品の権限境界は業務単位で素直に設計できる。請求書マッチング関数に Firecracker は要らない。だが「自律エージェントが業務全体を回す」という設計では、何をするか分からないので最強隔離が要る。サンドボックスの強度は、LLM ワークフロー象限を Autonomous Agentic Loop 象限で扱ったことによる調整コストとして現れているように見える。

### Human-in-the-Loop の構造的歪み

HITL の「Loop」は、本来は AI の出力を人間が改善するフィードバックループのはずだ。だが実際には、HITL は別の形で機能している。AI が処理しきれない LLM ワークフロー象限の判断を、人間が常時受け止める構造になっている。

RPA でスクリプト象限を機械化した組織で、結局例外処理担当が増えるのは、LLM ワークフロー象限が機械化されないまま残されるからだった。AI エージェントを導入しても、自律性を制御するための監視担当や、エージェントの出力を確認する担当が必要になる。対話形 (専門 chat agent) でも構造は同じで、法務相談や診断補助の chatbot の出力を専門家が逐一裏取りするように、対話の各ターンに人間の確認が貼り付く形になる。「人間が解放される」のではなく、「人間の役割が AI の不完全さを埋める方向にシフトする」。HITL という言葉が掲げる理想と、現場で人間が担っている役割は、別物に見える。

### 人為的に作られたアカウンタビリティ問題

本番運用が始まれば、システムの責任は運用責任者に移る。これはどんな業務システムでも変わらない。問題は、何かが起きたとき、運用責任者がそこから先で責任を適切な相手に redirect — 帰属先を切り分けて担当者に渡し直すこと — できるか、だ。

LLM ワークフロー象限のアーキテクチャがきちんと設計されていれば、運用責任者は redirect できる。各 LLM 呼び出しの入出力スキーマが言語化され、ワークフローのログから判定の連鎖が追跡できる。失敗したとき、運用責任者は調べたうえで「これは関数 f の精度問題なのでモデル選定担当に」「これはルーティングロジックの欠陥なので設計者に」「これは上流データの異常なのでデータ管理担当に」と切り分けられる。責任を運用責任者一人が抱え込む構造にならない。

ところが、LLM ワークフロー象限を ReAct ループに丸投げすると、この redirect が機能しなくなる。「なぜこの判断をしたか」をログから再構成しようとしても、ReAct ループの「思考」は事後的に意味を成しにくい。エージェントの runtime の判断は、設計者にもモデル選定担当にも、明確には紐付けにくい。Elish (2019) が *moral crumple zone* と呼んだ構造 — 自律システムの責任が「制御能力の限られた人間オペレータ」に押し付けられる構造 — が、ここで発動するように見える。redirect 先が無くなった責任が、運用責任者に貼り付いたまま剥がれない。

これは設計の必然的な帰結ではなく、LLM ワークフロー象限を Autonomous Agentic Loop 象限で扱ったことによる **人為的 redirect 不能性** に見える。LLM ワークフロー象限を本来の LLM ワークフロー象限のアーキテクチャで設計すれば、redirect は機能し、運用責任者は責任を抱え込まずに済む。

## (4) Autonomous Agentic Loop 象限こそ本物のアカウンタビリティ問題の発生地点

エージェントエコシステムのアカウンタビリティ議論 — サンドボックス、HITL、説明可能性、ガバナンス — は、ほとんどが LLM ワークフロー象限の混乱を扱っているように見える。本来発生しなくていい問題を発生させた帰結を、下流で繕う議論になっている。

Autonomous Agentic Loop 象限自体のアカウンタビリティ問題は、もちろん別に存在する。ReAct ループはブラックボックスで、判断連鎖を事後に再構成しにくい。三部作で扱ったのは、これを構造化設計 — 接続口の分離、追記専用ログ、承認ゲート (組織論で言えば職務分掌・四眼原則・最小権限の延長) — で取り扱う議論で、構造側に責任を分散させることで因果追跡と責任の所在を回復させる、というのが到達点だった。詳しくは「[事故のあとで因果を辿れるか](https://zenn.dev/shimo4228/articles/agent-causal-traceability-org-adoption)」を参照。構造化設計が機能するのは、各構成要素の寄与が事後に識別可能・分離可能であることを前提にしているからだ。

ところが ReAct のアーキテクチャはこの前提を崩す。LLM ワークフロー象限では各 LLM 呼び出しが固定の役割を持つので、失敗時に「関数 f の精度問題」「ルーティングロジックの欠陥」「上流データの異常」のどれかに切り分けられる。ReAct ループは違う。各 iteration の役割が runtime で決まり、モデルの判断、ツール選択、履歴の参照、プロンプト文脈の効きが混在する。出力は複数の判断要素の blend として現れるので、結果が誤ったときにそれぞれの寄与を遡及的に分離できない。

具体例として、ReAct エージェントに紛争案件の判例調査・論点整理から相手方への和解条件提示までを完結させたとする (現状は弁護士法と利益相反の枠組みで考えにくいが)。後で「不利な条件で合意してしまった」と判明したとき、モデルの判例解釈、文献検索のツール使い、過去事案からの patterns 適用、「リスク回避を優先」プロンプト指示が runtime で連鎖してその提示を作っているため、ログを遡っても「どの判断が不利な合意を生んだか」を独立した因子として切り出せない。和解条件は提示済みで、相手方が応諾すれば撤回できない。なぜそうなったかは事後に説明できない。説明できないエージェントの判断の責任を、引き受けられる人間はいるのだろうか。

この問いの答えは、redirect 不能性の正体を辿ってからしか出せない。LLM ワークフロー象限で人為的に作られた redirect 不能性は設計変更で解消できる。一方、Autonomous Agentic Loop 象限本来の業務 — 自律的判断が必要な業務 — に ReAct を当てた場合の redirect 不能性は、自律性そのものから来るので解消できない。これは技術の成熟度の問題ではなく、自律性を採用した帰結として原理的に発生する attribution gap だ。

だからこそ、Autonomous Agentic Loop 象限の業務にこのアーキテクチャを当てるかどうかは、技術的にできる/できないの軸ではなく、**attribution gap を代償として引き受けるかどうか**の判断になる。失敗の影響が可逆な業務、承認ゲートが上流に挟まっている業務であれば、代償は引き受けやすい。逆に説明責任の単位が業務側で定まっている業務では、blend された出力をその単位に収めにくく、代償が膨らむ。

代償を引き受ける主体の問題が、ここに重なる。自律性には責任が伴う。人間は法的主体として責任を引き受けられるが、エージェントは現時点では法的責任の主体ではない (将来的にはあり得るかもしれないが)。となると、attribution gap が開いた ReAct エージェントの判断について、それを引き受けられる人間も、引き受けられる主体としてのエージェントもいない、という空白が残る。

このセクションで見てきた通り、LLM ワークフロー象限の人為的 redirect 不能性とは別に、Autonomous Agentic Loop 象限本来の業務に ReAct を当てたときの attribution gap という別建ての問題がある — 前作で「Autonomous Agentic Loop 象限でこそアカウンタビリティ問題は深刻に立ち上がる」と一行で書いた中身は、こちらを指していた。

## 倒錯の構造

ここまでの観察を並べると、エージェントエコシステムの倒錯した姿が見えてくる。

業界は、本来 redirect 可能性が確保できるはずの LLM ワークフロー象限に Autonomous Agentic Loop 象限のアーキテクチャを当てて、人為的に redirect 不能性を作っている。サンドボックスの強度要請、HITL の歪み、moral crumple zone 的な責任集中の議論は、ここで発生している。

一方、Autonomous Agentic Loop 象限本来の業務に ReAct を当てた場合の原理的 redirect 不能性 — 自律性の代償として発生する attribution gap — の議論は、LLM ワークフロー象限の混乱を繕う議論ほどは深まっていない。前者がサンドボックスや HITL という具体的な技術対応まで降りているのに対し、後者は「AI の自律性には責任問題がある」という認識から先に踏み込んだ論が出にくい。さらに前者は redirect 先 (設計者・モデル選定担当・データ管理担当) が組織内にあるのに対し、後者は責任を引き受けられる主体そのものが現状不在で、redirect 自体が止まる場所がない。

その結果、attribution gap を引き受けることの妥当性、責任構造の原理的限界は、LLM ワークフロー象限の混乱の話の陰に隠れているように見える。

人為的 redirect 不能性 (解消可能) には議論が集中し、原理的 redirect 不能性 (解消不能) の議論にはまだ届いていない、という形になっている。

4 象限を最初から持っていれば、この倒錯は避けられたかもしれない。LLM ワークフロー象限はワークフロー型のアーキテクチャで扱う (運用責任者が責任を redirect できる)。Autonomous Agentic Loop 象限を機械化する場合は、attribution gap を代償として引き受ける。スクリプト象限は決定論で書く (問題は元々ない)。Algorithmic Search 象限は古典 AI / OR で扱う (LLM は要らない)。それぞれの象限に固有の設計指針があり、混ぜると壊れる。

## おわりに

業務を「決定論で書ける部分と、それ以外」の二分法で捉えると、「それ以外」を全部 ReAct に押し込むことになる。前作の 4 象限はそこに最初から第 3 の語彙 — LLM ワークフロー象限 — を入れる試みだった。LLM ワークフロー象限が独立した象限として呼べるようになると、業務の大半に必要なのは LLM ワークフロー象限のアーキテクチャだと素直に見えてくる。

エージェント設計の議論で抜けているのは、LLM ワークフロー象限を肯定形で名指しする語彙だ。否定形で「自律性は要らない」と言うだけでは、現場の設計者は Autonomous Agentic Loop 象限と LLM ワークフロー象限の間で迷い続ける。語彙が無い領域は、設計の判断が消去法に流れる。

そして本物のアカウンタビリティ問題は、LLM ワークフロー象限の混乱の方ではなく、Autonomous Agentic Loop 象限本来の業務に ReAct を当てたときの attribution gap にある。今のところ LLM ワークフロー象限の混乱を繕う議論ばかりが目立っているが、ReAct を機械化することの redirect 不能性は、これから本格的に問われる論点になるはずだ。

論点として、attribution gap の責任主体をどう設計するかも重なってくる。自動運転で事業者責任と保険制度を組み合わせた社会的回収の枠組みが模索されているように (ただし制度はいまも構築途上だ)、同種の経路に向かうのか、それとも別の道が必要か — その議論は ReAct エージェントについて、まだ業界の共有語彙にはなっていない。

ベンダーや設計者が悪い、という話ではない。業界の概念ストックに LLM ワークフロー象限を肯定形で呼ぶ語が無いまま、ReAct という強力な技法が登場してしまった、という時間軸の問題に見える。語彙が遅れているなら、現場の側から肯定形の名前を立ち上げていけばいい。前作と本記事はその試みの一つだ。
