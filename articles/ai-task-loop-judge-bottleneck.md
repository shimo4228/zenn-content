タスク台帳の下のほう、もう何週間もスクロールして見ていない領域はありませんか。

私の環境には 2 つのリポジトリ合計で 41 件のタスクが眠っていました。AI エージェントは毎日使っているのに、台帳は減りません。

ある朝、自作の「着手可能なタスクを一覧する」コマンドを叩いたら、答えは空でした。

```bash
python3 ~/.claude/scripts/claims.py ready
# （出力なし）
```

41 件あるのに、今すぐ実装に渡せる仕事はゼロ。実装力は余っていて、詰まっていたのは判断のほうだったのです。

この記事は、その 41 件を「判断・実装・人間」の三役に分けた AI ループで処理した 1 週間の運用記です。読み終える頃には、自分の台帳のどこが詰まっているのか、そして無人ループを組むなら何を最初に設計すべきかを判断できるようになります。

:::message
2 リポジトリ・1 週間・筆者ひとり（n=1）の記録です。数値はすべてログと commit から取った実測値で、一般化はその範囲で読んでください。
:::

## タスクは書いた瞬間から腐り始める

ループを組む前日、試しに 7 件のタスクを手動で実装セッションに配りました。

結果、7 件中 2 件は着手した時点で前提が崩れていました。依存していた仕様が変わっていたり、問題自体がすでに別の変更で消えていたり。

台帳の「いつかやる」は、書いた瞬間の世界を前提にしています。数週間放置されたタスクは、実装する前にまず「まだやる価値があるか」の再判定が要ります。

つまり台帳の処理には、実装より前に判断のレイヤーがあります。ここを自動化の設計に組み込まないと、AI は腐った前提の上に正しいコードを積んでいきます。

## 作ったものは 2 つ：役割の分離と、配管

やったことは 2 つです。まずタスク処理を三役に分離し、次にそれを無人で回す配管を敷きました。

三役の分離はこうです。

| 役 | 担当 | 具体形 |
|---|---|---|
| 判断 | 上位モデル（実装側より 1 段強いモデル）の常駐セッション。リポジトリごとに 1 本 | 台帳の全タスクを再判定し、生きているものだけ実装に配る |
| 実装 | 都度立ち上げる新セッション | git worktree 上で 1 タスクだけ実装。main には触らない |
| 人間 | 私 | merge・取り下げ・起票の最終承認だけ。最後のスイッチ |

Pull Request は使いません。実装セッションは task ブランチに commit を積むだけです。

検収は判断セッションが `git diff --stat` とテストのやり直しで行い、人間が承認したら fast-forward merge します。未マージのブランチ一覧が、そのまま検収待ちキューになります。

```bash
git branch --no-merged main   # 未マージ = 検収待ちキュー（PR の代替）
git merge --ff-only task/<name>   # 人間の「merge」の後にだけ
```

一人で回す分には、PR のレビュー UI もマージボタンも過剰でした。ブランチと ff-only merge だけで「人間が最後に確認する」構造は作れます。

## 実測：コードを書かずに、まず 10 件が消えた

三役をそろえて回した最初の 1 日（前日の 7 件テストとは別。この時点の運転はまだ手動で、無人化は後述します）の収支です。

- open は 2 リポジトリ合計で 41 件 → 22 件（13 → 5 と 28 → 17）
- 閉じたタスクは 27 件、merge は 13 回（両者は 1 対 1 ではありません。文書だけの merge も、merge なしで閉じたタスクもあります）
- サイクル中に 6 件を新たに起票した（6 件とも、起票の可否をその場で人間が承認したもの）

検算用に収支を書いておくと、閉じた 27 件のうち 2 件は実装のついでに直した隣接リポジトリのタスクで、41 件の外側です。41 − 25 + 6 = 22 で帳尻が合います。

27 件の内訳で目を引くのは、コードを書かずに閉じた分です。

実装に配る前の判断パスだけで、方針決定・取り下げなど 6 件が閉じました。読み取り調査だけのセッションが、さらに 4 件を閉じています。

判断パスは、閉じる以外の形でも台帳を直しました。「依存タスクが数週間前に完了していたのに blocked のまま放置」が 3 件、「再開条件が構造的に発火し得ない」が 1 件。

どれも状態を正すだけで前へ動きました。

台帳は実装で減る前に、判断で減ります。もしタスクが溜まって見えるなら、まず疑うべきは実装リソースの不足より、この再判定が誰の仕事にもなっていないことかもしれません。

なお実装側も手は動いています。1 日でパイロット含め 14 本の実装セッションが並列上限 3 で走り、merge は 13 回に至りました。

欠けていたのは実装力より、実装に渡せる形まで判断する層。それがこの数字の読み方です。

## 指示書は仮説として書く

実装セッションに渡す指示書（kickoff packet と呼んでいます）で、2 つ失敗しました。

**1 つ目。初日に書いた指示書は、全部どこかが間違っていました。** 前提が半分だけ真だったり、指定した修正方法では穴が塞がらなかったり。

対策は、指示書の先頭に「Phase 0：前提の再照合。反証されたら実装せず止まって報告」を置くことでした。指示書を命令として書くのをやめ、仮説として書くようにしました。

すると同じセッションが、間違った指示から正しい結果を出すようになりました。見つけた反証を報告させれば、判断側の材料も増えます。

**2 つ目。レビュー工程を指示書に列挙したら、列挙漏れが「省略の許可」に読まれました。** 実際に 1 本の実装セッションが、書かれていなかった簡素化レビューを飛ばしています。

対策は、工程の列挙をやめて規約への参照に置き換え、「指示書に書いていないことは規約が既定」と明記すること。

委任文書に書いた具体は、書かなかったことの免除として読まれます。少なくともこの実装セッションは、列挙をそう解釈しました。

## 無人ループは静かに死ぬ

ここまでは手動運用でした。次に無人化ですが、最初の設計は失敗しています。

Claude Code にはセッション内で定期実行を予約する機能があり、最初はこれでループを回そうとしました。しかしセッション内のタイマーは、セッションと運命を共にします。

再起動、ツールの更新、セッションの寿命。どれで止まっても、外からそれを検知する手段がありません。

失敗して大声を上げるループより、止まったことに誰も気づかないループのほうが厄介です。そこで設計原則をこう決めました。

**タイマーはセッションの外、判断はセッションの中、人間の答えもセッションの中だけ。**

具体的には macOS の launchd（cron 相当の OS 標準機構）が、数日おきに小さなシェルスクリプトを起動します。

このスクリプト（tick と呼んでいます）は台帳を読みません。やることは次で全部です。

```bash
# tick の仕事：生きた判断セッションを探し、無ければ立てて、サイクルを 1 回頼む
# （実物は ~/.claude/scripts/triage-tick.sh。要点のみ抜粋）
if ! find_live_triage_session; then
  spawn_session && rename_to_fixed_name
fi
# digest = 判断セッションがサイクル末尾に人間へ送る報告（次節の Slack 通知）
send_prompt "Unattended triage cycle. Go as far as the digest.
Do not merge, publish, or touch rules / hooks / security gates.
File nothing and drop nothing on your own."
```

判断の知能はセッション側にあり、tick は「生きているか確認して、起こすだけ」。賢さを配管に持たせないのは、壊れうる部品を減らすための設計判断です（耐久性そのものは、これからの定刻運用で検証します）。

### 生存信号：報告が来ないこと自体が警報

無人サイクルから Slack へ届くメッセージは 2 種類です。人間の判断が要る項目ごとの通知（1 件 1 通）と、サイクルの終わりに必ず送られる生存信号の 1 行。

> .claude triage cycle done: 1 decision pending (…)

定刻を過ぎてこの 1 行が来なければ、ループのどこかが死んでいます。

沈黙を異常のシグナルに変換しておくこと。それが無人化の本体でした。

ただし Slack は片方向です。返信を人間の答えとして扱うと、なりすましや誤読の経路が増えるので、merge などの答えは判断セッションの画面でだけ受け付けます。

実際、運用初日には判断セッションが「Claude Code が入力欄に自動表示した提案文」を人間の指示と誤読しかけました。人間の言葉をどのチャネルで受けるかは、無人化の前に 1 本へ絞っておく価値があります。

## ループが見つけた一番の穴は、台帳の外にあった

初回サイクルの副産物として、想定していなかった発見がありました。

私の環境には、commit のたびに走る機械ゲート（secret スキャン等）があります。ゲートは「このスクリプトは無人実行してよい」と人間が承認した対象の一覧を持つのですが、それが 2.5 週間前から更新されず古くなっていて、**ゲートが静かに休眠していた**のです。

誰も気づいていませんでした。

赤く落ちるゲートは、少なくとも気づかれます。静かに休眠したゲートは、緑のふりをして通し続けます。

無人ループを組んで初めて、「ループ自身の死活」と「ループが頼っている検証装置の死活」が同じ問題だと分かりました。

Addy Osmani は [Loop Engineering](https://addyo.substack.com/p/loop-engineering)（2026 年 6 月）で、コードを書いたモデルに自己採点させる甘さと、人間の検証スループットが並列度の上限を決めることを指摘しています。今回の運用はそれを実地でなぞった形です。

付け加えるなら、検証装置そのものも監視対象でした。Osmani の言う「done は主張であって証明ではない」は、ゲートにも当てはまります。

## まだ分かっていないこと

正直に書いておくと、この仕組みで検証できているのはまだ入口までです。

- 無人サイクルは各リポジトリ 1 回ずつ（手動起動がきっかけ）。launchd の定刻による自然発火は、執筆時点でまだ観測していません
- 初回の無人サイクルの中身は「blocked 4 件を全件照合、全件未発火、実装への配布 0、人間待ち 1 件」。地味ですが、配る仕事がない週に何もしないで正しく報告できることは、それ自体が確認項目でした
- Slack が落ちている間は生存信号ごと沈黙します。警報チャネルの単一障害点は未解決です

## 1 週間で人間に届いた判断は、1 通だった

執筆時点の open は、冒頭と同じ 2 リポジトリ合計で 22 件です（着手可能 2、判断待ち 1、条件待ち 19）。この 1 週間で 25 件が閉じ、6 件が新たに生まれた結果です。

そして初回の無人サイクルが人間に届けた判断依頼は、1 通でした。

自動化を始める前、私の仕事はタスクを眺めて、思い出して、着手して、途中で別のタスクに割り込まれることでした。いまは届いた 1 通に答えを返すことです。

実装は任せられます。判断も、その大半は任せられます。

最後に残るのは「これを merge していいか」「これはもうやらなくていいか」という短い言葉だけでした。

あなたの台帳の 41 件も、その大半は実装を待っていないかもしれません。まず 1 件、いちばん古い blocked タスクを開いて、その依存がまだ生きているか確かめてみてください。

ループを組むのはそれからでも、発見の大きさは変わらないはずです。

## 自分の環境に移すなら（コーディングエージェント向け）

この仕組みは筆者のローカル環境（macOS、launchd、自作のセッション管理ツール）に依存しているため、手順のコピーでは移植できません。試すなら、以下をそのままお使いのコーディングエージェントに貼り、まず読み取り専用の調査と計画だけをさせてください。

```text
この記事の設計を私の環境に適用する計画を立ててください。実装はまだしないでください。

前提の調査（読み取り専用）:
1. 私のタスク管理の現状（ファイル・ツール・件数・最終更新）を調べる
2. この OS で無人の定期実行に使える標準機構（launchd / systemd timer / タスクスケジューラ等)を特定する
3. 通知チャネル（Slack 等）への送信手段の有無を確認する

計画に含めるもの:
- 判断（タスクの再判定）と実装を別セッション/プロセスに分ける構成
- タイマーを対話セッションの外に置く配線
- サイクル終端の生存信号 1 行と、その不在を検知する方法
- 無人側が「してはいけないこと」の境界（merge・公開・設定変更の禁止）

計画を提示し、私の承認を得てから実装に進んでください。
```
