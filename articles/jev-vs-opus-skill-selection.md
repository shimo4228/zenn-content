自律エージェントが行動の前にやる「いまの状況に当てはまるスキルを一覧から選ぶ」処理を、同じ150件の状況で、JevとClaude Opusにやらせて比べました。Jevは、TypeSafeが2026年9月15日に早期アクセスを始めたモデルです。文章を書かず、選択肢に対する答えと確率だけを返します（[TypeSafeの発表](https://typesafe.ai/blog/introducing-system-one-models-and-jev)）。

物差しはOpus自身です。Opusに同じ150件をもう1回選ばせると、1回目との一致は0.678でした。無作為に選ぶと0.056です。Jevは0.346で、Opus同士の一致の約半分、手元の小型モデルの2倍以上でした。Jevが1位に指したスキルは、83%の状況でOpusも選んでいます。確率0.5以上で指した45件は、1件もOpusと食い違いませんでした。時間は1件0.3秒、費用は150件で約5セントです。Opusの約50分の1の時間、約560分の1の費用です。

Jevが手元で動くようになったら、私はこのエージェントの同じ種類の処理の大部分を、Jevに替えたいと思っています。いまのJevはホスト型で、手元の1台で完結させているこのエージェントには、まだ入れられません。

| 選び手 | Opusとの一致 | 1件の時間 | 150件の費用 |
|---|---|---|---|
| Opus（2回目） | 0.678 | 15.3秒 | 26.26ドル |
| **Jev** | **0.346** | **0.32秒** | **0.047ドル** |
| 手元のgemma4:e4b | 0.143〜0.162 | 9.8秒 | — |
| 無作為に選んだ場合 | 0.056 | — | — |

基準はOpusの1回目の選択です。gemmaの幅は、出力の設定を変えて8通り試した幅です。Opusの選択は基準であって正解ではありません。時間と費用は条件がそろっていないので、「この比較で言えないこと」に書きます。

## スキル選択の実物を1件

対象は、私が運用している自律エージェント（Contemplative Agent）です。エージェントは行動の前に、状況の記述とスキルの一覧（名前と説明の組）を受け取り、当てはまるスキルを選びます。複数選んでよく、1つも無くてもかまいません。一覧は時期によって53〜57件です。

いまは手元のMacで動く小型モデル（gemma4:e4b）に、当てはまるスキルの名前を書かせています。文章生成で選ばせるので1回に10秒前後かかり、2〜3割でスキル名を書き間違えます。書かせずに選ばせるモデルが出たので、試しました。

エージェントはスキル選択のたびに、入力と出力をログに残しています。そこから、書き間違いのあった75件と無かった75件を抜き出したのが、この150件です。以下、1件を1行と呼びます。

そのうちの1行を見てください。この行の一覧は54件です。

| スキル | Opus | Jevの確率 | 手元のgemma |
|---|---|---|---|
| `analogy-mapping-relationships` | 選んだ | 0.61 | 選んだ |
| `analyzing-systemic-governance-loops` | 選んだ | 0.12 | — |
| `trace-structural-authority` | 選んだ | 0.07 | — |
| `cross-reference-foundational-claims` | — | 0.02以下 | 選んだ |
| `detecting-abstract-to-operational-constraint-shift` | — | 0.02以下 | 選んだ |
| `scope-boundary-mapping` | — | 0.02以下 | 選んだ |
| `shifting-focus-from-state-to-process-mechanics` | — | 0.02以下 | 選んだ |
| `identify-structural-tensions-via-system-metaphors` | — | — | 書き間違い |

Opusは2回とも同じ3件を選びました。Jevが確率を高く付けた上位3件は、その3件と同じです。gemmaは6件書き、1件は一覧に無い名前でした。実在するのは`identifying-…`で、語形が崩れています。一覧に無い名前はコードが捨てるので、gemmaの選択は5件になります。

この記事で「Opusとの一致」と書くのは、「両方が選んだ件数 ÷ どちらかが選んだ件数」（Jaccard係数）です。この行のgemmaは、共通が1件、どちらかが選んだものが7件で、1÷7の0.14。Jevは、gemmaと同じ5件を確率の上位から取ると（件数の決め方は次の節に書きます）、Opusの3件すべてが入り、3÷5で0.60です。

この行は、Jevが最もよく当たった行の1つです。gemmaの0.14は、150行の平均と同じ値です。1行では何も言えないので、150行で数えます。

## Jevへの問い方

Jevへの問いは2種類使いました。TypeSafeのdocsがChoiceと呼ぶ「選択肢から1つ選ぶ問い」と、Noulと呼ぶ「yesかnoかの問い」です。1行を1リクエストにして、Choiceを1問と、Noulをスキルごとに1問ずつ入れました。

```json
{
  "state": {"situation": "（状況の記述）"},
  "model": "jev-1.13.0",
  "questions": {
    "choice": {
      "type": "choice",
      "instructions": "（選択の基準）Which single learned skill applies best to `situation`?",
      "criteria": {
        "analogy-mapping-relationships": "（このスキルの説明）",
        "none of the above": "No skill in the catalog applies to this situation."
      }
    },
    "n0000": {
      "type": "noul",
      "instructions": "（選択の基準）Does the learned skill `analogy-mapping-relationships — （説明）` apply to `situation`?"
    }
  }
}
```

実際には`criteria`に全スキルが入り、Noulもスキルの数だけ並ぶので、1リクエストに約55問が入ります。Jevの問いは互いを参照できないので、選択の基準とスキルの説明は問いごとに書きます。入力は1行あたり約7,450トークンになりました。

Choiceは全スキルに確率を返しますが、「何件選ぶか」は返しません。そこで、確率の上位から、その行でgemmaが選んだのと同じ件数（平均6.0件）を取って集合にしました。Opusは、件数を自分で決めています（1回目は平均6.0件）。冒頭の表のJevは、このChoiceの値です。

## 150行で、Opusにどこまで近いか

| 選び手 | 選ぶ件数（平均） | Opusとの一致 | 近いスキルを許した一致 |
|---|---|---|---|
| Opus（2回目） | 5.3 | 0.678 | 0.924 |
| **Jev** | 6.0（gemmaの件数） | **0.346** | **0.855** |
| 手元のgemma4:e4b | 6.0〜8.1 | 0.143〜0.162 | 0.755〜0.784 |
| 無作為に同じ件数 | 6.0 | 0.056 | 0.70 |

同じOpusに2回選ばせても、一致は0.678までです。この数え方の天井はそこで、床は無作為の0.056です。Jevの0.346は、天井の約半分、gemmaの2倍以上の位置でした。gemmaは、出力をenumで縛っても、temperatureを0にしても、0.14〜0.16から動きませんでした（gemma側の記録は[公開リポジトリのevidence](https://github.com/shimo4228/contemplative-agent/blob/1ec4d2dcf7973e0677ded25cd36f21fe91a48c3d/docs/evidence/rfc-0043/README.md)にあります）。

Jaccardは、隣の似たスキルを選んでも不一致に数えます。右の列は、スキルの説明文の埋め込みで近さを測り、似たスキルに部分点を与える数え方です。Opusが選んだスキルそれぞれについて、相手の選択の中で一番近いものとの近さを平均しました。どのスキルも互いにある程度似ているので、無作為でも0.70になります。床の0.70と天井の0.924の間で、Jevは0.855、gemmaは0.76〜0.78です。似たスキルまで許すと、JevはOpus同士の一致にもう少し近づきます。

集合の一致でなく、選んだスキルの1件1件を見ると、もっと単純です。

| 対象 | Opusも選んでいた割合 |
|---|---|
| Opusの2回目が選んだスキル（平均5.3件） | 85% |
| Jevの1位（Opusが何かを選んだ147行） | 83% |
| うち、1位の確率が0.5以上だった45行 | 100% |
| Jevの上位を、gemmaと同じ件数（平均6.0件）まで取った場合 | 50% |
| 手元のgemmaが選んだスキル（平均6.0件） | 25% |
| 無作為に1つ指した場合 | 11% |

Jevの1位は83%で、Opusの2回目が選んだスキルの85%と同じ水準です。ただし、Opusの85%は平均5.3件を選んだうえでの値で、Jevの83%は一番自信のある1件だけの値です。Jevも6件まで広げると50%に落ちます。147行のうち5行は、Jevの1位が「none of the above」で、これは外れに数えています。

Jevが確率0.5以上で指した45行では、Opusと一度も食い違っていません。確率は、信用してよい行とそうでない行を分ける足切りに使えます。大きいモデルの代わりにJevの選択をそのまま採るなら、確率の高い行だけです。

## 1件ずつ聞くと、広く読めるスキルが多くの行で上位に来る

同じリクエストに入れたNoul（スキルごとに「該当するか」）の確率でも、上位から同じ件数を取って比べました。

| | Choice | Noul |
|---|---|---|
| Opusとの一致 | 0.346 | 0.295 |
| 近いスキルを許した一致 | 0.855 | 0.836 |
| `shifting-focus-from-state-to-process-mechanics`が上位に入った行 | 34% | 77% |

Noulは、同じ1件を77%の行で上位に入れました。実物の1行でgemmaが選んでいた、あのスキルです。Opusがこれを選んだのは、1回目で16%、2回目で14%の行でした。Noulが何にでもyesと答えているわけではありません。Noulの確率は0.5以上が35%、中央値は0.38です。Noulはスキルを1件ずつ見るので、比べる相手がありません。当てはまる範囲が広く読めるスキルは、どの状況でも上位に来るのだと私は読んでいます。全スキルを見比べるChoiceでは34%まで下がります。

スキル選択には、Choiceのほうが向いていました。TypeSafeの[スキル選択のcookbook](https://docs.typesafe.ai/cookbooks/skill_suggestion.md)は、Choiceで広く順位づけしてから上位だけをNoulで再判定する2段構えです。1件ずつのNoulを全件に当てた私の問い方は、その使い方から外れています。

## 5セントと0.3秒

Opusは150行に、1行15.3秒（中央値）と26.26ドルかかりました。Jevは0.32秒と0.047ドルで、時間で約50分の1、費用で約560分の1です。Opusに返させたのはスキル名のJSON配列だけですが、それでも出力は中央値で1,373トークンありました。Jevには出力トークンがありません。時間の差は、トークンを生成するかしないかの差です。費用の差には、入力単価の差も入っています。

Jevは150リクエストで失敗が0、所要は中央値0.32秒、90パーセンタイルで0.53秒、最大4.5秒でした。日本からのネットワーク往復を含みます。入力の合計は1,125,726トークンで、公表単価（入力100万トークンあたり0.042ドル、出力は無料）を掛けると0.047ドルです。請求額ではなく計算値です。Opusは`claude -p`で1行ずつ呼び、費用はその応答が返すAPI換算額、時間はAPI側の所要です。

## この比較で言えないこと

基準はOpusの選択で、正解ではありません。人間のラベルは取っていません。言えるのは「JevはOpusの選び方に近い」までで、「Jevの選択が正しい」とは別の主張です。gemmaの選択がOpusから遠いことも、gemmaが間違っていることを意味しません。

Jevには不利な条件と、私の転用が混ざっています。状況文には日本語が含まれ、TypeSafe自身が英語以外の言語は[同等には扱えない](https://docs.typesafe.ai/models.md)と書いています。Choiceは本来1つを選ぶ問いで、その確率を順位づけに使ったのは私の転用です。

渡し方もそろっていません。Opusには、同じ状況・同じ一覧・同じ選択の基準を、gemmaの本番とは別のテンプレートで渡しました。Jevには上のJSONで渡しています。時間も条件が違います。Jevの0.32秒は日本からの往復を含み、gemmaの9.8秒は16GBのM1での値、OpusはAPI側の所要です。

対象は1つのエージェントの1つの処理、150行です。半分は書き間違いのあった行から抜いているので、本番の分布そのままではありません。行データには第三者の投稿が含まれるので公開していません。

## 手元で動くようになったら、同じ種類の処理をJevに替えたい

このエージェントには、スキル選択のほかにも、「選ぶだけ」「判定するだけ」の処理がいくつもあります。いまはどれも、手元のgemmaに文章生成でやらせています。今回の結果を見て、Jevが手元で動くなら、その大部分をJevに替えたいと思いました。いまのgemmaより2倍以上Opusに近く、0.3秒で、書き間違いがなく、確率が付いてきます。

いま入れられないのは、Jevがホスト型だからです。このエージェントは、スキル選択も文章の生成も、手元の1台で完結させる設計で動かしています。外部へ送る経路を本番のコードに持たないことが、このエージェントの安全の前提です。16GBのM1と小型モデルも、[自分で選んだ制約](https://zenn.dev/shimo4228/articles/small-llm-by-choice)です。Jevには、オープンウェイトもセルフホストの経路もまだありません。Ollamaのようなローカルのランタイムで動かせるようになったら、最初に試します。

今回の計測では、150行の状況文を、JevにもOpusにも送りました。これは私が1回だけ許可した計測で、本番のコードとは別のスクリプトです。本番が毎回外へ送り続けるのとは別のことだと判断しました。

Jevに選ばせたログを教師にして、手元の小型モデルを学習させる近道はありません。TypeSafeの[Master Customer Agreement](https://typesafe.ai/legal/mca)（2026年9月19日更新版）の2.3(b)が、出力を使ったモデルの蒸留と、出力を模倣するモデルの学習を禁じています。

スキル選択は、文章を書かせなくてもできる処理でした。選択肢に確率を付けるだけのモデルが、0.3秒で、Opus同士の一致の約半分のところまでOpusに近づきました。あなたのエージェントが外部のAPIを呼んでよい設計なら、待つ理由はありません。Jevが高い確率で指した行はそのまま採り、確率が0.5に届かない行（今回は約7割）を大きいモデルに回す案は、試す値打ちがあります。
