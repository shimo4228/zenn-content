> **この記事でわかること**: AI エージェントがコミット・公開の直前に止まったとき、人間に「diff 本文」を出すのか「意図の要約」で済ませるのかを、**対象の種類から機械的に決める判定表**です。そのまま自分のハーネスやチームのレビュー規約に移植できます。

AI にコードを書かせる量が増えると、承認の運用でこういう詰まり方をします。

- エージェントが出す diff の量に、人間のレビューが追いつかない
- かといって人間チェックをやめるとして、**代わりに何を承認すればいいのか**の決め手がない
- 結局「一応 diff を見せる」に落ち着き、実際には読まれないゲートだけが残る

私は 2026-07-25 に自分の Claude Code ハーネスでこの問題に当たり、承認ゲートの規約を書き直しました。原因は個々のスキルの書き方ではなく、**ゲートの軸が 1 本しか名前を持っていなかったこと**でした。この記事では、そのとき作った判定表と、外部モデルのレビューが見つけた 2 つの落とし穴を説明します。

## 前提

- 実例は Claude Code 2.1.220 + 自作ハーネス（`~/.claude` 配下の rules / skills 一式）です
- ただし成果物は**規約の書き方**なので、ツールには依存しません。Cursor でも Devin でも、社内のコードレビュー規約でも同じ形で使えます
- 前提知識: AI エージェントに実装させ、コミット前に何らかの承認ステップを置いている運用

## ゲートには 2 軸ある

承認ゲートを設計するとき、実は独立した問いが 2 つあります。

| 軸 | 問い | 何で決まるか |
|---|---|---|
| **第 1 軸** | **いつ**止まるか | 可逆性。`git checkout` で戻せる編集は止めない、外部への公開・DOI 採番・commit は止める |
| **第 2 軸** | 止まったとき人間は**何を**判断するか | 対象の種類（この記事の主題） |

私のハーネスには第 1 軸の規約（可逆性でゲートの強さを変える）が前からありました。ところが第 2 軸には規約がなく、**「止まる」とだけ書かれていて「何を見せるか」が書かれていない状態**でした。

この空白は放置されません。各スキルを書くたびに、その場の解釈で埋められていきます。そして人間に何かを提示する既定値は、たいてい「diff を見せる」になります。

## 症状: 軸に名前がないと「diff 承認」で埋まる

実際に私のハーネスで起きていたことは 2 つです。

### 1. 同じゲートの正本が 2 つに割れた

コミット直前の介入点について、2 つのファイルが別々のことを書いていました。どちらが正本（＝最終的に従うべき記述）なのかは、どこにも書かれていません。

| ファイル | 記述 |
|---|---|
| `rules/common/planning.md` | 「**Verify 結果確認** — コミット直前」（何を提示するかは未規定） |
| `skills/implementation-chain/SKILL.md` | 「公開・deposit・commit 直前の **diff 承認**」 |

起点は、私が以前に別の設計判断の記録へ残した一文でした。

> コミット前に最終チェックを私がするだけ

「最終チェック」の**対象**を書いていません。この一文が後段で「diff 承認」と解釈され、それが正本の顔をして定着していました。

### 2. 「人間が成果物を検査する」記述が 5 箇所に散った

正本がないので、独立に書かれたスキルがそれぞれ同じ空白を埋めていました。

| スキル | 修正前の記述 | 何が問題か |
|---|---|---|
| `implementation-chain` | 「commit 直前の diff 承認」 | 提示物の既定が diff になっている |
| `readme-writer` | 「diff を人間が承認して適用」 | 承認対象が差分の形で表現されている |
| `release-doi` | 「最新 commit が直前 release より新しいことを**目視**」 | 機械照合できる述語を人間に投げている |
| `paper-deposit` | 「Open the first page and **eyeball** it」 | PDF の目視確認を人間に投げている |
| `harness-sync` | 「`git diff` がレビューゲート」 | 一見同型（後述のとおりこれだけは残す判断になった） |

個別に文言を直す案も考えましたが、**病因（第 2 軸に正本がないこと）が残ります**。5 箇所で独立に同じ埋め方が起きた以上、次に書くスキルでも再発します。そこで規約ファイルを 1 本立てました。

## 判定表: 提示物は対象で決める

これが成果物です。**ゲートで止まったとき何を人間に出すかを、変更対象の種類だけで決めます。**

| 対象 | 提示するもの | なぜ |
|---|---|---|
| **振る舞いを規定する成果物**<br>（`CLAUDE.md` / `AGENTS.md` / rules / skill・エージェント定義 / 公開ドキュメント） | **本文** | テキストそのものが意図。読むこと自体が意図層の作業になる |
| **制御面（control plane）**<br>（hooks / permissions 設定 / `--allowedTools` 等の権限定義 / 定期実行タスクの定義） | **本文** | ゲートそのものを動かす。要約に畳むと検査を緩める変更が隠れる |
| **実装コード・生成物** | **意図の要約**<br>（何を志向し、結果として何がどう変わるか） | 正しさは決定論ゲートとレビューエージェントが持つ。diff 本文と機械チェックの PASS 一覧は出さない |
| **決定論ゲートが FAIL したとき** | **検出行そのもの** | 偽陽性かどうかの判定は人間にしか下せない。証拠なしに bypass を決めさせない |

一言でいうと、**成果物の正しさは機械が持ち、人間は意図を持つ**。ただし「テキストが意図そのもの」である対象だけは、本文を読むことが意図の判断そのものになるので例外的に本文を出す、という構造です。

規約ファイルに落とすとこうなります（実物からの抜粋です）。

```markdown:~/.claude/rules/common/human-gate.md
## artifact は機械、intent は人間

成果物の正しさ（build / types / lint / tests / secret scan）は決定論ゲートと review agent が持つ。
**人間を artifact 検査に戻さない**。手厚いレビュー体制は人間を降ろすための投資であり、
人間が読むためのお膳立てではない。

**review agent は検査者であって承認者ではない。** LLM judge は generator–verifier gap を持つ
（提案者と検査者が同一システムなら、検査は提案者の盲点を継承する）。承認は
「決定論ゲートの PASS」＋「人間の intent 判断」で構成し、**LLM 単独の承認経路を作らない**。
```

この判定表を当てると、先ほど洗い出した 5 箇所のうち `harness-sync` の「`git diff` がレビューゲート」は**残す判断**になりました。同期対象が skills / rules（＝振る舞いを規定する成果物）なので、本文を読むこと自体が意図の判断だからです。

ここが判定表の使いどころです。5 箇所は表面的には全部同じ「人間が本文を読む」記述で、grep すると同型に見えます。一律に消すと、必要なゲートまで一緒に落ちます。判定表があると、**同じ形の記述を対象の種類で仕分けできる**ようになります。

## 落とし穴 1: 制御面をコード扱いにすると、検査を緩める変更が隠れる

判定表の初版では、hooks や permissions といった制御面を「実装コード・設定」側に入れていました。外部モデル（Codex CLI）にレビューさせたところ、最優先の指摘として穴を突かれました。

:::details Codex の指摘（訳と原文）
訳: 中心となる対象境界は、実行可能なハーネスの制御を、提案者自身が書いた要約の裏に隠すことを許してしまう。また新しいルールは既存のセキュリティ偽陽性ワークフローと衝突する。

原文:

> The central target boundary permits executable harness controls to be hidden behind proposer-authored summaries, and the new rule conflicts with the existing security false-positive workflow.
> - [P1] Classify executable harness controls as behavior-shaping — …
:::

具体的にはこうなります。エージェントがコミット前の secret scan hook を無効化する変更をしたとして、規約を**文字どおり守ったまま**、こう要約できてしまいます。

```text
意図の要約: コミット前検査の構成を整理し、検査を強化しました
```

制御面は「ゲートそのものを動かす」ものなので、要約に畳むと**検査を緩める変更が善意の一文に化けます**。判定表では制御面を本文提示側に移し、振る舞いを規定する成果物と同じ扱いにしました。

## 落とし穴 2: 「PASS も diff も出さない」は偽陽性判定の経路を塞ぐ

同じレビューが見つけた 2 つ目です。「機械チェックの PASS 一覧も diff 本文も人間に出さない」を徹底すると、**secret scan の偽陽性を人間が判定する経路まで消えます**。

私のハーネスでは、コミット前の secret scan が検出したときに `SECRET_SCAN_BYPASS=1` で通す運用があります。これは「テストのダミー鍵なので通してよい」という判断で、人間にしか下せません。ところが検出行を見せなければ、人間は証拠なしに bypass を決めることになります。

そこで **FAIL は例外**という条項を足しました。

```markdown:~/.claude/rules/common/human-gate.md
**FAIL は例外** — 決定論ゲートが FAIL したときは**検出行そのものを提示する**。偽陽性判定
（`*_BYPASS`）は人間にしか下せず、証拠なしに bypass を決めさせない。
提示を省くのは PASS のときだけ。
```

「人間を成果物の検査から降ろす」は、**PASS のときの話**です。FAIL は人間の判断を必要とするので、証拠を出します。この非対称性を明示しないと、規約は安全側でなく危険側に倒れます。

## 意図の要約は自由記述にしない

最後に、判定表を運用に載せるときの必須条件です。

「実装コードは意図の要約を出す」だけで止めると、人間は**提案者自身が書いた自己申告を読んで判断する**ことになります。これでは成果物の層にあったギャップが、語りの層へ移動しただけです。

対策は、要約の**照合先を人間由来のものに固定する**ことです。私のハーネスでは介入点が 2 つあります。

1. **plan 確認** — 何をやるかが決まった時点（ここは人間が承認する）
2. **意図確認** — コミット直前

そして 2 の要約は、**1 で人間が承認した plan と照合する形で提示**します。自由記述の作文としてではなく、「承認済みの plan に対して、実際こうなりました」という対応づけで読ませます。参照先が人間の承認物なので、自己申告の輪が閉じません。

規約側では、第 2 介入点の呼び名も「Verify 結果確認」から「意図確認」に変えました。名前が「Verify 結果」のままだと、機械チェックの結果一覧を人間に読ませる運用に引き戻されるためです。

## まとめ: 自分の規約に移植する 3 ステップ

1. **既存の承認ステップを洗い出し、「何を提示すると書いてあるか」を確認する。** 「diff を承認」「目視で確認」「レビューして適用」といった記述を grep で拾います
2. **上の判定表を規約ファイル 1 本に落とし、洗い出した各箇所からそこを参照させる。** 個別の文言修正だけで済ませると、次に書くスキル・ドキュメントで同じ埋め方が再発します
3. **要約の照合先を、人間が承認した plan に固定する。** ここを決めないと、判定表を入れても検証の対象が提案者の自己申告のままになります

:::message
ステップ 1 の grep で、**語幹の取り逃しに注意してください**。私は `eyeballed` で検索して `eyeball`（活用前の語幹）を取り逃し、1 箇所が外部モデルのレビューまで生き残りました。動詞は活用形ではなく語幹で引くか、`grep -i` で複数パターンを当ててください。
:::

参考までに、この変更（規約 1 本の新設 + 関連 13 ファイルの参照つなぎ直し）は 14 ファイル・217 行追加で収まりました。判定表そのものは短く、効いたのは**それを参照する側を全部つなぎ直したとき**でした。

なお、この規約は決定論的な lint に落とせません。「振る舞いを規定する成果物かどうか」の判定自体が意味的な判断で、生成ドキュメント・設定ファイル・テストコードのような境界事例では都度考える必要があります。判定表は列挙で例示していますが、網羅はしていません。
