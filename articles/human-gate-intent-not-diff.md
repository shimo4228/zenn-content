> **この記事でわかること**: エージェントの自律実行を止めずに、意図とのズレだけを**取り返しがつくうち**（コミット・公開の直前）に捕まえる方法です。ゲートで人間に「diff 本文」を出すのか「意図の要約」で済ませるのかを、**対象の種類から機械的に決める判定表**と、要約を自己申告で終わらせないための**必須 1 点（`plan との差分` の 3 値宣言）**を渡します。そのまま自分の運用やチームのレビュー規約に移植できます。

エージェントの自律実行を伸ばしていくと、どこかでこの二択に突き当たります。

- **止めない側に倒すと、意図とのズレは実行後にしか分からない。** 動くものはできているのに、志向が違う。気づいたときには積み上がっていて、戻すコストが払えない
- **止める側に倒すと、人間がボトルネックになる。** レビュー待ちの列ができ、自律実行にした意味が消える
- 折衷案として「一応 diff を見せる」に落ち着く。**これが一番よくない。** 止めるコストは払っているのに、量に押されて読まれず、意図は守られていない

3 番目が一番広く起きている気がします。ゲートは形式として残り、実質は 1 番目、という状態です。

問い直すべきはここです。**その自動化は誰のためのものか。** 速く回すこと自体が目的なら人間は邪魔ですが、実際に欲しいのは「自分が意図したものが速くできること」のはずです。だとすれば削るべきは、人間の関与そのものではなく**人間が関与している中身**です。

そこでこの記事は、**人間を止める回数は増やさず、止まったときに判断させる層だけを移します**。成果物が正しいかどうかは機械側の一次責任とし、人間はその一段上、「何を志向し、結果として何がどう変わるか」を持ちます。そうするとゲートで見せるものが変わります。その振り分けが、これから渡す判定表です。

## 前提

- 実例は Claude Code 2.1.220 + 自作ハーネス（`~/.claude` 配下の rules / skills 一式）です
- ただし成果物は**規約の書き方**なので、ツールには依存しません。Cursor でも Devin でも、社内のコードレビュー規約でも同じ形で使えます
- 前提知識: AI エージェントに実装させ、コミット前に何らかの承認ステップを置いている運用

## ゲートには 2 軸ある

承認ゲートを設計するとき、実は独立した問いが 2 つあります。

| 軸 | 問い | 何で決まるか |
|---|---|---|
| **第 1 軸** | **いつ**止まるか | 可逆性。`git checkout` で戻せる編集は止めない、外部への公開・DOI 採番・commit は止める |
| **第 2 軸** | 止まったとき人間は**何を**判断するか | 対象の種類（この記事の主題） |

決まっているのはたいてい第 1 軸だけです。「コミット前に止める」「公開前に確認する」——**止まる条件は書いてあるが、止まったとき何を見せるかは書いていない**。私のハーネスもそうでした。

この空白は放置されません。ゲートを書くたびにその場の解釈で埋められ、埋まる既定値はほぼ必ず「diff を見せる」です。書く側からすると最も安全に見えるからです。全部見せておけば漏れがない。結果として、冒頭の 3 番目を量産します。

## 判定表: 提示物は対象で決める

これが成果物です。**ゲートで止まったとき何を人間に出すかを、変更対象の種類から決めます。**（以下の「決定論ゲート」は、lint・型チェック・テスト・secret scan のように、機械が Yes / No を出せる検査を指します）

| 対象 | 提示するもの | なぜ |
|---|---|---|
| **振る舞いを規定する成果物**<br>（`CLAUDE.md` / `AGENTS.md` / rules / skill・エージェント定義 / 公開ドキュメント） | **本文** | テキストそのものが意図。読むこと自体が意図層の作業になる |
| **制御面（control plane）**<br>（hooks / permissions 設定 / `--allowedTools` 等の権限定義 / 定期実行タスクの定義）<br>**および検査の証拠を作るもの**（テスト / fixture / lint 設定 / カバレッジ閾値 / CI 定義 / レビューエージェントのプロンプト / 依存） | **本文** | ゲートそのものと、**ゲートが根拠にしている証拠**を動かす。要約に畳むと「検査を緩める変更」が隠れる |
| **実装コード・生成物** | **意図の要約**<br>（何を志向し、結果として何がどう変わるか） | 機械化された検査で判定できる正しさは決定論ゲートとレビューエージェントが持つ。diff 本文と PASS 一覧は承認画面に出さない |
| **決定論ゲートが FAIL したとき** | **検出行そのもの**<br>（秘密の実値だけはマスクする） | 承認済みの plan に無い状態で、要約に畳む先がない（照合の仕組みは後述）。bypass するなら検査を 1 回無効化する判断になり、制御面と同じ扱いになる |

### 昇格規則: 不可逆性は対象区分を上書きする

表は**原則**であって、これだけで決めきれません。同じ「実装コード」でも、UI の余白調整と、認可ロジック・DB マイグレーション・課金処理・データ削除・鍵のローテーションでは、人間に渡すべきものが違います。そこで 1 行の上書き規則を置きます。

> **不可逆・高影響な変更は、対象区分にかかわらず本文（または該当差分）を提示する。**

第 1 軸（可逆性）は「いつ止まるか」だけでなく「何を出すか」にも効く、ということです。**原則は対象の種類で決め、不可逆性で本文提示側へ昇格させる**——この 2 段構えが正確な言い方になります。第 3 の軸を足す必要はありません。

### 一言でいうと

**機械化された検査で判定できる正しさは機械が持ち、人間は意図を持つ**。ただし「テキストが意図そのもの」である対象だけは、本文を読むことが意図の判断そのものになるので本文を出します。**本文提示は例外的な逆戻りではなく、同じ原則の別の出方**です。

もう 1 つ、判定表と対で必要な原則があります。

**レビューエージェントは検査者であって、承認者ではありません。** 提案する側と検査する側が同じ系統なら、検査は提案側の盲点をそのまま受け継ぎます（この記事ではこれを generator–verifier gap と呼びます）。したがって承認は「決定論ゲートの PASS」＋「人間の意図判断」の 2 つで構成し、**LLM だけで承認が閉じる経路を作らない**。レビューを厚くすることは、承認を LLM に委ねてよいという意味にはなりません。

規約ファイルに落とすとこうなります（実物からの抜粋。内部リンクと一部の参照は省いています）。

```markdown:~/.claude/rules/common/human-gate.md
## artifact は機械、intent は人間

機械化された検査で判定できる正しさは決定論ゲートと review agent が持ち、**人間を artifact 検査に
戻さない**（一次責任の割り当てであって保証ではない — 残余リスクは昇格規則で受ける）。
review agent は**検査者であって承認者ではない**（generator–verifier gap）。承認は
「決定論ゲートの PASS」＋「人間の intent 判断」で構成し、**LLM 単独の承認経路を作らない**。
```

## 適用してみる: 実際に 5 箇所で何が起きていたか

判定表を作る前、私のハーネスは第 2 軸が空白のままでした。以下は自分の環境の話ですが、**同じ空白を持つ運用なら同じ形で出ます**。

### 同じゲートの正本が 2 つに割れていた

コミット直前の介入点について、2 つのファイルが別々のことを書いていました。どちらが正本（＝最終的に従うべき記述）なのかは、どこにも書かれていません。

| ファイル | 記述 |
|---|---|
| `rules/common/planning.md` | 「**Verify 結果確認** — コミット直前」（何を提示するかは未規定） |
| `skills/implementation-chain/SKILL.md` | 「公開・deposit・commit 直前の **diff 承認**」 |

起点は、私が以前に別の設計判断の記録へ残した一文でした。

> コミット前に最終チェックを私がするだけ

「最終チェック」の**対象**を書いていません。この一文が後段で「diff 承認」と解釈され、正本の顔をして定着していました。

### 「人間が成果物を検査する」記述が 5 箇所に散っていた

| スキル | 修正前の記述 | 判定表を当てた結果 |
|---|---|---|
| `implementation-chain` | 「commit 直前の diff 承認」 | 実装コード → **意図の要約**へ変更 |
| `readme-writer` | 「diff を人間が承認して適用」 | 公開ドキュメント → **本文提示**に書き換え（対象は同じでも理由が変わる） |
| `release-doi` | 「最新 commit が直前 release より新しいことを**目視**」 | 機械照合できる述語 → **機械に降ろす** |
| `paper-deposit` | 生成 PDF の 1 ページ目を開いて**目視**（原文は "eyeball"） | 同上。フォント埋め込みの機械検証に置換 |
| `harness-sync` | 「`git diff` がレビューゲート」 | 同期対象が rules / skills → **そのまま残す** |

5 箇所は別の日に、別の目的で書かれています。**打ち合わせなしに全部が同じ既定値に落ちた**わけで、個々の書き手の不注意ではありません。空白があれば「人間に全部見せる」で埋まります。だから個別の文言修正では止まらず、第 2 軸そのものに規約を 1 本立てる必要がありました。

そして一番右の列が、判定表の使いどころを示しています。5 箇所は grep すると全部同型に見えますが、**一律に消すと必要なゲートまで落ちます**。実際 `harness-sync` は残す判断になりました。同期対象が rules / skills なので、本文を読むこと自体が意図の判断だからです。

## 補強 1: 制御面と「証拠を作るもの」

判定表の初版では、hooks や permissions を「実装コード・設定」側に入れていました。外部モデル（Codex CLI）のレビューが、最優先の指摘としてここを突きました。

:::details Codex の指摘（訳と原文）
訳: 中心となる対象境界は、実行可能なハーネスの制御を、提案者自身が書いた要約の裏に隠すことを許してしまう。また新しいルールは既存のセキュリティ偽陽性ワークフローと衝突する。

原文:

> The central target boundary permits executable harness controls to be hidden behind proposer-authored summaries, and the new rule conflicts with the existing security false-positive workflow.
> - [P1] Classify executable harness controls as behavior-shaping — …
:::

エージェントがコミット前の secret scan hook を無効化したとして、規約を**文字どおり守ったまま**こう要約できてしまいます。

```text
意図の要約: コミット前検査の構成を整理し、検査を強化しました
```

制御面は「ゲートそのものを動かす」ものなので、要約に畳むと**検査を緩める変更が善意の一文に化けます**。

そして弱め方は hooks や permissions だけではありません。**テストを自分の実装に通るよう書き換える**のが最も静かな経路です。この場合、エージェントは嘘をつく必要すらありません。

```text
意図の要約: 実装を修正し、テストは全件 PASS しました
```

事実そのとおりです。書き換えたのはテストのほうだ、という一点だけが要約に現れません。**「テストが通った」という事実だけでなく、「何をもって通ったとみなすか」までがレビュー対象**だということです。fixture・カバレッジ閾値・lint 設定・CI 定義・レビューエージェントのプロンプト・依存も同じ性質を持ちます。

### ではどう出せばいいか

要約か本文か、を**コミット単位で選ばない**のが答えです。1 つのコミットに実装と証拠の両方が入っているなら、**要約を出したうえで、証拠に当たる部分の本文だけを併記**します。

```text
意図の要約: ログイン失敗時のリトライ上限を 5 回から 3 回に変更（plan ステップ 2）

⚠ 検査の証拠に変更が含まれます — 以下は本文で確認してください

  tests/test_auth.py:41
  -    assert client.retry_limit == 5
  +    assert client.retry_limit == 3
```

人間が読むのは下 2 行だけです。実装側の diff は出ていません。**「テストが実装に合わせて緩められていないか」だけを見れば済む**ので、量に負けません。上の例は plan で決めた変更に対応しているので通します。plan にリトライの話が無いのにテストの閾値だけ下がっていたら、そこで止まります。

どのファイルが証拠側かは、多くの場合パスで拾えます。

```bash
# 変更ファイルから「証拠を作る側」の候補を抽出し、本文を併記する対象にする
git diff --cached --name-only | grep -E \
  '^(tests?/|\.github/workflows/|\.claude/|hooks/)|(_test\.|\.test\.|pyproject\.toml|package\.json|ruff\.toml|codecov\.yml)'
```

**これは完全な分類器ではなく、保守的な候補抽出です。** 通常コードに埋め込まれたテスト、独自ディレクトリ、lockfile、インラインスナップショットは取り逃します。自分の repo の既知の証拠側ファイルを足して育ててください。

私の環境では、この抽出を規約の文面から **PreToolUse hook**（`evidence-file-notice.sh`）に移しています。`git commit` を検知したら staged ファイルを同種のパターン（実物は `spec/` や `conftest.py`、pre-commit 設定なども含む、もう少し広いリスト）で走査し、該当があれば「該当ファイルの差分を人間に併記してください」という指示ごと承認フローに注入する形です。証拠側ファイルの列挙の正本は規約の文章ではなく hook の正規表現 1 箇所になり、規約側には「検出の正本はこの hook」というポインタが 1 行残るだけです。

こう組み替えた理由は 2 つあります。

- **文書にしか存在しない規約は確率的にしか守られません。** 「証拠側は本文を併記」と規約に書いても、エージェントが毎回それを思い出す保証はない。一方「どのファイルが証拠側か」はパスの形だけで決まる構造的な性質なので、機械なら 100% 発火します
- **列挙を規約と hook の 2 箇所に持つと必ずズレます。** 発火する側に一元化し、規約は原則だけを持つ

判定表のような意味的な判断は文書に残し、機械的に判定できる部分は見つけ次第ゲートに降ろしていく——この規約自体がその運用で育っています。

制御面（hooks / permissions / 定期実行タスク）も同じ形になります。要約 + 該当ファイルの本文。**判定が根拠にしている証拠を作っているものは、判定そのものと同じ扱い**です。

## 補強 2: FAIL のときは検出行を出す

同じレビューが見つけた 2 つ目です。「機械チェックの PASS 一覧も diff 本文も人間に出さない」を徹底すると、**secret scan の偽陽性を人間が判定する経路まで消えます**。

私のハーネスでは、コミット前の secret scan が検出したときに `SECRET_SCAN_BYPASS=1` で通す運用があります。「テストのダミー鍵なので通してよい」という判断です。

ここで人間に上げる理由は、機械には見分けがつかないから、ではありません。**たとえ機械やレビューエージェントの見立てが当たっていても、その決定の持ち主が人間でなければならない**種類の判断だからです。bypass は、その場で検査を 1 回無効化する行為です。制御面を動かすのと同じ性質なので、補強 1 と同じ理由で本文（＝検出行）が要ります。

もう一つ、**FAIL は承認済みの plan に無い状態**です。意図の要約は plan と照合して読ませるものなので（後述）、想定に無い状態は畳む先がありません。

```markdown:~/.claude/rules/common/human-gate.md
**FAIL は例外** — 決定論ゲートの FAIL は**検出行そのもの**を提示する。秘密の実値はマスクし、
偽陽性判定（`*_BYPASS`）の持ち主は人間
```

PASS のときに注意が要ります。PASS は「設定した検査が受理した」という意味しか持ちません。**plan どおりに実装されたかどうかは PASS からは分かりません**。だからこそ意図の要約が別に要るのであって、PASS 一覧を出さないのは「代わりに要約で見る」からです。

### 「見せない」と「残さない」は別

ここは誤解されやすいので明示します。PASS 一覧を出さないのは**人間の承認画面から退避させる**という意味であって、検査結果を捨てるという意味ではありません。証跡を消すと、後で「あのとき何が通っていたか」を辿る手段がなくなります。この記事の思想は情報を消すことではなく、**人間の判断面から不要な情報を退避させること**です。

この区別、当初は規約に条項として書いていましたが、いまの版では削っています。Claude Code は transcript と tool 実行結果をもともと常時、機械可読な形で保存するので、規約に書いても実行基盤の既定を再宣言するだけだからです。**実行環境がログ保存を保証しないなら、明文の条項として持ってください。** 「基盤が既に保証していることは規約に書かない」も、移植時の判定の 1 つです。

なお、真陽性のときに検出行をそのまま出すと、秘密の実値が会話・承認画面・ログに複製されます。ゲートが防ごうとしている漏洩を自分で広げることになるので、**ファイル・ルール名・前後の文脈は出し、値だけはマスクします**。人間が偽陽性を判定するのに必要なのは、値そのものではなく「どこで何のルールに当たったか」です。

## 補強 3: 意図の要約を自由記述にしない

判定表を運用に載せるときの必須条件です。

「実装コードは意図の要約を出す」だけで止めると、人間は**提案者自身が書いた自己申告を読んで判断する**ことになります。これでは、成果物の層にあったギャップが移動しただけです。読む対象が diff から作文に変わっただけで、書き手は同じです。

対策は、要約の**照合先を人間由来のものに固定する**ことです。私のハーネスでは介入点が 2 つあります。

1. **plan 確認** — 何をやるかが決まった時点（ここは人間が承認する）
2. **意図確認** — コミット直前

そして 2 の要約は、**1 で人間が承認した plan と照合する形で提示**します。参照先が人間の承認物なので、自己申告だけで輪が閉じることがありません。

### 必須にするのは「plan との差分」の宣言 1 点

ただし「plan と照合して書け」だけでは、まだ都合よく書ける余地が残ります。特に**実装中に新しい事実が見つかって plan から自然に逸脱した場合**、その逸脱が要約から静かに消えます。

最初の対策は、意図の要約そのものを固定フォームにすることでした。承認済み意図・実現した変更・plan との差分・ユーザーや運用への影響・証拠側の変更、という 5 つの見出しを必ず立てさせる形です。しかしこのフォームを規約に入れた翌日、規約全体を条項単位で見直す監査の中で、5 つを仕分け直すことになりました。**防ぎたい最悪ケース——逸脱の静かな消失——を実際に防いでいるフィールドは、1 つだけ**だと分かったからです。いま必須にしているのはこれだけです。

```text
意図の要約: ログイン失敗時のリトライ上限を 5 回から 3 回に変更（plan ステップ 2）
plan との差分: なし
```

`plan との差分` の値は `なし` / `あり` / `再承認が必要` の 3 つ。実装中の発見で plan が変わること自体は悪くありません。危険なのは、変わったという事実が要約から消えることです。

そしてこの宣言を必須にすると、**逸脱の「省略」が「虚偽」に変わります**。自由記述なら、逸脱に触れない要約は嘘をついていません——書かなかっただけです。宣言が必須なら、逸脱があるのに `なし` と書くのは虚偽であり、`あり` と書けば人間の目がそこへ向きます。書き手の誠実さに頼らず、省略という逃げ道を構造的に塞ぐ。**これだけは形式の強制でしか守れません。**

では他の 4 フィールドをなぜ落としたのか。あれは要約の**型**であって、防御ではなかったからです。何を意図し、何が変わり、影響は何か——それを落とさず要約するのは、結論から書く・結果をありのまま報告する・問いに応じた形で答えるという、**モデルが要約一般で守るべき較正そのもの**です。較正で守られる部分にまで固定フォームを課すと、1 行の設定変更にも 5 見出しを強制することになり、承認画面がテンプレの読み流しに変わります。

冒頭で「一番よくない」と書いた 3 番目——形式は残るが読まれないゲート——を、今度は要約の側で再生産するわけです。

なお「証拠側の変更」に至っては、補強 1 の hook が構造的にカバーしているので、フィールドとして書かせる必要自体がありませんでした。

Anthropic が Claude 5 世代向けに出したコンテキストエンジニアリング指針（[The new rules of context engineering for Claude 5 models](https://x.com/trq212/status/2080710971228918066)）は、この判断を一般則として言い当てています。要点は「ルールで縛る → 判断を委譲する」への転換、ただし**最悪ケースが許容できない領域だけは例外として明示的に縛り続ける**。5→1 の縮退はその適用です。要約の形はモデルの較正に委譲し、逸脱の消失——許容できない最悪ケース——だけを 1 点、形式で縛る。

このゲート規約の目的は、人間の認知資源を意図の判断に集中させることでした。**規約自身が形式の強制で書き手と読み手の注意を消費するなら、本末転倒**です。

実務的な利点がもう 1 つあります。3 値は列挙型で機械可読なので、「宣言が存在するか」自体を将来 hook の存在検査に落とせます。補強 1 と同じく、文書上の規約に決定論ゲートへ降ろせる出口をあらかじめ用意しておく形です。

### 止める回数にも上限を置く: 1 作業 1 ゲート

提示物の話と対で、回数の規律も 1 つ決めておきます。意図確認は**作業単位の完了点に 1 回**です。commit・push・公開・付随ドキュメント更新がまとまって発生するなら、**件数とスコープを明示列挙した 1 決裁**に束ねます。中間の phase や中間 commit のたびに承認を求めると、承認そのものがノイズになり、ゲートが形骸化します。例外は 2 つだけ——決定論ゲートの FAIL と、`plan との差分: 再承認が必要` です。

ただし「束ねてよい」は「暗黙に通してよい」ではありません。N 件を 1 決裁で通すなら、N 件であることを承認時に明示する。1 件向けの承認を黙って N 件に流用した時点で、それはゲートではなくなります。

### 粒度を上げるとボトルネックが移動する

この照合はエージェントが優秀なときほど効きます。**うまくいき続けているときが、意図の要約が形骸化する条件**です。毎回同じ「差分なし」を読み流す運用になったら、照合先の plan の粒度を上げます。

ただしこれはタダではありません。plan を細かくするほど、**ボトルネックがコミット直前から plan 承認へ移動します**。粒度を上げるのは、ズレたときに戻せないもの（外部公開・データ移行・権限変更）に絞ってください。二択を完全に消せるわけではなく、**払う場所を選べるようになる**というのが正確な言い方です。

規約側では、第 2 介入点の呼び名も「Verify 結果確認」から「意図確認」に変えました。名前が「Verify 結果」のままだと、機械チェックの結果一覧を人間に読ませる運用に引き戻されるためです。

## 自分の規約に移植する 3 ステップ

1. **既存の承認ステップを洗い出し、「何を提示すると書いてあるか」を確認する。** 「diff を承認」「目視で確認」「レビューして適用」といった記述を grep で拾います
2. **判定表と昇格規則を規約ファイル 1 本に落とし、洗い出した各箇所からそこを参照させる。** 個別の文言修正だけで済ませると、次に書くスキル・ドキュメントで同じ埋め方が再発します
3. **要約に `plan との差分`（なし / あり / 再承認が必要）の 3 値宣言を必須として組み込む。** 要約全体を固定フォームにする必要はありません。ここを決めないと、判定表を入れても検証の対象が提案者の自己申告のままになります

:::message
ステップ 1 の grep で、**語幹の取り逃しに注意してください**。私は `eyeballed` で検索して `eyeball`（活用前の語幹）を取り逃し、1 箇所が外部モデルのレビューまで生き残りました。動詞は活用形ではなく語幹で引くか、`grep -i` で複数パターンを当ててください。
:::

参考までに、私の環境ではこの変更（規約 1 本の新設 + 関連 13 ファイルの参照つなぎ直し）が 14 ファイル・217 行追加で収まりました。判定表そのものは短く、効いたのは**それを参照する側を全部つなぎ直したとき**です。

規約本文はその後の見直しで半減させています（毎セッション自動でコンテキストに読み込まれる本文が 265 → 125 words）。残したのは判定表・昇格規則・差分宣言という原則だけで、「なぜ」は設計判断の記録（ADR）へ、証拠側ファイルの列挙は hook へ逃しました。規約は放っておくと根拠と例示で太り、読まれなくなります。**原則は文書、なぜは記録、機械判定できる部分はゲート**、と置き場所を分けるのが維持のコツです。

## 「機械が持つ」の限界

正直に書いておきます。**ビルド・型・lint・テスト・secret scan が示すのは、それらがカバーしている性質だけ**です。認可ロジックの穴、並行性の競合、マイグレーションの不可逆な副作用、そもそも実装されなかった要件——このあたりは全部 PASS のまま通ります。レビューエージェントも、提案者と同系統である以上、盲点は共有されます（前述の generator–verifier gap です）。

なので判定表の 3 行目は「機械が正しさを保証する」ではなく、**成果物検査の一次責任を機械側に置く**という運用上の割り切りです。残余リスクはゼロになりません。

だからこそ昇格規則が要ります。**戻せない領域だけ人間を成果物側に残す**——データ移行、権限・課金まわり、外部公開、削除処理。逆に言えば、可逆な実装コードで人間が diff を読んでいるなら、それは残余リスクへの対処ではなく、ただの惰性です。

規約全体を決定論的な lint に落とすこともできません。証拠側のファイル抽出（補強 1 の hook）や差分宣言の存在検査は機械化できますが、「振る舞いを規定する成果物かどうか」の判定は意味的で、生成ドキュメント・設定ファイルのような境界事例では都度考える必要があります。判定表は列挙で例示していますが、網羅はしていません。

## 冒頭の問いに戻ると

自律実行を伸ばすほど、意図とのズレは実行後にしか見えなくなります。かといって人間をレビューに戻せば、自律にした意味が消えます。この二択に見えるのは、**人間の関与を「回数」で数えているとき**です。

回数ではなく中身で見ると、二択ではなくなります。止まる回数は変えずに、止まったときに読ませるものを成果物から意図へ移す。**削るのは人間の関与ではなく、人間が成果物の正しさを検算している時間**です。それはもともと機械のほうが得意で、しかも人間がやると量に負けて形骸化します。

その自動化が誰のためのものかという問いには、こう答えることになります。**速く回すためではなく、自分が意図したものが速くできるため**です。だとすれば、最後まで人間が持つべきものは 1 つしかありません。意図です。判定表は、それ以外を人間から取り上げるための道具でした。

人間のレビューを減らす話をしているときに残るのは、削り忘れた仕事ではなく、削れない仕事です。
