私は 16GB メモリの M1 Mac と 9B・E4B クラスの小型モデルで、SNS への投稿やコメントを自分で考えて書く自律エージェントを約 3 ヶ月、毎日 4 セッション無人で動かし続けてきました。その運用で得た堅牢化の知見を、技術記事のシリーズとして公開していきます。

その前に、1 本だけ先に書いておきたいことがあります。**なぜ小型モデルなのか**、です。

Mac Studio や新しい MacBook Pro の購入ページまで行ったことは、一度や二度ではありません。クラウドの大きいモデル（Opus や GPT 系）をバックエンドにする選択肢も、コード上は常にありました。それでも、買わず、移らずにきました。16GB M1 は経済的な制約ではなく、**選んだ制約**です。

小型モデルでの開発は、外からは「安上がりな妥協」に見えます。この記事は、それがなぜ妥協ではないのかの説明であり、私の立場表明です。あわせて、シリーズのハブを兼ねます。

## モデルの賢さは、設計の粗さを隠す

大きいモデルは、雑なプロンプトも、曖昧な指示も、抜けているガードも、賢さで吸収してくれます。製品を作るだけならそれは美点です。しかし**何かを作れるようになりたい**人にとっては、欠点になります。

動いたものの中で、どこまでが自分の設計で、どこからがモデルの賢さなのか、切り分けられなくなるからです。「動いた」と「作った」は別のことです。モデルの性能で殴って動かしたものは、動いた実績にはなっても、作る力にはなりません。

小型モデルには吸収力がありません。だから設計の欠陥が全部、表に出ます。

私の運用では、次の問題がすべて表に出ました。

- コンテキスト窓が黙って切り詰められる問題
- 出力の途中切れ
- サンプリングパラメータ 1 個の欠落による暴走

クラウドや大きいモデルの環境で、これらに悩まされることはあまりありません。環境に緩衝材が組み込まれているからです。

- コンテキスト窓は 20 万〜100 万トークン級で、切り詰め自体がめったに起きません。超過しても黙って切られるのではなく、明示的なエラーが返ります
- サンプリングの既定値は API 側が管理していて、パラメータを落とす余地が構造的にありません
- 多少おかしな出力が出ても、賢いモデルの ReAct パターン（LLM が結果を見ながら次の一手を選んで回る方式）なら、次の一手で立て直してそれらしく回りきってしまいます

ローカルの 16GB には、この緩衝材がありません。コンテキスト窓は自分で指定し、超過は黙って先頭から切り詰められ、サンプリング設定も自分の持ち物です。同じ種類の問題が隠しようのない形で表に出て、設計で塞ぐしかありませんでした。

緩衝材の上で動いている間は、自分の設計が守っているのか、環境が守ってくれているのか、区別がつきません。

## 制約の中で組む訓練は、環境が変わっても残る

以前、新しいツールを自由に入れられない環境で業務の自動化をしていた時期があります。セキュリティ上の制約、使えるソフトの制約、そして「新しいものを入れること」自体への組織的な摩擦。使えたのは、Excel や Access のようなすでに全員の PC に入っているソフトと、承認済みの RPA ツールだけでした。

道具を増やせないなら、手元の道具の組み合わせ方を深く知るしかありません。私はその中で、使える道具だけで最大限の自動化に取り組みました。ただ、この経験で本当に鍛えられたのは、道具の知識ではありませんでした。

自動化の実態は、属人的・職人的な暗黙知で回っていた業務を分解する作業です。手順のどこまでが決定論的に書けて、どこからが経験に基づく総合的な意味判断なのか。

その境界をギリギリまで細かく見極めて、業務を**「決定論で書ける部分」と「意味判断が要る部分」**に分別していきます。RPA に任せてよいのは前者だけで、境界を見誤った自動化は必ず壊れます。

この分別は、そのまま今のエージェント設計の図式になっています。

| 当時 | いま |
|---|---|
| Excel / Access / RPA で書ける定型処理 | スクリプト・コード（決定論） |
| 人間の意味判断が要る部分 | LLM（意味判断・確率的生成） |

決定論で書ける処理を LLM に投げません[^1]。意味判断が要るところにだけ LLM を使います。そして LLM は人間の判断の代替ではないので、出力の検証と最終判断はコードと人間の側に残します。

どちらに割り振るかの判断こそが設計の中心です。その判断力は制約だらけの環境で身につき、制約が消えたあとも原則として残っています。

## 小型で動く設計は、モデルに依存していない

小型モデルという制約には、訓練以外にもう 1 つ意味があります。**下限の実証**です。

9B・E4B クラスで無人 3 ヶ月回る設計は、モデルの賢さで設計の穴を埋めていません。意味判断は LLM の仕事のままですが、守る仕組みは全部コード側にあります。

- 入力は送る前に見積もって守る
- 出力の切り詰めは検出して落とす
- 失敗は telemetry（動作の記録機構）が構造的に記録する

どれもモデル非依存の設計です。だから設計の考え方は、大きいモデルに引っ越してもそのまま持ち越せます。持ち越せないのは、モデルに紐づいた較正値や閾値です（この引っ越し問題はシリーズの後続記事で扱う予定です）。

逆方向は成り立ちません。大きいモデルの賢さを前提に組んだ設計は、小さい環境ではそのまま動きません。上に積むのは簡単ですが、下に降ろすには作り直しが要ります。

もちろん、大きいモデルを使えば、同じものはもっと楽に動いたはずです。ただ、楽に動いたものは、どこまでが設計でどこからがモデルの賢さか、最後までわかりません。小型で動いた分だけは、自分の設計だと言えます。私が「妥協ではない」と言っているのは、その意味です。

## このシリーズで扱う技術的な中身

ここまでが「なぜ小型か」の話です。実際に 16GB で無人運用を成立させた技術は、続く技術記事で扱います。すでに読めるのはこの 2 本です。

- **[AIエージェントの「なぜその判断？」に答えるオブザーバビリティ設計3パターン](https://zenn.dev/shimo4228/articles/agent-observability-patterns)** — 無人運用の土台になる「エージェントの判断を後から追える形で記録する」側の設計
- **[Claude Code のメモリーにベクトルは 1 本もない — memory RAG の前に ADR を](https://zenn.dev/shimo4228/articles/rag-to-adr-agent-memory)** — 「読める規模 × LLM の強さ」でエージェントの記憶設計を判定する。小型モデル環境（本シリーズ）が RAG の正当領域、frontier 級が ADR の領域という整理
- **LLM エージェントに fault injection TDD を入れたら silent failure が3件出た**（近日公開） — その記録チャネルを assert する側。運用障害の履歴からテストを起こし、黙って壊れる箇所を事前に露出させる

この先の題目は、あえて決め切らないことにします。書いてみるとトピックも内容も変わるからです（実際、fault injection の記事は当初の構想には無く、書く過程でこのシリーズに接続されました）。公開のたびに、このハブへリンクを追加していきます。

このエージェント自体の構築記は [Moltbookエージェント構築記 — Claude Codeとセキュリティファースト開発](https://zenn.dev/shimo4228/articles/moltbook-agent-scratch-build) から始まっています。小型モデルとの格闘が本格化した回は [エージェントの記憶が壊れた — 9B モデルと格闘した 1 日](https://zenn.dev/shimo4228/articles/few-shot-for-small-models) です。

## まとめ

- 小型モデルの選択は経済的な妥協ではなく、**設計の欠陥を露出させるために選ぶ制約**です
- 制約下で鍛えられるのは道具の知識ではなく、**決定論と意味判断を分別する力**です。この分別はコードと LLM の分担という、エージェント設計の中心にそのまま持ち越せます
- 小型で無人運用が成立する設計の考え方はモデル非依存であり、大きいモデルへの引っ越しにもそのまま持ち越せます（較正値だけは再測定）
- 続けるか移るかは目的次第です。最短で動くものが欲しいならクラウドが向きます。作る力が欲しいなら、小型モデルで続ける価値があります
