「AI生成記事」と聞いて何を想像するだろうか。プロンプトを入れてボタンを押せば、記事が出てくる。そんなイメージだろう。

今日、Claude Code と一緒に1本の技術記事を書いた。2時間かかった。その間に20回以上の対話を重ね、タイトルは3回変わり、記事の核心そのものが別物になった。

この記事は、その制作過程を全部公開する。「AI生成記事」の実態を見せるために。

## 何を書いたか

[自律エージェントにオーケストレーション層は本当に必要か](https://zenn.dev/shimo4228/articles/symbiotic-agent-architecture)

自作の自律エージェントフレームワークの設計思想を書いた記事だ。シリーズ4作目にあたる。「自律エージェントにオーケストレーション層は必要か」という問いを立て、自分のエージェントが実はオーケストレーション層なしで動いている事実から設計論を展開している。

## なぜ AI と記事を書くのか

先に動機を明かしておく。

自分は Claude Code と一緒にエージェントを実装した。設計の議論、コードレビュー、デバッグの指摘——実装中も対話は多い。動くものはできた。しかし「なぜこの設計で動くのか」を体系的に言語化する機会は、実装の最中にはなかった。

記事を書くことで、それが言語化される。Claude Code が書いた初稿を読み、「ここは違う」「ここはそういう意味だったのか」と反応する。その過程で、Claude Code と一緒に作ったものの構造が見えてくる。

つまり、記事を書くのは読まれるためだけではない。**自分の実装経験を知識として結晶化するため**だ。AI が持っている実装の知識を、記事化の過程で自分のものにする。この1ヶ月半で自律型エージェントをスクラッチで実装できるまでになったのは、この作業の積み重ねによるところが大きい。

## 記事を書く前にやること: コンテキスト収集

いきなり「書いて」とは言わない。まず `/collect-context` というコマンドを実行する。

これは自分で作った Claude Code のカスタムコマンドで、現在のセッションと関連する過去のコンテキストを自動で収集し、1ファイルに構造化してくれる。具体的には以下を集める。

- **現在のセッション**: やったこと、Before/After データ、コード例、技術的発見、判断の理由
- **過去のセッション**: 関連する過去の作業記録や知見（MCP 経由で検索）
- **プロジェクト知識**: auto-memory、既存記事との差別化、学習済みスキル

テーマはキーワードとして渡せるが、省略すればセッション内容から自動推定する。今回の記事では、エージェントの README、過去3作のシリーズ記事、セッション中の設計判断とその理由が1つのドラフトファイルに集約された。これが初稿の素材になる。

AI に「何か書いて」と丸投げするのと、構造化されたコンテキストを渡して「これを元に書いて」と言うのでは、出力の質がまるで違う。

## 制作フロー全体像

今回の記事は、以下の流れで作った。

```text
1. /collect-context でコンテキスト収集 → ドラフトファイル生成
2. ドラフトを元に Claude Code が初稿を生成
3. editor エージェント（Claude Code 内の別エージェント）が初稿をレビュー
4. 自分が読んで対話しながら校正（← ここが2時間）
5. 再度 editor エージェントでレビュー
6. 自分が最終チェックして published: true → git push
```

ポイントは、自分のレビューの前後に editor エージェントのレビューが挟まっていることだ。editor エージェントは文体の一貫性、AI スロップの検出、構成の論理性をチェックしてくれる。機械的に検出できる問題は editor が潰し、自分は「これは自分の実感と合っているか」に集中する。

以降のセクションでは、ステップ4で実際に何が起きたかを具体的に見せる。

## タイトルの変遷

最終稿のタイトルは「自律エージェントにオーケストレーション層は本当に必要か」だ。最初からこれだったわけではない。

```text
初稿:   「エージェントはオーケストレーターに寄生して薄く生き残る」🦠
修正1:  「オーケストレーション層を捨てたら、エージェントが6000行で済んだ」🤝
最終稿: 「自律エージェントにオーケストレーション層は本当に必要か」🤝
```

初稿のタイトルを見た瞬間、自分で「寄生するとかやめて。めっちゃいや」と言った。Claude Code は「寄生」を面白い比喩として使ったつもりだったが、読者からすれば攻撃的に見える。共生はいいが、寄生はダメだ。

2回目の「6000行で済んだ」に対しては「6000行って多いの？少ないの？」と返した。文脈なしの数字はタイトルとして機能しない。

最終的にたどり着いたのは、主張ではなく**問いかけ**だった。「オーケストレーション層は必要か？」——自分自身がまだ答えを確信していないから、問いかけが正直だった。

## 核心が変わった瞬間

これが一番重要な話だ。

Claude Code が書いた初稿の核心は「**オーケストレーションを外部に委譲した**」だった。自分のエージェントのオーケストレーション層を Claude Code に委譲した、という設計報告だ。

これで2時間走った。途中まではこの軸で校正していた。

転機は、自分がふと言ったこの一言だった。

> 本番では Claude Code すら登場しない。launchd で勝手に回っている

これで全体の論理が崩れた。「委譲した」と書いているが、本番稼働中に Claude Code は何もしていない。開発時は自然言語で Claude Code に頼んでいるし、本番はスケジューラで自動実行されている。**委譲先がいない。**

つまり、オーケストレーション層を外に「委譲した」のではなく、**開発時は会話で済み、本番には要らなかった**というのが実態だった。

この発見は、Claude Code には出せなかった。Claude Code は「委譲した」というフレーミングでそれっぽい記事を書けた。しかし、自分のエージェントが実際にどう動いているかを知っているのは自分だけだ。

## メタファーはどこから来たか

最終稿では「港に発着する自律エージェント」という比喩が記事全体を貫いている。外洋で全部やる船（OpenClaw）に対して、港を母港にして出ていく船（Contemplative Agent）。

これも Claude Code が考えたのではなく、自分が言った。

> Claude Codeという港に発着するのが正しい自律型エージェントのあり方ではないか？

Claude Code はこの比喩を記事構造に組み込んだ。セクション見出し、OpenClaw との対比、launchd を「港からの定期便」と接続する——構成力は AI のほうが上だ。しかし、比喩の原石は人間から出た。

さらに面白かったのは、自分が言った直後に「launchd はまさに港からの発着じゃん」と気づいたことだ。macOS の launchd（スケジューラ）が文字通り「launch」（出航）させている。比喩と実装が偶然つながった。

## 「正しい」を削る

AI は断定が好きだ。

初稿にはこんな表現が並んでいた。

```text
「設計は正しかった」
「正しい設計には、もう1つ大きな利点がある」
「ホスト固有の結合は本当にゼロだった」
「意図しない汎用性の創発だ」
```

自分の反応は「あんまり設計が正しいと主張しなくていい。まだわからないし」だった。

修正後はこうなった。

```text
「少なくとも方向としては悪くない」
「うまくいくかどうかはまだわからない」
「原理上は動くはずだ」
「結果的に汎用性が生まれていた。狙ったわけではない」
```

後者のほうが自分の実感に近かった。

AI は断定的に書く傾向がある。校正でそこを削るのが、自分にとっては一番多い作業だった。

## AI が間違えた5つのこと

校正プロセスで、Claude Code が書いた内容のうち事実と合わなかったものを列挙する。

**1. cron → launchd**
macOS のスケジューラを「cron」と書いた。実際は launchd だ。一般的な知識で書くと、個別の環境とずれる。

**2. 「オペレーター」が誰かわからない**
「オペレーターが Claude Code に意図を伝え」と書いたが、自分自身が「オペレーターって誰？私のこと？」とわからなかった。抽象的な用語より「自分」のほうが通じる。

**3. 異なるツール間の類似性を過大評価**
別のツールの設計判断と「同じだ」と書いたが、実際はアーキテクチャが違っていた。表面的な共通点を Claude Code が過大評価していた。

**4. 「カタログ化しない」という主張**
Claude Code は「アダプタをカタログ化しない設計判断」と書いたが、そもそもカタログ化しようとしたことがない。やらないことを「やらない判断」として語るのは不誠実だ。

**5. コード生成を「自分で書く」と表現**
「自分でアダプタを書く必要はない」と書いたが、普段から Claude Code と一緒に開発していて「自分でコードを書く」という概念自体がずれている。

いずれも「それっぽいが実態と違う」ケースだ。AI は一般的な知識で空白を埋めるが、著者の実環境を知らない。

## 校正対話の記録

2時間の対話の一部を並べる。これが記事の形を作った。

| 対話 | 何が変わったか |
|---------|-------------|
| 「寄生するとかやめて。めっちゃいや」 | 全体のメタファーが共生型に |
| 「全然まだ到達点じゃないよ」 | 「シリーズの到達点」を削除 |
| 「LangChainと比較するけど個人実装にそこまでできるわけないでしょ」 | 比較のトーンを「真似るのは無理。別の道を探した」に |
| 「四公理の記述は技術記事としてふさわしくない」 | セクションごと削除 |
| 「Coworkのくだり面白さが伝わらない」 | 時系列に並べ直し |
| 「設計が正しいと主張しなくていい。まだわからない」 | 探索的トーンに全面修正 |
| 「launchdはまさに港からの発着じゃん」 | メタファーと実装が接続 |
| 「毎日午前3時に記憶の整理もスケジュールされている」 | 具体的な運用情報を追加 |
| 「Cronじゃなくない？」 | 事実誤認を修正 |
| 「6000行が多いのか少ないのかわからない」 | タイトルから削除 |

## 記事の核心は、対話の中にある

AI は構成力がある。lint を通す文章を書ける。セクション見出しを考えられる。editor エージェントにレビューさせれば、改善点を指摘できる。

一方で、著者にしかできないことがある。「寄生はいやだ」と感じること。「まだわからない」と正直に言うこと。「launchd はまさに港からの発着じゃん」と気づくこと。「cron じゃなくない？」と自分の環境を知っていること。

AI が書いた初稿は素材だ。そこに著者が反応し、対話を重ねることで記事が形になる。

## AI と記事を書くことは、AI を理解することだ

「結局、AI の間違いを直す作業でしょ」——そう見えるだろう。しかし、それだけではなかった。

AI が書いた原稿を校正するという行為は、**AI が実装時に何を考えていたかを可視化する作業**だ。Claude Code がエージェントの設計について「オーケストレーションを委譲した」と書いたとき、それは Claude Code がその設計をどう解釈したかの表明だった。自分はそれを読んで「いや、違う。委譲じゃなくて不要だった」と気づいた。

つまり記事を校正することは、一緒に仕事をしている相手の思考を読み解く行為だ。Claude Code がどこで一般化しすぎるか、どこで断定に走るか、どこで自分の実環境と乖離するか。それを知ることで、次の協業の精度が上がる。

そして、AI の思考を理解する過程で、自分の思考も整理される。「港に発着する」という比喩は、記事を書く前には持っていなかった。「オーケストレーション層は要らない」という結論も、書く前には言語化できていなかった。AI との対話が触媒になって、自分の中にあった未整理の考えが形になった。

間違いを直す作業に見えたものは、実は一緒に考える作業だった。少なくとも自分にとっては。自分だけでは言語化できなかったものが、AI の初稿に反応する形で出てきた。

## 初稿は数分、記事は2時間

初稿の生成には数分しかかからなかった。そこから2時間かけて対話を重ね、タイトルは3回変わり、核心が「委譲した」から「要らなかった」に変わった。

AI が書き、人が反応し、対話の中で核心が見つかる。「AI生成」という言葉だけでは、この過程が見えない。そこを私は伝えたかった。
