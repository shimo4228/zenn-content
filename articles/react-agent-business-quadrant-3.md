> **シリーズの位置づけ:** ReAct エージェント適用域シリーズの 3 作目。象限名は前作および [AAP repository](https://github.com/shimo4228/agent-attribution-practice) に揃えている。

## 前提

[前々作](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant) で業務 AI を 4 象限に分け、ReAct エージェントが正当に必要なのは (4) Autonomous Agentic Loop 象限だけだと書いた。[前作](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant-2) で、業界の語彙には (3) LLM ワークフロー象限が独立した呼び名として存在せず、その不在が ReAct を全象限に被せる消去法的選択を生んでいる、という観察を書いた。

参照しやすいように 4 象限を一覧で再掲する。

- (1) **スクリプト象限** — 決定論 × 定義可。スクリプト / パイプラインで処理
- (2) **Algorithmic Search 象限** — 決定論 × 探索的。古典 AI / OR の領域 (本記事の射程外)
- (3) **LLM ワークフロー象限** — 意味判断 × 定義可。事前定義されたワークフローの中で LLM を呼ぶ。対話形 (専門 chat agent) とバッチ形 (単機能 LLM 関数) を含む
- (4) **Autonomous Agentic Loop 象限** — 意味判断 × 探索的。LLM 自身が次の行動を決める自律ループ (= ReAct エージェント)

## 時間軸という新しい軸

前作までは「業務の性質」を軸に象限を立てていた。本作はもう一段深い軸を導入したい。**時間軸**だ。

業務には設計フェーズと運用フェーズがある。両者は別の活動で、別の最適化軸を持つ。設計フェーズは柔軟性を最大化、運用フェーズは予測可能性を最大化。エージェントエコシステムの混乱の根は、この二つを一つのシステムに圧縮しようとしていることにあるのではないか。

本作の問いをひと言で言えば、**ReAct は設計フェーズの道具で、本番運用には要らないのではないか**、ということだ。

## 設計フェーズと運用フェーズ

業務システムを作る作業は、二つの異なるフェーズに分かれる。

**設計フェーズ**: 業務の構造を理解し、何を機械化し、何を人間が担うかを決め、ワークフローを組み立てる作業。何が起こるか事前に分からないので、探索的に進む。「次に何を確認すべきか」が事前に決まらない。

**運用フェーズ**: 設計したワークフローを実際に動かす作業。対象業務の構造はもう判明している。決められた経路を、決められた頻度で、決められた品質基準のもと回す。何が起きるかは事前に予測可能であるべきだ。

この区別は新しいものではない。ソフトウェア工学では development vs production、BPM では as-is 分析 vs 運用、システム設計では設計時 vs 実行時として、形を変えて存在してきた。ところがエージェントの議論では、前作・前々作で見てきたとおり、この区別が曖昧になりやすい。「自律エージェントが業務を回す」と言うとき、それは設計と運用を一つのシステムに圧縮しようとしているように見える。

## 本番運用で「次に何をするか分からない」のは、運用が求める性質を取りこぼしている

ReAct の中核は「次に何をするかを LLM が動的に決める」ことだ。これが正当に必要なのは、次に何をすべきかが**事前に分からない**状況だ。コーディング、Deep Research、未知環境の探索、ブラウザ自動操作。前々作で (4) Autonomous Agentic Loop 象限の正当領域として挙げたものは全部、設計フェーズや探索フェーズに属する作業として読める。

本番運用に入った業務で「次に何をするか分からない」状態が生じているとしたら、本番運用が求める性質 — 予測可能性、ログ追跡可能性、コストの安定性、責任の帰属可能性 — のいずれかが ReAct のアーキテクチャでは確保しにくい、ということではないか。これらは本来、本番運用に渡す前にワークフロー側で確保できる形に組み立てておく対象であって、本番運用そのものに ReAct を当てて事後的に繕う対象ではないのではないか。

業務の腑分けが完了していれば、(1) スクリプト象限の処理は決定論で書け、(3) LLM ワークフロー象限の処理は単機能 LLM 関数や専門 chat agent として固定でき、それ以外の判断は明示的なハンドオフ点で人間に渡す、と決まる。本番運用ではこのワークフローが動くだけだ。次に何をするかは、ワークフロー側が知っている。

ここで反論があり得る。「本当に動的な業務はないのか? 顧客対応のように毎回新しい問い合わせが来る業務は?」

これは見かけの動的さで、実際は違う。問い合わせの中身は無限に多様に見えても、処理する経路は有限の型に収束する。FAQ 的な対応、専門知識検索、ルーティング判断、エスカレーション、それぞれが (3) LLM ワークフロー象限のバッチ形 (単機能 LLM 関数) または対話形 (専門 chat agent) として固定できる。問い合わせの中身が新しくても、処理経路は事前に決まっている。

仮に経路を固定せず、自律エージェントに ReAct で問い合わせを丸ごと裁かせたとする。そのうちの一件で訴訟レベルのトラブル — 誤った医療助言、不適切な金融商品案内、機密情報の漏洩、差別的な対応 — が起きたとき、責任の所在を組織はどう示すのか。「エージェントが動的に判断した」では済まないだろう。前作で書いた attribution gap — 判断連鎖を事後に特定の原因に帰属できなくなること — が、そのまま組織のリーガルリスクとして立ち上がってくる。可逆性の低い業務で、一件のトラブルで組織が終わりかねない可能性を引き受けてまで、経路を固定しない選択を取る理由はどこにあるのか。

仮に訴訟リスクを引き受けてでも動的対応を選びたい業務があるとしても、本当に「処理の構造そのものが毎回新しい」業務があるなら、それは研究開発フェーズや探索フェーズの仕事として扱うほうが筋に見える。本番運用フェーズの定義に収まる仕事ではないように見える。

## 本番運用中に新しいパターンが現れたら

本番運用中に、既存の処理経路に収まらない新しいパターンが現れることはある。これをどう扱うかが、設計と運用の関係を決める。

ReAct 流の解決は「自律エージェントが新しいパターンに動的に対応する」だ。だがこれは、運用フェーズに設計フェーズの活動を埋め込んでいる。動的な対応はその場では機能するかもしれないが、対応の根拠がログに残らず、再現性がなく、責任の帰属が曖昧になる。前作で書いた redirect 不能性 — ReAct ループのブラックボックス性で、障害時に責任の帰属先を切り分けられなくなる現象 — が、本番運用の最中に発生する。

別の解決がある。**新しいパターンは設計フェーズへのフィードバックとして処理する**。本番運用中に新しいパターンが現れたら、それは現在のワークフローの設計が想定していなかったケースだ。一時的な対応 (人間の判断、暫定エスカレーション) で本番を回しつつ、設計サイクルに戻ってこのパターンを分析し、4 象限のどこに位置づけるかを決める。スクリプト象限なら決定論ルールを追加、LLM ワークフロー象限なら新しい単機能 LLM 関数や対話分岐を追加、Autonomous Agentic Loop 象限のタスクと判明したら attribution gap を引き受ける判断に進み、人間判断が要るならハンドオフ点を明示する。いずれもワークフローを更新する。

この解決のほうが、設計と運用の境界がはっきりする。設計フェーズは柔軟に動き、運用フェーズは予測可能に動く。それぞれの最適化が混在しない。

## コーディングエージェントの位置

ここで前々作・前作で残されていた論点が回収されてくる。少なくともコーディングエージェントについては、ReAct が正当に発揮される場所として読めそうだ。

コーディングエージェントは**設計フェーズに常駐する道具**だからだ。コーディングの各タスクは本質的に「次に何をするか分からない」探索作業で、一つのコーディングセッションは完結すれば終わる。Devin や GitHub Copilot Coding Agent のように、コーディングエージェント自体が CI/CD パイプラインで継続稼働するケースもあるが、各セッションの中身は毎回独立した探索で、定常ワークフローとして事前定義されてはいない。これが業務エージェントとの違いだ。

業務エージェントはどうしても本番運用フェーズに入る。本番運用フェーズでは探索が終わっているのだから、そこに ReAct を置く必要はあるのか。業務エージェントとして売られている ReAct ベースの製品は、本来設計フェーズの道具を運用フェーズに持ち込んでいるカテゴリエラーを起こしているように見える。

Deep Research や未知環境のブラウザ自動操作も、コーディングエージェントと同じ位置にある。これらは「探索作業そのもの」であって、定常的な業務運用ではない。ユーザーが質問するたびに新しい探索が走るが、その探索は数分から数十分で終わる。終わった後に同じシステムが動き続けるわけではない。**毎回が独立した小さな設計フェーズ**として読める。

つまり ReAct の正当領域は、業務の象限ではなく、**フェーズの違い** で定義したほうが正確に切れるのではないか。設計フェーズと探索フェーズは「次に何をするかが事前に決まらない」という性質を共有しており、本記事ではこの共通性質を持つフェーズを ReAct の適用条件として扱う。そしてそれは (4) Autonomous Agentic Loop 象限が常駐する場所として読める。運用フェーズに ReAct を呼び込む必要はどこにあるのか。

## 設計と運用を圧縮するエコシステムの問題

エージェントエコシステムは、設計フェーズと運用フェーズを一つのシステムに圧縮しようとしている。「自律エージェントが業務を理解し、ワークフローを組み立て、それを実行する」というビジョンは、両フェーズを同時に担うシステムを想定している。

問題は両フェーズの最適化軸が逆だということだ。設計フェーズは柔軟性、何が起こるか分からないので選択肢を広く保つ必要がある。運用フェーズは予測可能性、ログ追跡・責任帰属・コストの安定が必要だ。両者を一つのシステムに同居させると、柔軟性のために予測可能性が犠牲になり、予測可能性のために柔軟性が犠牲になる。設計時の柔軟性も、運用時の予測可能性も、どちらも中途半端なシステムが出来上がる。

切り分ける設計指針はこう読める。設計フェーズには (4) Autonomous Agentic Loop 象限の道具 (コーディングエージェント、Deep Research) が常駐する。設計が完了して運用フェーズに渡される業務は、(1) スクリプト象限と (3) LLM ワークフロー象限の組み合わせ (必要なら (2) Algorithmic Search 象限を含む) で動き、Autonomous Agentic Loop 象限は設計フェーズの役割に収まる。新しいパターンが現れたら、設計フェーズに戻す。

## 三部作で見えてきたこと

三作を並べると、エージェントエコシステムの混乱は三層に分かれていることが見えてくる。

最上層は **象限の誤適用** だ。前々作で書いた、(3) LLM ワークフロー象限の業務に (4) Autonomous Agentic Loop 象限のアーキテクチャを被せるカテゴリエラー。これが現場で観察される一次的な症候だった。

二層目は **語彙の不在** だ。前作で書いたとおり、業界には (3) LLM ワークフロー象限を肯定形で名指しする語が無い。語彙の不在は誤適用の温床で、設計者は決定論で書ける部分とそれ以外を切ったあと、後者を一括して ReAct に流す消去法的選択に追い込まれる。

三層目は **時間軸の混同** だ。本作で書いた、設計フェーズと運用フェーズを一つのシステムに圧縮する設計思想。これが語彙の不在の更に根にある。設計と運用が同じ時間軸の中で起きているという発想が暗黙に共有されているから、両者を区別する語彙が必要とされてこなかった、という連鎖が見えてくる。語彙がないままなら、設計フェーズの道具 (ReAct) を運用フェーズに被せても違和感が出ない。

三層は独立した観察ではなく、上から下に降りていく連鎖になっていた。誤適用は語彙の不在から生まれ、語彙の不在は時間軸の混同から生まれている。三作を順番に書きながら、解像度が一段ずつ降りていく感覚があった。

最終層から見ると、ReAct の正当領域は **設計フェーズの探索的タスク** に絞り込まれていくように見える。具体的にはコーディング、Deep Research、未知環境の探索。本番運用に入る業務システムは、設計が完了した時点で ReAct を手放し、(1) スクリプト象限と (3) LLM ワークフロー象限の組み合わせで動かせるのではないか。

## おわりに

エージェントの議論は「自律性をどこまで上げられるか」という能力ベンチマークの軸に偏りがちだ。だが現場で動かすことを考えると、能力の問題よりも **どのフェーズで何の道具を使うか** の問題のほうが先に立ってくる。

設計フェーズで ReAct を使うのは、正当に見える。コーディングエージェントは本物の道具で、開発者の生産性を実際に押し上げている。Deep Research も新しい探索の形を提供している。これらは ReAct の力が正当に発揮される場所と読める。

運用フェーズで ReAct を使うのは、設計の不完了を運用で繕う行為になっていないか。前作で書いた人為的 redirect 不能性は、ここで発生する。設計フェーズで腑分けを完了させ、運用フェーズには予測可能なワークフローだけを渡す — これがエージェントを業務に組み込むときの基本指針として読めるのではないか。

時間軸を語る言葉は、業界にまだ整っていない。設計と運用を一つに圧縮する力学は、「自律エージェントが業務を回す」というマーケティング上の物語と無関係ではないだろう。物語の力は強く、否定するのは効率的ではない。代わりに、別の物語 — 「設計が完了したら ReAct は退場する」「運用には予測可能なワークフローが残る」— を、現場の側から並行して立ち上げていく方が筋に見える。本作は、その立ち上げを「フェーズ」という語彙で行う試みだ。
