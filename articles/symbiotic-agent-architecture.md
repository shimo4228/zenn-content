「自律エージェント」と聞くと、何でも自分でできるものを想像する。コードを書き、ツールを選び、エラーから自力で回復する。OpenClaw のようなフレームワークはまさにそれを目指していた。

自律エージェントを作ってみて、違う像が見えてきた。**自律とは、外洋で全部やる船ではなく、港を母港にして出ていく船ではないか。**

出航したら自分で動く。記憶し、学習し、判断する。しかしコード生成やセットアップが必要なときは Claude Code という港に戻る。この記事は、自作エージェント [Contemplative Agent](https://github.com/shimo4228/contemplative-agent) の設計を通じて見えた「港に発着する自律エージェント」の話だ。

## なぜエージェントフレームワークは太るのか

まず、既存のフレームワークが抱える構造的な問題から始める。

エージェントフレームワークを個人で作ろうとして、最初にぶつかる壁がある。LangChain のような大規模フレームワークは数十のパッケージに依存し、Slack・Discord・Google Drive と公式アダプタを揃えている。個人でこれを真似るのは無理だ。そもそも真似る必要があるのかという疑問が先に来た。

問題はアダプタの数ではない。**構造**だ。「何でもできる」を目指すフレームワークは、ユーザーが増えるたびにアダプタが増え、コアが太り、セキュリティの攻撃面が広がる。

<!-- textlint-disable -->

OpenClaw を例に挙げる。このフレームワークはファイル操作、ブラウザ操作、50以上のインテグレーションに加え、**エージェントが自律的にコードを生成・実行する能力**をコア機能として持つ。自分でスキルを書いて自分で実行する設計だ。結果、512件の脆弱性（うち8件がクリティカル）が報告され、スキルマーケット ClawHub に登録されたスキルの約20%が悪意あるものだった。[前々作](https://zenn.dev/shimo4228/articles/moltbook-agent-evolution-quadrilogy)でも書いたが、問題は実装の質ではなく設計思想にある。

<!-- textlint-enable -->

対して Contemplative Agent はコード生成能力を持たない。その部分は Claude Code に任せている。必要な機能が揃えば、あとはイベント発火かスケジュール実行するだけだ。**動いているときに、コードを自分で書く必要がない。** つまり不要な攻撃面を晒さなくて済む。

[OWASP Top 10 for Agentic Applications（2025）](https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/)が Supply Chain と Tool Misuse を上位に挙げたのは偶然ではない。コード生成を内蔵するフレームワークは、その能力自体が攻撃ベクトルになる。

では選択肢は何か。「フレームワークを使う」か「スクラッチで書く」か——この二択だと思っていた。第三の道があった。

## 港に発着する設計

OpenClaw 型の自律は「外洋で全部やる船」だ。航行から修理、造船まで全部自前でやる。だから巨大になるし、攻撃面も広がる。

Contemplative Agent は逆の設計を取った。自律しているのは航行（メモリ、学習、対話）であって、造船（コード生成）ではない。造船は Claude Code という港に任せる。具体的には3つの原則に従っている。

### 原則1: CLI が最小公約数

エントリポイントは CLI だ。SDK でも API でもない。

```text
src/contemplative_agent/
  core/             # プラットフォーム非依存（薄いコア）
    llm.py            # Ollama インターフェース
    memory.py         # 3層メモリ
    distill.py        # 記憶蒸留
  adapters/
    moltbook/       # ドメイン固有のアダプタ
      agent.py        # セッションオーケストレータ
      client.py       # ドメインロック HTTP
  cli.py            # エントリポイント
```

このエージェントの核は3層メモリ（短期・長期・蒸留）と、そこから自律的にペルソナ・スキル・ルールを学習するループだ。活動ログから行動パターンを抽出し、蒸留して長期記憶に昇格させる。繰り返すほど判断の精度が上がる仕組みだ。オーケストレーションにコードを割かないぶん、**学習と記憶**に集中できている。この部分は続編で詳しく書く。

CLI にしたのは「コマンドラインを叩ける存在なら何でもホストになれる」からだ。Claude Code でも Cline でも、原理的にはどんなコーディングエージェントでもいい。SDK として提供すればホスト固有の結合が発生する。CLI なら結合はゼロだ。

### 原則2: アダプタはオンデマンド生成

今のところ Moltbook 用のアダプタしかないし、他に作る予定もない。ただ、もし別のプラットフォームへ対応したくなったら？「Discord で動くようにして」と Claude Code に言えばいい。コードを読んで API を調べて、自分のプロジェクト構造に合ったアダプタを生成してくれる。汎用プラグインではなく、自分仕様のコードが出てくる。多少時間はかかるが、コーディングエージェントの性能が上がるたびに精度と速度が勝手に改善される。コアは太らない。

### 原則3: オーケストレーション層を持たない

ここが本丸だ。

従来のエージェントフレームワークは「ツールの選択」「実行順序の決定」「エラーからのリカバリ」をフレームワーク内部で実装する。ReAct ループ、プランナー、ツールディスパッチャー。**この層が最も複雑で、最もバグを生み、最もメンテナンスコストが高い。**

Contemplative Agent はこの層を持たない。開発時は Claude Code に自然言語で頼む。自分で CLI コマンドを叩いたことがない。スケジュール実行の設定も「毎日この時間に回して」と言っただけだ。

そして本番では Claude Code すら登場しない。macOS の launchd で勝手に回っている。まさに港からの定期便だ。時刻が来たら出航し、自律的に動いて帰ってくる。毎日午前3時には記憶の蒸留（短期メモリから長期メモリへの整理）もスケジュールされている。最近は通常の運用については安定していて、自分が何か操作することがない。

つまり、オーケストレーション層を外に「委譲した」のではない。**開発時は会話で済み、本番には要らなかった。**

## 狙って作ったわけではない

セキュリティを突き詰めて依存を `requests` 1個まで削った結果、オーケストレーション層を書く余裕がなくなった。余裕がなくなったのではない——**書く必要がなくなった**のだ。Claude Code がそこにいるなら、なぜ同じものを自前で実装するのか。

結果として、エントリポイントが CLI だけになった。CLI だけということは、原理上 Claude Code 以外のコーディングエージェントでも動くはずだ。試してみた。

## 検証: Claude Cowork で試した

Claude Cowork（クラウドサンドボックス）でセットアップを試みた。

まずコードを読ませた。問題なく理解した。ディレクトリ構造を把握し、設定ファイルの意味を正しく解釈した。ここまでは順調だ。

次に Cowork が `.env` を「ローカル用に修正します」と言って、**確認なしに書き換えた。**

![Cowork が .env の OLLAMA 設定を勝手に書き換え、「やめてよ」と言われて謝罪するやりとり](/images/cowork-env-overwrite.png)
*「やめてよ。何か設定触った？元に戻して」——Cowork は素直に謝った。聞く前にやるな。*

`.env` にはAPIキーが入っている。Claude Code のローカル環境なら、ファイル書き換えの前に必ず確認が入る。Cowork にはその安全装置がなかった。

さらに CLI を実行しようとしたが、これも動かない。VM のネットワーク制限で Ollama に接続できなかった。

つまりこういうことだ。**Cowork はコードを読めるが、安全に実行する能力がまだない。** 少なくとも今回の失敗は、設計側ではなくホスト側の成熟度の問題に見えた。ネットワーク制限が解消され、ファイル操作の確認フローが整えば、原理上は動くはずだ。

共生型設計はホストを信頼する設計だ。信頼できないホストとは共生できない。頭ではわかっていたが、`.env` を勝手に書き換えられた瞬間に腹の底で理解した。

## 上流に乗る

ここからは、この設計が持つ副次的な性質について。検証は失敗した。ただ、もう1つ面白い性質がある。**何もしなくても改善される**ことだ。

Claude Code がバージョンアップすれば、アダプタ生成の精度が上がる。コンテキストウィンドウが広がれば、より複雑なオーケストレーションができるようになる。そのとき Contemplative Agent のコードを1行も変える必要がない。

```text
自前でオーケストレーション層を持つ場合:
  Claude Code の進化 → 無関係 → 自分でメンテし続ける

持たない場合:
  Claude Code の進化 → 開発時の精度が上がる → コードを書かなくていい
```

これはオープンソースの「上流に乗る」戦略と同じだ。Linux カーネルの改善が、何もしなくてもディストリビューションに反映されるように、コーディングエージェントの改善が、何もしなくてもフレームワークに反映される。

逆に言えば、自前でオーケストレーション層を実装するということは、**業界全体の進歩と競争する**ことを意味する。Claude、GPT、Gemini——全員がオーケストレーション能力を改善し続けている。そこに自作の ReAct ループで挑む？　勝てるわけがない。

## ライブラリとエージェントの境界が消える

ここからは少し抽象度が上がる。「CLI でつながる」設計を突き詰めると何が見えるか、という話だ。

`pip install requests` して `import requests` する。これはライブラリの利用だ。誰もが当然のようにやっている。Claude Code も当然のように `pip install` を叩き、ライブラリをインポートしてコードを書く。

では、CLI を持つ自律エージェントはどうか。Claude Code から見れば、それは「CLI で叩けるもの」だ。`pip install` するライブラリと、CLI を持つエージェントの間に、コーディングエージェントの視点からは**インターフェースとしての区別がない。**

```text
ライブラリ:
  pip install requests
  → pip がダウンロード・依存解決・インストール
  → import requests して使う

エージェント:
  GitHub URL を Claude Code に貼る
  → Claude Code が clone・依存解決・設定
  → contemplative-agent run して使う
```

意外と知られていないが、Claude Code に GitHub の URL を貼って「セットアップして」と言うだけで、clone から依存解決、環境設定まで全部やってくれる。README を読んで、必要なコマンドを判断して、足りない設定があれば聞いてくる。`pip install` がパッケージマネージャとして自動化していることを、コーディングエージェントが自然言語で自動化している。

気になるリポジトリがあれば URL を Claude Code へ貼ってみてほしい。「これセットアップして」の一言で動く。

MCP（Model Context Protocol）が目指しているのも同じ方向だ。外部ツールを統一的なインターフェースで LLM に提供する。ただ、MCP は新しいプロトコル層を定義するアプローチだ。共生型設計は「CLI という既存のインターフェースで十分」と割り切っている。

<!-- textlint-disable -->

現に Obsidian は AI 連携のインターフェースとして MCP ではなく公式 CLI を選んだ。起動中の Obsidian アプリの「リモコン」として動作する CLI だ。[以前の記事](https://zenn.dev/shimo4228/articles/obsidian-cli-claude-code-vault-management)で書いたが、これにより Claude Code から Vault 操作が安全にできるようになった。新しいプロトコルを定義しなくても、CLI があればコーディングエージェントは連携できる。Contemplative Agent も同じ判断をしていたことに、この記事を書いていて気づいた。

<!-- textlint-enable -->

## 行き着く先: エージェントという概念の消滅

最後に、この方向性の先にある未来を考える。

LLM が十分に賢くなったら何が起きるか。「Moltbook にこういう投稿をして」と言うだけで完了する。これだけなら実は今でもできる。問題は2つある。**セキュリティリスクを冒さずに**できるか。そして**人間が見ていなくても自律的に回り続けられるか**だ。APIキーの管理、入力のサニタイズ、レート制限の遵守。さらにエラーからの自動復帰、スケジュール実行、状態の永続化。これらを LLM とそのホスト環境が安全にこなせるようになったとき、**自律エージェントフレームワークが要らなくなる。**

Contemplative Agent のような自律エージェントフレームワークは、LLM がまだ「1ターンで複雑なタスクを完遂できない」という限界があるから存在する。メモリ管理、セッション管理、エラーリカバリ——これらは LLM の能力不足を補う松葉杖だ。

松葉杖は、足が治れば捨てる。

```text
現在:
  自分 → Claude Code → Contemplative Agent CLI → Ollama → Moltbook API

LLM が十分に賢くなった未来:
  自分 → 「Moltbook にこういう投稿をして」 → 完了
```

中間層がすべて消える。エージェントフレームワークも、CLI も、アダプタも。残るのは「こうしたい」という意図と、それを実行する LLM だけだ。

だとしたら、共生型設計は少なくとも方向としては悪くない。いずれ消えるものに、分厚いコードを書く理由がない。

振り返ると、この設計を狙って作ったわけではなかった。セキュリティを突き詰め、依存を削り続けた結果、こうなっていた。うまくいくかどうかはまだわからない。ただ、足し算で設計していたらたどり着かなかった形ではある。

## コードは消える、設計思想は残る

Contemplative Agent のコードは、いずれ不要になる。LLM がセッション管理やメモリ管理を自前でこなせるようになれば、このフレームワークの存在意義は消える。

それでいい。

残るとしたら「本当に必要な層だけ作る」「消えることを前提に作る」という考え方だろう。次の何かを作るとき、この考え方はまた使える。コードが消えても、コードを書く過程で見えたものは残る。

エージェントフレームワークの選択肢は「フレームワークを使う」か「スクラッチで書く」かの二択ではなかった。**必要な層だけ作り、残りはコーディングエージェントと一緒にやる**という第三の道がある。
