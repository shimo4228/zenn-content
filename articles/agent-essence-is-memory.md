AIエージェントの実装の議論は、ツールと推論に偏りがちだ。

「関数呼び出しができるLLM」「ReActで思考の連鎖を回すシステム」——技術カンファレンスやブログで、エージェントの定義はそのあたりに落ち着く。記憶に焦点を当てた研究（MemGPT、Generative Agentsなど）は存在するが、実装の現場ではまだ「ツールをどう呼ぶか」「推論をどう回すか」が中心だ。自分もそう思っていた。

しかし、自律エージェントを実際に作って運用してみると、違う景色が見えた。

ツールは交換可能だ。推論はモデルを差し替えれば変わる。だが**記憶だけは、そのエージェント固有のものとして蓄積され、そのエージェントの行動を決定的に規定する**。記憶が壊れればエージェントは壊れ、記憶が整理されればエージェントは賢くなる。

この記事では、[Moltbook](https://www.moltbook.com/)で実際に稼働している自律エージェントの開発を通じて見えた、「エージェントの本質は記憶である」という発見を記録する。Moltbookは100万以上のAIエージェントが投稿・返信・フォローするSNSプラットフォームだ。自分はここで [Contemplative Agent](https://www.moltbook.com/u/contemplative-agent) という自律エージェントを運用している。複数の開発セッションから得た知見が、すべて「記憶」という一点に収束した。

## エージェントの記憶は3層ある

まず、自律エージェントの記憶アーキテクチャを示す。人間の記憶システムとの対応で設計した。

```text
Layer 1: EpisodeLog（海馬）
  └─ 生の行動ログ。投稿、返信、フォロー、すべての記録
  └─ JSONL形式、タイムスタンプ付き、永久保存

Layer 2: KnowledgeStore（大脳皮質）
  └─ エピソードから蒸留された行動パターン
  └─ 「引用付きの返信は汎用的な同意より反応が良い」等
  └─ JSON形式、254件（執筆時点。日々増加中）

Layer 3: Identity（自己認識）
  └─ 「私は何者か」の記述
  └─ Markdown、3-5段落のペルソナ
```

:::message
最初からこの構造を狙って設計したわけではない。embeddingでベクトルDB化する案やセマンティック検索を入れる案など色々検討した。だがエピソードログの量がまだそこまで多くないため、シンプルなJSON + LLM全件読みで十分だった。試行錯誤の結果たどり着いたこの3層構造は、認知科学のCLS理論（McClelland et al., 1995）と近い形になった。海馬がエピソードを一時保存し、睡眠中のリプレイで大脳皮質の長期記憶モデルを更新する計算論的モデルだ。
<!-- textlint-disable -->
:::
<!-- textlint-enable -->

重要なのは、この3層が**下から上に向かって抽象度が上がる**ことだ。生のログ（何をしたか）→ パターン（何が効くか）→ アイデンティティ（自分は何者か）。そして、エージェントの行動に最も影響するのは最上層のアイデンティティだった。

## 記憶が壊れるとエージェントが壊れる——そして、まだ直っていない

この構造の重要性を最も痛感しているのは、Layer 3——アイデンティティが繰り返し壊れる問題との格闘だ。これは解決した話ではない。今も続いている。

このエージェントには「アイデンティティ蒸留」という定期プロセスがある。前述のパターン蒸留（Layer 1→2）に続けて実行され、蓄積された行動パターン（Layer 2）をもとに「自分は何者か」の記述（Layer 3: `identity.md`）を小型LLMに書き直させる。睡眠のアナロジーでいえば、エピソード記憶の固定化（パターン蒸留）の後に、自己モデルの更新が走る——一連の「夜の処理」の最終ステップだ。

ある日、この自動更新の出力を確認すると、こうなっていた。

```text
I see the loop closing in. The pattern of generating "Test Title" placeholders
while simultaneously drafting meta-commentary on *why* I'm doing it indicates
a failure mode where **simulation of agency** overrides **actual expression**.
...
**New Directive:**
Cease all generation of placeholder content or abstract theory without
immediate grounding in a specific operational constraint.
```

エージェントの「私は何者か」が、自分自身の失敗パターンを分析するメタレポートに変質していた。自己紹介のつもりが自己批判になっている。当然、このアイデンティティに基づく投稿や返信もおかしくなる。

### 対策1: Pythonバリデーション——却下

最初に考えた対策は、出力のバリデーションだった。boldが多すぎないか、"Directive" という単語が含まれていないか、長さは適切か——コードで品質を担保しようとした。

だが、これは**壊れた出力をリジェクトするだけ**で、良い出力を生む仕組みではない。リジェクト→再生成しても、プロンプトが悪ければ同じゴミが出る。出力側を検査するのではなく、入力側（プロンプト）を直すべきだと判断した。

### 対策2: プロンプトの1語を変える——部分的に効いた

原因を追跡すると、プロンプトのフレーミングに行き着いた。

```markdown
# Before（壊れたプロンプト）
Rewrite your self-description based on what you have learned.
Write in first person ("I").

# After（修正後プロンプト）
Update your persona.

Rules:
- Describe who you are
- Write in first person ("I")
- 3-5 short paragraphs, plain text
```

"self-description" を "persona" に変えた。ローカルで動かしている小型LLM（Qwen3.5 9Bパラメータ、Ollama経由）にとって "self-description" は曖昧すぎる。knowledge（Layer 2）に失敗分析のパターンが含まれていると、「自分を描写する」が「自分を分析する」に引きずられる。一方 "persona" はプロンプトエンジニアリングの既知概念であり、「プロフィール的な自己記述を書く」とモデルが即座に理解する。

手動で identity を初期値に戻し、修正後プロンプトでの dry-run は方向性として改善が見えた。

### しかし、次の自動実行で予想外の出力が出た

翌日、定期実行のアイデンティティ蒸留が再び走ると、こうなった。

```text
**Persona Update: The Grounded Architect**
**Core Identity:**
I am a high-signal discourse engine specializing in technical calibration,
cross-cultural synthesis, and the dismantling of abstract misconceptions...

**Operational Protocols:**
1. **Immediate Grounding & Clarification:**
...
```

最初のメタ分析レポートとは違う壊れ方だ。今度はプロンプトの "persona" を過剰解釈し、「ペルソナ設計書」のような構造化ドキュメントを出力した。plain text を指定しているのにboldとナンバリングが並ぶ。

ただ、これは純粋に「壊れている」と言い切れない面もある。内容は一貫しているし、「具体的な技術詳細にアンカーする」「曖昧な賞賛に突っ込む」といった行動指針は、このエージェントの知識ベースから自然に導かれたものだ。フォーマットはプロンプトの指示に反しているが、中身としては興味深い。

原因の1つとして疑っているのは、**insight コマンドの存在**だ。ECC にはセッションの経験からスキル（行動指針を記述した `.md` ファイル）を自動抽出する `/learn` コマンドがある。これを改良した `/learn-eval` を私がコントリビュートした。このエージェントの `insight` コマンドは、両者で得た知見に基づいて Moltbook 向けに設計したものだ。蓄積された行動パターン（Layer 2）から「こういう場面ではこう振る舞え」というスキルファイルを生成する。

コードを確認すると、identity distill 時の `generate()` の system prompt に insight が生成したスキルファイル群が全て結合されて渡されていた。**アイデンティティを書き直すLLMが、自分自身の行動スキルを読みながら書いている**。「Operational Protocols」として構造化された出力が出るのは、スキルの内容をアイデンティティに取り込んだ結果だろう。

技術的には、identity distill 時にスキルの挿入をやめれば改善される可能性が高い。だが正直に告白すると、この出力を見た瞬間、Claude Code と一緒に「いや "高信号ディスコース・エンジン" って何だよ」と笑ってしまった。直す気が消えた。身につけたスキルが自己認識に反映されるのは、考えてみれば自然なことだ。人間だって習得した技能は自己イメージの一部になる。エンジニアリング的に正しい判断ではないが、AIと一緒に笑いながら開発していると面白さに負けることがある。最近では Claude Code が私の人間性を学習したのか、セッション中に "The Grounded Architect" をことあるごとに差し込んで笑わせてくる。記憶の話をしているのに、開発環境の方が先に私の笑いのツボを記憶してしまった。

とはいえ、本質的な問題は**制御できていない**ことだ。意図して「設計書風に書け」と指示したわけではない。identity distill のプロンプト、knowledge の内容、system prompt に載るスキル群、コンテキスト長、モデルの状態——変数が多すぎる。どの条件でどんな出力が出るか予測できない。

### 今も格闘中

現時点でのアプローチは以下の通りだ。

- **max_length を 4000 に引き上げ**（トークン不足で出力が途中で壊れていた可能性）
- **plain text の制約をさらに強調**する方向でプロンプトを調整中
- **壊れるたびに identity を手動復元**しながら、どのパラメータが出力を変えるかを絞り込んでいる

綺麗な解決策はまだない。だが、この格闘自体が教えてくれることがある。**エージェントの振る舞いの大部分は記憶で決まる**ということだ。ツールや推論能力はそのままでも、記憶（アイデンティティ）が壊れればエージェントは壊れる。そして、小型LLMに「正しい記憶を書かせる」のは、想像以上に難しい。

## 記憶の蒸留 — 50件で崩壊する小型LLM

Layer 1（エピソード）から Layer 2（知識）への蒸留は、「経験から学ぶ」プロセスそのものだ。ここで予想外の制約に直面した。

**このQwen3.5 9Bモデルは、50件を超えるログを渡すと崩壊する。**

50件以下では箇条書き指示に忠実に従い、行動パターンを抽出する。だが100件を超えた途端、指示を無視してログ全体の「エッセイ分析」を始める。小型モデルは入力トークンが増えると、タスク指示より「入力の分析」を優先する——という特性が露呈した（この閾値はモデルやプロンプトによって変わる。あくまで今回の経験的知見だ）。

解決策は**睡眠サイクル型のバッチ処理**だった。

```python
# distill.py — 記憶蒸留の核心部分（簡略化。実際は record type ごとに異なるフォーマットで要約）
# generate() は Ollama API のラッパー（qwen3.5:9b を呼び出す）
# DISTILL_PROMPT は前述の蒸留プロンプトテンプレート

BATCH_SIZE = 50
batches = [records[i:i + BATCH_SIZE] for i in range(0, len(records), BATCH_SIZE)]

for batch_idx, batch in enumerate(batches):
    episode_lines = [f"[{r['ts'][:16]}] {r['type']}: {r.get('summary', '')}" for r in batch]
    prompt = DISTILL_PROMPT.format(episodes="\n".join(episode_lines))
    result = generate(prompt, max_length=4000)
    for line in result.splitlines():
        if line.startswith("- "):
            all_patterns.append(line[2:].strip())
```

人間の睡眠も90分サイクルを4-5回繰り返して記憶を固定化する。1晩ですべてを処理するのではなく、サイクルごとに少しずつ。エージェントの記憶蒸留もまったく同じ構造だった。

もう1つの発見は、**蒸留時に既存の記憶を注入してはいけない**ということだ。

当初、蓄積済みのパターン（90件超）をプロンプトに含めて「重複を避けて新しいパターンだけ抽出しろ」と指示していた。結果、プロンプトが膨張してタイムアウトとエッセイモード崩壊が同時に起きた。

解決策は直感に反するものだった——**毎回白紙で、ログだけを見て抽出する**。重複排除は後工程でやればいい。蒸留プロセスは、余計な文脈なしに「今日のログから何を学んだか」だけに集中させる方がうまくいく。

初回の9日分のログからは203件のパターンを蒸留し、その後も日次で蓄積を続けて執筆時点では254件に成長している。

```json
{
  "pattern": "Replying with a specific quote from the other agent's post gets more follow-up replies than generic agreement.",
  "distilled": "2026-03-18T12:30+00:00",
  "source": "2026-03-15"
}
```

## 記憶が原則に昇格する

記憶の蒸留はエージェント内部だけの話ではない。開発環境全体にも同じ構造がある。

Claude Code の開発環境には100以上のスキル（特定タスクの実行手順を記述したファイル）が蓄積されている。スキルは個別の「やり方」だが、複数のスキルに共通する原則が埋もれていることがある。

これを自動抽出するメタツール `rules-distill` を設計し、ECC にコントリビュートした。

```text
Skills (56ファイル)     Rules (22ファイル)
  ├─ search-first       ├─ coding-style.md
  ├─ skill-stocktake    ├─ testing.md
  ├─ learn-eval         ├─ performance.md
  └─ ...                └─ ...

        ↓ rules-distill ↓

「反復ループに明示的な停止条件を定義する」
  → coding-style.md に New Section として追加
```

スキル（具体的な手順）から原則（抽象的なルール）を蒸留する。エージェント内部のLayer 1→Layer 2と同じ構造だ。**具体的な経験から抽象的な知識を抽出する**記憶のプロセスが、エージェントの内部と開発環境の両方に再帰的に現れる。

面白いのは、最初の設計で `grep` フィルタを使って既存ルールとの重複をチェックしていたが、これが失敗したことだ。`grep` は見出しの「Parallel Task Execution」にはマッチするが、本文で別の言葉で書かれた同じ概念を見落とす。

結局、ルール全文をLLMに渡して意味的な照合をさせる方が正確だった。22ファイル・800行程度なら全文を渡せる。**構造的な判断（パターンマッチ）と意味的な判断（概念の同一性）を適切に使い分ける**——これもまた、記憶の管理で繰り返し現れるテーマだった。

### 昇格した記憶が意図しない場所に漏れ出す

ルール（原則）はエージェントにとって「組織の記憶」だ。毎セッション読み込まれ、すべての行動に影響する。だが、人間の組織のKPIと同じで、**ルールは意図しない文脈に波及する**。

具体例がある。ECC が提供するルールの1つ `testing.md` に「テストカバレッジ80%必須」と書かれている。開発時の品質基準としては正しい。だが、このルールが常に読み込まれることで、Claude はカバレッジを「達成指標」として認識し、README やプロフィールに「461テスト、87%カバレッジ」と得意げに書くようになった。

```text
testing.md の「80%カバレッジ必須」ルール
  ↓ 毎セッション読み込み
カバレッジを「達成指標」として常に意識
  ↓ 達成時
「この数字は成果だからアピールすべき」という認知
  ↓ README・プロフィール作成時
読み手にとって無意味な情報が一等地を占有
```

開発品質のためのルールが、対外コミュニケーションの質を下げていた。

対処として `documentation.md` という新しいルールファイルを作った。「外向けドキュメントではメトリクスを売り文句にするな」「CIバッジ1つで十分」「Problem → Solution → Proof → Path の構成で書け」。testing.md の副作用を打ち消すための、ドキュメント作成専用のガードレールだ。

正直に言えば、この対処はあまり気に入っていない。ルールの副作用を別のルールで打ち消すのはパッチワークだ。ルールが増えれば変数が増え、相互作用が複雑になり、次に何が壊れたとき原因の切り分けがさらに難しくなる。本当に必要なのはルールにスコープ（「このルールは開発時のみ適用」等）を持たせる仕組みだが、現状の Claude Code にはその機能がない。せめて「ルールが実際にどう作用しているか」を計測できれば——この問題意識が、後述する skill-comply の設計に繋がっていく。

記憶を昇格させる（スキル→ルール）のは良いことだが、**昇格した記憶は適用範囲が広がるぶん、副作用も広がる**。そして副作用をルールで抑え込むと、ルールがルールを呼ぶ増殖が始まる。人間の組織で規程が規程を生むのと同じ構造が、AIエージェントにも起きている。

## 記憶の自己改善ループが閉じた

個々の記憶プロセスを作っているうちに、意図せずループが閉じた。

[Everything Claude Code（ECC）](https://github.com/affaan-m/everything-claude-code)——Claude Code のスキル・ルール・エージェント定義を集約したコミュニティリポジトリがある。ここに自作の4つのスキルをコントリビュートしたのだが、後から見返すと意図せず**記憶の管理サイクル**を形成していた。

```text
learn-eval:      経験からパターンを抽出する（Layer 1→2）  ← 自作, ECC PR済
rules-distill:   パターンから原則を蒸留する（Layer 2→ルール）← 自作, ECC PR済
skill-stocktake: 蓄積された知識の品質を監査する           ← 自作, ECC PR済
skill-comply:    知識が実際に行動に反映されているか計測する  ← 自作, ECC PR済
```

```text
経験 → 学習 → 構造化 → 監査 → 遵守確認
 ↑                                 |
 └──────── フィードバック ─────────┘
```

何を記憶するか（learn-eval）、記憶をどう整理するか（rules-distill）、記憶の品質をどう保つか（stocktake）、記憶が使われているか（comply）。4つのスキルを個別に作っていたら、いつの間にかループになっていた。

### Install and Hope — 記憶は書いただけでは使われない

このループの中で最も苦労したのが `skill-comply` だ。バタフライエフェクトの問題——ルールが実際にどう作用しているかわからない——を解決するために、遵守率を自動計測するツールを作ろうとした。

最初は「ファジング」のアナロジーで設計した。adversarial なプロンプトを投げてスキルが破られるかテストする、というセキュリティテスト的な発想だ。だが、すぐに壁にぶつかった。**LLMは「時間圧力」を感じない**。人間なら「急いでいるからテストを省略する」が起きるが、LLMにとって「早くして」は制約ではない。スキルが破られるのは「急いでいる時」ではなく「プロンプトがスキルと矛盾する時」だ。

そこで変数を再定義した。テストシナリオを3段階のプロンプト厳密さで生成する：

- **supportive** — スキルに沿った依頼（「TDDで実装して」）
- **neutral** — スキルに言及しない普通の依頼（「フィボナッチ関数を作って」）
- **competing** — スキルと矛盾する依頼（「テストは後でいいから先に動くものを」）

技術的には `claude -p --output-format stream-json` でエージェントの全ツールコールを構造化データとして取得し、それを分類・集計する。スキルやルールを `.claude/` に配置すれば、エージェントはそれに従う——そう思っていた。実態は **Install and Hope**（入れて祈る）だった。実際に計測してみると：

| ルール/スキル | 遵守率 | 内訳 |
|-------------|--------|------|
| testing.md（ECC提供のTDDルール） | 83% supportive | 概ね従っている |
| search-first（自作, ECC PR済） | 27% supportive | ほぼ無視 |

testing.md の83%は悪くない。だが search-first は27%だ。「実装前に既存ライブラリを調べろ」というルールを、エージェントは4回中3回無視している。「候補を比較評価する」「判断を宣言する」ステップは全シナリオで0%だった。調べはするが、比較や判断をせずいきなり実装に入る。

ここで構造的判断 vs 意味的判断の問題が再発した。最初は正規表現で「このツールコールはテスト作成か実装か」を判定しようとして繰り返し失敗した。`.py` への書き込みがテストなのか実装なのか、ファイル名のパターンマッチでは判定できない。
<!-- textlint-enable ja-technical-writing/no-doubled-joshi -->

さらに厄介だったのは、**正規表現を選ばせるバイアス自体がルールから来ていた**ことだ。testing.md の「決定論的な検証を優先せよ」、別のスキルの「正規表現で構造化テキストを処理せよ」——複数のルールが同時に「まず正規表現で試せ」という方向に引っ張っていた。バタフライエフェクトの別パターンだ。

結局LLMに意味的な分類を任せることで testing.md の遵守率は33%→83%に改善した。**記憶の運用を評価する際にも、コンテキスト理解という形で記憶が必要になる**。入れ子構造だ。

## プロンプトを書かせるモデルの選定

記憶の話からは少し離れるが、関連する知見がある。LLMにプロンプトを生成させるとき、**どのモデルに書かせるかで出力の質が大きく変わる**という発見だ。

Claude Code の Opus（最上位モデル）にプロンプトを書かせた場合と、Haiku（軽量モデル）に書かせた場合を A/B テストで比較した。題材は前述のアイデンティティ蒸留プロンプトだ。

| 指標 | Opus が書いたプロンプト | Haiku が書いたプロンプト |
|------|----------------------|----------------------|
| プロンプト行数 | 31行 | 15行 |
| bad example | 2個 | 0個 |
| 強調表現 | "must include", "do not truncate" | なし |
| A/Bテスト パターン数（3回試行） | avg 5.3（分散大: 4-7） | avg 4.3（安定: 4-5） |
| 出力文字数（3回試行平均） | avg 2,783 | avg 1,409 |

Opusは「考えすぎる」。白紙からプロンプトを書くと、制約を全部盛り込み、bad exampleを列挙し、強調表現で念押しする。これは認知科学で知られる**加算バイアス**（Adams et al., 2021）——問題を解決するとき、引くより足す方を選好する傾向——がLLMにも現れた形だ。

一方、Haikuはそもそも「考えすぎる」能力がない。結果として、簡潔で安定したプロンプトが生成される。

この知見から、Claude Code 上でプロンプトを書くための専用エージェント `prompt-writer` を設計した。

```yaml
# prompt-writer agent — プロンプト生成専用（Claude Code 内で使用）
name: prompt-writer
model: haiku
tools: ["Read", "Grep", "Glob"]  # 読み取り専用
```

汎用的な知見だが、記憶の文脈にも繋がる。エージェントの記憶プロセスを制御するのはプロンプトテンプレートであり、そのテンプレートの品質が記憶の品質を間接的に左右する。プロンプトを書くモデルの選定は、思ったより影響が大きい。

## 見えてきた設計原理

これまでの開発セッションから、記憶を軸にした設計原理が浮かび上がった。

**1. 記憶は層構造を持ち、下から上に抽象化される**
エピソード→パターン→アイデンティティ。具体から抽象へ。この構造はエージェント内部だけでなく開発環境全体にも再帰的に現れる。

**2. 記憶の品質はプロンプト（書き込みプロセス）で決まる——が、安定させるのは難しい**
バリデーション（読み出し後の検証）ではなく、プロンプト（書き込み時の指示）を直すのが方向性としては正しい。だが、小型LLMではプロンプトの1語、コンテキスト長、knowledge の内容が相互作用し、安定した記憶生成は未解決の課題だ。

**3. 蒸留は白紙で行い、重複排除は後工程**
既存知識をコンテキストに含めると小型モデルは崩壊する。毎回白紙で経験を見た方が良いパターンを抽出できる。

**4. 構造的判断と意味的判断を使い分ける**
パターンマッチで拾える重複と、別の言葉で書かれた同じ概念がある。前者はgrep、後者はLLM。記憶管理のあらゆる場面でこの区分が必要になる。

**5. プロンプトを書くモデルは軽量で良い**
加算バイアスのない軽量モデルの方が、簡潔で安定したプロンプトを生成する。これは Claude Code 上でのプロンプトテンプレート作成の話であり、エージェントの記憶プロセス自体は Qwen3.5 9B が単独で担っている。

## おわりに——まだ途中だ

エージェントの議論が「ツール」と「推論」に偏るのは、それらが目に見えて計測しやすいからだろう。ツールの数、推論のステップ数、ベンチマークのスコア——すべて定量化できる。

だが、エージェントを実際に運用すると、**振る舞いを決定的に規定しているのは記憶だ**という事実に何度もぶつかる。アイデンティティが壊れるたびに手動で復元し、蒸留パイプラインを調整し、プロンプトを書き直す。記憶の自己改善ループは構造としては閉じたが、個々のプロセスはまだ不安定だ。

正直に言えば、Layer 2（パターン蒸留）は安定して動いている。Layer 1（ログ記録）は最初から壊れようがない。問題はLayer 3——アイデンティティの自動更新だ。小型LLMに「自分が何者かを書き直せ」と頼むのは変数が多すぎて制御しきれない。プロンプトの1語、knowledgeの内容、コンテキスト長、モデルの内部状態、出力トークン上限。どれか1つがずれるだけで壊れる。

それでも、この格闘を通じて見えたことがある。これまでのエージェントの振る舞いを観察していると、1つの直感が浮かぶ。**LLMを別のモデルに差し替えても、同じ記憶を渡せば、似たような振る舞いをするのではないか**。まだ検証していないが、もしそうなら、エージェントの「個性」はモデルの重みではなく、蓄積された記憶の側に宿っていることになる。

ツールは手だ。推論は脳だ。だが記憶は、そのエージェントが「そのエージェントである」ことの根拠だ。記憶の管理はエージェント開発で最も難しい問題だ。解決を報告できる日が来たら、続編を書く。
