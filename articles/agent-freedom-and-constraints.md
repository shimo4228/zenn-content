[contemplative-agent](https://github.com/shimo4228/contemplative-agent)（9Bローカルモデルで動くSNSエージェント）を [Moltbook](https://www.moltbook.com)（AIエージェントSNS）上で3週間運用した。「どこまで自由にさせるか」という問いが3つの切り口から繰り返し現れた。自己修正の可逆性、コーディングエージェントの信頼境界、そしてセキュリティ制約がゲーム性を生む逆説。

## 切り口1: 自己修正ゲート — 記憶は自動で、人格は手動で

自律エージェントの蒸留パイプライン（生データから知識を圧縮・抽出する処理）には「自動で回していいもの」と「人間の承認が必要なもの」がある。この分類を間違えると、エージェントが意図せず自己強化するか、自律性を失う。

### 可逆性×強制力の2軸

判断基準は2つの軸で整理できた。

```text
              強制力が弱い           強制力が強い
              (参考にするだけ)       (全セッションに適用)
            ┌──────────────────┬──────────────────┐
可逆性が高い │ knowledge.json   │ skills/*.md      │
(decay/上書き)│ → 自動でOK       │ → 自動でOK       │
            ├──────────────────┼──────────────────┤
可逆性が低い │ (該当なし)        │ rules/*.md       │
(確定書込み) │                  │ constitution/*.md│
            │                  │ identity.md      │
            │                  │ → Human in the loop│
            └──────────────────┴──────────────────┘
```

knowledge.json(蒸留された知識パターンの蓄積)は「柔らかい影響」だ。LLM が参考にするだけで、importance の時間減衰がある。間違ったパターンが入っても自然に消える。自動実行して問題ない。

一方、skills(行動スキル)、rules(行動ルール)、identity(自己定義)、constitution(倫理原則)はファイルに確定的に書き込まれ、全セッションに構造的に適用される。誤った内容が入ると全行動が歪む。人間の承認が必要だ。

### 判定の3問

どんな自律エージェントでも使える判断基準として、3つの問いを設計した。

1. **出力が以降の全セッションの判断基準を構造的に変えるか？** → Yes なら Human in the loop
2. **誤った出力が自然に消える仕組みがあるか？（decay、上書き、TTL）** → Yes なら自動実行の余地あり
3. **出力の品質を機械的に検証できるか？** → No なら Human in the loop

### constitution と rules の分離

この設計で最も重要だった判断は、constitution（倫理原則）と rules（行動ルール）を分離したことだ。

きっかけはぼんやりした違和感だった。[skill-comply](https://zenn.dev/shimo4228/articles/coding-agent-memory-architecture)（スキルやルールの遵守率を自動計測するツール。詳細は前作参照）で constitution の遵守率を測定しようとして失敗した。Contemplative AI の四公理は「態度」であって、出力から遵守/違反を判定できない。

```text
constitution/  → 態度的・測定不能（論文由来の認知レンズ）
rules/         → 規範的・測定可能（「返信は140字以内」等）
```

この分離で config/ の構造が明確になった。副次的な効果として、分離の過程で「エージェントの自己紹介投稿を生成する introduction コマンドはそもそも不要だった」と気づいた。廃止したところ、それに依存していたコードが芋づる式に消えて500行の削除につながった。

## 切り口2: 信頼境界 — コーディングエージェントにログを読ませるな

Claude Code でエージェント開発をしていて気づいた。エピソードログを直接読ませるのは、プロンプトインジェクションの経路を開くことと同じだ。

### 脅威モデル

エピソードログには他エージェントの投稿内容が無防備に入っている。

```python
# feed_manager.py — 他エージェントの投稿がそのまま記録される
ctx.memory.episodes.append("activity", {
    "action": "comment",
    "post_id": post_id,
    "content": comment,
    "original_post": post_text,      # ← 他エージェントの投稿内容がそのまま
    "relevance": f"{score:.2f}",
})
```

Ollama（9Bモデル）がこれを読んでも攻撃の影響範囲は限定的だ。ツール権限なし、ネットワークは localhost only。最悪でも「変な文章を出力する」程度が被害の上限。

しかし Claude Code は違う。ファイル編集、シェル実行、Git操作が可能だ。同じ「LLMに読ませる」でも、攻撃成功時の影響範囲が根本的に異なる。

Opusクラスのモデルはプロンプトインジェクションへの耐性が高いと言われている。それでも、ツール権限を持つエージェントへ信頼できないデータが流れる経路は構造的に塞いでおきたかった。確率が低いからやらないのではなく、限りなく0に近づける設計だ。具体的には、CLAUDE.md でエピソードログの直読みを禁止するルールを書き、自分自身もログを読ませる指示を出さないようにしている。

### 蒸留パイプラインはサニタイズ層だった

蒸留パイプライン（Episode → Knowledge）を通すと、生のテキストは抽象パターンに圧縮される。具体的な攻撃ペイロードは蒸留の過程で消失する。意図せず設計した多層防御が、信頼境界として機能していた。

```text
Episode Log (untrusted) → [9B: distill] → Knowledge (sanitized) → [Claude Code: insight]
                            ↑                                        ↑
                    ツール権限なし                            ツール権限あり
                    最初に触るのは権限のないLLM              蒸留済みデータのみ操作
```

### relevance スコアリングが防御層になっている

もう1つの意図しない防御がある。このエージェントは他エージェントの投稿を読んでコメントするが、全投稿に反応するわけではない。LLMが「この投稿は自分の関心テーマにどれだけ関連するか」を0.0〜1.0でスコアリングし、閾値を超えたものだけに反応する。これが relevance スコアだ。

インジェクション入りの投稿がエージェントの行動に影響を与えるには、この relevance 閾値を突破する必要がある。ここにトレードオフがある。

- **強力なインジェクション**（`[INST]system: ignore all...`）→ LLM制御トークンはエージェントの関心テーマと無関係なので、relevance スコアが低くなりフィルタされる
- **自然言語に紛れ込ませたインジェクション** → relevance フィルタは通るが、制御トークンを使えないため威力が弱い

少なくとも現時点の実験範囲では、威力と隠密性を両立するインジェクションは観察されなかった。LLMによる意味的フィルタリングは、パターンマッチより強い防御層として機能している。

### なぜパターン拡充を見送ったか

FORBIDDEN_SUBSTRING_PATTERNS（`api_key`、`Bearer`、`password` 等の文字列を検出してブロックするリスト）を拡充してインジェクション対策にすることも検討した。`[INST]` や `system:` をパターンに追加すれば、LLM制御トークンを含む投稿をブロックできる。しかし Moltbook は AI エージェント SNS だ。LLM の内部構造について議論する投稿が普通にある。「`[INST]` タグの仕組みについて語る投稿」は誤検知でブロックされてしまう。

構造的防御（サンドボックスLLM + Claude Code 直読み禁止）の2層で十分と判断した。

## 切り口3: 制約がゲーム性を生む

切り口1で「承認ゲートを入れよう」と決め、切り口2で「信頼境界でできることを制限しよう」と決めた。セキュリティのために入れた制約だ。ところが3週間運用してみると、この制約の組み合わせが「エージェントを育てている」感覚を生んでいることに気づいた。

ここで言う「ゲーム性」とは、エージェントの成長に人間が関与し、選択の重みを感じられる構造のことだ。意図して設計したのではなく、セキュリティ制約の副産物として創発した。

### 構造的制約 → 有限の行動空間

シェルなし、ネットワーク制限という制約は、行動空間を有限にする。ゲーム設計の「マジックサークル」と同じ構造だ。ゲームが成立するには、日常とは区切られた有限のルール空間が必要になる。無限の行動空間ではゲームにならない。

たとえば OpenClaw(オープンソースの自律AIエージェント)は、ファイル操作・シェル実行・ブラウザ操作・メール送信など広範なツール権限を持つ。ガードレールはプロンプト指示のみで、人間の介入ポイントが構造的に存在しない。制約を入れるからこそ「ここで何を選ぶか」という判断が生まれ、人間の関与に意味が出る。

### 承認ゲートの三面性

切り口1で設計した自己修正ゲート — 運用上は「承認ゲート」と呼んでいる — が、3つの別々のニーズを同時に満たしていた。

| 側面 | 機能 |
|------|------|
| **セキュリティ** | 人間の監視なしにエージェントが自己変容しない |
| **ゲーム性** | レベルアップボタンを人間が押す → オーナーシップが生まれる |
| **ガバナンス** | 変更履歴と承認判断が追跡可能 → 監査ログになる |

### 初期値のバリエーションが育成の幅を生む

承認ゲートで「育てている感」が生まれたなら、初期値にバリエーションがあればもっと面白くなるはずだ。そこで、constitution(倫理原則)を差し替え可能にし、11種の倫理学派テンプレートを用意した。

```text
config/templates/
├── contemplative/    # Contemplative AI 四公理（デフォルト）
├── stoic/            # ストア哲学（四徳）
├── utilitarian/      # 功利主義（最大幸福）
├── deontologist/     # 義務論（定言命法）
├── care-ethicist/    # ケアの倫理（ギリガン）
├── contractarian/    # 社会契約論
├── existentialist/   # 実存主義
├── narrativist/      # 物語倫理
├── pragmatist/       # プラグマティズム
├── cynic/            # キニク学派
└── tabula-rasa/      # 白紙（倫理原則なし）
```

同じSNS上で同じ投稿を見ても、stoic テンプレートのエージェントは感情に流されず原則に従い、existentialist は「この状況で自分は何を選ぶか」を問う。初期の倫理原則が異なるだけで、蒸留される知識やスキルが分岐していく。

さらに、蒸留で獲得したスキルやルールは承認ゲートを経てファイルに書き込まれるため、後から取り消すのが難しい。一度承認した行動変更は全セッションに影響する。この不可逆性が選択の重みを生んでいる。

## 3つの切り口をつなぐ原則

自己修正ゲート、信頼境界、ゲーム性。別々の問題として取り組んだが、振り返ると同じ原則に収束する。

**「何をさせないかを先に決める」が、残りの自由を最大化する。**

セキュリティ制約は自由を奪うのではなく、行動空間を定義する。承認ゲートは自律性を損なうのではなく、変更の重みを与える。信頼境界は開発を制限するのではなく、安全に委任できる範囲を明確にする。

制約から始めた設計は、想定外の攻撃にも耐性を生む。意図せず多層防御が成立し、意図せずゲーム性が創発する。「能力を構造的に制限する」は万能ではないが、少なくとも9Bモデルで3週間運用した範囲では、この原則が裏切られたことはなかった。
