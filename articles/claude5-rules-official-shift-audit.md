> **この記事でわかること**: Claude 5 世代（Opus 5 / Fable 5）向けに Anthropic が公式に打ち出した「ルールは減らして判断に任せる」方針を踏まえ、旧世代向けに書き溜めた自作ルール（CLAUDE.md / rules）を本体の指示と照合し、「残す・直す・退役させる」を判定する手順です。

Claude Code を長く使っている人ほど、こういう不安があるはずです。

- 旧世代モデルの弱点を補うために書き溜めた CLAUDE.md や rules が、Claude 5 でも有効なのか分からない
- 公式が「ルールは減らせ」と言い始めたが、自分の**どの**ルールが削減対象なのか判別できない
- かといって一括で消して挙動が悪化するのも怖く、手を付けられない

私は 2026-07-25 に自分の `~/.claude` ハーネス（CLAUDE.md や rules などの自作設定一式）でこの棚卸しを実施し、常駐ルール（毎セッション自動でロードされる分）を 5,789 words から 2,463 words まで削減しました（計測の内訳は記事末尾）。この記事では、そのとき使った照合手順を再現可能な形で説明します。削減量そのものより、**「何を根拠に、どのルールを、どう処分するか」の判定手順**が持ち帰りどころです。

## 背景: 公式が「ルールの書き方」を変えた

2026-07-24（Opus 5 ローンチ当日）、Anthropic は [The new rules of context engineering for Claude 5 generation models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) を公開しました。要点は 2 つです。

第一に、Anthropic 自身が Claude Code の system prompt を 80% 以上削除しています。

> We removed over 80% of Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss on our coding evaluations.
> （Claude Opus 5 や Claude Fable 5 のようなモデル向けに、Claude Code の system prompt の 80% 以上を削除したが、我々のコーディング評価に計測可能な劣化はなかった）

第二に、context engineering の方針転換を 6 対の Then → Now で明示しています。

| Then（旧世代向け） | Now（Claude 5 世代向け） |
|---|---|
| ルールを与える | 判断に任せる |
| 例を与える | インターフェースを設計する |
| 全部を前置きに載せる | 段階的開示（progressive disclosure） |
| 繰り返して強調する | 簡潔なツール説明 |
| CLAUDE.md にメモリを書く | auto-memory |
| 簡素な仕様 | 豊富な参照資料 |

同記事は、指示が増えすぎた状態の実害として「競合する指示」を挙げています。system prompt・skills・ユーザー指示が衝突し、"leave documentation as appropriate"（適宜ドキュメントを残せ）と "DO NOT add comments"（コメントを書くな）が**同一リクエスト内に共存**する、という例です。

つまり削減の理由は「トークン節約」だけではありません。**自作ルールが本体の指示と衝突し、モデルに矛盾の解決を押し付けている**ことが問題です。ここから、どのルールが衝突しているかを見つける手順に入ります。

## 前提: 照合の正本は system prompt と tool description

自作ルールと同じ context にロードされてモデルへ届いているのは、**system prompt と tool description** です。これが照合の正本で、第一歩はこれを素直に読むことです。公式ドキュメントやブログは推奨を述べているだけで、推論時にモデルへは届いていません。

食い違いの意味もこの違いで変わるため、名前を分けておきます。

| 層 | 中身 | 推論時にロードされるか | 食い違いの名前 |
|---|---|---|---|
| **runtime 層** | system prompt + tool description | **される**（自作ルールと同時に context に載る） | **競合**（モデルが矛盾解決を迫られる） |
| **guidance 層** | 公式ドキュメント・公式ブログ | されない | **ドリフト**（公式推奨から離れているだけ） |

競合と呼べるのは両方が同じ context に載っているときです（tool description は、そのツールが使えるセッションでのみロードされます）。

:::message
以降の実例はすべて私の `~/.claude` ハーネス（Claude Code 2.1.220、2026-07-25〜26 に照合実施）のものです。
:::

## Step 1: 今の runtime 層を実セッションから採る

最初の作業は「自作ルールが何と同居しているか」を正確に知ることです。ここに罠があります。**runtime 層は自分の設定リポジトリの外からも注入されるため、`~/.claude` 配下をいくら読んでも全体は分かりません。**

実例を挙げます。私のセッションの system prompt には次の一文が常駐していました。

> "Do not call the AgentTool unless the user requested it"

ところが `~/.claude` 配下を grep しても、この文字列はどのファイルにも存在しません（注入元は未特定です。ハーネス本体か plugin 由来と推測していますが、確認できていません）。設定ファイルだけを照合対象にすると、この種の指示を見落とします。

したがって採取は実セッションから行います。方法は 2 つです。

**tool description は実物を取得します。** Claude Code に対して、対象ツールの description を出力させます。

```text
EnterPlanMode ツールの description を逐語で引用してください。要約しないでください。
```

**system prompt はセッション内で引用させます。** こちらは自己申告なので、「逐語で」と明示して要約を防ぎます。

```text
いまロードされている system prompt から、
plan mode / コミットメッセージ / スコープの扱いに関する指示を逐語で引用してください。
```

照合したいテーマごとに聞くのがコツです。「全部出して」は長すぎて要約が混ざります。テーマの一覧は**自作ルール側から**作ります。先に自作ルール（rules / CLAUDE.md）の全ファイルを開き、各指示をテーマ（計画・コミット・レビュー・スコープ…）に割り当ててから、テーマごとに runtime 層へ問い合わせる。こうすれば少なくとも自作ルール側の照合漏れはなくなります。

2 つ注意があります。第一に、逆方向の漏れ（存在を知らない runtime 指示）はこの手順では拾いきれないので、検出ゼロは「競合なし」ではなく「この質問では見つからなかった」と読みます。第二に、**この採取はどちらもモデル経由の自己申告で、実際の入力と完全に一致する保証はありません**。採取結果はスクリーニングとして使い、ルールの処分（退役・反転）を決める前には、別セッションでも同じ文言が再現するかを確認してから動くのが安全です。

## Step 2: 自作ルールと突合して 3 分類する

採取した runtime 層と自作ルールを突き合わせ、食い違いを 3 つに分類します。

| 分類 | 意味 | 私のハーネスでの検出数 |
|---|---|---|
| **競合** | runtime 層と食い違う指示・情報が同時にロードされている | 2 件 |
| **冗長** | runtime 層にほぼ同じ指示が既にある | 1 件 |
| **ドリフト** | guidance 層（公式 doc）の推奨から離れている | 3 件 |

### 競合の実例 1: plan mode 禁止ルール

私の `planning.md` には旧世代の「すぐ実装に走らない癖」への対策として、こう書いてありました。

> 直接的な実装指示には即座に実行する。plan mode に入らない

一方、同時にロードされていた `EnterPlanMode` の tool description（Claude Code 2.1.220）はこうです。

> "Prefer using EnterPlanMode for implementation tasks unless they're simple."
> "If unsure whether to use it, err on the side of planning"
> （実装タスクには、単純なものを除き EnterPlanMode を優先せよ。迷ったら計画側に倒せ）

方向が真逆の指示が同じ context に同時にロードされ、モデルはそのたびにどちらかを黙って選んでいたことになります。

### 競合の実例 2: 幽霊設定を参照するルール

もう 1 件はもっと質が悪いパターンでした。前提として、Claude Code は既定でコミットメッセージ末尾に `Co-Authored-By: Claude ...` という行（trailer）を付けます。GitHub 上でコミットの共作者として Claude が表示される、あの帰属表示です。この帰属表示を出すかどうかをめぐって、私の `git-workflow.md` にはこうありました。

> Note: Attribution disabled globally via ~/.claude/settings.json.
> （帰属表示は settings.json でグローバルに無効化済み）

ところが実際の `settings.json` を確認すると、該当する設定キー（`includeCoAuthoredBy`）は**存在しません**でした。

```bash
python3 -c "import json; print('\n'.join(sorted(json.load(open('settings.json')).keys())))"
# includeCoAuthoredBy は出力されない
```

設定をいつか消したのか、最初から書き間違えていたのかはもう分かりません。確実に言えるのは、**ルールは自分の根拠が消えたことを検知できない**ということです。コードなら参照先が消えればエラーになりますが、ルールは「無効化済み」と主張し続けたまま、runtime 層の「コミットメッセージに Co-Authored-By trailer を付けよ」という指示と食い違ったまま常駐し続けました。

なお厳密に言えば、このルールの一文は「trailer を付けるな」という指示ではなく、「無効化済み」という（誤った）事実記述です。ただし runtime 層の指示と食い違う情報として同じ context に載り続ける点で、私は競合側に数えました。

:::details 放置した競合はどう解決されていたか（モデル依存の観測、限界付き）
この幽霊設定の競合を放置していた期間のセッションログを調べると、興味深い割れ方をしていました。同一の Claude Code version（2.1.220）・同一の rules で、Opus 5 のセッション 2 本はコミットに trailer を**付け**、Fable 5 のセッション 1 本は**付けない**。各セッション内では 100% 一貫していました。

つまり矛盾した指示を放置すると、その解決のされ方はモデル任せになり、モデルが変わると挙動も変わりうる、ということです。

ただし限界を明記します。これは統制比較ではなく自然観察です（タスク内容もユーザー指示も異なる 5 コミット）。「モデル依存の可能性が高い」までしか言えません。また観測されたのは帰属表示という実害ゼロの差分で、実害のある競合が同じ割れ方をするかは未確認です。
:::

### 冗長の実例: スコープ厳守ルール

競合とは別に、「言う必要がなくなった」ルールもありました。私の自作ルールにあった「スコープが指定されたら厳守する」は、Claude 5 世代の system prompt にほぼ逐語で存在します。

> "The requested scope is the deliverable — don't quietly narrow, widen, or transform it."
> （依頼されたスコープがそのまま成果物である——黙って狭めたり、広げたり、変形したりしない）

これは衝突していないので害は小さいものの、常駐トークンを払って本体と同じことを言っているだけです。公式記事の「Repeat yourself → Simple tool descriptions」の転換そのものでした。

### ドリフトの実例: レビューの確信度しきい値

ドリフトは 3 件検出しました。ここでは代表として 1 件を説明します。残る 2 件——コミット前の検証ステップの扱いと、レビューを別エージェントに分けるルール——は判定で扱いが分かれたため、Step 3 と「落とし穴」の節でそれぞれ説明します。

代表例は、レビュー用エージェント定義に書いていた「確信度 80% 以上の指摘だけ報告せよ」でした（冒頭の system prompt 80% 削減とは無関係の数字です）。[公式の Opus 5 プロンプトガイド](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)は、同じ方向の抑制指示を例に挙げて戒めています（80% という数値そのものへの言及ではありません）。

> If your review prompt says "only report high-severity issues" or "be conservative," the model may follow that instruction literally and report less; ask it to report everything and filter in a separate pass instead.
> （レビュープロンプトに「重大な問題だけ報告せよ」「保守的に」と書くと、モデルはそれを文字通り実行して報告を減らす。全部報告させて、別パスでフィルタせよ）

これはロード時の競合ではありませんが、公式が「モデルはこの種の指示を文字通り実行して報告を減らしうる」と明言している以上、置いたままでは指摘の取りこぼしにつながります。旧世代でどの程度実害があったかは検証していませんが、少なくとも現世代では公式が例に挙げて戒める型の指示なので、ドリフトとして扱いました。

## Step 3: 「競合 = 悪」とせず判定枠で処分する

3 分類ができたら処分を決めます。ここで重要なのは、**競合やドリフトを機械的に削除対象としない**ことです。自作ルールには、そもそも製品既定を意図的に上書きするために書いたものが含まれます。方向が逆というだけでは、事故なのか意図なのか区別できません。

私は各件を次の 4 つの観点で判定しました。

| 観点 | 問い |
|---|---|
| **意図** | 本体の既定を上書きしたくて書いたのか、当時は競合していなかっただけか |
| **根拠** | ADR（設計判断の記録）や事故メモなど、書いた理由の記録が残っているか |
| **鮮度** | 前提にした製品挙動（旧世代の弱点など）は今も成立しているか |
| **失効条件** | どうなったらこのルールを見直すか、決めてあるか |

処分例を 3 つ示します。

**退役（鮮度が失効）**: plan mode 禁止ルール（競合の実例 1）は、旧世代が「計画せず走り出す」弱点への対策でした。Claude 5 世代では本体側が計画を推奨するようになり、前提が消えています。意図的な上書きとして維持する理由もないので退役させました。

**退役（競合 + 冗長）**: `git-workflow.md` には、幽霊設定の一文（競合の実例 2）に加えて、コミットメッセージ形式や PR の書き方などモデルと runtime 層が既にカバーしている内容しか残っていませんでした。競合部分を直しても残りは冗長です。それならファイルごと要らない、と判断して退役させました。

**保持（意図と根拠が生存）**: 一方、「レビューは実装者と別のエージェントプロセスで走らせる」という自作ルールは残しました。公式ガイドには「自分の作業の検証にサブエージェントを使うな（do not use subagents to verify or double-check your own work）」という一文があり、一見このルールと衝突して見えます。

しかし文脈をきちんと読むと、これは分業レビューの否定ではありません。この一文は「サブエージェントの起動を制御する」節にある、**コスト抑制のために開発者がプロンプトへ足せる例文**の 1 フレーズです。前提として公式は「Opus 5 は言われなくても自分の作業を検証する。明示的な検証指示は過剰検証を招くだけなので削れ」と述べており、委譲も増えた新世代が「念のための二重チェック」用サブエージェントまで反射的に立てるとコストが膨らむ——その歯止めとして例示されています。一方で同じ doc は、書き手と検証者を分ける writer–verifier パターンを Opus 5 の得意分野として肯定的に挙げてもいます。

こちらの自作ルールは 2 段になっています。土台は「レビューを実装者と同一コンテキストでやらせない」（同一コンテキストのレビューは実装者の盲点を継承するから）。そのうえで重要な変更では**別モデル**（私の場合は Codex CLI）にレビューさせ、盲点を脱相関させます。後者は保持で迷いませんでした——別モデルによるレビューは Claude Code 本体がいくら進化しても構造的に提供できない能力なので、本体側に吸収されようがありません。設計判断は ADR に記録済みです。

一方、前者（同一モデルでの別プロセスレビュー）は、公式が抑制したい「検証パスの追加」と重なる可能性が残ります。ここが解釈を含む部分で、Opus 5 の自己検証が盲点継承の問題まで解消するなら土台側は不要になるかもしれません。前提が変われば見直す、失効条件付きの保持です。

この判定枠を回してみて分かったのは、**根拠の記録（ADR や事故メモ）があるルールは判定が速く、確度も高い**ということです。記録があっても退役はします（plan mode ルールは理由が分かっていても鮮度の失効で退役）。記録が左右するのは処分の結果ではなく、判断にかかるコストです。根拠を書き残していないルールは、消してよいかの判断自体が git log の考古学になります。

## 落とし穴: 公式の指摘を機械適用すると誤診する

公式ガイドには「レガシーなハーネスの足場が足す検証ステップも削減対象」という記述があります。これを機械的に適用すると誤診します。

私の自作ルールにはコミット前の Verify ステップとして 8 項目（build / type check / lint / tests / secret scan / 依存監査 / doc 同期確認 / git status 確認）がありました。「検証ステップは削れ」を文字通り適用すると全部が削除対象に見えます。

しかし公式が問題視しているのは**モデルの自己検証を増やす指示**です。8 項目の大半は build やテストなど決定論的なコマンド実行で、モデルの判断を増やしていません。判定軸はこうなります。

- その検証を**機械**（コマンド・hook）がやる → 残してよい
- その検証を**モデル**が自分の判断でやる → 公式の指摘対象。削減を検討

もう 1 つの落とし穴は、**削除では足りず「反転」が要るケース**です。前述の「確信度 80% 以上だけ報告」を単純削除すると、そのセクション（ノイズ抑制の枠組み）自体は残り、抑制方向に効き続けます。私は節を「確信度で抑制するな。全部報告し、呼び出し側が別パスでフィルタする」に書き換えました。方向が変わった指示は、削るのではなく逆向きに書き直す必要があります。

## 結果と数値

重心は判定手順にありますが、参考までに私のハーネスの Before / After です（`wc -w` 実測、CLAUDE.md + rules の常駐合計）。

| 時点 | 常駐 words | ファイル数 |
|---|---|---|
| 棚卸し前 | 5,789 | 20 |
| 棚卸し後（2026-07-26 時点） | 2,463 | 14 |

なお「競合を解消したから性能が上がった」とは主張しません。私の環境には矛盾解決のコストを測る計器がなく、効果の定量は冒頭に引用した Anthropic の計測（80% 削除で劣化なし）に依っています。この記事が示すのは効果の証明ではなく、**設定ドリフトの実例と、それを見つけて処分する手順**です。

## まとめ: 次にできること

1. 実セッションから runtime 層（system prompt + tool description）を採取する。設定リポジトリだけ見ても全体は分からない
2. 自作ルールと突合し、競合・冗長・ドリフトに分類する
3. 「競合 = 悪」とせず、意図・根拠・鮮度・失効条件の 4 観点で残す・反転・退役を判定する
4. 公式の削減推奨は「モデルの自己検証」と「機械の検証」を区別して適用する

そして今回の教訓を 1 つ足すなら: **ルールを書くときに根拠と失効条件を書き残しておく**ことです。白状すると、私も体系的にやれていたわけではありません。ADR が残っていたルールは判定が数分で済み、残っていなかったルールは git log の考古学になり、幽霊設定にいたっては消えた時期の特定すらできませんでした。ルールは自分の根拠が消えたことを検知できないので、次の世代交代のときに判定できるかどうかは、いま残すメモで決まります。
