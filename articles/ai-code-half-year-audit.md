半年前、Claude に書かせた CLI ツールがあります。テスト 694 本は全て緑、mypy と ruff もクリーンでした。

当時「[LLM の出力は信用するな](https://zenn.dev/shimo4228/articles/ecc-journey-part2)」という記事まで書いて、防御策を 6 つ並べています。

その自信作を先日、現世代の AI 2 系統に丸ごとレビューさせました。

検証にかけた指摘（延べ 31 件）は**全件が実在するバグでした。重複を除いて約 25 件、誤検出ゼロ**です。

ただし、この記事の主題は「どんなバグがあったか」ではありません。

知りたかったのは、**半年前の世代の AI（と、それを支えていたハーネス）が書いたコードは、今の目で見てどの水準だったのか**です。

監査から出た成績表を先に置きます。

- **骨格（設計）**: 今も通用した。設計の変更が要る指摘は Vision まわりの 2 件だけで、修正はパッチリリースに収まった
- **外部と接する細部**: 出荷水準に達していなかった。リバーシブルカードの Anki 送信と大きい画像の抽出は、実装された日から一度も正しく動いていなかった
- **経年劣化**: 確認できず。「書いた後に世界が動いて壊れた」確定例は 1 件もなく、確認できた壊れ方はすべて「最初から」だった

以下、この 3 行を数字で裏づけます。

## 実験設定: 半年の時差がある 2 世代を対決させる

被験体は [pdf2anki](https://github.com/shimo4228/pdf2anki)。PDF から Anki 暗記カードを自動生成する Python 製 CLI で、2026 年 2 月に 10 日間で実装したものです（当時の記録は[別記事](https://zenn.dev/shimo4228/articles/ecc-journey-part1)にあります）。

書いた側と監査する側には、半年分の世代差があります。モデルも、ハーネス（Claude Code に載せるスキル・ルール・フックの一式）も、です。

| | 書いた側（2026-02） | 監査した側（2026-08） |
|---|---|---|
| モデル | Claude Opus 4.6（一部 Sonnet 4.5）※コミットの Co-Authored-By より | Claude Fable 5 + GPT-5.6-Sol（Codex CLI 経由） |
| ハーネス | ECC 導入初期。コミュニティ製スキル集で足場を厚く積んでいた時期 | 足場の解体後。スキル・ルールを大幅に削減した薄い構成 |
| 品質保証 | TDD + 当時世代のコードレビュー | 本記事の 2 コマンド |
| コードの状態 | テスト 694 本 passed・mypy/ruff クリーン | 同左（2 月の実装完了後、機能追加なし） |

ECC（Everything Claude Code）はコミュニティ製の Claude Code 拡張集です。当時のモデルの弱さをスキルやルールの束（本記事ではこれを「足場」と呼びます）で底上げする思想で、私のハーネスはここから始まり、その後[膨張と棚卸し](https://zenn.dev/shimo4228/articles/ecc-journey-part3)を経て解体へ向かいました。

:::message
以下の実測はすべて 2026-08-13 時点のものです。

モデル・価格・ツールの挙動は変わり続けるので、再現するときはその時点の最新で読み替えてください。
:::

## やったこと: 2 系統のレビューを並走させる

使ったのは 2 コマンドだけです。どちらも読み取り専用で、コードは変更しません。

1 つ目は Claude Code 内蔵の `/code-review`。ディレクトリを丸ごと対象に指定し、effort を high にして全体を見せます。

```text
/code-review src/pdf2anki high
```

2 つ目は OpenAI Codex CLI をレビュアーとして呼ぶ [codex-review](https://github.com/shimo4228/codex-review) スキルです。プロンプト駆動モードで、焦点を明示して起動します。

```bash
bash ~/.claude/skills/codex-review/codex-review.sh "Review the entire codebase under src/pdf2anki/ (not just the diff). Focus on: correctness bugs, error-handling gaps, API misuse (Anthropic SDK, PyMuPDF, Gradio, Textual), security issues, cost-tracking accuracy in cost.py, cache integrity in cache.py, and concurrency/state bugs. Report concrete findings with file:line references. Ignore style nits."
```

別系統のモデルを重ねるのは、同じモデル系統だと盲点まで共有してしまうからです。この設計意図は[前作](https://zenn.dev/shimo4228/articles/codex-review-cross-model-decorrelation)に書きました。

監査の規模感だけ数字で置いておきます。

| 項目 | 実測値 |
|---|---|
| Codex（GPT-5.6-Sol）の指摘 | 15 件（P1 = 最優先 ×6、P2 = 次点 ×9）。コード読解で全件実在確認 |
| Claude（Fable 5）の検出フロー | 8 観点 → 候補 44 → 重複排除 32 → 正確性候補 16 を個別検証 → 16 CONFIRMED / 0 REFUTED（数件は venv での実行再現つき） |
| 両者合算（重複除去後） | 約 25 件。うち 23 件を修正し [v0.3.1](https://github.com/shimo4228/pdf2anki/releases/tag/v0.3.1) をリリース（39 files, +739/−361） |

## 水準判定 1: 致命かトリビアルか

25 件と聞くと壊滅的に響きますが、玉石混交です。重大度で仕分けるとこうなりました。

| 重大度 | 件数 | 中身 |
|---|---|---|
| **機能不全**（使えば失敗する） | 4 | リバーシブルカードの Anki 送信（全件失敗）/ 大きい画像の Vision 抽出（全滅）/ カード種類が混在した TSV の import 不整合 / 長大 PDF の Vision 一括送信 |
| **静かな漏れ**（金とデータ） | 約 13 | batch 実行の予算チェック素通り / コストの 3 倍過大計上 / prompt cache 課金の未計上 / 応答 1 つの不良でファイル全カード喪失 / 設定したモデル指定の無視 など |
| **堅牢性・UX** | 約 8 | TUI の表示スキップ / エラー時に不親切なクラッシュ / リトライの二重掛け など |

分布から言えることが 2 つあります。

第一に、**クラッシュして暴れるバグがほぼない**こと。大半は黙って失敗するか、黙って間違った金額を記録する類です。

だからデモは完走し、テストは緑で、半年間だれも気づきませんでした。

第二に、機能不全の上位 2 つ（リバーシブルカード送信・大画像抽出）は、**実装された日から一度も正しく動いたことがない**こと。存在しないノートタイプ名を送り、存在しない API の呼び方をしていたので、これは推測抜きに演繹できます。

つまり半年前のコードの水準は、「動くが粗い」ではありません。**「主要機能の一部が死んでいることに、テストも作者も気づけない状態で出荷されていた」**です。

一方で、骨格側の判定材料も添えておきます。25 件のうち設計の変更が要る指摘は Vision の一括送信まわりの 2 件だけで（今回は見送り）、残る 23 件は局所修正で閉じました。

修正全体が 39 files・+739/−361 のパッチリリースに収まったのは、骨格が現世代の目にも耐えたからです。

:::details 代表バグの中身（コード付き。興味のある方だけ）
**① 存在しない Anki ノートタイプ名**（機能不全）

```python
# 修正前の src/pdf2anki/anki_connect.py:95-102
# Anki 標準名は "Basic (and reversed card)"。実在しない名前を送っていた
model_name = "Basic (and target: reversed card)"
```

テストが緑だった理由は、テスト自身が同じ誤った文字列をアサートしていたからです。

```python
# 修正前の tests/test_anki_connect.py:200
assert payload["params"]["note"]["modelName"] == "Basic (and target: reversed card)"
```

**② 存在しない PyMuPDF API 呼び出し**（機能不全）

```python
# 検証時の再現（pymupdf 1.26.7）。修正前の src/pdf2anki/image.py:156 相当
import pymupdf
src = pymupdf.Pixmap(pymupdf.csRGB, pymupdf.IRect(0, 0, 100, 80))
scaled = pymupdf.Pixmap(src, 50, 40, None)          # 正しい書き方は動く
bad = pymupdf.Pixmap(src, pymupdf.Matrix(0.5, 0.5))  # TypeError
```

この TypeError は広域の `except Exception: continue` に握り潰され、「一定サイズを超える画像だけが黙って消える」挙動として潜伏していました。検証エージェントは 2000×2000 の画像を含む PDF で抽出 0 枚になることを実行再現しています。

**③ 旧世代の価格が書き込まれた単価表**（静かな漏れ）

```diff
# src/pdf2anki/cost.py:17-21 — モデル単価（$/MTok, input/output）
- "claude-haiku-4-5":  (0.80, 4.00)   # 実勢は $1 / $5（20% 過小）
- "claude-opus-4-6":   (15.00, 75.00) # 実勢は $5 / $25（3 倍過大）
+ "claude-haiku-4-5":  (1.00, 5.00)
+ "claude-opus-4-6":   (5.00, 25.00)
```
:::

## 水準判定 2: なぜテストは緑のまま半年間もったのか

破れていた 25 箇所には、共通の機序が 2 つありました。細部より、この機序のほうが持ち帰る価値があります。

**機序 1: 思い込みごとテストが緑になる。**

テストは外部の本物（Anki・PyMuPDF・API）を偽物（モック）で置き換えます。今回のバグはほぼ全てが、この置き換えの境界の外側にいました。

実装とテストを同じ AI が同じセッションで書くと、思い込みも両側に複製されます。テストは「実装が自分の思い込みと一致するか」しか検証できず、「思い込みが世界と一致するか」は検証できません。

テストという営みが無力なのではありません。今回の修正でも、実物の PyMuPDF で大きい画像を処理するリグレッションテストを追加しており、この種のバグは今後テストで捕まります。

無力なのは、実装と同じ思い込みで書かれたモックです。

**機序 2: 書き手（AI）の知識が、書いた時点で既に古い。**

コードの単価表には、Opus 4.6 が $15/$75、Haiku 4.5 が $0.80/$4.00 と書かれていました（実勢はそれぞれ $5/$25 と $1/$5）。この誤った数字は、1 世代前の Opus 4/4.1 と Claude 3.5 Haiku の価格にぴったり一致します。

[Opus 4.6 のローンチ発表](https://www.anthropic.com/news/claude-opus-4-6)（2026-02-05）には "Pricing remains the same at $5/$25 per million tokens" とあり、実装は 02-08。

つまりモデルは、**学習時に覚えた旧世代の相場を、新モデルの価格としてそのまま書き込んだ**のです。

しかも実装翌日に書かれた repo 内の調査文書には正しい価格が記録されていました。正解はすぐそこにあったのに、コードには記憶が書かれた。

白状すると、この記事の下書きも最初「書いた後の値下げで壊れた」と説明していました。ファクトチェックで否定されるまで、私はそのもっともらしい記憶を信じていたわけです。

鮮度切れは、書き手が AI でも人間でも紛れ込みます。

この 2 つの機序はどちらも「最初から壊れていた」を生みます。そして確認できた壊れ方はすべてこのどちらかで、「書いた後に世界が動いて壊れた」確定例は今回ゼロでした。

**半年前のコードは経年劣化していたのではありません。最初から壊れたまま、気づかれずに動いていただけです。**

対策も機序に対応します。思い込みの複製には、実装と独立した実物との突き合わせ（別系統のレビューや実機検証）。鮮度切れには、書くとき 1 回きりでない、書いた後の照合。

今回の 2 コマンドは、その両方を安価にまとめて実行する手段でした。

## 監査側の発見: 2 つのモデルは違う場所を見ていた

両モデルの指摘の重なりは、同一ファイル・同一趣旨を 1 テーマと数えて 4 テーマ（件数では 5〜6）。**件数ベースで約 2 割**しか重なりませんでした。

| 区分 | 件数 | 傾向 |
|---|---|---|
| 両者が独立に一致 | 4 テーマ | 予算バイパス・キャッシュキー不備・ノートタイプ名・モデル選択の無視 |
| Codex のみ | 約 10 件 | **外部契約に強い**: API 価格、prompt cache の課金体系、Anki の TSV インポート仕様 |
| Claude のみ | 約 10 件 | **実行時の失敗経路に強い**: 存在しない API 呼び出し、例外の伝播、部分失敗時のデータ損失 |

裏返すと、**片方だけなら約 25 件のうち 6 割前後しか見つからなかった**ことになります。

両者が独立に一致した 4 テーマは優先度シグナルとして機能しました。系統の違う 2 つのモデルが同じ場所を指したなら、そこはまず本物です。

実際、修正は「両者一致 + 課金系 → データ全損系 → UX 系」の順で進めました。

## 足場はどこまで解体できたか

もう 1 つ、この監査で測りたかったのが実験設定の表の**ハーネスの行**です。

半年前は、モデルの判断を補うための足場（スキル・ルール・手順書といった指示の束）を厚く積んでいました。いまの私はそれを解体し続けています。

| 時期 | ハーネスの状態 |
|---|---|
| 2026-02（実装期） | ECC 導入初期。足場を厚く積んで当時のモデルを底上げ |
| 2026-03 | ECC 本体が 116 スキルまで膨張。プラグインを無効化し、手元に導入していた 33 スキルも 16 まで削減 |
| 2026-07 | 常駐ルール約 8–9k トークンを削減。「旧世代の弱さを補う指示は、新世代には足かせ」という判断 |

薄いハーネスの現世代セットは、厚いハーネス時代の生産物をどこまで検分できるのか。

結果は、検証にかけた指摘 31 件（15+16）が全件実在・誤検出ゼロ。著者が書き足した手順書なしでこの精度が出ました。

ただし、手順が消えたと言うと不正確です。`/code-review` 自体が「8 観点で探索 → 検証エージェントが反証」という多段の手順を内蔵しています。**手順は著者の外付けから、ツールの内蔵へ移った**のです。

一方で、指示の足場とは別の層で**まだ稼いでいた仕組み**が 2 つあります。

1 つ目は機械ゲート。修正コミットは pre-commit フック（セキュリティスキャン → フォーマッタ → シークレット検出）に 3 回差し戻され、3 回とも実修正で通過しました。

LLM の出力を機械で検査する層は、現世代でも仕事をしています。

2 つ目は人間の介入点。レビューエージェントが検証待ちのまま約 40 分停止し、再開指示を送って初めて完走しました。

「止まったら人が押す」ボタンはまだ要ります。

**判断を教える足場は剥がせた。検査する仕組みと、止まったとき押す介入点は残った**。これが解体の現在地です。

:::details 運用 Tips（再現するときの細かい注意）
- **レビューエージェントの停止**: バックグラウンドのレビューは「タスク完了」とは限りません。単に「停止」しているだけのことがあります。今回も約 40 分の無活動後、「検証結果を回収して最終レポートを」と一言送ったら約 2 分で完走しました
- **価格・仕様の修正は必ず現在の一次情報と照合**: 「AI がそう言ったから」で価格表を直すと、鮮度切れの事実をもう 1 件仕込むだけです
- **修正順は「両者一致 + 課金系」から**: 2 モデルが独立に一致した指摘は誤検出リスクが最も低く、課金系は放置コストが実費で出ます
- **コスト感**: Claude 側レビューのサブエージェントは合計約 20 万トークンを消費しました（95,229 + 106,860）。effort high の全体レビューは安くないので、かけるなら節目ごとが現実的でしょう
:::

## まとめ: 成績表の読み方

半年前の世代セット（Opus 4.6 + 厚いハーネス）が書いたコードの水準は、こうでした。

- **骨格は合格**: 設計変更が要ったのは Vision まわりの 2 件だけ。修正はパッチリリースで収まった
- **外部と接する細部は落第**: 機能不全 4 件・静かな漏れ約 13 件。一度も動いたことのない機能があった
- **経年劣化は確認できず**: 確認できた壊れ方は全部「最初から」。半年間それが見えなかっただけ

そして、この水準差を**テストの緑は何も教えてくれませんでした**。694 本の緑のテストは、「主要機能が死んでいる」ことと半年間共存していたのです。

測定器になったのは、系統の違う 2 つのレビューでした。片方だけなら 6 割しか見えなかったので、2 系統であることに意味があります。

ハーネス側の答えも 1 行で置けます。判断を教える足場は剥がせた、検査する仕組みと止まったとき押す介入点は残った、です。

手元に「数ヶ月前に AI に書かせて、テストが緑のまま動き続けているコード」があるなら、同じ測定は 2 コマンドでかけられます。

そして半年後には、今日の Fable 5 が書いたコードもまた、次の世代に監査される側へ回ります。そのとき何点と出るか。それを測れる形にしておくことが、いまできる備えだと思っています。
