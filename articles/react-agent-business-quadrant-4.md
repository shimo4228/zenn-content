> **シリーズの位置づけ:** ReAct エージェント適用域シリーズの 4 作目。象限名は前作群および [AAP のリポジトリ](https://github.com/shimo4228/agent-attribution-practice) に揃えている。

## 前提 — 4 象限の再掲

[初作](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant) で立てた 4 象限を再掲する。

- (1) **スクリプト象限** — 決定論 × 定義可。スクリプト / パイプラインで処理
- (2) **Algorithmic Search 象限** — 決定論 × 探索的。古典 AI / OR の領域
- (3) **LLM ワークフロー象限** — 意味判断 × 定義可。事前定義されたワークフローの中で LLM を呼ぶ
- (4) **Autonomous Agentic Loop 象限** — 意味判断 × 探索的。LLM 自身が次の行動を決める自律ループ (= ReAct エージェント)

前作までは (3) と (4) を「業務の性質に応じてどちらかを選ぶ」という二項対立として扱ってきた。[前作 2](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant-2) は業界に (3) を語る語彙が定着していないことを指摘し、[前作 3](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant-3) はその二項対立を業務システム軸で捉えて設計フェーズと運用フェーズの Phase Separation を導入した。本作はその Phase Separation を個々のスキル設計の解像度まで降ろし、二項対立の間に **連続的なグラデーション** が存在することを示そうとする。

## 観察 — 同じ仕事が複数の形態で生きている

私の手元のリポジトリを見渡すと、概念的には同じ仕事をしている関数が、複数の異なる形態で実装されている。[AKC (Agent Knowledge Cycle)](https://github.com/shimo4228/agent-knowledge-cycle) — エージェントが自分の出力から知識を蒸留して自己改善する 6 フェーズのサイクル — の中の **Promote フェーズ** がその典型例だ。スキルの中に繰り返し現れる原理を抽出してルールに昇格させる仕事に当たる。一般化すれば「**繰り返しから原理を抽出する**」仕事だ。ログからアラートルールをマイニングする作業、コードベースから共通パターンを見つけてリファクタリングする作業、顧客サポートの会話ログから FAQ を編む作業も、同じ族に属する。

[`contemplative-agent`](https://github.com/shimo4228/contemplative-agent) には [`core/rules_distill.py`](https://github.com/shimo4228/contemplative-agent/blob/main/src/contemplative_agent/core/rules_distill.py) という Python の関数がある。埋め込みでスキルをベクトル化し、`cluster_patterns` でテーマ別クラスタリングを作り、`MAX_RULES_BATCH=10` で LLM のバッチを組み、クラスタ閾値は `CLUSTER_THRESHOLD_RULES=0.65` に校正ファイル付きで決定されている。LLM 呼び出しはパイプラインの中の一ステップに過ぎず、判断の大半は事前にコードへ凍結されている。

一方 [`rules-distill`](https://github.com/shimo4228/claude-skill-rules-distill) スキル (`~/.claude/skills/rules-distill/SKILL.md`) は自然言語で書かれている。Phase 1 で `scan-skills.sh` がファイル一覧を作り、Phase 2 でサブエージェントにテーマ別クラスタの判断を委ね、バッチをまたいだマージも LLM 判断が決める。スクリプトは一覧の作成と永続化にだけ使われ、判断本体はランタイムの LLM の手にある。

両者は同じ仕事をしている。にもかかわらず実装は劇的に違う。

## 表層仮説 — モデルの能力

最初に思いつく説明は **モデルの能力** だ。`core/rules_distill.py` は 9B のローカルモデル環境で動くために書かれた。9B ではテーマ別クラスタの判断をランタイムで頑健に走らせるのが難しい、というのが手元での実装観察だった。だから埋め込み + クラスタリング + 閾値調整という決定論的な足場で 9B の役割を「与えられたクラスタからルール候補を一つ生成する」に限定している。逆に Opus をランタイムで呼べる Claude Code 環境では、その足場は要らなくなる。クラスタ判断もマージ判断も LLM が文脈全体を踏まえて行える。

これは AKC が記録している設計原則 — README の Design Principle 5「Evaluation scales with model capability — 小さなモデルはルーブリック評価で、Opus class は全文脈を踏まえた質的評価で動かす」 — と整合する。原文では評価の文脈に絞られているが、能力に応じて判断スケールを変えるという発想を実装位置の選択に敷衍すれば、9B 時代の Python パイプラインと Opus 時代の自然言語スキルは、その敷衍の二端点として読める。

しかしこの説明は実装位置の表層を撫でているに過ぎない。能力の差は確かに観察される事実だが、それは **より深い決定の下流の結果** だ。

## 深層仮説 — AAP フェイズ

前作 [本番運用に ReAct は必要か](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant-3) で書いた **設計フェーズと運用フェーズの区別** に戻る。実装位置を本当に駆動しているのはこのフェーズ軸だ。

`contemplative-agent` は **運用フェーズ** に置かれている。一度デプロイされた後、入力は決まった経路を流れる。入力 (人格テンプレート、対話、メモリ) と出力 (応答、ログ) の境界は事前に確定していて、内部の知識サイクルも同様に事前定義された 6 フェーズで動く。パイプラインが運用フェーズで凍結されているからこそ、`core/rules_distill.py` のように 埋め込み / クラスタリング / 閾値 / バッチ 構造を Python に焼き込める。9B はこの環境で *選べる* 帰結であって、原因ではない。

実際、`contemplative-agent` のパイプラインは LLM 呼び出し部分をオプションで Claude や GPT モデルに切り替えられるように作られている。能力を上方にスケールさせても LLM 関数のパイプライン自体は基本的に壊れない。これは表層仮説 (能力がパイプライン構造を要求している) への反証実験になっている。仮に能力が原因なら、Opus class に置き換えた瞬間にパイプライン構造は冗長になって崩れていくはずだ。だが実際には崩れない。**パイプライン構造を要求しているのは能力ではなく、運用フェーズというフェーズ決定** だ。能力はフェーズ決定の下流で選ばれる帰結に過ぎない。

`Claude Code` は **設計フェーズに常駐する道具** だ。各セッション自体が探索作業で、対象コードベースも IDE も使われるエージェントも、扱うファイル種別 (.py / .ts / .md / .ipynb / 任意) もセッションごとに動く。ある時は Python プロジェクト、ある時は Next.js プロジェクト、ある時は ADR 中心の文書リポジトリ。スキルがパスやファイル構造を事前確定すれば、環境が動いた瞬間に壊れる。だからスキル本体は自然言語で書かれてランタイムのコンテキストに適応する。Opus はそのランタイム適応に必要な全体的な判断を支える *帰結* であって、原因ではない。

つまり、

- contemplative-agent が `core/rules_distill.py` 形式で書ける = **運用フェーズでパイプラインを凍結したから**
- Claude Code が `rules-distill` スキル形式で書かざるを得ない = **設計フェーズで環境を凍結できないから**

能力はこのフェーズ決定の下流にあるように見える。フェーズが「ハードコード可能」と「柔軟性必須」の境界を引き、その境界の中で能力の選択が成立する。AKC の「能力 ↑ → 全体的な判断 OK」という敷衍は、フェーズ決定を所与としたときに成り立つ二次的な原則として読める。

## フェイズ内部 — 同じフェーズでもタスクで位置が動く

設計フェーズに視点を絞っても、実装位置はさらに分かれる。

[`skill-comply`](https://github.com/shimo4228/claude-skill-comply) というスキルがある。Claude のスキル / ルール / エージェント定義がランタイムで実際に守られているかを測定するスキルだ。3 段階のプロンプト強度 (supportive → neutral → competing) でシナリオを自動生成し、`claude -p` を走らせ、ツール呼び出しのトレースを分類して遵守率をレポートする。ディレクトリには `pyproject.toml` / `prompts/` / `fixtures/` / `tests/` / `scripts/` / `results/` が並ぶ。シナリオ実行が再現可能でなければ遵守率に意味がない、というのがタスクの内部要件だ。一般化すれば、コードの静的解析 (lint や SonarQube) やベンチマークの自動測定と並ぶ仕事 — **同じ入力に同じ判定が返る** ことが要求される。設計フェーズの中のスキルだが、**評価測定というタスク性質が再現性を要求する**。

一方 [`search-first`](https://github.com/shimo4228/claude-skill-search-first) というスキルは、新規実装前に既存ライブラリ・ツールを探すスキルで、ディレクトリには `SKILL.md` 一ファイルしかない。scout エージェントに委任して Adopt/Extend/Build の判定を返す。一般化すれば、新機能を作る前にエンジニアが GitHub や PyPI を巡回して候補ライブラリを絞り込み、文脈に応じて Adopt か Build かを判断する作業に近い。毎回同じ候補集合が返る必要はなく、文脈に応じた判定が求められる。設計フェーズの中のスキルで、**選定判断というタスク性質が純粋な判断** を要求する。再現性は副次的で、毎回少し違う候補集合を返しても問題ない。

両方とも設計フェーズ内にあり、Opus + 開放環境という同じ環境で動く。にもかかわらず実装位置はワークフロー寄り (`skill-comply`) と ReAct 寄り (`search-first`) に分かれる。これはフェーズが決まった後でも、**タスク性質が独立に位置を引っ張る** ことを示している。

ただしフェーズとタスクは完全に直交しているわけではない。運用フェーズで再現性要求が高いタスクは強くワークフロー側に押される、というようにフェーズがタスクの表れ方を変える側面もある。本作は二軸を粗く分けて扱うが、相互作用の大きさを精緻に見るのは本作の射程外。

## 同じフェーズ軸がスキル内部にも降りる

同じフェーズ軸はスキル単位だけでなく、スキル内部のサブコンポーネント単位にも降りる。[`skill-stocktake`](https://github.com/shimo4228/claude-skill-stocktake) と [`context-sync`](https://github.com/shimo4228/claude-skill-context-sync) の対比が象徴的だ。

`skill-stocktake` はインストール済みの Claude のスキルとコマンドを一覧して品質を監査するスキルだ。「どのスキルファイルを評価対象にするか」というドメイン定義をスクリプトでハードコードしている (`~/.claude/skills/`、`{cwd}/.claude/skills/`)。一般化すれば、SBOM (Software Bill of Materials、ソフトウェアに含まれる依存ライブラリの一覧) 生成や依存性スキャンに連なる仕事 — 「対象を機械的に列挙する」ことを要求される。利点は **取りこぼしがない** こと。欠点は **Claude Code 環境前提** であって、別のコーディングエージェント環境ではそのままでは動かない。汎用化を考えるとエージェントごとにスクリプトを書き分けることになり、メンテナンスコストがかさむ。

`context-sync` はプロジェクトのドキュメント (CLAUDE.md / CODEMAPS / ADR / README など) の役割重複・陳腐化・欠落を検出して修正するスキルだ。`skill-stocktake` と違ってドメイン定義を LLM の全体的な判断に委ねている。一般化すれば、テックリードがプロジェクトのアーキテクチャを読み解いて「ここの説明が古い、こっちは ADR に動かすべき」と判断する作業に近い。だから llms.txt を見つければそれも同期対象に含めるし、Codemaps や ADR、AGENTS.md (名前違いで同じ機能を果たすファイル) も気を利かせて検出する。利点は **環境横断的な可搬性**。欠点は実行ごとに **検出範囲が揺れる** こと、そして本格的なコードベース規模になると、検出できても **差分を完全に捕捉しきれない**。

| 比較項目 | skill-stocktake | context-sync |
|---|---|---|
| ドメイン定義の置き場所 | スクリプト固定 | LLM 判断 |
| カバレッジ | 取りこぼしなし | 揺れる |
| 可搬性 | 単一環境前提 | 環境横断 |
| 規模耐性 | 高 | 低 |

ここで言う「サブコンポーネント」は、スキル内部にある処理ステップのことだ。1 つのスキルは外から見れば 1 つの仕事だが、内部では複数のステップに分かれている。`skill-stocktake` を例にとれば、(A)「どのスキルファイルを評価対象にするか」を決める **対象列挙** のステップと、(B)「各スキルの品質を判断する」 **品質判断** のステップに分けられる。`context-sync` も同型で、(A)「どのドキュメントを sync 対象にするか」(対象列挙) と (B)「内容の古さ・移動すべき箇所を判断する」(品質判断) の 2 ステップに分けられる。本作で言うサブコンポーネントとは、この A や B のような **スキル内部のステップ** を指している。

これが示すのは、フェーズ軸が **スキル単位だけでなく、スキル内部のサブコンポーネント単位でも降りる** ことだ。同じフェーズに属する 2 スキルでも、ステップごとの配置は違う。`skill-stocktake` は A (対象列挙) をスクリプト、B (品質判断) を LLM に置く **ハイブリッド配置**。`context-sync` は A も B も LLM に置く **ReAct 寄り配置**。同じスキルの中でも、ある部分はワークフロー側、別の部分は ReAct 側に分けられる。

設計フェーズ内で両者が違う配置を取るのは、**対象の特定可能性** に差があるからだ。設計フェーズは「環境が動く」のが性質だが、対象によって動き方が違う。`skill-stocktake` の対象である Claude のスキルは、`~/.claude/skills/` (グローバル) と `{cwd}/.claude/skills/` (プロジェクト) という **固定された場所・固定された命名規則** で置かれている。設計フェーズでもスクリプトでパスをハードコードできる。一方 `context-sync` の対象 (`CLAUDE.md` / `CODEMAPS/` / `docs/adr/` / `AGENTS.md` / `llms.txt` ...) はコードベースによって配置位置も命名も変わる。スクリプトに書ききれないから、LLM の全体的な判断に委ねるしかない。

さらに、LLM 判断側を選んだ場合の限界として **規模耐性** がある。中規模のコードベースまでは LLM の全体的な判断で網羅できるが、本格的な規模になると差分の捕捉漏れを起こす。能力が十分上がってもこの取りこぼしは残る。AKC 設計原則 (能力 ↑ → 全体的な判断 OK) は、**対象の特定可能性** も **規模耐性** も、いずれも射程に含めていない。

## おわりに

(3) LLM ワークフロー象限と (4) Autonomous Agentic Loop 象限は、業務の性質を分類する軸としては有用だ。だが個々のスキル設計を考えると、両象限の間には連続的なグラデーションがあり、そのグラデーション上のどこに着地するかは **フェーズ決定が一次的に決めているように見える**。能力の差はフェーズ決定の下流で観察される結果に過ぎない。

[前作 2](https://zenn.dev/shimo4228/articles/react-agent-business-quadrant-2) で指摘したとおり、業界には (3) を独立した象限として語る語彙がまだ定着していない。本作はそこからさらに、二項対立の中の連続的なグラデーションに踏み込もうとしている。同じ仕事が運用フェーズと設計フェーズで違う位置に実装される。同じフェーズでもタスク性質が違えば位置が動く。一つのスキルの内部でも、サブコンポーネントごとに位置が分かれる。

前作の Phase Separation は業務システムの軸として書いたが、本作はその軸が個々のスキル設計の解像度まで貫いていることを示そうとした。同じフェーズ軸が、業務の分割とスキルの実装位置の両方を一次的に決めている。

一つの方向として残るのは、フェーズが変われば最適位置も動くという観察だ。ある環境では正解だった実装位置が、フェーズが変われば最適でなくなる。これが示す問いをどう実装に落とすかは、まだ答えが手元にない。本作の射程を超える設計課題として残しておく。
