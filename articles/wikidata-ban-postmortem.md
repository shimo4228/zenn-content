> **この記事でわかること**: 「Wikidata に登録すれば AI に引用されやすくなる」という発想の落とし穴です。規約準拠のつもりで 6 週間かけて作った 109 item が一夜で全削除された一次資料をもとに、自己登録という経路のどこが危ういのかがわかります。

2026 年 7 月 16 日の朝、Wikidata からの通知に気づきました。開くと、アカウントは無期限 block。理由の欄には "Promotion-only account" とあります。最初の感想は「えっ、何もしていないのに」でした。

削除ログを引くと、01:58:29 から 02:00:51 まで、**約 2 分半で自分の作った 109 item がすべて一括削除**されていました。6 週間かけて構築したものが、一夜で消えたことになります。

「Wikipedia や Wikidata に載っている対象は AI に引用されやすい。だから自分の作品もエンティティとして登録しよう」— LLM 時代の発見可能性(いわゆる GEO)の文脈で、この発想を見かけたことがある人は多いはずです。私はそれを実行して、この結果になりました。

不可解なのは、**個別の編集はすべて規約準拠のつもりだった**ことです。Wikipedia に自分の記事を書いてはいけないことは知っていました。ただ Wikidata の方針は異なり、出典要件を満たす限り自分自身の item の編集は一般に許容されています(ガイドライン [Wikidata:Autobiography](https://www.wikidata.org/wiki/Wikidata:Autobiography) に明記)。

その理解のもとで、statement には出典を付け、Wikidata の制約チェックも通し、talk page への警告は一度もありませんでした。block 通知にも、個別編集の違反の名指しはありません。それでも全損しました。なぜでしょうか。

この記事でやることは 3 つです。

1. **なぜ全損したか** — 判定が編集単位でなくアカウント単位で行われる構造を説明します
2. **当日中に閉じた事故対応** — 撤退判断、参照の除去、謝罪の設計まで、実際にやったことを示します
3. **失敗を規範に変換する方法** — この事故を設計原則(ADR)と常駐ルールに変換した手順を示します

## 前提

- **GEO (Generative Engine Optimization)**: 生成 AI の回答に自分のコンテンツが引用されるよう最適化する考え方。概念の正典は [Aggarwal et al. (KDD 2024)](https://arxiv.org/abs/2311.09735) です
- **item**: Wikidata の登録単位。人・作品・概念などが 1 item = 1 QID(Q で始まる ID)を持ちます
- **ADR (Architecture Decision Record)**: 設計判断を、文脈・決定・却下した代替案とともに記録するドキュメント形式
- 本記事の件数・時刻・block 理由の文言は Wikidata の公開 API で機械検証できます(検証コマンドを本文に載せます)。レートリミットの観測など、ログの残っていない箇所はその都度「著者の観測」と明示します

## 何を作っていて、何が起きたか

前提として、私は研究成果を複数の公開リポジトリ(以下「研究リポジトリ群」)として GitHub で運営しています。作っていたのは、その識別子を Wikidata 上で相互リンクさせる層です。著者の item、リポジトリの item、論文の item を Wikidata に作り、論文が引用している外部文献の書誌 item(skeleton)も作って、引用関係のプロパティで結んでいく。

編集は AI エージェント(Claude Code)に実行させる半自動で、まとまった書き込みの前に私が承認する運用です。すべての編集に出典を付け、6 週間かけて 109 entry まで積み上げました。

動機は GEO 文献です。生成 AI の引用元を実測した調査では、Wikipedia が ChatGPT の引用ドメインの最上位圏(Reddit に次ぐ 2 位クラス)に安定して入るとする報告が複数あります([Semrush](https://www.semrush.com/blog/most-cited-domains-ai/)、[Ahrefs](https://ahrefs.com/blog/most-cited-domains-in-chatgpt/) など)。Wikidata 単体の効果を測った実測は、調べた範囲では見つけていません。

それでも「Wikipedia の裏で機械可読の実体データを供給しているのは Wikidata だから、エンティティとして載っていれば AI からの発見可能性は上がるはずだ」— そう読んで、この層に投資しました。いま振り返ると、この時点ですでに実測と期待の境界が曖昧でした。

| 時期 | やったこと |
|---|---|
| 06-07 | 著者 item + 論文 3 + リポジトリ 7 を作成 |
| 06-12 | 引用文献の skeleton(出典だけを持つ書誌 item)27 件 + 引用関係の辺を追加 |
| 06-13〜26 | 外部識別子の追加、論文 item 追加 |
| 07-15〜16 深夜 | skeleton 19 item 新規作成 + 引用辺を 14→33 に一括同期 |
| 07-16 01:58–02:01 UTC | **109 item 一括削除 + アカウント無期限 block** |

block の理由は "Promotion-only account: Promoting Tatsuya Shimomoto"。つまり「宣伝専用アカウント」判定です。削除ログの理由は "Spam / advertising: Mass deletion"。この判定は今でも誰でも検証できます。

```bash
# 2026-07-16 の一括削除ログから、対象アカウント関連の削除件数を数える
curl -s "https://www.wikidata.org/w/api.php?action=query&list=logevents&letype=delete&leuser=The%20Squirrel%20Conspiracy&lelimit=500&format=json" \
  -A "audit/1.0" | python3 -c "
import json,sys
evs = json.load(sys.stdin)['query']['logevents']
mine = [e for e in evs if 'Shimo4228' in e.get('comment','')]
print(len(mine))  # → 109
"
```

block の理由の文言も、block 一覧 API でそのまま取れます。

```bash
# 現在有効な block の対象・日時・理由を取得する
curl -s "https://www.wikidata.org/w/api.php?action=query&list=blocks&bkusers=Shimo4228&bkprop=user%7Cby%7Ctimestamp%7Creason&format=json" \
  -A "audit/1.0" | python3 -m json.tool
```

なお Wikidata API は User-Agent なしのリクエストを 403 で弾くので、`-A` の指定が必要です。

## 原因: 判定は編集単位ではなくアカウント単位

機械的な検証(出典の有無、制約チェック、スキーマ妥当性)が測るのは**編集 1 件ごとの技術的妥当性**です。一方、Wikidata の人間の管理者が見るのは**アカウントの投稿履歴全体が描くパターン**でした。

私の 109 entry は、著者・著者の作品・著者の論文・著者の論文が引用する文献、と種類は分かれていても、**すべてが一人の人物を指す網**を描いていました。初見の管理者がこの履歴を開けば、個別編集の丁寧さとは無関係に「宣伝専用」に見えます。

実際、block 通知に個別編集への違反指摘はひとつもありません。判定の粒度が違うのです。

もうひとつ、発覚のタイミングを決めたのは速度だったと読んでいます。block の約 10 時間前の深夜、私は skeleton 19 item の新規作成と引用辺の一括同期を実行していました。その最中、エージェントから「一部の item が投稿できない」という報告が繰り返し上がっていました(当時のログは残っていないので、ここは著者の観測です)。

「Wikidata 側の一時的なサーバーエラーかもしれない」という見立てで、時間を置いて投稿を再開しました。投稿は通り、「サーバーが正常に戻ってよかった」とすら思いました。その翌朝が block です。

管理側が何を検知したかの記録は私には見えないので、速度と発覚の因果は証明できません。ただ、教訓としては断定側に倒すべきでした。非 bot アカウントがスロットル上限に張り付く行動は、新規作成フィードや編集速度のパトロールで最も目立ちます。

レートリミットの連発は「時間を置けば直る障害」ではなく「その速度と量はそのアカウント種別にとって異常だ」という**警報**として扱い、その場で止まって見直すべきでした。エラーが解消して投稿が通ったのは「正常化」ではありません。パトロール面に最も目立つ行動を、再開しただけでした。

振り返ると、承認の仕方にも穴がありました。19 item の作成を「一括同期を実行してよいか」という 1 回の判断で通していたのです。1 件ずつなら立ち止まれたかもしれない判断が、一括化で実質 19 分の 1 に薄まっていました。

## 誤解の出所: 「Wikidata は自己登録してよい」はどこから来たか

では、冒頭に書いた「Wikipedia はだめでも Wikidata は許容されている」という理解は、どこから来て、どこで誤りに変わったのでしょうか。出所は 4 つありました。

1. **Wikidata の方針は実際に Wikipedia より緩い。** ガイドラインが自分自身の item の編集を一般に許容しているのは冒頭で見たとおりで、この理解自体は誤りではありません。加えて、学術文献の書誌データを Wikidata に集積する WikiCite のような取り組みでは、研究者が文献データを自分で整備する文化があります。誤りだったのは「個別の編集が許容されている＝アカウント全体でどれだけ積んでも安全」という飛躍です
2. **生存者バイアス。** 削除された自己登録は観測できません。目に入るのは生き残った事例だけです
3. **検証の軸の取り違え。** 私の検証ループは出典・制約・スキーマという技術的準拠だけを測って PASS を出し続けました。「管理者にどう見えるか」という軸は測っていませんでした
4. **notability の誤認。** DOI は自己サービスで採番できる識別子ですが、それを特筆性の論証に使えると誤認していました

そして最も痛い事実はこれです。**私は半分知っていました。** Wikipedia への自己引用は「利益相反の規範違反」として事前に検討して却下済みでした。それでも「散文の百科事典はだめ、構造化データは別」と境界を引き直して実行しました。境界線を引く場所を間違えると、半分知っていても事故は起きます。

## 当日の対応: 撤退を選び、参照を消し、謝罪する

事実確認(上の削除ログ取得)を終えた時点で、最初の分岐は「block 解除を申請するか、撤退するか」でした。

| 選択肢 | 判断 | 理由 |
|---|---|---|
| block 解除の申請(appeal) | **却下** | 仮に通っても、この層は運営側の判断でいつでも取り消せるままです。拒否されたのは実行の巧拙ではなく「自分で自分の権威データを作る」という前提そのものでした |
| 撤退 + 教訓の文書化 | **採用** | 取り消された層への参照を消し、失敗から設計原則を抽出して、二度と同じ経路を選ばない構造を作ります |

撤退で最初にやるべきは、**死んだ参照の除去**でした。私の研究リポジトリ群は機械可読メタデータ(JSON-LD の knowledge graph など)に Wikidata の QID への `sameAs` リンクを埋めていて、その参照先はすべて 404 になっています。

404 への同一性リンクを放置することは、クローラーに対する誤情報であり、皮肉にもスパムの典型パターンの模倣になります。9 リポジトリ + 配信ミラーから、この日のうちに全 QID 参照を除去しました。

除去は雑にやると別のものを壊します。使ったのは「JSON として妥当」と「変化は除去だけ」の 2 段ゲート付きスクリプトです。

```python
# purge_wikidata.py(この日のための一回きりのスクリプト、リポジトリ未コミット)の要点:
# 対象行を除去したあと、2 つのゲートを通してから書き込む
text = "".join(out_lines)
after = json.loads(text)          # ゲート 1: JSON として妥当か
assert after == strip_wd(before)  # ゲート 2: 意味の変化が「除去」だけか
```

:::details 一括除去で実際にハマった 2 点
- **生成スクリプトの中のハードコード**: データファイルから QID を消しても、ページ生成スクリプトに QID が直書きされていて、再生成すると復活しました。生成物を purge するときは生成元を疑う必要があります
- **数値の言い直し漏れ**: リポジトリ内の「ADR は 20 本」のような数値の記述は、人手レビューでは 6 ファイル見落としました。見つけたのはファイル実体を正として全ファイルの数値主張を走査する既存の検証スクリプトです。人手の網羅性より機械の走査が信頼できる場面でした
:::

最後に謝罪です。ここで 1 つ設計判断をしました。**block 解除の要求を含まない、純粋な謝罪だけを talk page に投稿する**ことです。解除要求を添えた瞬間、謝罪は交渉の道具に見えます。

投稿の時点で、Wikidata 書き込みの自動化スキルと API 認証情報の削除は済ませていました(その手順を公開していた連携用リポジトリも同日中に削除しています。研究リポジトリ群そのものは残していて、消したのは書き込み手段です)。「もうやらない」を言葉でなく実態で示せる状態でした。

管理者の判定は公正だったと考えています。この事故がコミュニティに実際に残したのは、109 件を審査して一括削除するという管理者の手間でした。

:::details block 中でも自分の talk page には書ける
サイト全体の編集禁止でも、block のパラメータが自分の talk page の編集を禁止していなければ、ログイン API 経由で自分の talk page には投稿できます(ログアウト状態は IP の自動 block で弾かれました)。投稿は既存の BotPassword を使った一回きりのスクリプトで行い、実行後に認証情報を削除しました。
:::

## 再発防止: 記録は ADR に、行動はルールに

事故対応と並行して、この失敗を「気をつけよう」で終わらせないための固定を 2 つの層で行いました。**判断の記録(ADR)**と、**日々の行動を変えるルール**です。

まず記録の層。ADR が保存するのは「なぜ撤退したか・なぜ二度とやらないか」という判断の理由で、将来のセッションで同じ議論を蒸し返さないためのものです。書いたのは「エンティティの実在証明は自己主権でやる」という 1 本で、骨子は 4 点です。

1. **第三者が統治する層は、取り消され得る前提で設計する** — その層が丸ごと消えても戦略が生きるか。荷重のかかる参照を、取り消され得る層に置かない
2. **他者に作られた言及(earned)だけを祝福し、自己作成(self-created)の経路は選ばない** — 依頼して作ってもらうのも不可
3. **取り消されたら、死んだ参照は速やかに消す。ただし日付付きの歴史記録は書き換えない** — 現在形の主張と歴史の記録は役割が違います
4. **回避しない** — 別アカウント・ログアウト編集・第三者への代理依頼は、統治側との不一致を恒久的な敵対関係に変えるだけです

もうひとつ、対応の順序に原則を置きました。「登るな」という看板は、登ろうとしている側には効きません。効くのは登る手段がそもそも存在しないことです。

だからこの日の対応は、**手段の削除(スキル・認証情報・リポジトリ)→ 仕組み化(ルールへの明文化)→ 言葉(謝罪)** の順で行いました。禁止の強さは「不在 > 仕組み > 看板」の順です。

ただし、**再発防止として実際に効くのは ADR ではありません**。記録は読み返されるとは限りません。行動を変えるのは、実行主体である Claude Code への**指示ファイル**です。エージェントはセッション開始時にルールファイルを自動で読み込んでから作業を始めるので、そこに書いた教訓は「思い出す」必要がありません。今回は 3 つの置き場に分けて書き込みました。

| どこに | 何を |
|---|---|
| 全プロジェクト共通のルール(`~/.claude/rules` — 毎セッション自動読み込み) | 「レートリミットの連発は警報。burst を止めて人間に報告」「N 件の書き込みを 1 決裁で通さない。承認には件数とスコープを明示」 |
| 学習メモ(`~/.claude/skills/learned` — 外部への一括書き込み作業のときに参照) | 実行前に「初見の管理者がこのアカウント履歴を開いたら何に見えるか」を問う(プラットフォーム非依存の自問) |
| 当該プロジェクトの指示ファイル(そのリポジトリで作業するときに読み込み) | 自己登録経路の全面禁止(変種 = 別アカ・匿名・代理も同罪) |

これで「連発したら止まって報告」が、次の深夜に私やエージェントが思い出せるかどうかに依存しなくなりました。教訓が人間の記憶ではなく、エージェントの起動シーケンスに組み込まれた状態です。

なお、hook による強制は見送りました。「外部への一括書き込み」は決定論的に検出できず、誤検知で作業が止まるコストの方が大きいためです。強制は機械的に判定できる箇所に限り、判断を要するものはルールと問いの形で残す。この線引き自体も再発防止設計の一部です。

## まとめ: 効果と経路を分けて考える

この事故が教えるのは「Wikidata は無意味」ではありません。**効果と経路は別物**です。

- **効果**: Wikipedia のようなオーソリティ面での被言及が AI の引用に効くことは、複数の実測が支持しています。Wikidata への期待はその延長線上にあります(ただし Wikidata 単体の効果の実測は薄い、というのが調べた範囲の正直なところです)
- **経路**: その言及を**自分で作る**(self-created)経路は、個々の編集が許可されていても、アカウント単位の統治判定で全損し得ます。私の場合は全損しました。だから私は、**他者に作られる**(earned)言及だけを頼る方針に切り替えました

GEO 文献は効果を語りますが、経路の区別まで教えてくれるものはほとんどありません。私の 109 item はその区別の授業料でした。

外部プラットフォームへの一括書き込みを計画している人は、実行前にこの 5 問を通してみてください。

- [ ] このアカウントの履歴 + 今回の書き込みを合成すると、初見の管理者には何に見えるか
- [ ] 書き込み対象が自分・自分の作品・自分への参照に偏っていないか
- [ ] 件数とスコープを承認時に明示したか(N 件を 1 決裁で希釈していないか)
- [ ] レートリミットのエラーが出始めたら停止する条件を決めてあるか
- [ ] この層が丸ごと取り消されたとき、何が壊れるか列挙したか

私の手元には今、earned の経路しか残っていません。他者に引用されるだけの内容を作り、実際に AI に引用されたかを測る。近道が消えただけで、それは本来の出発点だったはずです。

自己登録なしで AI からの引用に届くのか — 図らずも、この事故がその実験条件を作りました。
