2026年10月、個人サイトをClaude Code（Opus 5.5）で作りました。骨格はすぐにできました。そこから半日、ずっと細部を詰めていました。日本語の見出しの先頭に来るかぎ括弧を本文の端の外に出すこと（ぶら下げ）、行頭に来てはいけない文字（行頭禁則）、英語の段落や見出しの最後の行に1語だけ残ること、リンクの下線の深さ、暗い配色でのコントラストです。神は細部に宿るという視点を大事にして、細かな点まで詰めてほしいと頼むと、Opus 5.5は直してくれました。専門家役のレビュアーにも読ませて、指摘は数十件になりました。

ただ、日本語の組版も、アクセシビリティも、私の専門外です。どこを見ればよくて、何をもって良しとするのかを、私は知りません。

そこで、仮説を立てました。専門外の分野でも、細部を要素に分け、要素ごとの評価基準をリサーチして設定できれば、要素に1つずつ当たることで、専門知を高いレベルで組み立て直せるのではないか。

この仮説を手順にする設計をモデルに頼むと、最初に、サイトの検査スクリプト（`eval/run.mjs`）の中身が報告されました。入っていたのは、HTMLの妥当性、画面からのはみ出し、最後の行の1語残り、axeによるアクセシビリティの検査といった、どのサイトにも当てはまる検査だけでした。禁則も、ぶら下げも、検査になっていません。半日かけて直した細部の多くは、次にCSSを変えたときに崩れても、誰も気づかない状態でした。この記事は、その仮説をサイトで試した記録です。

## 専門家が知る、要素と測り方

専門家は、物事の構成要素がわかっています。だから、何をいじればどう変わるかがわかり、どう評価すればいいかもわかります。この3つを、専門外の私の側で書き出せれば、専門家と同じところを見られるはずです。

そこで、細部を規則1つ分の大きさの要素に分け、その要素を単位と呼ぶことにしました。単位には次の4つを書きます。初めの3つが専門家の3つに当たり、4つ目をそこに足します。

- `what` — 何の規則か
- `cause` — 何を変えれば動くか
- `eval` — 出力にどう現れるか
- `why` — その規則が読者に何をするか

サイトの単位を1つ、主な行だけ示します。日本語の見出しがかぎ括弧で始まるとき、かぎ括弧を本文の端の外に出し、次の文字を端にそろえる、という規則です。

```yaml:eval/units.yaml
- id: ja-quote-hang
  field: Japanese typesetting
  what: In a quoted section title the first letter after 「, not the mark, sits on the column edge, on every line of the title.
  why: The quoted phrase reads as a lemma aligned with its gloss; a mark that juts or a letter that sits in reads as an error.
  eval:
    judge: machine
    check: ja-quote-hang
    expect: first letter within 0.5px of the content edge, at 375 and 1280, in the author's font (Hiragino on macOS)
  cause: ".section-title:lang(ja):has(> q:first-child) { text-indent }, :lang(ja) { text-spacing-trim }"
  status: frozen
```

`expect`は、かぎ括弧の次の文字が端から0.5px以内にあることです。幅375pxと1280pxの両方で、ヒラギノで測ります。`cause`は、それを動かすCSSの場所です。

評価基準は、私の頭からは出しません。外にある基準の文書から取ります。日本語組版なら[JLReq](https://www.w3.org/TR/jlreq/)（W3Cがまとめた日本語組版処理の要件）、アクセシビリティなら[WCAG](https://www.w3.org/TR/WCAG22/)です。基準を持って読むのは、レビューのたびに新しく立ち上げるレビュアーです。日本語の組版、英語の組版、アクセシビリティ、アートディレクションの4役で、それぞれがビルドしたページを実際のブラウザ（Chrome）で測ります。レビュアーには、過去の指摘と単位の一覧を見せません。答えを持っている読み手は、同じ指摘を繰り返すからです。

日本語組版のレビュアーの指摘は、たとえば次の形で返ってきます。

```text
3. fix — the Latin–Japanese space in running text is 0.33em (the Hiragino space); JLReq's default is a quarter em.
   Fix body:lang(ja){word-spacing:-0.08em} with display lines reset → 0.25em.
```

和文と欧文の間の空きが0.33emで、[JLReqの既定は1/4em](https://www.w3.org/TR/jlreq/#handling-of-western-text-in-japanese-text-using-proportional-western-fonts)、という指摘です。私には、この差を目で見つけることはできません。ただ、基準がJLReqにあることと、測った値がそこからずれていることは、確かめられます。

## 細部を、赤になれる検査に

単位は、直したら検査にして凍結します。凍結した検査は、1つのコマンドで全部走り、崩れていれば赤、守られていれば緑になります。いまは私のMacで回していて、CIにはまだ入れていません。レビュアーの指摘から直すものを選んで採り、直して、凍結するまでを1ラウンドとして、これを繰り返します。終わりの目安は、新しく採る指摘が0になるラウンドです。

ja-quote-hangを例に、1つの単位がどう凍結されるかを追います。最初にサイトで単位を作って回したとき、Opus 5.5はかぎ括弧のぶら下げのずれを新しい不具合として見つけ、直しました。直した後のスクリーンショットを見て、私は「これ古いバージョンのサイトじゃない？」と返しました。その回は、公開版より古いブランチで回っていました。公開版では、そのずれはもう直っていました。単位は、公開版の上でしか意味を持ちません。

公開版の上で回し直すと、この単位は、今度は別の理由で赤になりました。375pxと1280pxの両方で、かぎ括弧の次の文字が端から+0.84pxの位置にありました。見出しには0.04emの字間を付けていて、その字間が、外に出したかぎ括弧にも付いていたのです。かぎ括弧の字間だけを0にすると、ずれは+0.0pxになりました。

直したら、その検査が本当に効いているかを確かめます。原因をわざと小さく壊してビルドし、全部の検査を回します。この単位では、かぎ括弧を本文の端の外に出しているCSSの1行を、次のように変えます。

```diff css
- text-indent: -0.5em;
+ text-indent: -0.4em;
```

赤になったのはこの単位だけで、ほかの単位は緑のままでした。これで、この検査がこの規則を測っていると言えます。

壊しても緑のままなら、壊し方か検査のどちらかが、その規則を捉えていません。実際にありました。広い画面で、かぎ括弧で始まる節の見出しを、本文のスクロール中も画面に残す規則は、最初の`sticky`の指定を消しても緑のままでした。後ろの方にある別の規則が、同じ指定をもう一度していたからです。下線の長さの単位も、壊した値の代わりに余白が幅を保ち、緑のままでした。どちらも、検査ではなく壊し方の側の問題でした。前者は効いている後ろの規則を壊すように、後者は原因の指定を一式まとめて壊すように書き直し、赤になることを確かめてから凍結しました。

## 回して、届かなかったところ

レビューは、1回の作業で3ラウンドまでと決めて回しました。その3ラウンドで、新しく採る指摘が0になるラウンドは来ませんでした。どのラウンドでも、7件以上の指摘を新しく採りました。

指摘を受けた修正が、別の細部を2回壊しました。英語のリンク名を途中で改行させない修正は、改行しない空白を使っていました。英文書体のCharterでは、その空白が普通の空白のちょうど2倍の幅で作られていて、単語の間が倍に開きました。英語の作品紹介の行の最後に1語だけ残らないようにする修正は、日本語の紹介の行にも効いてしまい、語の途中で行が切れました。どちらも、次のラウンドのレビュアーが見つけ、新しく採る指摘に加わりました。それからは、修正の範囲を、指摘が名指した言語とページに限っています。

## 任せた判断が、Safariで覆った

レビュアーには決められない、好みの判断も残りました。下線の深さ、スクロールで文字を薄くする度合い、暗い配色の緑の彩度などです。最初は1件ずつ決めようとしましたが、途中で「全部あなたの推奨でやっといて」と任せました。仕上がりを見て、「全体的にクオリティー感が上がってプロっぽくなった」と思いました。

そのあと、私はSafariで自己紹介のページを開き、こう書きました。「aboutの日本語ページだけ改行位置変じゃないか？（の後に改行したり、M1MAc上の　の後に改行したり、あと文の幅がまちまちなのも変な感じがするけど」。2か所の「の後」は、それぞれ始め丸括弧の直後と、「M1 Mac上の」の直後を指します。任せた判断のうち2件を、ここで覆しました。

1件目は、日本語の紹介文を、見出しと同じく、日本語の文字の間では改行しない指定にしたことです。紹介文で改行できる位置は、「上の」の後のように前もって決めておいた所だけになり、それでも行からあふれる所では、ブラウザが無理に改行しました。Safariでは、その無理な改行が始め丸括弧の直後に来ていました。凍結した検査はChromeでしか走っておらず、Chromeでは始め丸括弧が次の行に送られていたので、検査は緑でした。紹介文は普通の地の文に戻しました。2件目は、日本語の地の文を両端揃えにせず、行末を不揃いのままにする判断です。Safariで読むと行の幅がまちまちに見えたので、画面の幅が30rem（480px）以上のときは両端揃えにしました。

覆った2件は、私に聞かずに決めたから覆ったのではありません。私が読む環境で見ずに決めたから覆りました。

そこで、凍結した単位を全部、Safariのエンジン（WebKit）でも回しました。Chromeで緑だった49単位のうち、7単位が赤になりました。

- 2単位は、測り方の違いでした。WebKitは行頭の文字の位置を尋ねると前の行の末尾の位置も返し、SafariのTabキーは既定ではリンクに止まりません。検査の側を直しました
- 2単位は、エンジンによる描き方の差でした。許容幅を広げました
- 3単位は、Safariで実際に崩れていました。サイトを直しました

これで、凍結した49単位は、Chromeでは全部、WebKitでは、検査にChromeの開発者向けの仕組み（CDP）が要る1単位を除く48単位が緑になりました。49単位のそれぞれを壊す、54通りの壊し方がリポジトリに残っています。記録した単位は全部で56あり、残りは、検査を置かずに私が目で読む5単位と、まだ検査のない1単位、使わなくなった1単位です。

## 決めたこと、決めていないこと

仮説は、ある程度成立したと思います。専門外の組版とアクセシビリティを、私は単位に分けて、外の基準で測りました。サイトはシンプルながら、クオリティー感のあるものになりました。

この経験から、決めたことが3つあります。

1つ目は、任せるなら途中で止めず、完成形まで回してもらうことです。モデルが私の代わりに決めたことのうち、影響の大きいものだけを見せてもらい、私は完成物を見て判断します。ただし、モデルが決めるときは、私が読む環境で測ってもらいます。私はSafariで読むので、WebKitでも測ります。

2つ目は、全体の印象を検査にしないことです。ページ全体の見え方、余白のリズム、各節の導入文が中身を言えているかなどの5単位は、検査を置かず、私が読むものとして残しました。全体の印象にモデルが点数を付けても、その数字では何を直せばいいかがわからないからです。

3つ目は、この手順を、サイトだけでなくコードと文章にも使うことです。サイトで回していた手順は、途中からClaude Codeの4つのスキルにしていました。

- detail-review — レビュアーを立ち上げて指摘を集める
- detail-units — 指摘を単位に分ける
- unit-eval — 単位を検査に凍結する
- detail-loop — それを順に回す

この4つを、コードと文章にも使える形に直しました。そして、この記事でも試しています。文章では、detail-loopが直すのは表記、用語、リンク、コード、図といった見せ方で、言い回しと主張を変える案は、任されていても私への提案として返ってきます。この記事では、その提案の採否も任せました。仮説と、それがある程度成立したという評価は、私が決めています。

決めていないこともあります。新しく採る指摘が0になるラウンドには、まだ届いていません。検査が守るのは、これまでに見つけた細部だけです。まだ見つけていない細部は、レビューでしか見つかりません。
