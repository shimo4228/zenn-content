Claude Code のハーネス（スキル・ルール・エージェントを構造化した実行環境）を整理する過程で、「AIハーネスツールは構造的に収益化が難しい」という結論に辿り着いた。33個のスキルを16個に整理し、ECC（Everything Claude Code、コミュニティ主導のスキル・エージェントパッケージ）の内部構造を解析した記録。

## スキル抽出の4手法を全部試した

Claude Code でスキル（再利用可能な行動パターン）を抽出する手法は4つある。全部試して分かったのは、最高品質は対話で、セーフティネットとして learn-eval を残すのが正解ということだ。

### 比較表

| 手法 | ソース | what | why | 品質 | 頻度 |
|------|--------|------|-----|------|------|
| **skill-create** | Git履歴 | ○ | × | 低 | 1回きり |
| **learn** | セッション全体 | ○ | △ | 低〜中 | 毎セッション |
| **learn-eval** | セッション + 自己評価 | ○ | ○ | 中〜高 | 手動 |
| **対話** | 議論の中で | ○ | ○ | 高 | 自然発生 |

要点だけ書く。skill-create は Git 履歴から「何が変わったか」（what）しか取れず「なぜそうしたか」（why）が欠落する。learn は品質ゲートなしで毎セッション自動抽出し、48件に膨れた。learn-eval は自己評価ゲートを通すのでゴミスキル率が ~60% → ~10% に改善した。しかし最高品質は対話の中で自然にスキル化の必要性が浮かび上がるパターンだった。learn-eval は「拾い漏れ防止のセーフティネット」として残す価値がある。

## ハーネス整理 — 33スキルを16に

Claude と対話で1個ずつ評価した。

| 指標 | Before | After |
|------|--------|-------|
| スキル数 | 33 | 16 |
| コマンド数 | 47 | 22 |
| エージェント数 | 18 | 11 |
| ECC プラグインエントリ | 71 | 0 |
| 削除行数 | — | 16,000+ 行 |

ECC プラグインを無効化し、ローカル管理に一本化した。

### ECC v1.9.0 の内部解析

v1.9.0 の「選択インストール」を内部解析した。

- `--with lang:python` と `--with lang:typescript` が同じモジュールに解決される
- 実際の選択粒度は19モジュール単位。スキル単位の取捨選択は不可能
- プロファイル5種は事前定義の固定セット

```
ユーザーが期待するもの: 「Python だけ入れたい」
実際に起きること: 全言語スキルが丸ごと入る
```

### 対話的スキル選択の優位性

v1.9.0 の Python 関連差分6候補を対話で1個ずつ評価した例:

1. pytorch-patterns → PyTorch 使ってない。不要
2. pytorch-build-resolver → 同上
3. documentation-lookup → Context7 既に動いてるが、スキルで変わらない
4. data-scraper-agent → Gemini Flash 前提。特定スタックに寄りすぎ
5. prompt-optimizer → ECC 全コンポーネント前提。プラグイン削除した今は合わない
6. ai-regression-testing → AI盲点の回帰テスト。概念が言語非依存で実用的

採用: 6のみ。CLI の `--with lang:python` では6個の個別評価は不可能だ。

### continuous-learning v2 は動いていなかった

ECC の目玉機能、observer-loop + instinct学習 + confidence scoring。少なくとも自分の環境では、初期から動作せず有効な学習結果を生成しなかった。残骸として365行のスキル + 2.8MBの observations.jsonl + 48プロジェクトファイル + 12コマンド。全て削除した。

## AIハーネスツールの構造的限界

整理を通じて見えたのは、ECC 固有の問題ではなく、AIハーネスツールという形態自体の構造的限界だ。

### 知識の最適な配布形態は Markdown

ハーネスの価値は知識の構造化（スキル、ルール、ベストプラクティス）にある。しかしその知識の最適な表現は Markdown だ。LLM が直接読める。ツールで包む層がなくても、`.md` ファイルを配置するだけで機能する。

課金ポイント（CLIツール、インストーラー、状態管理）はユーザーがスキップできる層に位置している。

### 参入障壁の消失

```
従来: アイデア → 実装（数ヶ月）→ プロダクト → 囲い込み → 課金
AI時代: アイデア → 実装（数分）→ 誰でもコピー可能
```

アイデアを聞いた瞬間に実装できるなら、ツールで囲い込む意味がない。

### 砂時計型の価値構造

「コードがビジネスにならない」のではなく「コードだけではビジネスにならない」。

- **上**: 何を作るかの判断、ドメイン知識、ユーザー理解 → 残る
- **中**: 実装レイヤー → 価値がゼロに近づく
- **下**: データ、インフラ、物理的制約 → 残る

ECC の116スキル分の知識は「上」に属する価値だが、CLIツールという「中」の層で課金しようとしている。ミスマッチだ。

### LLM の進化と順行する設計 vs 逆行する設計

LLM が賢くなると不要になるもの:
- 具体的な手順書（「pytest の fixture はこう書け」）
- コード例のカタログ
- フォーマット/lint のスキル
- **ECC の116スキルの大半がここに属する**

LLM が賢くなっても残るもの:
- 「いつ棚卸しすべきか」の判断基準
- 「何を忘れ、何を覚えるか」の原則
- 「対話で決める」というプロセス設計

ハーネスツールのビジネスは、LLM の進化に逆行する商品を売っている。

### Scaffold Dissolution — 足場は溶ける

AKC（[Agent Knowledge Cycle](https://github.com/shimo4228/agent-knowledge-cycle) — 調査→抽出→整理→昇格→計測→保守の6フェーズで知識を循環させるアーキテクチャ）のスキル群を明示的に呼ばなくても、対話の中でサイクルが自然に回ることを発見した。

スキルは足場だ。サイクルが身体化されると不要になる。サイクルの原則をルール（1ファイル）に蒸留すれば、116スキルをインストールする必要すらない。スキルの「配布」自体が価値を持たなくなる。

## 建設的な展望

否定だけで終わらせない。

**残る収益化ポイント**:
- **ランタイムツール**: AgentShield のような実行時セキュリティは、知識ではなく機能。価値がある可能性
- **データ**: 実行統計、スキル使用率、回帰パターンの蓄積
- **スポンサーシップ**: 知識の生産者として支援を受けるモデル。GitHub Sponsors、企業スポンサー

**開放型のアプローチ**:
概念を囲い込まず開放し、DOI で帰属を守る。収益化を前提にしないことで、概念の流通速度を最大化する。認知から直接的な収益ではなく、研究者・実践者としてのポジションを確立する。

ECC の88K+ Stars と30+人のコントリビューターは本物の資産だ。知識の蓄積と認知は実績として残る。そこから直接的な収益に変換する経路が細いだけで、資産自体の価値は高い。
