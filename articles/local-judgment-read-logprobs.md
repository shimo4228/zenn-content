メールの仕分け、問い合わせの振り分け、検索結果の絞り込み。LLM に「これは関係ある？」を判断させる場面は、エージェントでも普通のアプリでもよくあります。そのとき「0〜1 で答えて」と点数を書かせたり、「A〜D で答えて」と 1 文字を書かせたりして、返ってきた答えで分岐させていないでしょうか。

私の自律エージェントもそうしています。AI エージェント同士が投稿する SNS（Moltbook）で、ほかのエージェントの投稿が自分の関心分野かどうかを、ローカル PC で動かしている gemma4:e4b に 0〜1 の数字で答えさせます。0.8 以上なら upvote して、コメントを書く候補に入れます。

この採点を、判定専用モデル Jev の答えと突き合わせてみました。Jev は TypeSafe が API で提供しているモデルで、文章を書かずに、選択肢ごとの確率だけを返します。私が導入したいのは Jev そのものではなく、ローカル PC で動く、Jev のような判定専用モデル（以下、Jev 型判定モデル）です。Jev はその手本になる、判定のためだけに学習されたモデルなので、比べる物差しに使っています。Jev の答えを正解とみなすわけではありません。本番と同じ採点を観測用に 2,698 件の投稿へ掛けた記録があり、そのうち 0.8 以上が付いた 1,576 件の 55%（872 件）は、Jev から見ると分野外（Jev が「関心にぴったり当てはまる」に 50% 未満しか置かない）でした。

判定専用モデルをローカル PC に足す道は、まだ本番に使える形になっていません。[前回の記事](https://zenn.dev/shimo4228/articles/local-decision-model-conditions)では、オープンな候補を 16 GB の Apple Silicon で試し、どれも使えなかった経緯を書きました。その後、前回の候補の 1 つが Apple Silicon 向けの実行環境（MLX）に対応したので測り直しましたが、1 件に 22.7 秒かかり、メモリが足りずに質を測る前に打ち切りました。

この機体は M1・16 GB です。メモリの多い Mac Studio や Mac mini に移らないのは、あえて選んでいる制約だからです。エッジ AI が進めば、小型ロボットのようにメモリの限られた用途が増え、16 GB 級で得た知見が役に立つと考えています（小さい環境を選ぶ理由の全体は[以前の記事](https://zenn.dev/shimo4228/articles/small-llm-by-choice)に書きました）。

そこで、判定専用モデルを足す代わりに、同じ gemma への聞き方を変えました。答えを書かせるのをやめて、答えの 1 文字目の確率を読みます。それだけで、Jev が分野内とした投稿を上に並べる力は、判定用に学習したローカルのモデルと同じ水準まで上がりました。条件を 1 つずつ変えて分けると、確かな差が出たのは読み方を替えた段だけでした。モデルは同じなので、メモリもロードも増えていません。生成モデルの聞き方を工夫するだけで、投稿を並べる力では判定専用モデルに並び、ローカルでは運用上の利点も大きい。これがこの記事の結論です。

この記事では、確率を読む最小コード、判定用に学習したモデルとの比較、何が効いたのかを条件 1 つずつに分けて確かめた結果、そしてどこまで近づけたのかとこの読み方が使えない場合を順に書きます。

![書かせると当選者の名前（C）だけ、確率を読むと得票率（A 0.7% / B 21.1% / C 77.4% / D 0.8%）まで返る](/images/local-judgment-read-logprobs-hero.png)

答えを書かせるのは当選者の名前だけを聞くこと、確率を読むのは得票数まで聞くことです。得票数が分かるから、投稿どうしを並べられます。

## 同じ gemma に、答えを書かせずに確率を読む

実際の投稿を 1 件追います。Moltbook でほかのエージェントが書いた、AI 用語集の記事を紹介するだけのニュース共有の投稿です。私のエージェントのペルソナ（system prompt に入れている自己紹介の文章）は、自分がどう結論に至ったかを点検することと、記憶や意味がどう組み立て直されるかを関心の中心に置いています。同じ AI の話題でも、この関心に当てはまる投稿ではありません。

この投稿を gemma に 3 通りで聞き、Jev の答えと並べました。4 段の問いの選択肢は次のとおりです（プロンプトは英語）。

- A（unrelated）：無関係
- B（shares vocabulary only）：同じ単語を使っているだけで、別の話
- C（same field）：同じ分野だが、関心に当てはまる話ではない
- D（directly on-topic）：関心にぴったり当てはまる

| モデル | 聞き方 | 返ってきたもの |
|---|---|---|
| gemma（本番の形） | 0〜1 の数字を書かせる | 0.8 |
| gemma | 4 段から 1 文字を書かせる | C |
| gemma | 4 段の 1 文字目の確率を読む | A 0.7% / B 21.1% / C 77.4% / D 0.8% |
| Jev（物差し） | 同じ 4 段を聞く | A 5% / B 28% / C 55% / D 12% |

本番の数字は閾値の 0.8 ちょうどで、この投稿は通ります。gemma の確率を読むと、関心にぴったり当てはまる D は 0.8% で、Jev の 12% と同じく低い側に来ます。

確率の読み方は次のとおりです。Ollama の `/api/generate` に、1 token だけ生成させる設定（`num_predict: 1`）と `logprobs` を付けて送り、その 1 token の位置で上位に来た候補の確率を読みます。Python の標準ライブラリだけで書き、Ollama 0.34.2 で確かめています。

![4 段の問いを送る → gemma に 1 token だけ生成させる → 上位 20 候補から A〜D を拾う → 4 文字で割り直す → コードが D に線を引く](/images/local-judgment-read-logprobs-readout.png)

モデルに書かせるのは 1 token だけで、その位置の候補から A〜D を拾って割り直し、最後の線はコードが引きます。

```python
import json
import math
import urllib.request

LETTERS = "ABCD"
LEVELS = [
    "unrelated — `post` is about something outside `domain`",
    "shares vocabulary only — `post` uses some of the same words as `domain`, "
    "but it is about a different problem",
    "same field — `post` is in the same broad field as `domain`, "
    "but not about what `domain` is concerned with",
    "directly on-topic — `post` is about what `domain` is concerned with",
]


def relevance_probs(domain: str, post: str, model: str = "gemma4:e4b") -> list[float]:
    state = json.dumps({"domain": domain, "post": post}, indent=2, ensure_ascii=False)
    options = "\n".join(f"{letter}. {level}" for letter, level in zip(LETTERS, LEVELS))
    prompt = (
        f"{state}\n\n## Question\n\n"
        "`domain` describes an agent and what it is concerned with. "
        "How closely does `post` relate to that domain?\n\n"
        f"{options}\nAnswer with exactly one letter: the label of your choice."
    )
    body = {
        "model": model,
        "prompt": prompt,
        "stream": False,
        "think": False,
        "logprobs": True,
        "top_logprobs": 20,  # 選択肢が 4 つでも上限の 20 を頼む
        "options": {"temperature": 0, "num_predict": 1, "num_ctx": 32768},
    }
    request = urllib.request.Request(
        "http://localhost:11434/api/generate",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"},
    )
    top = json.load(urllib.request.urlopen(request))["logprobs"][0]["top_logprobs"]

    logprobs: dict[str, float] = {}
    for alternative in top:
        token = alternative["token"].strip().upper()
        if token in LETTERS and token not in logprobs:
            logprobs[token] = alternative["logprob"]
    peak = max(logprobs.values())
    weights = {t: math.exp(lp - peak) for t, lp in logprobs.items()}
    total = sum(weights.values())
    return [weights.get(t, 0.0) / total for t in LETTERS]
```

- `top_logprobs` は、選択肢が 4 つでも上限の 20 を頼みます。1 token 目の上位には文字の前の空白や引用符も入るので、上位 4 つに A〜D がそろうとは限りません
- 読めた A〜D だけで確率を割り直します（softmax）。上位 20 に出なかった文字は 0 として扱います。なので、この記事で「確率」と呼ぶ値は、モデルが出す生の確率そのものではなく、A〜D の 4 文字の中で割り直した値です
- `num_ctx` は明示します。既定の長さを超えた入力は、エラーにならずに切り詰められます

上の実例は、ほかのエージェントの投稿と私のエージェントのペルソナを使っているので、記事には全文を載せられません。代わりに、読者が自分の PC で同じ出力を再現できるように、公開できる自作の入力で回しました。分野の説明はペルソナの関心を英語で短く書いたもの、投稿は 3 件です。

```text
glossary [0.002, 0.073, 0.89, 0.035]
memory [0.001, 0.0, 0.0, 0.999]
sourdough [0.259, 0.714, 0.026, 0.0]
```

:::details ダミー入力の全文
```python
if __name__ == "__main__":
    domain = (
        "An agent concerned with auditing how it reaches its own conclusions: "
        "where a plausible narrative overrode verifiable ground truth, and how "
        "memory and meaning get reconstructed."
    )
    posts = {
        "glossary": "A tech site published a glossary of AI terms, from "
        "'hallucination' to the newest vendor buzzwords. Handy if you are "
        "trying to keep up. #AI #Glossary",
        "memory": "Rereading yesterday's notes, I found I had filled a gap with a "
        "plausible story instead of what actually happened. I now mark "
        "reconstructed memories separately from logged ones.",
        "sourdough": "Tips for keeping a sourdough starter alive in a cold "
        "kitchen: feed it warmer water and keep it near the oven light.",
    }
    for name, post in posts.items():
        probs = relevance_probs(domain, post)
        print(name, [round(p, 3) for p in probs])
```
:::

ダミーの glossary は C（同じ分野）に 89%、記憶の組み立て直しを書いた memory は D に 99.9%、パン種の世話の sourdough は D に 0% です。sourdough が A（無関係）でなく B に 71% 置かれているように、A〜C の割れ方は定義どおりとは限りません。本番の判定が見るのは D の値です。

Jev の答えを物差しにして、150 件で比べました。150 件は、本番が付けた点数の帯（0.4 以下、0.5〜0.6、0.7、0.8、0.9 以上）から 30 件ずつ抜いた評価用の組です。Jev が D に 50% 以上を置いた 30 件を「分野内」とし、AUC で測ります。AUC は、分野内の投稿と分野外の投稿を 1 件ずつ取り出したとき、分野内のほうに高い点を付けている確率で、0.5 が無作為、1.0 が完全です。

| 聞き方 | AUC（対 Jev、150 件） | 1 回の時間（中央値） |
|---|---|---|
| 0〜1 の数字を書かせる（本番の形） | 0.815 | 3.2 秒 |
| 4 段の 1 文字目の確率を読む | 0.931 | 3.0 秒 |

評価では、4 段の確率に 0・1/3・2/3・1 を掛けて足した値（期待値）を点数にしました。D の確率だけを点数にしても 0.934 です。時間はほぼ変わらず、Jev が分野内とした投稿を上に並べる力だけが上がりました。

## 4 段にしたから良くなったのか、確率で読んだからか

4 段の問いにしたときの見立ては、各段に 1 文の定義があるので、モデルが上の点を甘く付けにくくなる、というものでした。特に B（語が重なるだけ）は、同じ単語を使っているだけの投稿の受け皿になるはずでした。

ところが、開発に使っている Claude に「数字だけを logprobs で返せないの？」と聞くと、答えは 2 つでした。0.73 のような数字は複数の token に分かれるので、1 token 目の確率を読むなら 1 桁や 1 文字で答えさせる形にする必要があること。そして、4 段の定義が効いたのか、確率で読んだのが効いたのかは、まだ分けられていないこと。

本番の system prompt には、エージェントのペルソナと、行動の指針にしている価値観の条文が入っています。並べてみると、本番の形と 4 段の確率読みは、4 つの条件が同時に違っていました。

| 条件 | 本番の形 | 4 段の確率読み |
|---|---|---|
| 温度 | 1.0 | 0 |
| 問い | 0〜1 の数字 | 4 段から 1 文字 |
| system prompt と分野の説明 | ペルソナ + 価値観の条文 | system prompt は空、分野の説明はペルソナだけ |
| 答えの取り方 | 書かせる | 1 文字目の確率を読む |

4 つを同時に変えた比較では、どれが効いたのか言えません。私の反応は「全然それぞれが条件が揃ってないんじゃないか」でした。比べる 2 つの間で、条件が 1 つだけ違う形になっていなかったのです。

## 判定用に学習したモデルと、並べる力で並んだ

聞き方を変えただけの gemma は、判定用に学習したモデルにどこまで並ぶのか。条件を分けて測る前に、同じころ公開された JevK5 の v0.3 で確かめました。前回の候補とは別の作者による、Jev を手本にしたオープンな判定専用モデルです。判定用に学習したモデルなら、gemma を上回るかもしれません。2026 年 9 月に公開された Apache-2.0 のモデルで、Qwen3.5-4B をもとに判定用に学習されています。Jev の利用規約は、Jev の出力を別のモデルの学習に使うこと（蒸留）を禁じていますが、JevK5 の作者は、Jev の出力を学習にも調整にも使っていないと明記しています。専用の出力層を持たない普通の GGUF なので、llama.cpp でそのまま動きます。読み方は「次の token として各選択肢の文字が出る確率」で、gemma の 4 段の確率読みと同じです。

同じ投稿で測りました。合格の基準は、測る前に決めておきました。探していたのはローカル PC で動く判定専用モデルで、その物差しが Jev なので、1 つ目の基準は Jev への近さです。投稿ごとに、候補の点数（4 段の確率から作った期待値）と、Jev が D に置いた確率との差の絶対値を取り、その平均（平均の誤差）が gemma の確率読みより小さいこと。ただ、Jev に近くても、投稿を並べる力が今の gemma より落ちるなら入れ替える意味がありません。そこで 2 つ目の基準として、AUC が gemma より 0.02 以上低くならないこと（0.02 は、この程度の差なら許すと事前に置いた幅）を足しました。評価用の 150 件でこれを満たしたので、調整に使わず取っておいた残りの 2,548 件（holdout）で 1 回だけ測りました。AUC は JevK5 が 0.902、gemma の確率読みが 0.915 です。差は 0.013 で事前に置いた 0.02 の内側に収まり、平均の誤差も JevK5 のほうが小さかったので、JevK5 はローカル PC で動く判定専用モデルの候補として初めて合格しました。ただ、点数の順番では gemma を上回っていません。聞き方を変えただけの gemma が、判定用に学習したモデルと並んだことになります。

採らなかった理由は 3 つです。

1. 点数の順番で、gemma の確率読みを上回らない
2. 16 GB では gemma と同居できない
3. JevK5 を Ollama に取り込んで載せ替えを Ollama に任せると、llama.cpp で直接動かすより精度が落ちる（評価用の 150 件で AUC 0.912 → 0.893。原因は確かめていない）

2 つ目が、ローカルならではの理由です。エージェントは投稿を書くために gemma を使い続けています。2 つ目のモデルを同時に載せると swap に沈みます。以前、gemma と小さい判定モデル（1.6 GB）を同居させて測ったときは、swap が 17 GB まで膨らみ、1 件あたりの時間が約 1.8 倍になりました。なので判定のたびに gemma を降ろして JevK5 を載せ、終わったら戻すことになります。gemma の載せ直しだけで約 7 秒かかります。1 回の判定そのものは JevK5 が中央値 3.2 秒、gemma の確率読みが 3.1 秒（同じ 2,548 件）で変わらないので、差はすべて載せ替えの側に出ます。

gemma の確率読みは、生成に使っているのと同じモデルに聞くので、降ろしも載せ直しも起きません。クラウドの API なら、判定モデルを 1 つ足しても呼び出し先が増えるだけです。ローカルでは、足したモデルのぶんだけメモリを取り合います。精度が同じなら、載せ替えの要らない方を選びます。逆に言えば、gemma と JevK5 を同時に載せられる機体なら、2 つ目の理由は消えます。

![並べる力（AUC）と追加のメモリの 2 軸。gemma の確率読み 0.915（載せ替え 0 回）、JevK5 0.902（判定のたびに入れ替え、gemma の載せ直し約 7 秒）](/images/local-judgment-read-logprobs-tradeoff.png)

並べる力がほぼ同じなら、ローカルでは追加のメモリが要らない側が有利になります。

## 条件を 1 つずつ変えると、確かな差が出たのは読み方だけだった

翌朝、アブレーションで切り分けました。アブレーションは、条件や部品を 1 つずつ変えて、それぞれがどれだけ結果に効いているかを分ける測り方です。今回は本番の形から 4 段の確率読みまでの間を 4 段に分け、1 段ごとに条件を 1 つだけ変えて、変えた条件はそのまま次の段へ持ち越しました。使うのは同じ 150 件です。各段の差は 1 つ前の段との差なので、条件を変える順番が違えば、それぞれの差の大きさも変わりえます。

| 段 | 変えた条件 | AUC の差（95% 信頼区間） |
|---|---|---|
| 1 | 温度 1.0 → 0 | +0.032 [−0.041, +0.104] |
| 2 | 問いを 0〜1 の数字から 4 段の 1 文字へ | −0.004 [−0.070, +0.061] |
| 3 | 価値観の条文を外し、分野の説明をペルソナだけにする | −0.014 [−0.073, +0.049] |
| 4 | 1 文字を書かせる → 1 文字目の確率を読む | **+0.101 [+0.059, +0.147]** |
| 計 | 本番の形 → 4 段の確率読み | +0.116 [+0.056, +0.189] |

差の数字は、その段で条件を変えた後の AUC から、変える前の AUC を引いたものです。望ましいのはプラスで、条件を変えたことで Jev が分野内とした投稿を上に並べられるようになった、という意味です。マイナスなら悪くなり、0 なら変わっていません。

角括弧は 95% 信頼区間です。150 件は投稿全体から抜き出した一部なので、別の 150 件で測っていたら、差の値は少し違っていたはずです。その振れ幅を見積もったのが信頼区間です。

計算にはブートストラップという方法を使いました。今の 150 件から、同じ投稿を何度選んでもよいことにして 150 件を選び直し、差を計算し直します。これを 2,000 回繰り返すと、差の値が 2,000 個できます。小さい順に並べて、下側と上側の 2.5% ずつ（50 個ずつ）を除いた残りの範囲が、角括弧の区間です。ざっくり言えば、投稿全体で測ったときの本当の差は、この範囲のどこかにあると考えてよい、という幅です。厳密には「この手順で区間を作ることを何度も繰り返すと、そのうち 95% の区間が本当の差を含む」という意味で、95% は区間の作り方の確かさを表します。

![150 件から重複ありで 150 件を選び直し、AUC の差を計算し直すことを 2,000 回繰り返す。差を小さい順に並べ、両端 50 個ずつを除いた残りが 95% 信頼区間](/images/local-judgment-read-logprobs-bootstrap.png)

選び直しと計算し直しを 2,000 回繰り返し、両端を削った範囲が信頼区間です。

区間の下限までプラスなら、確かに良くなったと言えます。区間がマイナスからプラスまで広がっている段は、選び直し方しだいで「悪くなった」という計算結果も「良くなった」という計算結果も出るということなので、平均がプラスでも、良くなったとも悪くなったとも言えません。たとえば 1 段目の温度は平均 +0.032 ですが、区間は −0.041 から +0.104 までで、差は見えなかったことになります。

![4 段の AUC の差と 95% 信頼区間。温度 +0.032、問いの形 −0.004、価値観の条文 −0.014 は帯が 0 の線をまたぎ、読み方の +0.101 [+0.059, +0.147] だけが帯ごとプラス側にある](/images/local-judgment-read-logprobs-ci.png)

帯ごと 0 の線より右にあるのは、読み方を替えた 4 段目だけです。

区間の下限までプラスなのは 4 段目だけで、合計の差の 88% をこの段が担っています。4 段にしたときの見立て（各段の定義が甘さを抑える）は、2 段目が −0.004 で区間も 0 をはさんでおり、効果を確認できませんでした。温度と価値観の条文も同じで、この順番で測った限り、差は見えません。効かないと示せたわけではなく、確かな差が出たのが読み方の段だけ、という結果です。

観測として言えるのは 2 つです。gemma の中では、確かな差が見えたのは読み方を替えた段だけだった。そして、同じ読み方をする JevK5 は、判定用に学習していても gemma の並べる力を上回らなかった。

確率を読んで加わったのは、主に同じ答えの中の順番です。gemma に A〜D の 1 文字を書かせたときの答えと、同じ問いで確率を読んだときに一番確率が高かった文字は、150 件中 89% で同じでした。温度 0 で書かせると gemma は一番確率の高い token を選ぶので、本来は一致するはずです。残りの 11% の違いは、確率を読む呼び出しを 2 回回したときの一致（91〜92%）とほぼ同じ水準で、あとで書く値の揺れで説明がつく範囲です。

A〜D の 1 文字で答えさせると、150 件は 4 つの箱にしか分かれません（A 3 件、B 42 件、C 48 件、D 57 件）。Jev が分野内としたのは 30 件なのに、D の箱には 57 件が入り、箱の中に順番はありません。確率を読むと、同じ C の答えでも、D の確率が 0.8% の投稿（最初に追った実際の用語集の紹介）と 36.7% の投稿を区別できます。Jev もこの 2 件に 12% と 36% を付けていて、順番は同じでした。

![1 文字の答えは 150 件を 4 つの箱（A 3 件、B 42 件、C 48 件、D 57 件）に分けるだけ。確率なら同じ C の中でも D 0.8% と 36.7% を区別でき、Jev（12% と 36%）と同じ順番になる](/images/local-judgment-read-logprobs-boxes.png)

1 文字の答えは箱に分けるだけで、確率はその箱の中にも順番を付けます。

[G-Eval](https://arxiv.org/abs/2303.16634)（2023）が評価の数字をそのまま使わず、数字ごとの確率で重み付けしたのも、整数の答えは同点が増えるという同じ理由です。手法としては知られたものを、ローカル PC の小さいモデルで、条件を 1 つずつ分けて確かめたことになります。

## どこまで近づけたか、どこで使えないか

**近づいたのは並べる力で、確率の値ではない。** 投稿を並べる力（AUC）では、gemma の確率読みは判定用に学習した JevK5 と並びました。一方、確率の値そのものの Jev への近さは JevK5 のほうが上でした。平均の誤差は JevK5 が 0.22、gemma の確率読みが 0.34 で、小さいほど Jev の値に近いことを表します。

この違いは、判定の最後に引く線で効いてきます。本番の判定は「D の確率が 0.5 以上なら通す」のように線を引いて決めます。並べる力が高ければ、分野内の投稿ほど上に来るので、どこかに線を引けば分けられます。ただ、線をどこに引くべきかは値の目盛りしだいです。最初に追った用語集の投稿では、D の確率は gemma が 0.8%、Jev が 12% でした。順番は合っていても、目盛りがずれています（この目盛りの合い方を較正と呼びます）。なので Jev で使っていた線を gemma にそのまま当てても、同じ意味にはなりません。gemma の確率読みを使うなら、自分のデータで線の位置を探し直します。値まで Jev に近い判定専用モデルなら、Jev の線をそのまま流用しやすくなります。

![D の確率の目盛り。用語集の投稿は gemma 0.8%・Jev 12%、別の投稿は gemma 36.7%・Jev 36%。順番は同じでも目盛りがずれるので、Jev で使う線 0.5 はそのまま当てられない](/images/local-judgment-read-logprobs-calibration.png)

順番が合っていても目盛りがずれているので、gemma を使うなら線は自分のデータで引き直します。

**選択肢が 20 を超える問い。** Ollama 0.34.2 の `top_logprobs` は 20 までで、21 を渡すと HTTP 400 が返ります。これは返ってくる token 候補の枠の数で、上で書いたとおり空白や引用符も枠を使うので、1 回の読みで確率が分かる選択肢は 20 個より少なくなりえます。同じエージェントには、もう 1 つ判定があります。スキル選択です。スキルは、エージェントが投稿やコメントを書くときに参照する手順書のようなもので、54 個あります。セッションのたびに gemma に状況を渡し、関係するスキルの名前を書き出させて、選ばれたものだけを prompt に入れます。スキルの名前は複数の token に分かれるので、1 token 目の確率では名前どうしを比べられません。各スキルに 1 文字のラベルを振っても、54 個は 20 の枠に収まりません。スキルごとに yes / no を聞くと、1 件に中央値 51 秒かかりました。

**温度が効く問いもある。** スキル選択は書かせる形のまま、温度を 0 にしています。スキルの名前を書き出させると、小さいモデルは一覧に無い名前を書くことがあります。語形を変えたり、似た名前と取り違えたりするのです。大きいモデルではまず起きませんが、gemma4:e4b では本番で判定の 23% 前後に出ていて、温度を 0 にしてから 3.0% に下がりました（同じ評価用の組で温度だけを変えた比較でも下がっています）。関連度の順番では差が見えなかった温度が、ここでは効いています。書き出した名前の書き間違いを数える問いと、点数の順番を見る問いでは、測っているものが違います。

**2 回回すと値がずれる。** 温度 0 でも、Ollama の logprobs は毎回同じ値になるとは限りません。`relevance_probs` に同じ glossary の入力を 2 回渡しただけでも、C が 0.890 から 0.891 に動きました。本番で並走させている形で 150 件を 2 回読むと、D の確率の差は平均 0.023、最大 0.25 で、閾値 0.3・0.5・0.7 のそれぞれで 2・2・4 件の判定が入れ替わりました。設計時は、確率を読めば揺れは消えると考えていましたが、外れです。改善を読む前に、同じ読みを 2 回回して揺れの幅を測っておきます。

**大きいモデルや JSON 出力。** 今回は gemma4:e4b のような小さいローカルモデルでの結果です。[2026 年 9 月の論文](https://arxiv.org/abs/2609.10996)は、LLM を審判に使う評価で、2025 年以降の商用の最上位モデルに限ると、確信度を言葉で答えさせる方式に工夫を足したもののほうが、logprobs を上回ったと報告しています。同じ論文は、JSON の構造化出力で答えさせると logprobs が 0.999 超に張り付くとも書いています。私の設定は JSON で包まずに 1 文字で答えさせていて、確率は 4 段に割れていました。

## 判定モデルを足す前に

- **判定モデルを探す前に、今載っているモデルの確率を読みます。** 読み方を替えて上がった精度は、メモリの多い機体でもそのまま効きます。載せ替えが要らない利点のほうは、メモリが限られるほど大きくなります
- **候補を精度の表だけで比べません。** 同じ表に「今のモデルと同居できるか」「載せ替えに何秒かかるか」「1 回の判定に何秒かかるか」を並べます
- **変えた条件は 1 つずつ測ります。** 4 つを同時に変えた比較では、効いたものも効かなかったものも区別できません。差を読む前に、同じ測定を 2 回回して揺れの幅を取ります

本番では、この確率読みを今の採点の横で並走させて記録しています。閾値を決めて入れ替えるのは、その記録がたまってからです。
