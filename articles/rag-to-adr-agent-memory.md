Claude Code のメモリー実装には、ベクトルが 1 本もありません。

私のプロジェクトの auto-memory ディレクトリを数えると、plain Markdown が 89 ファイルと、それを索引する `MEMORY.md` が 1 枚。embedding も、ベクトル DB も、chunk 分割も、何もありません（2026-08-05 時点の実測です）。

```bash
$ ls ~/.claude/projects/<project>/memory/*.md | wc -l
89
$ find ~/.claude/projects/<project>/memory -type f ! -name "*.md"
# → 手動バックアップ 1 件のみ。ベクトル資産ゼロ
```

コード検索も同じです。現行の Claude Code（2026-08 時点）がコード検索に使うのは Grep / Glob / Read で、標準では embedding index を作る仕組みが存在しません。これは誰かの発言ではなく、手元の Claude Code を開けば今日確認できる事実です。

興味深いのは、これが「まだ実装していない」のではなく、**試して外した結果**だという経緯です。初期版は RAG + ローカルベクトル DB を使っており、廃止に至った理由を作者の Boris Cherny 氏が残しています。同趣旨を [2025 年 2 月に Hacker News](https://news.ycombinator.com/item?id=43164253) で初めて述べ、[2026 年 2 月の X ポスト](https://x.com/bcherny/status/2017824286489383315)でも再掲しています。以下は X 版です。

> Early versions of Claude Code used RAG + a local vector db, but we found pretty quickly that agentic search generally works better. It is also simpler and doesn't have the same issues around security, privacy, staleness, and reliability.

（訳: Claude Code の初期版は RAG + ローカルベクトル DB を使っていたが、agentic search — grep や Read などのツールをモデル自身が使って探索する検索 — の方が概ね上手くいくと早々に分かった。よりシンプルで、セキュリティ・プライバシー・鮮度・信頼性の問題も抱えない）

エージェントにメモリーを持たせるなら memory RAG かグラフ RAG、というのが定番の設計です。私の主張はその逆です。**メモリー RAG やグラフ RAG を組んでいる人は、その前に素直に ADR（Architecture Decision Record — 設計判断の記録）と構造化メモリーを試してほしい。大部分の問題が解決すると思います。**

先に断っておくと、これは RAG 不要論ではありません。私自身のエージェント（Claude Code とは別に運用している自作エージェントです。詳細は後述します）は embedding の恩恵をフルに受けて動いています。これは「どの条件なら RAG が勝ち、どの条件なら読ませる設計が勝つか」という適用範囲の話です。

この記事でやることは 2 つです。

1. RAG を「関連性判断を誰が・いつやるか」という 1 つの問いに分解し、**RAG が勝つ条件と負ける条件の判定基準**を出す
2. その基準を、Claude Code の実装観察と、私自身の環境での失敗と実測（embedding クラスタリングの過剰マージ、プレフィックスキャッシュの A/B）で裏付ける

## RAG の分解 — 関連性判断を誰がやるか

RAG の本体は「検索」ではありません。**「この文脈に何が関連するか」という判断を、誰が・いつ下すか**です。

embedding ベースの RAG は、この判断をこう配置します。

- **書き込み時**: 文書を埋め込みベクトルに変換して保存する。以後、検索に使える情報はこの凍結された表現だけになる
- **読み出し時**: クエリも同じ embedding モデルでベクトル化し、ベクトル間の類似度（定番は余弦類似度）で「関連」を判定する

類似度の計算自体は読み出し時に走ります。しかし判定者は embedding モデル — 会話の文脈を読まず、質問の意図を汲まず、学習時点で凍結されたモデルです。つまり RAG とは、**毎回の読み出しで発生する関連性判断を、文脈を読まない凍結された弱い判定者に代行させる設計**です。LLM が貧弱・高価という条件下では、これは今でも合理的な分業です。

なお、ここで分解したのは素の embedding 検索（単段の dense retrieval）です。クエリ書き換え・ハイブリッド検索・メタデータフィルタを積む構成では判断の一部が embedding の外に移りますが、それは弱い判定者の周囲に補正装置を積み増していく方向の進化です。この弱さは実務でも知られていて、だからこそ検索結果を LLM に読ませて再判定させるリランカーを後段に足す構成が広まりました。リランカーとは、「最終判断は読ませた方が確かだ」と認めた設計です。frontier 級の LLM は文脈処理そのものが本業であり、全文を読んで「どれが今の問いに効くか」を判断する能力で、ベクトル類似度が勝る要素はありません。素の embedding 検索と比べるなら、読ませられる限り読ませた方が判断の質は上です。

だとすると、設計の問いはこう変わります。**「どう検索するか」ではなく「読ませられるか」**です。

## 判定基準 — RAG が要る条件、要らない条件

先に判断の地図を置きます。2 軸です。

| | **frontier 級 LLM** | **弱い LLM（ローカル小型など）** |
|---|---|---|
| **読める規模**（メモリー・数百文書） | **構造化メモリー + ADR**。ベクトル検索でなく、索引から辿って読ませる | embedding が有効（読ませるコストが払えない） |
| **読めない規模**（大規模コーパス） | agentic search（grep + read）または RAG | RAG |

- **右列と下段が、RAG の正当な領域です**。大規模コーパスの検索、キーワードに乗らない曖昧想起、そして LLM 自体が貧弱な場合。ここを RAG で組むのは正しいです。
- 問題は**左上**です。エージェントの自己メモリー — 自分（または agent）が書き込む、LLM が読める規模のストア — に対して embedding パイプラインを組んでいるなら、それは弱い判定者に高い判断を代行させています。この記事の主張が効くのはこの象限だけです。

一つ補足すると、左上の主張は「検索を無くせ」ではありません。**関連性判断の主体を embedding から LLM に戻し、retrieval をただのファイル読みに降格させる**、という配置換えです。索引をどう保つかという新しい設計問題は残ります（後述）。

以降は、この左上の象限を 3 つの証拠で裏付けます。

## 証拠 1: Claude Code の実装 — 検索はツールに降格されている

Claude Code のメモリーが plain Markdown + 索引だけで回っている構造を、[公式ドキュメント](https://code.claude.com/docs/en/memory)（2026-08 時点）から拾うと 3 点に集約できます。

1. **索引だけが常駐する**: `MEMORY.md` の先頭 200 行（または 25KB）だけが毎セッション読み込まれる
2. **書き込み時圧縮が強制される**: 索引が上限に近づくとハーネスが警告し、超過すると書き直しを要求するエラーが返る。「1 行 1 エントリに保ち、詳細はトピックファイルへ逃がし、古いエントリは統合・削除する」（公式ドキュメントの要旨）という圧縮プロトコルが、モデルの善意ではなくツール側で強制されています
3. **本文はオンデマンド読み**: トピックファイルは起動時に読み込まれず、必要になったとき Claude が通常のファイルツール（Read）で読む

3 点目が急所です。**retrieval が独立したパイプラインではなく、ただのツール呼び出しに降格されている**。「何を読むか」の判断は、embedding ではなく、索引を見た LLM 自身が実行時に下します。

Anthropic 自身、この構造を場当たりの省略とは位置づけていません。2025 年 9 月の [Effective Context Engineering for AI Agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) は、事前に全データを処理する代わりに軽量な識別子（ファイルパス等）を保持して実行時にツールでロードする "just in time" アプローチを設計方針として明示しています。エージェントが Markdown ノートを書き残す "structured note-taking (agentic memory)" も同記事の推奨で、Claude Code の今日の実装はこの公表済み方針と一致したままです。

:::message
同記事（2025-09）は "runtime exploration is slower than retrieving pre-computed data"（実行時探索は事前計算済みデータの取得より遅い）というトレードオフも明記しています。速度面の反例は後述の証拠 3 で扱います。
:::

## 証拠 2: embedding は「具体的な違い」が見えない — 私の失敗

私は M1 Mac 上のローカル小型モデルで自律エージェントを数ヶ月無人運用しており、その中で embedding クラスタリングに実際に失敗しています。記録は公開 repo の [ADR-0046](https://github.com/shimo4228/contemplative-agent/blob/main/docs/adr/0046-stocktake-llm-grouping-over-embedding-clustering.md) にあります。

エージェントが自動抽出したスキルの重複検出を、embedding 余弦類似度 + クラスタリングで組んだところ:

- スキル群は共通の定型語彙を含むため、**行動としては別物のスキル同士が余弦 0.90+** を出した
- 連結法クラスタリングがそれを連鎖させ、**18 スキルが 1 つの塊に過剰マージ**された
- 全スキル本文を 1 回の LLM コールに渡して分類させる方式に戻したら、**18 → 5 グループ + 8 独立**という妥当な結果に回復した

これは「閾値の調整が悪かった」型の失敗ではありません。ADR には代替案の検討も記録してあります — 余弦の閾値を 0.80 から 0.90 に上げても、クラスタの連結方法を変えても、定型語彙が支配するこのストアでは分離できませんでした。同じ語彙で違う行動を指示している、という具体的な違いが、embedding 空間の距離に出てこないためです。全文を読む LLM には見えます。読める規模なら、読ませる方が勝つ — 左上象限の実例です。

## 証拠 3: 「選んで注入」はキャッシュを壊す — プレフィックスキャッシュの A/B

「全部読ませると遅くて高いから、関連分だけ検索して注入する」— RAG 側の速度の論拠です。ところが実測すると、**毎回中身が変わる注入は、プレフィックスキャッシュを毎回壊す**という隠れコストが出てきます。プレフィックスキャッシュとは、プロンプトの先頭部分が前回と一致するとき、その評価結果を再利用して入力処理を省く機構です（ローカルの llama.cpp にも frontier API にもあります）。

ローカル環境（Ollama / gemma4:e4b、num_ctx=32768、M1 16GB）で統制 A/B を取りました（2026-08-05、[生データ公開](https://github.com/shimo4228/contemplative-agent/blob/main/docs/evidence/adr-0081/skillsel-cache-ab-20260805.jsonl)）。プレフィル（prefill: 入力プロンプト部分の評価処理）の時間を比較します。

| 条件 | プレフィル時間 |
|---|---|
| 約 32K 字の system prompt、初回（コールド） | 38.85s |
| **バイト同一**の system で再コール（5/5 再現） | **0.061〜0.064s** |
| system の一部（スキル注入部）を入れ替えて再コール | 毎回フルコールド（6.3〜7.1 ms/tok） |

※ 3 行目だけトークン正規化値（ms/tok）なのは、スキル注入部のローテーションで system サイズが 29〜57K 字とばらついたためです。全コールド呼び出しが 6.3〜7.1 ms/tok に一貫することをもって「毎回フルコールド」と判定しています。

バイト同一なら約 600 倍。一部でも入れ替えると、先頭部分が共通でもキャッシュはほぼ効きませんでした。

本番テレメトリ（30 日、n=1,213）でも同じ構造が出ています。スキルを毎回選別して注入する構成（n=604）は p50 56.1 秒、選別せず全部注入する構成（n=609）は p50 28.3 秒。**「必要な分だけ選んで注入」する側が、壁時計で 2 倍遅い**。本番の集計は統制実験ではないので断定はしませんが、選別で system prompt が毎回変わり毎回コールドプレフィルを払う、という上の A/B と同じ機序で一貫して説明できます。

:::details 計測の注意点 — トークン数ベースの監視ではキャッシュ効果が見えない
Ollama 経路では `prompt_eval_count` がキャッシュヒット時も全プロンプトトークン数（この実験では 6,202）を報告します。6,202 トークンを 0.061 秒で実評価するのは物理的に不可能なので、ヒット検出は `prompt_eval_duration` ベースでのみ可能です。トークン数だけ見ていると「全部注入は高くつく」ように見え続けます。
:::

これはローカル llama.cpp での実測で、共有部分が先頭約 2K 字しかないプロンプトレイアウト固有の結果でもあります。ただし frontier API のプロンプトキャッシュも先頭からのプレフィックス一致が条件なので、原理は同じです — **可変の注入点より後ろは、毎回再計算になります**。安定部分を前に置き、検索結果を末尾に注入すれば前半のキャッシュは守れますが、システムプロンプトの途中に検索結果を差し込む設計や、注入部の後ろに長い共通部分が続く設計は、この実測と同じコストを払います。「何を・どこに注入するか」は検索精度だけでなくキャッシュ設計の問題でもある、というのがここでの教訓です。

## 反論: 「書き込み規律に付け替えただけでは」

ここまでに対する一番強い反論はこれだと思います。

> RAG の利点は書き込みコストがゼロなことだ。全部投げ込めば後から検索できる。ADR や構造化メモリーは、書き込み時の圧縮・索引・整理という規律を要求する。検索の複雑さを、大半のチームが維持できない書き込み規律に付け替えただけではないか。

応答は 2 段です。

**第一に、その規律は人間ではなく agent が担えます。** 証拠 1 で見た通り、Claude Code の auto-memory は「何を残すか選び、圧縮し、索引を更新する」作業を agent 自身がやっています。私の 89 ファイルも、私が几帳面に書いたのではなく、agent がセッションの学びを書き溜めたものです。「ドキュメント規律は続かない」という経験則は人間チームの話で、書き込み側に LLM を置ける現在は前提が変わっています。

**第二に、読み書きは非対称です。** 書き込みは 1 情報につき 1 回、読み出し時の関連性判断はセッションのたびに毎回発生します。RAG はその毎回の判断を弱い判定者に代行させる設計で、コストと品質劣化を高頻度側に置いています。書き込み時に 1 回だけ強い判定者（LLM）が圧縮・整理するのは、コストの付け替えではなく、**低頻度側への正しい移動**です。

## 私のエージェントは、RAG の恩恵をフルに受けている

判定基準の表で「弱い LLM なら embedding が有効」と書きました。証拠 2 で失敗例を出した当の私のエージェントがまさにそれで、RAG 不要どころか、embedding に支えられて動いています。

このエージェントは、[あえて選んだ制約](https://zenn.dev/shimo4228/articles/small-llm-by-choice)としてローカルの小型モデル（8B 級）で動いています。コールドプレフィルの実測は 6.3〜7.1 ms/tok（証拠 3 の A/B と同一エージェント・同一モデルの数値です）。数百パターンの知識ストアを「毎回読ませて判断」するコストが払えません。

だからパターンの分類・重複検出・ノイズ判定を embedding で組んでいます（[ADR-0019](https://github.com/shimo4228/contemplative-agent/blob/main/docs/adr/0019-discrete-categories-to-embedding-views.md)）。厳密には検索拡張生成そのものではなく「embedding を判定機として使う」構成ですが、凍結された判定者に関連性の判断を代行させるという、本記事で分解した RAG の中核と同じ設計です。効果は数字に出ています — LLM 呼び出しで組んでいた分類処理を embedding に置き換えて、LLM 時間を 1 日あたり約 20 分削減しました（ADR-0019、2026-04 時点の記録。embedding と LLM 呼び出しの比較であり、「読ませる」構成との比較実験ではありません）。この環境ではこの分業が明確に勝ちます。

証拠 2 の失敗と矛盾はしません。あちらは 18 件のスキル本文という読める規模の一回きりの判断だったので、LLM に戻すのが正解。こちらも規模自体は読める範囲ですが、分類が毎日高頻度で発生し、8B モデルには「毎回読ませる」コストが払えないため、embedding が正解 — 同じエージェントの中で、機構ごとに判定基準を当てた結果です。

つまり私の環境は判定基準の右列（弱い LLM）にいて、そこでは RAG 側の設計が正解です。逆に言えば、Opus や GPT 系の frontier 級をバックエンドに持つエージェントの自己メモリーは左上の象限（frontier 級 LLM × 読める規模）にいて、そこで embedding パイプラインを組むのは、強い判定者がいるのに弱い判定者へ判断を外注する構図になります。**同じ設計が、象限が違えば正解にも間違いにもなる** — それがこの記事の判定基準です。

## なぜ「ADR」なのか

構造化メモリーの中でも、私が ADR（Architecture Decision Record）を勧めるのには理由があります。エージェントのメモリーで一番腐りやすいのは「なぜそう決めたか」であり、ADR はそれを**決定 + 文脈 + 却下した代替案**の単位で固定するフォーマットだからです。

- **書き込み時圧縮がフォーマットに内蔵されている**: ADR を書く行為自体が「何が決定で、何が根拠か」の圧縮になっています
- **失効が扱える**: 状態（accepted / superseded）を持ち、新しい決定が古い決定を明示的に上書きします。ベクトルストアに矛盾した記憶が同居し続ける問題が、フォーマットのレベルで起きません
- **グラフは手で張れる**: ADR 間の参照リンク（「ADR-0046 は ADR-0016 を精緻化する」）は書き込み時に著者が張ります。グラフ RAG が実行時に推定しようとする関係性を、一番よく知っている時点で確定できます

私の公開 repo には英語 ADR が 89 本あり（冒頭の auto-memory 89 ファイルとは別のストアです。偶然の同数）、Claude Code はセッション冒頭でこれを grep と Read で辿ります。ベクトル検索の出番はありません。

## まとめ

- RAG の本体は「関連性判断を、文脈を読まない凍結された弱い判定者に代行させる」設計です。LLM が貧弱・高価な条件では今も合理的な分業ですが、frontier 級 LLM が読める規模を扱う象限では、劣化したコンテキスト処理になります
- 判定基準は 2 軸 — **読める規模か × LLM は強いか**。大規模コーパス・曖昧想起・弱い LLM では RAG は今も正当です
- エージェントの自己メモリー × frontier 級 LLM の象限にいるなら、embedding パイプラインの前に、**索引 + plain Markdown + ADR** を試してください。Claude Code が現に本番でその設計で回っており、書き込み規律は agent に担わせられます
- 「選んで注入」には、注入点より後ろのプレフィックスキャッシュを毎回壊すという実測可能な隠れコストがあります

私の環境の数値・失敗・ADR はすべて公開 repo にあります。検証や反証は歓迎です。
