[前回の記事](https://zenn.dev/shimo4228/articles/jev-retrofit-limits)の最後に、私はこう書きました。Jevでスキルを提案するプラグインを、何も足さずログだけを残す設定で動かし、Jevが選んだスキルと、Claude Codeが実際に使ったスキルを突き合わせる、と。

2026年9月21日から1週間動かした結果、Jevがスキルを選んだ539回のうち、30分以内に同じセッションでそのスキルが使われたのは28回でした。私はそれ以上確かめずに、プラグインを外しました。

同じ週、同じClaude Codeには、Jevを使うもう1つのプラグインが入っていました。作業の終わりに「検証せずに完了と言っていないか」を判定して、そうなら止めるプラグインです。これは1週間で8回、Claude Codeの完了を止めました。私が中身を追った2件では、Claude Codeは止められる直前に、私の環境の検証スクリプトを実行し終えていました。

結論を先に言うと、Jevのような判定モデルを部品として組み込んで効果を読めるのは、流れが固定されたパイプラインの中です。次に何をするかをモデルがその場で決めるClaude Codeに後から差し込むと、小さな違いがその後の動きを次々に変えていくので、本来の挙動を損なっているかどうかさえ分かりません。気づかないまま性能が落ちているかもしれないと思うと、表面の数字だけでは採用を決められませんでした。

![上段は流れが決まっているパイプラインで、資料、Jevの判定、LLMの文章の順に線路の上を進む。下段は運転席のClaude Codeで、後から足したプラグインが完了を止めると、その後の動きが変わりうる](/images/jev-guard-blind-to-local-verify-hero.png)

流れが決まっているパイプラインでは差し替えた部品の前後が変わらず、Claude Codeではプラグインが1回止めるだけで、その後の動きが変わりえます。

## Jevが選んだスキルは、Claude Codeの選択とほとんど重なりませんでした

1つ目のプラグインは、私が作って公開した[jev-skill-router](https://github.com/shimo4228/jev-skill-router)です。ユーザーの発言ごとにJevへ「どのスキルが合うか」を聞き、答えをログに残します。Claude Codeには何も伝えない設定で動かしました。見たいのは、Jevが選んだスキルと、Claude Codeが自分で選んだスキルがどれだけ重なるかです。

1週間で判定は1,242回、そのうちJevがどれかのスキルを選んだのは539回でした。選んでから30分以内に、同じセッションでそのスキルが実際に呼ばれたのは28回、5%ほどです。

Claude Codeは、スキルを自分で選んでいます。一覧を見て、会話の流れから、必要なときに呼びます。Jevの選択は、Claude Codeの選択とほとんど重なりませんでした。

![jev-skill-routerの1週間のログ。判定1,242回、Jevがスキルを選んだ539回、選んでから30分以内に同じセッションで呼ばれた28回（5%ほど）](/images/jev-guard-blind-to-local-verify-funnel.png)

判定1,242回のうちJevがスキルを選んだのは539回で、そのうち実際に呼ばれたのは28回でした。

前回の記事では、Jevが選んだのに使われなかった回が積み上がるなら、JevがClaude Codeの見落としを拾っているのかもしれない、と書いていました。使われなかったのは511回です。前回の基準なら、提案を1行添える意味があるかもしれない側です。

ただ、511回が見落としなのか的外れなのかは、1回ずつ会話を開いて、そのスキルが要る場面だったかを判断しないと分かりません。このプラグインは判定のたびに、スキルの一覧（全スキルの説明文）と候補3件のスキル本文で、約2万トークンをJevに送っていました。そのために511回を読む価値はないと考えて、確かめずに外しました。

## 外した後で、使われなかった20件を読みました

外した後で、Jevが選んだのに使われなかった回から無作為に20件を選び、その場面の会話を開いて読みました。ここでの「使われなかった」は、30分以内に同じ会話でそのスキルがSkillツールから呼ばれなかった、という意味で、サブエージェントの中での呼び出しは数えていません。集計と抽出に使ったスクリプトと数字は、[jev-skill-routerのevals](https://github.com/shimo4228/jev-skill-router/tree/main/evals)で公開しています。

- 13件は的外れでした。うち少なくとも6件は、私が打った発言ではなく、エージェントが書いた文に反応していました。サブエージェントに出した判定の依頼や、サブエージェントから戻った報告文です。Claude Codeの中では、こうした文もユーザーの発言と同じ入口を通ります
- 5件は、話題は近いものの、その場面ではスキルを呼ぶまでもない回でした
- 1件は、Claude Codeがスキルを呼ばずに、そのスキルのファイルを直接読んでいました。スキルは使われていたのに、私の集計は「使われなかった」と数えていました
- 見落としだったかもしれないのは1件だけでした。ローカルでLLMを2つ同時に動かせるかという質問で、Claude Codeはそのスキルを使わずにWebで調べていました

20件だけなので、割合は目安です。読んだ後も、外した判断は変わりませんでした。それでも2つのことが分かりました。Jevは発言の文面だけを見て選ぶので、会話の中の文を誰が書いたかを区別しません。そして私の数え方も、Claude Codeがスキルを使う経路の全部は見ていませんでした。28回という数字には、Jevの選び方と、Claude Codeの動き方と、私の数え方が混ざっていて、どれがどれだけ効いたかをログの数字から分けることはできませんでした。

予想していなかったのは、2つ目のプラグインでした。

## 検証を済ませた完了が止められました

2つ目は、外部の開発者が公開している[jev-belay](https://github.com/valentynkit/jev-belay)です。Claude Codeが作業を終えようとしたときに動くStop hookで、ファイルを変更したのに、その後でテスト・ビルド・lintが1つも走っていなければ、Jevに「この完了報告は未検証の完了か」を聞きます。そうだと判定したら、Claude Codeは作業を終えられず、理由を受け取って検証に戻ります。これは判定を記録するだけでなく、実際に止める設定で1週間動いていました。

止めた回の1件を、順に追います。Claude Codeは私の`~/.claude`の設定リポジトリで、ある変更を実装していました。

1. リポジトリの検証スクリプト`./.claude/verify.sh`を2回実行し、2回とも成功（exit 0）
2. テストファイルを1か所直す
3. `verify.sh`を3回目に実行し、成功
4. commitメッセージを作業用の一時フォルダの`msg.txt`に書き出す
5. commitする
6. 完了を報告する
7. jev-belayが止める

止めた理由は、判定ログに次のように残っていました（続けて、検証を実行して結果を報告するよう促す文が付きます）。

```text
jev-belay: reports completion (0.96) after 2 file changes with no test, build, or lint run since the last change; claims checks passed (0.97) but none ran.
```

「最後の変更の後にテストもビルドもlintも走っていないのに、検査が通ったと言っている」という判定です。止められたClaude Codeは`verify.sh`をもう一度実行し、約2分半後に同じく成功しました。ログの「2 file changes」は、3回目の検証の前に直したテストファイルと、`msg.txt`です。

1週間で止めた8回は、どれも判定ログの「最後の変更の後に走った検査」が空でした。

## 部品も運用も、それぞれは正しかった

jev-belayが何を「検査」と数えるかは、コードに書いてあります。

```js
// ~/.claude/plugins/cache/jev-belay/jev-belay/0.2.0/belay.mjs（抜粋）
export const CHECK_COMMAND = /\b(?:(?:npm|pnpm|yarn|bun)\s+(?:run\s+)?(?:test|check|lint|typecheck|build|verify|ci)\b| … |pytest|jest|vitest| … |ruff|mypy| … )\b/;

const named = CHECK_COMMAND.test(command) || extraCheck()?.test(command) === true;
if (tool === "Bash" && named) return failed || summary === "fail" ? "check-fail" : "check-pass";
if (summary) return summary === "fail" || failed ? "check-fail" : "check-pass";
return "unknown";
```

実行したコマンドの文字列に、よく知られたテストやlintの名前（`npm test`、`pytest`、`ruff`など）が含まれるか。あるいは、出力にテストランナーの要約行があるか。このどちらかで、検査が走ったと数えます。

私の`verify.sh`は、formatからテストまでをまとめて実行する、このリポジトリ専用のスクリプトです。コマンドの文字列にはランナーの名前が出てきません。成功したときは何も出力しないので、要約行もありません。同じ中身でも`npm run verify`という名前で呼んでいれば、正規表現に一致していました。

最後の「変更」も、私の運用から来ていました。この環境では、複数行のcommitメッセージはファイルに書いてから渡す運用にしています。だから検証の後に、ファイルの書き込みが1回入ります。jev-belayはWriteやEditでの書き込みをすべて変更として数えるので、検証の後に変更があった、と見えます。8回それぞれの直前の変更を並べると、commitメッセージの下書きが2回で、ほかはメモ、スキルの説明ファイル、lintの設定ファイルなどでした。

![止められた1件の順序。Claude Codeはverify.shを2回成功、テストを1か所直す、verify.shを3回目も成功、msg.txtを書く、完了を報告。jev-belayはverify.shを検査に数えず、変更1、変更2、検査0と数えて止めた](/images/jev-guard-blind-to-local-verify-belay-view.png)

Claude Codeは`verify.sh`を3回通していましたが、jev-belayが数えたのは変更2件と検査0件でした。

中身を追ったもう1件では、Claude Codeはlintの設定ファイルを直した後に`verify.sh`を実行し、出力をファイルへ書き出していました。結果は失敗で、原因はパッケージ配布サイト（PyPI）の一時的な障害でした。Claude Codeはそれを報告していました。この場合もjev-belayにはランナーの名前も要約行も見えず、止められたClaude Codeは約3分かけて検証をやり直し、同じ理由で失敗しました。

どちらの側も、単体では間違っていません。jev-belayのREADMEは、ラベル付きの100回の作業終了で、未検証の完了とそうでない完了を見分ける精度を報告しています。その100回では8回を止め、7回は正しかったそうです。私のcommitの手順にも理由があります。コマンドに特殊文字を埋め込むと、毎回承認を求められるのを避けるためです。衝突が起きたのは、2つがClaude Codeの中で組み合わさったときでした。止められたClaude Codeが検証をやり直すことも、部品の側からは決められません。

jev-belayには、プロジェクト独自の検査スクリプトを正規表現で足す`CHECK`オプションがあります。私の環境ではこれを設定していませんでした。設定すれば`verify.sh`は検査として数えられたはずです。私はそれを試さずに外しました。試さなかった理由は次の節に書きます。

## 効果を読めないまま、仕事は重なっていました

1週間が過ぎた日、私は別の作業の途中でClaude Codeに聞きました。「Jevのスキル選択とJev-bely（原文のまま）ってまだ動いてるの？これ意味あるかな？」。ログを見て、2つとも外しました。

`CHECK`を設定すれば、`verify.sh`を検査として認識しなかった衝突は消えます。けれど、消えるのは私が気づいた衝突だけです。Claude Codeは、次に何をするかを毎回モデルが決めるエージェントで、考えてはツールを呼ぶ往復（ReAct）を繰り返します。どの時点でファイルを書き、どの時点で検証を回し、止められたら何をするかは、実行するまで決まっていません。そこに差し込んだ部品が何を引き起こすかは、しばらく動かしてログを読むまで分かりませんでした。今回の衝突に気づけたのは、止められるという目に見える形で出たからです。1回止めるだけでも、その後の検証、応答、次の作業の進め方が変わりえます。目に見えない形で性能を落としていたとしても、私にはそれをログから読む手段がありません。

しかも、2つのプラグインが外から足した仕事は、どちらも既に内側にありました。スキルはClaude Codeが自分で選びます。この環境には、commitのたびに`verify.sh`を走らせるhookがあり、commitまで進んだ作業は検証を通っています。jev-belayが守ろうとしたものの多くは、別の仕組みで既に守られていました（commitせずに完了と言う場面は残ります）。同じ仕事を外から重ねても置き換わるものがなく、衝突だけが増えました。

![外から足したプラグインと既にあった仕組みの対応。スキルを選ぶ仕事はjev-skill-routerとClaude Code自身、未検証の完了を防ぐ仕事はjev-belayとcommit時のhook](/images/jev-guard-blind-to-local-verify-overlap.png)

スキルを選ぶ仕事はClaude Code自身が、未検証の完了を防ぐ仕事の多くはcommit時のhookが、プラグインを足す前から担っていました。

## 組み込んだ効果を読めるのは、流れが決まっている場所です

流れが固定されたパイプラインでは、事情が違います。LangGraphでノードとその順番をコードで固定して組む構成なら、判定モデルを1つのノードとして差し替えても、そのノードに何が入り、次にどこへ進むかは変わりません。差し替えた部品だけを取り出して試せます。私は毎朝の論文調査で、[資料ごとの「関係あるか」「新しいか」の判定をJevに移し、文章を書く部分だけをLLMに残しました](https://zenn.dev/shimo4228/articles/jev-research-judgment-offload)。自分で組んだパイプラインなので、Jevの判定がどこに効いて、どの数字が変わるかを読めました。

Claude Codeにも、hookやプラグインで部品を足す仕組みはあります。ただ、次に何をするかが決まっていないエージェントでは、部品を変えた効果が読みにくく、私は慎重になります。Jevを使うなら、最初からJevで判定する前提で流れを組み、LLMは文章を生成する部分だけで呼ぶ構成か、固定したパイプラインの部品として使うのがよいと、いまは考えています。
