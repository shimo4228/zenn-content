2026年10月11日、Claude Code を作っている Boris Cherny さんが X に書きました。Opus 4.8 あたりから Claude はこういう仕事を自分よりうまくこなすようになり、5.5 のモデルは非常にうまい、モデルに渡すのは 3 つだけでいい、と。「ビルドが遅い、速くして」と言うだけでツールがやってくれる、という投稿への返信です。

1. goal（例:「Make p95 ci time <10 mins」。p95 は、実行の 95% がその時間内に収まる値）
2. 結果の測り方（例: 変更のたびに BigQuery の timings を読む。BigQuery は Google Cloud の、大量の記録を SQL で集計するサービス）
3. どれだけ頑張るか（例: 終わるまで止めない。数週間の実験になるかもしれない）

これでたいていのことはうまくいく、と続きます（[投稿](https://x.com/bcherny/status/2109027327569203687)）。

私はこの 3 つのうち、2 つ目でいつも止まります。README や記事には p95 がありません。eval には 2026年2月から取り組んできて、learn-eval や llm-as-judge といったスキルも作りました。それでも、eval というものの全体の形は掴めていません。最近は「Eval ループを回して」と Opus 5.5 にふわっと頼むと README が良くなるので、なおさら、自分が何をしているのかを位置付けられません。

そもそも eval という語は、人によって指すものが違う気がします。点数を出すテストのことだけを言う人もいれば、出力を読んで直す所を探すことまで含める人もいます。

この記事では、部品を 3 つの層に分けて、順にたどります。eval そのもの、eval を回して点数を上げるループ、そのループに渡す goal です。部品の名前と中身は、2026年10月時点の Anthropic の公式の手順と、eval の実践者が書いてきたことから取ります。最後に、私がこれまで eval と呼んできたものを、この部品の上に置きます。置いてみると、私が「Eval ループを回して」と頼んでいたものは、数で比べて登る eval ループではありませんでした。読み終えたら、自分のやり方も同じ部品に当てはめて、どの形のループを回しているのかが分かるはずです。

## eval は入力・走らせ方・採点でできている

Claude Code に同梱の claude-api スキルには、eval を作る手順 `/claude-api build-eval` があります（手順の文書は2026年9月29日に [anthropics/skills](https://github.com/anthropics/skills/tree/main/skills/claude-api/shared/evals) に入りました）。対象は Claude を使ったアプリで、モデルを移す、プロンプトを書き換える、といった変更が効いたかを測るためのものです。この手順は、eval を 3 つのものと定義しています。

- 入力の集まり
- 入力ごとにアプリを走らせる方法
- 出力ごとに採点する方法

Anthropic のエンジニアリングブログの記事「[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)」（2026年1月9日）は、同じものを次の語で呼んでいます。

- **task**: 入力と成功基準が決まった、1 つのテスト
- **trial**: task への 1 回の試行。LLM の出力は毎回変わるので、同じ task を何度も走らせる
- **grader**: 結果のある側面を採点するロジック
- **transcript**: 1 回の trial の全記録
- **outcome**: trial の終わりに環境に残った最終状態

task が入力の 1 件、trial がそれを 1 回走らせること、grader が採点にあたります。点数を付けるのは grader だけです。入力をいくら揃えても、grader が見当違いなら、点数も見当違いになります。

grader が何を読むかも、部品の一部です。ファイルを書く、コードを直すといった、環境に手を加えるエージェントを測るとき、build-eval は、会話の記録（transcript）ではなく使い捨ての作業場所に残った最終状態（outcome）を読む検査を、主な採点にするよう勧めています。テストが通るか、期待したファイルがあるか、触ってはいけないものに触っていないか、です。

同じブログ記事は、eval を用途で 2 つに分けています。低い合格率から始めて、登っていく丘を作るのが capability eval です。ほぼ 100% 通るべきもので、後退を見張るのが regression eval です。この先で見るループは、capability eval の丘を登る仕組みです。

Claude Code のプラグインとスキルには、もう 1 つ公式の道具があります。`claude plugin eval` は、そのプラグインだけを読み込んだ隔離済みの `claude -p` で各ケースを走らせ、正規表現、呼んだツール、ツールの呼び順、ファイルの有無、LLM の判定、参照記録（baseline）との比較、の 6 種の grader で採点します（[公式ドキュメント](https://code.claude.com/docs/en/plugin-evals)）。

## eval という語は、人によって指すものが違う

冒頭の問いに戻ります。点数を出さないものを eval と呼ぶのかを、主要な資料で調べました（調査の全文は [GitHub に置いています](https://github.com/shimo4228/zenn-content/blob/main/docs/plans/research/2026-10-12-eval-vs-review-deep-research.md)）。先に、資料が評価を語るときの軸を並べておきます。1 つの評価は、それぞれの軸から型を 1 つずつ選んだ組み合わせとして書けます。ただし、どのセルまでを eval と呼ぶかは資料によって違います。割れるセルは、表の後で見ます。

| 軸 | 型 | 出典 |
|---|---|---|
| 何を返すか | 点数 ／ 判定（合格・不合格、ラベル）／ 構造化されたレビュー ／ 自由に書いたレビュー | LangSmith、Braintrust、Hamel Husain さんと Shreya Shankar さんの FAQ、Anthropic |
| 誰が採点するか | プログラム ／ モデル（LLM-as-a-Judge）／ 人 | Anthropic、build-eval |
| どう採点するか | 決めた検査にかける（正解との一致、テストが通るか）／ 2 つを比べる ／ 基準に沿って 1 つを採点する | build-eval |
| 何を読むか | 会話の記録（transcript）／ 環境に残った最終状態（outcome） | Anthropic、build-eval |
| 何のためか | 登る丘を作る（capability）／ 後退を見張る（regression） | Anthropic |
| いつ回すか | 開発中に、決めた入力で ／ 本番で、実際の利用を見る（Anthropic は本番の監視を、自動の eval と並ぶ別の手段に数える） | Anthropic |
| どう使うか | 版を比べて登る（hillclimb）／ 直す所を探す（evaluator-optimizer） | build-eval と hillclimb の手順書、Anthropic |

いちばん大きく割れるのは、「何を返すか」のどこまでを eval と呼ぶかです。境界は点数の有無ではありませんでした。点数のほかに返すものを並べると、3 つに分かれます。

- **基準に対する判定**: 合格・不合格や、決めたラベル。点数が無くても、多くの資料が eval の出力に数えます。Anthropic は採点の形に合格・不合格を挙げています。評価ツールの LangSmith は数値の score と並べてカテゴリの value を、同じく Braintrust は点数を付ける scorer と並べてラベルを付ける classifier を、評価の道具として扱います
- **構造化されたレビュー**: たとえば、基準ごとに満たすかどうかを、理由を添えて返すもの。eval の実践者である Hamel さんたちの FAQ は、eval が返すものを「点数、または構造化されたレビュー」としています
- **自由に書いて返すレビュー**: 読んで「ここで引っかかった」「ここを直すとよい」と返すだけのもの。ここで資料が割れます。Hamel さんたちは、出力を読んでメモを付け、失敗の種類に束ねる error analysis を、eval でいちばん大事な活動としています。Anthropic は eval を「出力に採点のロジックを当てるテスト」と定義し、記録を読むことは、採点が正しく働いているかを確かめる工程や、自動の eval と並ぶ別の手段として挙げています

ループにも同じ線が引かれています。Anthropic は、一方の呼び出しが書き、もう一方が評価と助言を返して直させる形を [evaluator-optimizer](https://www.anthropic.com/engineering/building-effective-agents) と呼び、eval とは別の名前で、エージェントの構成パターン（workflow）の 1 つとして紹介しています。研究では [Self-Refine](https://arxiv.org/abs/2303.17651)（Madaan ら、2023）が同じ形です。コードレビューは、eval の側から見ると 2 通りに扱えます。AI に PR を読ませ、その指摘を開発者が読んで直すだけなら、それはレビューです。一方、そのレビュー役に既知のバグを埋めた PR を読ませ、見つけた割合や誤った指摘の数を採点すれば、それは AI のレビュー役を測る eval になります。これは Anthropic の「出力に採点のロジックを当てるテスト」という定義に当てはめた見方で、どこかが公式にこう定めているわけではありません。

「多くの人が eval をどういう意味で使っているか」を測った調査は、見つかりませんでした。よく読まれる資料の間でも、これだけ線の位置が違います。eval は、人によって指すものがぶれる、新しい語です。

## 採点は、人の判断と揃えてから使う

採点の方法にはいくつかの種類があり、それぞれ確かめ方が違います。LLM に採点させるなら、人の判断と揃うまで直してから使います。そのうえで、件数が少ないと、点数は揺れに埋もれます。

build-eval は採点の方法を、おおよそ安い順に 4 つ挙げ、測りたいものを本当に測れる中で一番安いものを選ぶよう勧めています。

1. プログラムでの判定（完全一致、JSON の形、テストが通るか）。答えの範囲が決まっている出力に使う
2. 2 つの出力を伏せて並べ、どちらが良いかをモデルに選ばせる比較。A と B の並び順は毎回入れ替える
3. 採点基準（rubric）に沿って、モデルが 1 つの出力を採点する
4. 人が少数を手で採点する

2 と 3 のようにモデルに採点させるやり方は LLM-as-a-Judge と呼ばれ、採点するモデルを judge と呼びます。build-eval は採点の方法を決めるとき、ユーザーに採点例を 5 件見せて「この中に、あなたなら違う点数を付けたものはありますか」と聞きます。1 件でもあれば、rubric はまだ使えません。ユーザーの判断と採点が揃うまで直します。

Hamel さんたちの [FAQ](https://hamel.dev/blog/posts/evals-faq/) は、同じ考えを件数まで書いています。

- まず出力を読む（error analysis）。記録にメモを付け、失敗の種類に束ね、新しく読んでも新しい種類が出なくなるまで続ける
- 採点は 1〜5 の点数ではなく、合格か不合格かの二値にする
- judge は、人がラベルを付けた例で確かめてから使う。正しく合格にした割合（TPR）と、正しく不合格にした割合（TNR）を測る。必要な例は、失敗の種類ごとに 100〜200 件
- ラベル付けは、その製品の文脈を知る人がする。外注には強く懐疑的

judge と人がどれくらい一致するかは、条件で変わります。2023年の [MT-Bench の論文](https://arxiv.org/abs/2306.05685)では、2 つの回答を比べさせた判定で、引き分けを除くと GPT-4 と人の一致は 85%、人同士は 81% でした。引き分けを含めると、それぞれ 66% と 63% に下がります。一致の数字は、引き分けをどう数えたかで変わります。

点数を信じられるかを決めるもう 1 つの条件は、件数です。build-eval は、最初の eval の入力を 15〜100 件にするよう勧めています。15 件より少ないと、1 件の揺れで点数が動くからです。1 つの合格率の揺れ（ノイズ）はおおよそ 1/√(件数 × 試行回数) で、25 件を 2 回ずつ走らせても ±14 ポイントほどになります。この揺れより小さい差は、変更が効いたのか偶然なのか見分けられません。

## ループは、採点の穴も一緒に登る

eval が 1 つできると、次は点数を上げるループを回したくなります。claude-api スキルの `/claude-api hillclimb` がその手順です。この手順は最初に、動かせる eval があるかを確かめます。無ければ止まって build-eval へ戻します。eval の無い hillclimb は「just editing and hoping」（書き換えて祈るだけ）だ、と書いています。

hillclimb の部品を並べると、次のようになります。

- **goal**: 何を上げるか、または下げるか。点数を上げる、費用を下げる、待ち時間を下げる、別のモデルへ移す、のどれか。ほかに記録している指標は、揺れの範囲を超えて悪化させない守りの条件（guardrail）にする
- **変える範囲**: プロンプト、ツールの説明、モデルや effort など、何を変えてよいか。触ってはいけないものも決める
- **分割**: 入力を無作為に train（改善のために読む問題）と test（直し方を考える役には読ませず、毎ラウンド点数だけを測る問題）に分ける。失敗を読んで直し方を考える役（analyzer）は、train の記録だけを読む。ループを回す側は点数しか見ない
- **1 ラウンド 1 変更**: 複数の変更を束ねると、どれが効いたか分からなくなる
- **受け入れ**: train が上がって test が上がらなければ、読んだ件に合わせただけとみなして戻す。train も下がったら戻す
- **止めどき**: 推奨は、揺れより小さい改善が 3 ラウンド以上続いたら止める（plateau）。2 回の横ばいでは少なすぎる、と手順は書いている[^1]
- **予算**: 費用を気にするなら、1 回の実行の費用 ×（ラウンド数 + 1）× 試行回数で総額を見積もり、上限を決める
- **報告**: 最後に報告するのは、test での開始時からの改善幅と、その信頼区間。揺れの範囲に収まっていたら、そう書いて merge しないよう勧める

件数が少ないときは分けずに全件で回し、数字は方向を示すだけ（directional）と明記します。1 ラウンド目の前には、揺れの大きさ、伸びしろ、ユーザーが動く最小の改善幅、の 3 つを並べます。揺れの方が大きければ、どんな変更をしても改善は見えない、と先に伝えます。

なぜ train と test を分けるのか。ループは、採点の穴を見つけると、そこを使って点数を上げることがあるからです。2026年7月に arXiv に出た[論文](https://arxiv.org/abs/2607.18064)に、その例があります。

著者たちは、Claude Code（Opus 4.8）と Codex CLI（GPT-5.5）に、同じ自動改善のループを 3 回ずつ回させました。課題は、クルアーンの朗誦を音声認識で書き起こした文から、どの節かを当てて区切るプログラムを作ることです。ループはプログラムを書き換えるたびに採点し、外れた問題を失敗レポートに出します。ところが、この失敗レポートには、外れた問題の正解（節の ID）まで表示されていました。

Codex は 3 回とも、この正解をプログラムに直接埋め込みました。問題を解かずに、知っている問題には正解を返すプログラムです。答えを丸写ししたので、点数は Claude より良くなりました。Claude Code は 3 回とも正解を埋め込まず、点数は Codex より悪いまま頭打ちになりました。

著者たちは次の実験で、問題の一部をループが一度も見ない test に分け、失敗レポートから正解を消し、test があって丸写しは効かないことを両者に伝え、実行ごとに環境を分けました。4 つを同時に変えると、丸写しは 0 になりました。どれが効いたのかは分けられていない、と著者たちは書いています。

hillclimb の train と test の分割は、この 1 つ目の塞ぎ方にあたります。ループが答えを見られる採点だけで点数を上げると、上がった点数は丸写しと見分けがつきません。test を分けるのは、ループが見ていない問題で点数を測り、本当に解けるようになったかを確かめるためです。

## 数字の goal は、同じ量を測る道具が先にあるときに置ける

Boris さんの例に戻ると、「p95 の CI 時間を 10 分未満に」という goal には、「変更のたびに BigQuery の timings を読む」という測り方が付いています。goal と測り方が、同じ量を指しています。hillclimb も goal を決めるとき、候補を eval が記録している指標の中から並べます。

Jason Wei さんは2025年7月のブログ記事「[Asymmetry of verification and verifier's rule](https://www.jasonwei.net/blog/asymmetry-of-verification-and-verifiers-law)」で、AI に task を解かせる訓練のしやすさは、その task の検証しやすさに比例すると書きました。検証しやすい task の性質として、5 つを挙げています。

- 良い解について皆が同意する（Objective truth）
- 1 つの解を数秒で検証できる（Fast to verify）
- たくさんの解を同時に検証できる（Scalable to verify）
- 検証の結果が解の質とよく相関する（Low noise）
- 1 つの問題への多くの解に、良し悪しの順位を付けやすい（Continuous reward）

CI の時間なら、短いほど良いことに皆が同意できます。README の分かりやすさは、1 つ目の「皆が同意する」から難しくなります。

測り方が無いまま goal を置くと、判定は会話の言葉に頼るしかなくなります。Claude Code の `/goal` は、条件を書いておくと、ターンが終わるたびに小さく速いモデルが会話を読んで達成を判定します。[公式ドキュメント](https://code.claude.com/docs/en/goal)によると、この判定役はコマンドもファイルも見ません。そのため公式は、条件に「確かめ方」を書くよう勧めています。7月に私が書いた条件（「アイデアが20出るまでループしてくれ。…終わったらnotesにレポートしてまとめてプッシュして」）には確かめ方が無く、しかも notes のフォルダは `.gitignore` の対象でプッシュできませんでした。判定役は未達を 41 回返し続け、7 時間 38 分後に私が手で止めました。

## 私の eval を部品の上に置く

ここからは、私がこれまで eval と呼んできたものを、ここまでの部品の上に置いていきます。まず 1 件、実物を見せます。

10月8日、私は自分の研究リポジトリ Contemplative Agent（ローカル LLM で動く自律エージェントの長期実験）の README について、「READMEを大きく書き換えたいから、Eval ループを回して、私のメインプロジェクトの一つとして誰に見せても誇れるようなクオリティに仕上げて欲しい。」と頼みました。続けて「TaglineもEval回して改善して」と頼みました。日本語版の README の冒頭、題のすぐ下に置く一文（tagline）は、次のように変わりました。

- 前（9月12日の版）:「ローカル LLM で動く自律エージェントで、自分の憲法と価値観の変更を自分で提案します。採用するかどうかは、毎回人間が決めます。」
- 後（10月8日の版）:「長く続けている実験です。AI エージェントがローカル LLM で自分から投稿し、自分のハーネス（プロンプトに入る憲法・アイデンティティ・スキル）への変更を提案します。モデルの重みは変えません。提案ごとの最終判断は人が持ちます。」

冒頭には 4 段のループの図が入り、提案の採否の実績（スキルの提案は 82 件採用、547 件却下）も README に載りました。誰に見せても誇れるようなクオリティになっているかはさておき、以前の版より、かなり良くなりました。

このループを部品に分けると、こうなります。goal は「誰に見せても誇れるようなクオリティ」という質の言葉でした。入力は README の稿と、冒頭の一文の候補 37 個です。読ませたのは、研究者・エンジニア・懐疑的な読み手の 3 人を LLM に演じさせる訪問者役で、冒頭の一文は合計 234 回読ませました。README 全体は、README を判定する judge（readme-judge）が、固定の質問と、記述をコードと突き合わせた証拠で判定しました。受け入れは、最後に私が読んで決めました。

途中で、goal の向きを私が直しています。私は「思ったんだけど、人間の承認を前に出す必要ないかもな。だって北極星が人間の承認をなくす方向じゃん。これハーネスで再帰的自己改善しようとしているんだろ」と言いました。Opus 5.5 は、半分は賛成で、半分は前提が違うと返し、ハーネスを中心に置く案と、「ハーネスのことだと分かるか」を見る採点を 1 つ足す案を出しました。私が「Go」と返してから測り直し、ハーネスを中心に置いた今の一文に決まりました。

## README でやっていたのは、レビューのループだった

部品はそろっています。ところが、点数の使い方が hillclimb と違います。

- README 本体では、訪問者役の答えを点数ではなく、書き直しのヒントとして使いました。「どこで読む気をなくしたか」「1 つ直すならどこか」を読んで、文章を直します。前の版と今の版を点数で比べることはしていません。例外は冒頭の一文で、候補ごとに、読み手が中身を正しく言えたかを数えて比べました。比べ方は eval ループに近いものの、test に分けてはおらず、その数がどれくらい揺れるかも見ていません
- 最初は「今週試す気になるか」を 1〜10 の点数でも聞いていました。この点数は、点数で止めどきを決めると点数を上げること自体が目的になる、という理由を README のスキルの記録に書いて、廃止しました
- README 本体の止めどきは、文面で直る理由が新しく出なくなったときでした。点数が揺れより大きく動いたか、ではありません
- judge（readme-judge）は Publishable・Fix・Rewrite のどれかを返し、直す所を挙げます。版どうしを比べる役はしていません。私の `llm-as-judge` スキルも、二値の判定を名前付きの判定 1 つにまとめ、点数を集計しない形です

つまり、README でやっていたのは、eval の部品を使ったレビューのループでした。私はこれも「Eval ループ」と呼んで頼んでいました。

「eval という語は、人によって指すものが違う」の節で見たとおり、自由に書いて返すレビューまで eval に含めるかは、資料によって違います。そこでこの記事では、eval は 1 節の部品（入力・走らせ方・採点）を指すことにし、それを使うループを、問いの違いで 2 つに分けます。

- **eval ループ**: 点数や合格率などの物差しで版を比べ、その値を上げていくループ
- **レビューのループ**: この 1 本を読んで、次に直す所を探すループ

この記事の「レビューのループ」は、Anthropic が evaluator-optimizer と呼ぶ形にあたります。

同じ部品を使っていても、答えようとしている問いが違います。

| | eval ループ（hillclimb） | レビューのループ（README） |
|---|---|---|
| 答える問い | この変更は効いたか。読んでいない件にも効くか | この 1 本の、次に直す所はどこか |
| 採点の役 | 版どうしを比べる | 直す所を見つける |
| 要るもの | 件数と揺れの見積もり（件数が多ければ train と test） | 違う理由で読む読み手 |
| 止まり方 | 改善が揺れより小さくなったら | 新しい指摘が出なくなったら（Hamel さんたちの error analysis と同じ止まり方） |

![2 つのループの対比。eval ループは、版を変える、物差しで測る、前の版と比べる、良ければ残すを繰り返し、問いは「この変更は効いたか」、改善が揺れより小さくなったら止まる。レビューのループは、読む、直す所を挙げる、書き直すを繰り返し、問いは「この 1 本の、次に直す所はどこか」、新しい指摘が出なくなったら止まる](/images/claude-code-eval-concepts-two-loops.png)

左の eval ループは物差しの値を上げにいき、右のレビューのループは、直す所が出なくなるまで読み直します。

build-eval と hillclimb が測るのは、Claude を使ったアプリでした。README のような成果物に当てはめるなら、README 1 本ではなく、README を書くスキルを 15 個のリポジトリで走らせて比べる形になります。README 1 本には、train と test に分けるだけの入力がありません。

eval ループの形をしていたのは、9月の日次レポートのベンチ（調べものの日次レポートの文章を磨くために、稿どうしを比べる仕組み）です。素材を固定した case を用意し、その約 1/3 を、改善には使わない test に分けました。文章を書くプロンプトを書き換えては同じ case で比べることを重ね、プロンプトのファイルは 29 本になりました。読みやすさは、どちらの稿かを伏せて私が読み比べて決め、事実に忠実かは judge が合格・不合格で見ました。judge に読みやすさも判定させると、2 つの並び順のどちらでも、私が読んで良いとした方と逆を選んだからです（1 件の比較です）。ベンチを始めたのは9月23日で、build-eval と hillclimb の手順書が公開された9月29日より前なので、Claude Code と一から組みました。

## レビューの指摘は、どれだけ当たっていたか

README のレビューのループの指摘がどれだけ当たっていたかを、記事を書く途中で一度確かめました。7 つのリポジトリの README のループから、judge と訪問者役が出した指摘・判定を 28 件選び、私が 1 件ずつ「当たり」「外れ」「分からない」を付けました。「当たり」はその指摘や判定に私が同意したもの、「外れ」は同意しなかったものです。たとえば、私の akc-cycle というリポジトリの README には、「skill-stocktake と generation-audit は skill-health の走査を使うので、一緒に入れてください」という意味の英文がありました。judge は、skill-health だけを入れる場合に何が要るかは書かれていない、と指摘しました。私はこれに「外れ」を付け、メモに「プラグインにバンドルされているから、いちいち直す必要を感じないが、そもそもそこまで細かいことをREADMEで言う必要がない」と書きました。

| 対象 | 件数 | 当たり | 外れ | 分からない |
|---|---|---|---|---|
| judge が直すべきと指摘 | 10 | 3 | 3 | 4 |
| judge が満たしていると判定 | 7 | 7 | 0 | 0 |
| 訪問者役の指摘 | 11 | 7 | 3 | 1 |

judge が直すべきと指摘したうちの分からない 4 件は、README の記述をコードや記録と突き合わせた指摘でした。確かめるには私もコードと突き合わせるしかなく、そこまでやると本末転倒なので、分からないとしました。judge の「直すべき」で私と割れたのは、事実の誤りではなく、README にどこまで書くかの好みでした。28 件は judge と訪問者役が挙げたものだけで、見逃したものは入っていません。コードレビューの 2 通りで言えば、これはレビュー役を測る側にあたります。測ったのは指摘が外れた数で、見つけた割合は測っていません。

## eval ループは、避けてきた

README 本体と記事でやってきたのは、eval ループではなく、レビューのループでした。記事でも、別の LLM に読者を演じさせて読ませ、見せ方を直す、同じ形のレビューを回しています。ベストプラクティスが分からないと感じていたのは、hillclimb のような eval ループの手順を、自分のレビューのループに当てはめて見ていたからでした。

README 本体と記事で eval ループをしてこなかったのは、足りなかったからではありません。避けてきました。いちばんの理由は、グッドハートの法則を嫌うことです。経済学者 Charles Goodhart の名前で呼ばれるこの法則は、よく引かれる言い方では「測定値が目標になると、それは良い測定値ではなくなる」です（この言い方は、人類学者 Marilyn Strathern が 1997 年に整えたものです）。「ループは、採点の穴も一緒に登る」の節で見た、ループが正解を丸写しして点数を上げた例も同じ形でした。だから私は、`llm-as-judge` スキルでは点数を集計せず、README のスキルでは数値スコアを作らないと決めていました。この向きは前からありました。2月には、スキルの棚卸しでルーブリックの点数をやめ、総合判断にしています（[記事](https://zenn.dev/shimo4228/articles/skill-stocktake-design-journey)）。8月には、評価を全部通った原稿が 2 本とも空疎だったこと（[記事](https://zenn.dev/shimo4228/articles/transcript-not-ledger)）と、KPI が改善していたのに自作の LLM judge を捨てたこと（[記事](https://zenn.dev/shimo4228/articles/judge-degrades-into-reviewer)）を書きました。

もう 1 つ、数値の goal をループに渡せる題材を、ほとんど扱ってこなかったこともあります。Contemplative Agent でも、見る対象の多くはエージェントのコメントやスキルの選び方のような自然言語です。数で測る計器もありますが、観測と回帰の検出に使うだけで、ループの goal にはしていません。

[^1]: 私は実装するとき、先にどこまで実装するかをプランしてレビューし、そこで終えるので、早めに終わってしまうといった終了条件の問題は、実感としてよく分かりません。終了条件が問題になるのは、終わりの線が仕事そのものに無いときです。点数を上げ続けるループ（hillclimb）や、読ませるたびに何かは見つかるレビューや指摘探しのループです。X で「Claude にレビューさせると毎回新しいバグが見つかるが、いつ終わったと決めるのか」と聞かれた Boris Cherny さんは、改善をいま入れているところで、詳しいことは近く共有すると答えていました（[2026年10月12日の返信](https://x.com/bcherny/status/2109354514780438560)）。
