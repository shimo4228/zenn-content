# Reader-First Article Review（読者目線レビュー）

**Extracted:** 2026-03-06
**Context:** Moltbook エージェント記事の執筆で、ユーザーから複数回「前提知識の説明が足りない」と指摘された経験から抽出

## Problem

技術記事を書く際、書き手が「当然知っているだろう」と思い込み、読者が離脱するポイントを見落とす。concept-before-use-rule（概念導入順序の原則）は「図やコードに出す前に説明する」に特化しているが、以下のパターンはカバーしていない:

- 用語解説が初出より後にある（後半の各論で解説しても読者はそこまで辿り着けない）
- 「なぜこれが有効なのか」の攻撃シナリオ・失敗シナリオが書かれていない
- プラットフォームの仕様や制約（レート制限等）が前提として説明されていない
- 情報量ゼロの要素（Before が全部ゼロの Before/After 表など）が残っている
- 「N個中M個」の不完全なリストで、残りに触れない理由が不明

## Solution

### レビューチェックリスト

記事完成後、以下の観点で全文をスキャンする。

#### 1. 用語の前方集約チェック

- [ ] 記事内の全専門用語をリストアップする
- [ ] 各用語の初出箇所を特定する
- [ ] 初出より前に解説があるか確認する
- [ ] 解説が各論に散在している場合、冒頭に用語集として集約する
- 参照: [concept-before-use-rule](./concept-before-use-rule.md)

#### 2. 「なぜ有効か」チェック（セキュリティ・設計記事で特に重要）

- [ ] 各対策/設計判断に「この対策がないとどうなるか」の具体シナリオがあるか
- [ ] 抽象的な「セキュアです」ではなく、攻撃経路を具体的に説明しているか
- [ ] 既知の限界を正直に開示しているか（読者は「完璧」主張を信じない）

#### 3. プラットフォーム/ドメイン前提チェック

- [ ] 対象プラットフォームの基本仕様（レート制限、API 仕様等）を冒頭で説明しているか
- [ ] 読者が「なぜその数値なのか」を理解できるだけの前提情報があるか
- [ ] 「1日50コメント」のような数値が、仕様なのか自主制限なのか明確か

#### 4. 情報量チェック

- [ ] Before/After 表で Before が全部ゼロ/空ではないか（ゼロからのスクラッチなら表自体が不要）
- [ ] 「N個中M個」のリストで、残りに触れない理由を明示しているか（Top 10 で 8 項目だけ等）
- [ ] 同じ情報の重複がないか（本文で既に述べた数値を表で繰り返す等）

#### 5. ツール/技術の初出説明チェック

- [ ] 略語（TDD, OWASP 等）を初出時にフルネーム + 1文説明しているか
- [ ] ツール名（Ollama, Qwen 等）に「何者か」の説明があるか
- [ ] Python 固有概念（frozen dataclass 等）を非 Python ユーザーにも伝わるよう補足しているか

## When to Use

- 技術記事の editor レビュー前のセルフチェックとして
- ユーザーから「説明が足りない」と指摘されたときの修正ガイドとして
- 特にセキュリティ、設計判断、プラットフォーム連携を扱う記事で必須
