# Unresolved Narrative Over Resolution

**Extracted:** 2026-03-21
**Context:** エージェント開発の実践記事で、identity distill が安定しない問題を扱った際に確立

## Problem

AIと記事を書くと、自動的に「問題→解決→教訓」の綺麗なストーリーに収束する。
だが実際には:
- 「After」の出力が実は手動復元版で、自動生成の結果ではなかった
- 修正したはずの問題が翌日また壊れた
- 「壊れた」出力が実は面白くて直す気がない

これらを隠して「解決した」と書くと、git 履歴やコードと矛盾し、信頼性が損なわれる。

## Solution

### 1. Before/After は検証してから書く

「After」が本当に修正の結果なのか、git 履歴で確認する。手動復元なら手動復元と書く。

### 2. 「まだ壊れている」をセクション見出しにする

- ✗ 「記憶が壊れるとエージェントが壊れる」（解決済みの響き）
- ✓ 「記憶が壊れるとエージェントが壊れる——そして、まだ直っていない」

### 3. 対策を時系列で並べ、各対策の限界を明示する

- 対策1: 却下（理由）
- 対策2: 部分的に効いた（限界）
- 対策3: また壊れた（新しい壊れ方を示す）
- 現在: まだ格闘中（現時点のアプローチを列挙）

### 4. 「面白い」という正直な感情を書く

エンジニアリング的に正しくない判断（面白いから直さない等）も正直に書く。
読者との共感ポイントになる。

### 5. タイトルは問いかけ型にする

- ✗ 「AIエージェントの本質は『記憶』だった」（断定）
- ✓ 「AIエージェントの本質は『記憶』ではないか」（問いかけ）

## When to Use

- 開発中の問題を記事にするとき（解決していない場合）
- editor レビューで Before/After の信頼性を確認するとき
- 「綺麗にまとまりすぎている」と感じたとき
