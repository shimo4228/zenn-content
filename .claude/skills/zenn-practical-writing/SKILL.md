# zenn-practical-writing — Zenn/Dev.to 記事の実用軸

**この記事で守ること**: 読者が記事を開いて数秒で「これは何で、読めば自分に何ができるようになるか」がわかり、そのまま手を動かして再現できる。理解に認知リソースを使わせない。

これが Zenn/Dev.to チャンネルの既定の声。essay（思索・意見）や paper（論文）は別チャンネルに独自の声があり、それらとは意図的に文体を分ける。

---

## Scope — いつ使うか

| 書くもの | 使うもの |
|---|---|
| **Zenn/Dev.to の記事**（tech / idea 問わず全て） | **このスキル（既定）** |
| 学術 paper / preprint | `paper-ecosystem` skill |
| genuine な思索エッセイ | note（JA 正本・初出）→ Substack（EN 翻訳）へ。`writing-ecosystem` skill。文体は `.claude/rules/zenn-writing.md` のチャンネル表 |

**Zenn/Dev.to は type（tech/idea）で声を分けない** — すべて実用軸（即実用。文体はチャンネル表）。Zenn frontmatter の `type` は platform 要件として残るが voice は分岐しない。毒humor/刃牙 の personality は話題が合えば任意で足せる（[zenn-idea-voice](../zenn-idea-voice/SKILL.md)）。

判定: Zenn/Dev.to に出すなら実用軸（このスキル）。思索を綴る genuine エッセイは note → Substack（別 channel）へ。

## 継承と上書き（writing-ecosystem との関係）

genre 中立の canon は `writing-ecosystem` skill を正本として **defer**（再掲しない）。essay 固有の Voice だけ **override** する。

| writing-ecosystem の資産 | このスキルでの扱い |
|---|---|
| Craft 規約（単数の読者と語りかけの積極形・強い動詞・能動態・10% 編集・スペーシング・密度 > 字数） | **継承**（defer。実用記事にもそのまま適用） |
| AI-slop 禁止リスト（日英） | **継承**（defer。実用記事でも誇張語は使わない） |
| タイトルの誠実さ・煽り禁止 | **継承**（defer） |
| ネタ選定 3 軸（検索需要 / 競合 / 一次情報） | **継承**（defer） |
| 自リポ言及の節度（本文 self-link は導線 or 一次資料のみ・同一 repo 1 回まで） | **継承**（defer。クレジット型リンクは関連リンク節へ寄せる） |
| Voice（発見調・結論の問い化・断定→弱化・初期経典の語り口） | **上書き**（実用軸では使わない。直接指示。下記「語り」参照） |
| Section Length（1 節が全体の 30% を超えない） | 継承 |

## 実用軸の 5 ルール

ユーザーの 5 マーカーを、検証可能な具体ルールに落とす。

| マーカー | 具体ルール |
|---|---|
| **情報密度を抑えめ** | 1 節 1 論点。前置き・throat-clearing を削る。短段落。密な散文より箇条書き/表。読者に再読を要求しない |
| **図や実コード** | 1 記事に図/表を **≥1**。コードは**コピペで動く自己完結**（file path + 言語タグ + input→output を必ず示す） |
| **すぐ使える** | task 志向。再現可能な成果物を渡す。前提（バージョン・必要物）を**冒頭に列挙**。手順は順序付き・欠落なし |
| **低認知負荷** | 見出しは outcome を述べる。前方参照禁止。深掘りは `:::details` に progressive disclosure |
| **用途が瞬時にわかる** | **第一画面（タイトル + 掴み）**で「これは何 / 読後に何ができるか」が伝わる。結果駆動タイトルが主役。「わかること」1 行の blockquote は**任意の装置** — タイトル 50 字に載せきれない約束があるときだけ使う（全記事同一の定型行は corpus レベルのテンプレ臭になる） |

### 「低密度」の誤読を防ぐ（重要）

**情報密度を下げる ≠ 内容を薄くする。** 削るのは冗長・前置き・二重説明であって、技術的実質は削らない。深い記事でも、余計な認知負荷を載せなければ実用軸に乗る。「浅い記事を量産する」ことではない。

### 環境依存の実装は「人間向けナラティブ → エージェント向け実装契約」に分ける

次の 3 条件をすべて満たす記事では、二層構成を既定にする。

1. 読者のローカル環境・設定・既存ファイルを変更する
2. 絶対パス、既存設定、シンボリックリンク、認証状態などによって正しい手順が変わる
3. コーディングエージェントが読み取り専用で環境を調査し、個別の実装計画を作れる

**前半は人間向けの記事として完結させる。** 問題、既存手段が足りない理由、採用する境界、残すもの、トレードオフ、成功状態までを説明する。後半を読まない人にも「自分に必要か」「何を変える設計か」が伝わらなければならない。技術情報を落とすのではなく、人間の判断に必要な事実は前半へ、環境固有の実装条件は後半へ配置する。

**後半は単独でエージェントへ渡せる実装契約にする。** 記事 URL と prompt を渡すだけで、エージェントが次を行える状態にする。

- 最初は読み取り専用で調査し、変更を加えず計画で止まる
- 変更対象と変更しない対象を列挙する
- 既存ファイルを上書きせず、差分・競合・シンボリックリンク・絶対パスを確認する
- 各手順に復旧方法、検証方法、成功条件を付ける
- LLM の自己申告ではなく、ファイル・ログ・コマンド出力など実体で検証する
- 未検証の前提と、人間が承認すべき判断点を分離する
- 明示承認を受けるまで実装しない

prompt の直後には、人間が承認時に見る要点を短く置く。読者へ「記事をそのまま実行させる」のではなく、**この記事を材料に、その環境用の計画を作らせる**。

この構成は全記事へ一律適用しない。安全で安定した単一コマンド、環境差のない API 例、概念解説だけの記事では、通常の人間向け how-to を使う。後半を agent handoff にしたことを理由に、前半の説明や技術的根拠を省略してはならない。

### 導入の設計（一瞬でわかる × 引き込み）

記事の軸は「読者のどの問題に効くか」。著者の体験談は素材であって軸ではない（2026-07-11 の記事再構成で確定）。ただし軸が正しくても、**引き込みがなければ読み始まらない**（2026-07-30 Kaguura 原則の取り込みで改稿 — docs/adr 参照）。全記事の既定構成は「一瞬でわかる → 引き込み（掴み）→ 緊張 → 解決 → Higher Ground」。

- **一瞬でわかるは第一画面の機能要件** — 結果駆動タイトルと掴みで「これは何 / 読後に何ができるか」が伝わること。「わかること」1 行はタイトルで足りないときだけの任意装置（2026-07-30 必須化を廃止 — 掴みの前のメタ行は小さな warm-up fluff であり、タイトルの約束の二重化）
- **掴みは読者の問題を具体的シーンとして描く** — 読者が「自分のことだ」と感じる具体的な場面・あるあるから入る（低認知負荷の Calm Story）。壁の箇条書きは掴みの一実装であって必須形式ではない。箇条書きにするなら、各項目が読者の実感に接地した具体的な文であること（抽象的な問題リストは掴みにならない）
- **掴みと結論の少なくとも一方で、読者に直接語りかける**（2026-08-20 追加。正本: writing-ecosystem「語りかけの積極形」）— 読者の状況を名指す問い・直接の指示・読者主語の約束のいずれかを 1 箇所以上。三人称の状況描写だけの掴みは「自分のことだ」の半分しか作れない — 読者に向いた文が「言われている」感を作る。名指しは具体的に（誰にでも当てはまる一般論の問いは語りかけにならない）
- **緊張 → 解決** — 掴みの後に、問題の深さ・放置コスト・パラドックスを短く示し（Plunge）、成果物をそれへの答えとして提示する
- **禁止は warm-up fluff** — 執筆理由・背景説明・読者に接続しない自分語りの前置き。個人的エピソード自体は禁止しない — **読者の問題に接続するエピソードは掴みとして機能する**。接続しないエピソードが離脱要因（従来の「個人的エピソード始まりは離脱要因」の一律禁止はこの精密化で置き換え）
- **体験談は各論の中で「解決の証拠」として使う** — 「私の運用でこれが解決したのは〜」の形で、対応する論点の直下に 1 段落へ圧縮して置く
- **制作過程のメタ話は本文に置かない** — どうレビューを回したか・どう公開したか等は読者の問題解決に寄与しない。削除するか、脚注・別記事に逃がす

判定: 導入に (a) 読者の問題が具体的シーンとして登場するか、(b) 緊張（放置コスト・パラドックス）があるか、(c) 掴みか結論に読者へ向いた語りかけ（問い・指示・約束）があり、それが読者の具体的状況を名指しているか、を確認する。エピソードが導入にある場合は「読者の問題に接続しているか」で採否を決める。

## 語り：直接指示（essay との最大の差別化点）

**文体（ですます / だ・である）の実値はここには無い** — `.claude/rules/zenn-writing.md` の
チャンネル表が正本。本節が持つのは**語りの型**で、これは文体とは別の軸。

essay が「〜ではないか」と問い化するのに対し、**実用 how-to は直接指示で言い切る**。

| | essay | 実用（このスキル） |
|---|---|---|
| 語り | 発見調（〜だった、〜に見えた） | 直接指示（〜します、〜してください） |
| 結論 | 問い化（〜ではないか） | 言い切り（〜になります、〜できます） |
| 例 | 「〜と読める」 | 「まず X します」「Y を実行します」 |

- 文体は **1 記事内で混在させない**（混在は読者にノイズ）
- AI-slop 禁止と誠実さは essay と共通。「言い切る」と「煽る/誇張する」は別物——`writing-ecosystem` の Title Conventions と禁止リストは実用記事でも守る
- 英語名詞句の連結禁止は `writing-ecosystem`「専門用語の緩和策」が正本（ここには再掲しない）

## Diátaxis での位置づけ

Zenn/Dev.to 実用記事は Diátaxis の **how-to（課題達成）** と **reference（逆引き）** 象限。

- **how-to** — 「X を Y する方法」。ゴール駆動。読者は目的を持って来る
- **reference** — 「X の設定/API 一覧」。lookup 駆動
- **tutorial**（学習 journey）— 副次的に可（初心者向け連載など）
- **explanation**（なぜ論・思索）— **対象外**。essay 象限 → `writing-ecosystem` / note → Substack へ

## 実用記事の構成テンプレート

```markdown
# タイトル（成果物 or 解く課題が一目でわかる。結果駆動 — 第一画面の主役）

[任意: タイトルに載せきれない約束があるときだけ > **この記事で作れるもの/わかること**: 1 行]

[掴み: 読者の問題を具体的シーンで描く（Calm Story）→ 緊張: 放置コスト・パラドックスを短く → 成果物を答えとして提示。「導入の設計」参照]

## 前提
- [バージョン・必要なアカウント・前提知識]

## [手順 or 逆引き見出し（outcome を述べる）]
（実コード：コピペで動く。file path + 言語タグ）
（input → output を示す）

[条件付き: 環境依存の変更なら、ここまでで人間向けナラティブを完結させる]

## [この設計をあなたのエージェントに計画させる]
[読み取り専用の環境調査と計画だけを求める、単独で渡せる prompt]
[人間の承認点 → 承認後の実装依頼 → 実測による成功条件]

## 落とし穴 / Tips
:::details ハマったら
[progressive disclosure。本筋を膨らませない]
:::

## まとめ（Higher Ground — 読者が「学んだ」と感じて終える。次にできること）

## 関連リンク（本文で著者自身のリポジトリ/ツールに言及した場合）
[記事内で紹介した外部リポジトリ・ツールの URL を再掲。最後まで読んだ読者は導入意欲が高い。**紹介 repo が1つでも、著者の GitHub ハブ（プロフィール/一覧 repo）への導線を必ず含める**——ハブは読者を著者の全リポジトリへ送るので、言及 repo の数に依らず付ける。具体的なハブ URL はユーザー固有の設定なので、この skill には書かず**プロジェクト側の規約（例: CLAUDE.md）で指定する**]
```

形式・記法・frontmatter・emoji・topics の詳細は [zenn-format](../zenn-format/SKILL.md) が正本。

## 執筆プロセス（サブエージェントに委譲しない）

記事の執筆は Claude Code 本体が直接行う。専用の執筆エージェントには委譲しない。

### Phase 0: 記事タイプ判定（Phase 1 より前）

構成案の前に [zenn-editorial-judgment](../zenn-editorial-judgment/SKILL.md) の「記事タイプの事前判定」を通す。**立場表明・マニフェスト**と判定された記事では装置系項目が免除される — **免除される装置の定義は下の「受け入れチェックリスト」が持つ**（ここには再掲しない）。

### Phase 1: 構成案（着手前に確認）

1. **読者の問題文を 1 文で書く** — 「◯◯に困っている読者が、この記事を読むと◯◯できるようになる」。これが書けないネタは実用軸に乗らない（軸の再考 or essay チャンネルへ）。以降の構成・導入・タイトルはすべてこの 1 文に従属させる
2. 素材を読み込み、**コア論点**を 1 文で書く
3. 独立論点を数える。**4 を超えるなら分割を提案**（Zenn/Dev.to チャンネルの実値。エッセイチャンネルの同値は `essay-reviewer` が別に持つ — 片方だけ動かさない）
4. シリーズ記事なら先行記事との重複リスクを確認
5. 実装面を `人間向け how-to` / `人間向けナラティブ + エージェント向け実装契約` のどちらで渡すか宣言する。二層構成の 3 条件に該当するなら後者を既定にする
6. セクション構成案を提示し、**ユーザー確認を待ってから執筆に入る**

### Phase 2: 執筆

上記の「実用軸の 5 ルール」「文体」に従って直接執筆する。

### Phase 3: 自己プリフライト（レビューエージェントに渡す前）

- [ ] 独立論点数が上限内（Phase 1 参照）
- [ ] AI-slop スキャン（`writing-ecosystem` の禁止リスト）
- [ ] タイトルが規約に合致
- [ ] 用語が初出で説明されている
- [ ] シリーズ先行記事との重複がない
- [ ] 段落密度の閾値超過がない（正本: `writing-ecosystem`「段落密度の機械的閾値」。全段落について確認）
- [ ] **10% 編集パスを実施した** — 第 2 稿 = 第 1 稿 − 10%。warm-up・中盤の繰り返し・つなぎ語を削り、「論点を進めない文」を残していない（正本: writing-ecosystem の Craft 規約）
- [ ] 二層構成を採用した場合、前半だけで人間向けナラティブが完結し、後半だけで読み取り専用の計画依頼として成立する

## 素材集め（書く前の準備）

実用記事は具体素材が命。書き始める前に:

1. **並列リサーチ** — 対象技術 / 組み合わせ先 / 既存記事との差別化ポイントを Task tool で並列に調べる
2. **実体験ログ** — つまずき→原因→解決を表（#, 問題, 原因, 解決）に整理。記事の「オチ」になる気づきを特定
3. **context ファイルに集約** — `drafts/article-context_<topic>-<date>.md` に企画・タイムライン・技術コンテキスト・差別化・リサーチ要点をまとめてから執筆。
   セッション内外の素材を証拠台帳（Claims Register・一次/⚠未検証の tier 付き）にまとめるなら
   **global `collect-context` skill を読んでから実行する**（手順の正本はあちら。台帳は fact-checker への入力にもなる）

AI 対話などの**生ログ**は `articles/_context/{slug}-{source}-log.md` に退避する（Zenn の同期対象外。詳細は `.claude/rules/zenn-writing.md`）。

## 受け入れチェックリスト（客観・全 Zenn/Dev.to 記事）

公開前に機械的に確認できる項目。`quality-gate` skill がこれを gate する。

**装置の定義（免除の対象。この 5 つが唯一の定義）**: ①**実用記事の掴み**（読者の問題を
具体的シーンで描く導入）②判断表 ③診断コマンド ④任意の「わかること」1 行 ⑤前提列挙・図/表 ≥1。
**立場表明・マニフェスト**と判定された記事（Phase 0 参照）ではこの 5 つを免除する。

**免除されないもの**: 導入の骨格そのもの（Calm Story → Plunge → Solution → Higher Ground）。
「掴み」という語は 2 つの意味で使われるので注意 — 免除するのは①**実用記事の掴みの形式**であって、
エッセイ 4 段構成の Calm Story ではない。立場表明は 4 段構成で導入を組む。

- [ ] 第一画面（タイトル + 掴み）で「これは何 / 読後に何ができるか」が伝わる（「わかること」1 行は任意 — 置く場合はタイトルの重複でなく補完になっているか確認）
- [ ] 導入に読者の問題が具体的シーン（掴み）として登場し、緊張 → 解決の流れがある。体験談は「読者の問題に接続する掴み」か「各論内の解決の証拠」に限る（「導入の設計」参照）
- [ ] 前提を列挙している
- [ ] 実コードがコピペで動く（file path + 言語タグ付き）
- [ ] 図/表が ≥1 ある
- [ ] 見出しが outcome を述べている（scannable）
- [ ] 1 節 1 論点、前方参照なし
- [ ] AI-slop なし（`writing-ecosystem` の禁止リスト）
- [ ] 本文中の自リポリンクが「導線 or 一次資料」に限られている（クレジット型は関連リンク節へ。`writing-ecosystem` の自リポ言及の節度）
- [ ] 独立論点数が上限内（判定の閾値は レビュー agent が持つ。Phase 1 参照）
- [ ] 文体がチャンネル表（`.claude/rules/zenn-writing.md`）どおりで、1 記事内で混在していない
- [ ] 見出し・地の文で英語名詞句を複数連結していない（カタカナ化/日本語訳。固有名詞・定着語は例外）
- [ ] 説明なしで見出しにだけ登場する専門用語がない（初出定義 or 見出しから除去）
- [ ] 環境依存の変更記事では二層構成の採否を判断済み。採用時は (a) 前半だけで判断できる、(b) 後半が計画で停止する、(c) 変更対象・非対象・復旧方法・成功条件・人間承認点がある

## Anti-Patterns

- ❌ **完成稿の事後リライトでエンゲージ最適化** → これは catchify（ADR-0001 で禁止）。このスキルは**書く時の生成既定**であって、書き上げた文章を読者受け狙いで作り替える pass ではない。「誰のために変えるか」（著者の思考 vs 読者受け）が判定式
- ❌ **情報密度を下げる＝内容を薄くする** → 削るのは冗長・前置きだけ。技術的実質は残す
- ❌ **図を飾りで入れる** → 理解を 1 ステップ短縮する図だけ。装飾図は認知負荷を上げる
- ❌ **essay の問い化・発見調を持ち込む** → それは `writing-ecosystem` の領分（文体はチャンネル表が正本）
- ❌ **動かないコード / 断片だけのコード** → コピペで動かないコードは実用軸違反
- ❌ **環境依存の変更コマンドを、そのままエージェントに実行させる** → まず読み取り専用で環境を調査し、計画と承認点を出させる
- ❌ **後半をエージェント向けにしたので前半の根拠を削る** → 分けるのは読者と実行責任。情報量ではない
