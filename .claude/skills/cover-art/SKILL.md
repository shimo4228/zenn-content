# cover-art — 記事の見出し画像

見出し画像は、読者が記事を開く前の期待を作る。画像を添えるだけで見出しは「正しそう」に見え、
誤った期待は本文を読んだ後も残る。だから本文が回収しないものを絵で足さない。
この skill の目的はクリック率ではない。題と画像だけを見た人の期待が本文と一致することを目指す。

## 入力と完了条件

入力は、内容 GO とタイトル確定が済んだ原稿の path と、出す媒体。作るのはこの後で、題と命題が
動くと画像の主題も動くからである。

画像は、Codex で案ごとに 1 枚ずつ並列に生成して著者が 1 枚を選ぶ（下の「生成」）か、著者が自分の生成ツールで
作る。この skill は主題の案・プロンプト・生成・点検を受け持つ。

完了は、媒体ごとの画像ファイルが下の「点検」を全部通り、alt が決まった状態。

headline-craft が見出し画像の構図メモ（焦点の対象・要素の数）を出していれば、主題を決める材料に使う。記事の
見出し画像には文字を入れないので、構図メモの文字の位置は使わない。

## 媒体の仕様

| 媒体 | 寸法・容量 | 切れ方 | 置き場 |
|---|---|---|---|
| note | 推奨 1280×670（約 1.91:1）、最大 10MB | 推奨と違う比率はトリミングされ、ブラウザとアプリで見え方が違う | `images/covers/<slug>-note.png` |
| Substack | post / social preview は 1200×630 以上 | Center か Smart で自動に切り抜く。公式ページは同じ箇所に「14:10」とも書いていて、数値どうしが合わない | note と同じ 1 枚 |
| DEV | cover は 1000×420（約 2.38:1） | 上下が切れる | `images/covers/<slug>.png`（GitHub raw URL で参照する） |
| Zenn | 見出し画像の欄がない（emoji が担う） | — | 作らない |

as-of: note は noteヘルプ「登録画像の推奨サイズ一覧」（2026-10-01 閲覧）。Substack と DEV は 2026-11-02 の調査で、
Substack の 1200×630 は第三者の解説とも一致する。

原版は 1 枚、1280×670 で作る。主題と意味を担う部分は中央の 60% に収める。Substack の小さいリンクカードが一番
きつく切り、DEV は上下が切れるので、周辺は切れても意味を失わない余白にする。DEV 用は原版から切り出す。

```sh
sips -c 538 1280 images/covers/SLUG-note.png --out images/covers/SLUG.png
sips -z 420 1000 images/covers/SLUG.png
```

## 主題を決める

1. 記事を 1 文に要約し、題と画像を見た人が一目で何を感じるかを「視覚の命題」として 1 文で書く
2. 視覚の命題を、比喩 1 つで描く。比喩の材料は本文の中から取る — 本文が使う比喩・概念の名前（「外部の目盛り」
   「説明する側に回る」など）や、本文の具体物どうしの関係（並び・向き・距離・大きさ）。本文の物をそのまま写した
   だけの絵は、正しくても何も問わない（2026-11-14 の 3 案で著者が「なんとも言えない」と止めた）。本文に無い
   比喩の物を足すと、開いた読者が別の話だと受け取る
3. 題が言うことを画像で繰り返さない。題は何を論じるかを言い、画像は何について・どの場面から論じるかを見せる。
   意味をずらして好奇心を作ることはしない
4. 本文に無い人物・出来事・成果は描かない。実在の人物と、撮影したように見える出来事の場面も描かない（画像は
   見出しの真実らしさを押し上げる）
5. 案を 2〜3 個出す。各案に視覚の命題と「比喩の材料が本文のどの段落の、何か」を 1 行添え、著者が選ぶ。宗教や思想の色が強い画風は、
   著者が本文で避けた色と照合する

## プロンプト

制約は混ぜずに、次の 6 行に分けて書く。生成ツールに比率・サイズ・除外の設定があれば、プロンプトとは別にそれも
使う（Midjourney は `--ar` と `--no`、OpenAI と Gemini の画像 API は size / aspect ratio）。

- **用途と命題**: 「note の記事の見出し画像」と用途を言い、視覚の命題を 1 文で書く
- **内容**: 比喩の場面。素材・形・光・画材を名指しする（曖昧な主題は平均的な絵になる）
- **構図**: 主対象を中央 60% に置く。小物・細い線・細かい模様を減らし、大きな形と色面で描く
- **文字**: 文字・数字・ロゴ・透かし・看板・文字に見える模様を入れない（題は媒体のタイトル欄が出す）
- **形式**: 1.91:1、1280×670 以上。1.91:1 を選べないツールでは 16:9 で作り、高さを幅÷1.91 に切る
  （例: 1920×1080 なら `sips -c 1005 1920 <in> --out <out>`）
- **避けるもの**: 本文に要らなければ、人型ロボット・光る脳・回路模様・青紫のネオン・ホログラムの画面・「AI」の文字。
  代わりに本文固有の物・行為・場所を描く

画風は前の記事に揃えない。主題と同じく、画風（色域・光・質感・写真調か絵か）も記事ごとに本文の内容から選び、
主題の案と一緒に出す。前の記事の見出し画像と揃えるかは聞かない（2026-11-14 著者判断）。

## 生成（Codex）

主題の案 2〜3 個それぞれに 6 行のプロンプトを英語で書き、Codex CLI の `$imagegen`（gpt-image-2）で 1 案 1 枚を
並列に作る。案を 1 つの呼び出しにまとめると、案どうしが似る。作業ディレクトリは scratchpad の下に記事ごとに切る。

```sh
S=<scratchpad>/cover; mkdir -p "$S"   # p1.md〜p3.md に案ごとのプロンプトを置く
for i in 1 2 3; do
  (printf '$imagegen Read p%s.md in the current directory and generate exactly one image with gpt-image-2 from that specification. Save it as %s/cover-%s.png. Reply only with the saved path.\n' "$i" "$S" "$i" \
    | codex exec --skip-git-repo-check --sandbox workspace-write -C "$S" - > "$S/log-$i.txt" 2>&1 &)
done
```

- 指示は stdin で渡す（`-` が stdin の印）。`$imagegen` を引数に書くとシェルが変数として展開するので、printf の
  単一引用符の中に置く
- 終わりは `cover-*.png` が 3 枚そろうか、`codex exec` の process が無くなったかで見る。1 枚は 1〜数分かかる。
  失敗した案は `log-<i>.txt` の末尾で理由を読み、その案だけ回し直す
- 3 枚を Read で開いて点検 1〜3 を先に済ませ、通った案を著者に見せる。著者が「どれも違う」と言ったら、
  画像を足すのでなく主題の案（比喩の選び方）からやり直す（2026-11-14 の 1 回目がそうだった）
- 比率は生成ツール任せになる。2026-11-14 は 1734×907（1.912）で出て、切らずに使えた。1.90〜1.92 から外れたら
  上の「形式」の行のとおり `sips -c` で高さを切る
- 選んだ 1 枚を `images/covers/<slug>-note.png` に写す。生成に使ったプロンプトとログは scratchpad に置き、repo に入れない

## 点検

著者が画像を置いた後、順に行う。

1. **寸法と容量** — 原版は幅÷高さが 1.90〜1.92、幅 1280 以上、10MB 未満。DEV 用は 1000×420 ちょうど。透過があれば、暗い背景で線が消えるので
   不透明に書き出し直してもらう

   ```sh
   sips -g pixelWidth -g pixelHeight -g hasAlpha images/covers/SLUG-note.png
   ls -l images/covers/SLUG-note.png
   ```

2. **目視** — 画像を Read で開き、文字・文字に見える模様・個人情報・画面の写り込みが無いこと
3. **縮小** — 長辺 320 に縮めた写しを開き、一番目に入るものが選んだ主題か。四辺が白い背景にも暗い背景にも溶けないか

   ```sh
   sips -Z 320 images/covers/SLUG-note.png --out <scratchpad>/cover-small.png
   ```

4. **期待の一致** — 本文を読んでいない読み手に、題と画像だけを見せる。聞くのは「何の話だと思うか」と
   「何が出てきそうか」で、自由に答えてもらう。本文未読の人に見せられるなら、それを優先する。headline-craft が
   題の初見読みに使う `read.sh` は文字しか渡せないので、画像はサブエージェントで代える。画像を
   `<scratchpad>/cover-check.png` に写し、題とその path だけを渡す（本文・brief・slug は渡さない）。repo の文脈は残るので、
   補助の読みとして扱う。答えに本文の中心の対象が一つも出なければ、主題を選び直す
5. **回収** — 画像が示す物・人・場面を 1 つずつ、本文の段落に対応させる。対応しないものは画像から消してもらう

## alt と AI 開示

- **alt**: 題と重なるだけの飾りなら空にする。本文の具体物を示す画像なら、その画像が記事について伝えることを
  1 文で書く（見た目の逐語説明にしない）。入力欄がある媒体では入れる（Substack は画像のメニューから編集できる）
- **AI 開示**: AI で生成した画像を使うとき、本文末尾の AI 開示に画像の 1 文を足すかを著者に聞く。開示の型
  （`.claude/skills/writing-ecosystem/references/publication-procedures.md`）の枠に画像の項目は無く、内容 GO 後の本文に
  触れるので著者が決める。足すときの例（illustrative）: 「見出し画像は <ツール名> で生成し、描くものと構図は私が
  選びました。」

## 則の強さ

上の則は、根拠の強さが揃っていない。弱い則は、著者が記事に合わせて破ってよい。

| 則 | 根拠 |
|---|---|
| 画像は期待と真実らしさを作るので、本文に無いものを足さない | 強い（無作為化した実験が複数） |
| 画像に文字を入れない | 強い（アクセシビリティの公式基準）。クリックや理解への効果は中程度 |
| 比率・中央寄せ・縮小と切り抜きの点検 | 強い（媒体の公式仕様） |
| 題と画像で役割を分ける | 中程度（隣接分野からの推論） |
| 本文から取った比喩 1 つで視覚の命題を描く | 弱い（編集のイラストの実践者の指南が一致する。直接比べた研究はない。2026-11-14 に「比喩より本文の具体物」から著者判断で反転） |
| AI 記事の定番の絵を避ける | 弱い（特定の絵柄の評価を測った研究がない。AI 生成と見られると信頼が下がる場面があることは複数の研究にある） |
| 画風も記事の内容から選び、シリーズで揃えない | 著者の判断（2026-11-14）。揃える側の根拠はブランド研究と note の公式ガイドで中程度、個人のシリーズを比べた実験はない |
| 期待の一致を指標にする点検 | 弱い（この用途で検証された手法ではない。誤誘導の研究を目的に合わせて組んだもの） |
