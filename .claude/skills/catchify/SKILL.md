# Catchify — 記事構造キャッチー化スキル

読者が冒頭30秒で「読み続ける」と決める構造で記事を書く。zenn-writer の「声のトーン・タイトル設計」を補完し、「冒頭・見出し・セクション書き出し」の構造パターンを定義する。

## いつ使うか

- **新規執筆時**: zenn-writer と併用。冒頭と見出しの設計段階で参照する
- **既存記事のリライト**: レポート調で書かれた記事の構造を事件調に変換する
- **editor レビュー前**: editor に渡す前に構造を整えておく（editor 後の大幅書き換えを防ぐ）

## 診断フェーズ: 二極分化チェック

記事を読み、以下の2タイプに分類する。

| タイプ | 特徴 | 判定基準 |
|--------|------|----------|
| **キャッチー型** | 冒頭が「事件」で始まる | 冒頭3行に数字・失敗・矛盾・ツッコミがある |
| **レポート型** | 冒頭が「説明」で始まる | 冒頭が「〜を作った」「〜がある」「〜について」で始まる |

**レポート型と判定したら、以下の改稿パターンを適用する。**

## 改稿パターン

### 1. 冒頭3行の事件化（最重要）

Zenn のフィードでタイトルをクリックした読者は、冒頭3行で「読み続けるか」を決める。

**必須3要素:**
1. **具体的な数字** — 8,500行、61%、397問、200回
2. **予想外の展開** — 「ゴミだった」「壊滅的だった」「キレられた」
3. **短い感情的な一言** — 1文。パンチライン。

**変換パターン:**

```
# BEFORE（レポート型）
Claude Code を使い始めて 1 ヶ月、気づけばセッション数は 270 を超えていた。

# AFTER（事件型）
承認ダイアログを 1 日 200 回叩いた。コンテキストが飛んで
「さっきの話、覚えてないんですけど」と言われた。
```

```
# BEFORE（レポート型）
Claude Code のスキルコレクションを定期的に棚卸しする
`/skill-stocktake` コマンドを作った。

# AFTER（事件型）
同じプロンプトで同じファイルを処理させたら、毎回違う
ファイル一覧が返ってきた。3回やって3回とも違う。
```

**アンチパターン:**
- 自己紹介から始める（「筆者は〜」「〜を使い始めて」）
- 定義から始める（「〜とは」「〜がある」）
- 目的から始める（「この記事では〜」「本記事の目的は〜」）

### 2. 見出しの感情化

見出しは記事のスキャンポイント。読者は見出しだけ流し読みして、読むセクションを選ぶ。

**変換ルール:**
- 機能名ではなく「何が起きるか/起きたか」で書く
- 読者の痛みか、驚きを入れる
- 疑問形・命令形・体験形のいずれかにする

| BEFORE（機能名） | AFTER（体験） |
|-------------------|---------------|
| ステータスラインでコンテキスト残量を可視化する | コンテキストが飛ぶ前に気づく |
| パーミッション許可リストで承認ダイアログを消す | 「許可しますか？」を 1 日 200 回叩く地獄から抜ける |
| PostToolUse フックで自動テスト | Claude に TDD を強制する |
| プロジェクトスキルとグローバルスキルを分ける | iOS 開発中に textlint を引用された日 |
| エージェントに起動条件を教える | 「レビューして」と毎回頼むのをやめた |

### 3. セクション書き出しの問題先行

各セクションの最初の文を「効果」「機能説明」ではなく「問題」か「事件」から始める。

**変換パターン:**

```
# BEFORE
**効果**: コンテキストウィンドウの突然死を防ぐ。

# AFTER
Claude Code の最大の罠は、コンテキストウィンドウが
静かに埋まっていくことだ。
```

**「効果:」ラベルは全削除する。** 効果は読めば分かる。問題を先に書けば、読者は「自分にも起きている」と感じて読み続ける。

### 4. AI の人格化

AI を「ツール」ではなく「同僚」として記述すると、読者の感情移入が生まれる。

| ツール記述 | 人格化記述 |
|-----------|-----------|
| Claude Code がコマンドを実行する | Claude が勝手に `git add .` した |
| エージェントが品質チェックを行う | Claude 自身に直させる |
| セッション終了時に検証する | 散らかしたまま帰ろうとするのを止める |

### 5. 結論の結晶化

結論は「まとめ」ではなく「一言で言い切る」。

```
# BEFORE
10 個の設定に共通するのは、「意識しなくても勝手に動く」ことだ。

# AFTER
デフォルトのまま Claude Code を使うのは、
シートベルトなしで高速道路を走るようなものだ。
```

## チェックリスト

改稿後に以下を確認する。

- [ ] 冒頭3行に「数字」「予想外」「パンチライン」の3要素があるか
- [ ] 見出しが「機能名」ではなく「体験」になっているか
- [ ] 各セクションが「問題」か「事件」から始まっているか
- [ ] 「効果:」ラベルが残っていないか
- [ ] AI が「ツール」ではなく「人」として書かれているか
- [ ] 結論が「まとめ」ではなく「一言」になっているか

## 適用しないケース

- **HowTo/チュートリアル記事**: 手順の明確さが最優先。冒頭は「何ができるようになるか」でよい
- **リファレンス/チートシート記事**: 網羅性が価値。ドラマは不要
- **すでにキャッチー型の記事**: 過剰な煽りは逆効果。診断フェーズで「キャッチー型」と判定したらスキップ

## 他スキルとの連携

### 新規執筆フロー

| 順序 | スキル | 役割 |
|------|--------|------|
| 1 | `zenn-writer` + **`catchify`** | タイトル・声のトーン（zenn-writer）+ 冒頭・見出し・書き出しの構造（catchify） |
| 2 | `editor` agent | 技術的正確性・品質レビュー（内容に大幅なメスが入る） |
| 3 | ユーザー確認 | 最終判断 |
| 4 | `seo-optimizer` + lint | タイトル最終調整 + textlint/markdownlint（最終版に1回だけ） |

### 既存記事リライトフロー

| 順序 | スキル | 役割 |
|------|--------|------|
| 1 | **`catchify`** | 診断 → レポート型ならリライト |
| 2 | `editor` agent | リライト後の品質確認 |
| 3 | ユーザー確認 | 最終判断 |
| 4 | lint | textlint + markdownlint（最終版に1回だけ） |

**lint は常に最終工程。** editor が内容を大幅に変更するため、editor の前に lint しても二度手間になる。

### zenn-writer との分担

| 観点 | zenn-writer | catchify |
|------|-------------|----------|
| タイトル設計 | 9パターン、40文字ルール、3案比較 | — |
| 声のトーン | 毒ユーモア、刃牙リファレンス | — |
| 冒頭3行 | — | 事件化（数字・予想外・パンチライン） |
| 見出し | — | 機能名→体験に変換 |
| セクション書き出し | — | 問題先行、「効果:」ラベル禁止 |
| AI の描写 | AI へのツッコミ | AI の人格化（同僚として記述） |
| 結論 | — | 結晶化（一言で言い切る） |
