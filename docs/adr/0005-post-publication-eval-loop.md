# ADR-0005: 実測ベースの事後 Eval ループ — 予測型エンゲージメントレビュアーの不採用

## Status

Accepted (2026-07-27)

## Context

「読者が有用・面白いと感じたか、フォローしたいと思ったか」という読者価値の視点を記事品質アップに繋げたい、という要求から出発した。既存レビューチェーン（editor / fact-checker / zenn-clarity-reviewer / codex-review）は全て欠陥検出型で、「欠陥ゼロだが読者に刺さらない記事」を検出する装置がなかった。

選択肢は 2 系統あった: (a) 公開前に LLM が面白さ・フォロー意向を推定する**予測型レビュアー**、(b) 公開後の実測メトリクス（いいね・reactions・views・フォロワー）で閉じる**事後 Eval ループ**。

## Decision

**事後 Eval ループを採用し、予測型レビュアーは作らない。**

構成（grill-me で確定した 5 決定点）:

1. **収集**: `scripts/metrics_snapshot.py` が Zenn（非公式 API、認証不要）と Dev.to（DEVTO_API_KEY）から記事単位メトリクス + フォロワー総数を取得し、`scripts/metrics/snapshots.jsonl` に追記する（raw 値のみ、上書きなし）
2. **トリガー**: `article-stocktake` skill 実行時に都度取得。launchd 自動化はしない（累積値なので情報は失われず、常駐ジョブの保守を避ける。Prototype Before Scale）
3. **置き場**: 生データは public repo 内（公開情報の写し、Build in Public と整合）。判定（ランク・所見）は非公開の memory `article-quality.md`
4. **ランクとの関係**: 実測 tier（相対 上位/中位/下位）を既存の内容品質ランク A/B/C と**別軸で並記**する。乖離が主シグナル — A×実測下位 = 配信・タイトルの問題（Distribution 層で対処）、B/C×実測上位 = 読者需要のあるテーマ（企画の判断材料）
5. **還流の線引き**: ideation Step 1 の**情報源**に実測サマリを追加するが、**推薦理由・優劣づけには使わない**。ideation Notes の「検索流入やバズを理由にテーマを推薦しない」（Content Integrity）は維持する

## Alternatives Considered

- **予測型エンゲージメントレビュアー（公開前に LLM が推定）** — 不採用。理由 3 点: (1) chain 内レビュアーは「指摘 → 修正」の圧力構造を持つため、フォロー意向最適化の指摘は catchify（エンゲージメント目的の事後改変、ADR-0001 で禁止）の再導入になる。(2) 「面白さ」は decidable でなく、実測 ground truth が入手可能なのに LLM の憶測で代替することになる。(3) 旧バズ傾向分析のタイトル設計ルールは 2026-03-24 に「概念の誠実な呼びかけ」への転換で廃止済みで、予測 judge はこの転換の巻き戻しになる
- **launchd 定期自動収集** — 不採用（現時点）。公開直後の伸び速度分析が必要になったら再検討。まず手動リズムで価値を確認する
- **実測をランク基準に統合（実測低迷は降格）** — 不採用。内容品質と実測読者価値を 1 軸に混ぜると「良い記事だが届かなかった」という乖離情報（このループの主シグナル）が消える
- **配線せず人間が読むだけ** — 不採用。還流が著者の記憶頼みになり、ループが閉じない

## Consequences

- 記事品質の改善が「予測の議論」でなく「実測の乖離」から始められる。旧バズ分析（memory: buzz-analysis.md）と違い、還流先がタイトル・インプレッション（Content 改変圧）ではなく企画・配信レイヤーに限定される
- 公開前チェーンは欠陥検出に純化されたまま増えない（ADR-0004 の「機械検査できない直交観点のみ agent 追加可」とも整合 — 読者価値は実測で機械観測可能なので agent を作らない）
- snapshots.jsonl は追記のみで成長する。肥大化したら年次ローテーション等を検討（現状 1 回 ~120 行なので月次でも年 1.5k 行程度、当面問題ない）
- フォロワー総数は記事帰属不能な粗い指標に留まる（トレンドのみ）
