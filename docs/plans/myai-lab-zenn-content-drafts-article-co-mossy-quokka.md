# Zenn 記事執筆: lint は足し算ではなく引き算の道具

## Context

証拠台帳 `drafts/article-context_tdd-scaffold-dissolution-timing_2026-08-28.md` を素材に
Zenn 記事を 1 本書く。

台帳が想定していた枠（「モデル世代が上がったときテスト規律をいつ畳むか」）は、著者との
検算で**成立しないことが判明した**。棄却した前提と理由:

| 台帳の前提 | 棄却理由 |
|---|---|
| chaos-TDD が「畳めなかった規律」 | `CLAUDE.md:88` 自身が「新しいチェーン段ではなく TDD ステップ内の規律」と書いている。Chain Matrix の発火条件とは水準が違い、対比に使えない。機械強制も無い（`verify.sh` / `verify.md` に entry 0 件） |
| `generation-audit` の invoke 1 回 = 形骸化 | Opus 5 リリース時に作って以来 Claude は新モデルを出していない。**1 回は設計どおりの正常値** |
| verify ゲート 3 週間沈黙 = 命題の反証 | 単なる失念。修理も exit 71 の分岐 1 つ。持ち上げすぎ |

著者が示した実際の枠は 3 段階:

1. 最近の一連の作業は**オーバーエンジニアリング抑制のシリーズ**。実装チェーンを
   太らせすぎたので削っている
2. **その中で lint は「足すもの」ではなく「減らす方向の道具」**。一瞬で終わり LLM の
   ようなコストもかからない。lint でカバーできない本当に重要なところへ LLM を移している
3. **足したのも複雑性チェックと予算。コードをシンプルにするためならもっと足したい。
   放っておくと LLM のコードは複雑になる**

3 点目が軸を確定させる。「足すか減らすか」ではなく **「複雑さが増える方向か、減る方向か」**
で見ている。lint は行数としては足し算だが複雑さとしては引き算なので、躊躇なく足せる。
LLM レビューの系統は行数でも複雑さでも足し算なので削る。

一次ソースにも接続が残っている。ADR-0055（8/27）が監視計器の新設を却下して「削減だけが
機構総量を減らせる唯一の手である」と書き、その**翌日** ADR-0056 が同じ却下へ日付つき注記で
射程を狭めた（「増えるのは既存 config の行だけ」）。

意図する成果: LLM レビューを積み上げて重くなった読者へ、**足す／減らすではなく複雑さの
増減で見る判断軸**と、**何を機械へ降ろせて何を降ろせないか**の見分け方を渡す。
`review-chain-damping`（未公開、ADR-0055 = なぜレビューを減らしたか）の続編。

### 著者確認済みの決定（2026-08-28）

- **中心命題**: lint は減らす方向の道具。機械で終わることを降ろし、LLM を本当に重要な
  ところへ移す
- **シリーズ化**: 本文で明示する（「ここ数週間、実装チェーンを削る作業を続けている」）。
  直近 6 週で 5 本目という飽和リスクへの答えにもなる
- **TDD 降格の扱い**: 全体の流れの中で判断してよい → **シリーズの先行例として、順序の
  強制を外し coverage 床を機械に残した 1 例に短く留める**。4 分解の表は出さない

### 執筆時の精密化ルール（Fable review 由来）

- **日付**: 台帳のセッション時刻は **UTC**、ADR の Date と commit は **JST**。X 投稿は
  8/27 付だが、著者が見たのは **8/28 07:38 JST**。「8/27 の夜に見た」は誤り。
  投稿日と閲覧日を分けて書く（B-2）
- **必要性の段**: 13 件 / 4,580 関数 = 0.3%。人間コードとの比較も時系列増加の実測も無い。
  「分布が命題を証明した」ようには書かず、**著者の作業仮説 + tail が長い実測**として書く（B-3）
- **実行時間とコストの対比**: lint の実行時間も LLM レビューのトークン費用も計測が無い。
  数値の表を作らない。著者発話の引用に留める（B-4）
- **判断則の節**: ADR-0056 が却下した 2 つ（global 数値閾値の一律適用、82 repo への
  backfill）を留保として明示する。書かないと読者が ADR-0042 の退役させた
  「repo と一致しない固定チェックリスト」を再生産する（F-3）
- **裁定と軸を混ぜない**: 文書上の裁定基準は「機構の新設か否か」。「複雑さの向き」は
  その背後の判断軸。ADR-0056 の内容として「複雑さの向きで裁定した」とは書かない（A-2）

### 執筆前に決める / やること

- **F-2 分布表の正本**: ADR-0056 Context にあるのは要約 2 数値（C901 p99 10〜27、
  LOC p90 185〜862）のみ。9 repo の per-repo 全表は scratchpad 由来で揮発性。
  → **全表を載せるなら執筆時に live 再実測して as-of を付ける。しないなら要約 2 数値に

- **A-3 thesis の土台発話**: 中心命題の根拠になった著者発話 3 つは本セッションの会話中の

## 実行手順

### Phase 1 — 執筆

- 新規: `articles/lint-as-subtraction.md`（slug 仮。タイトル確定時に見直す）
- frontmatter は `zenn-format` が正本。`published: false`、`published_at` は Phase 4 で
- 規模: 15,000〜20,000 bytes、H2 8〜10 本（直近 3 本の実績帯）

  なので引かない
- `## 関連リンク` に定型 2 行（Markdown 正本 / 著者 GitHub）+ `review-chain-damping`

### Phase 2 — 構造凍結 → review panel（並列）

`.claude/rules/publishing-channels.md` の Zenn 行に従う:
- `editor` agent
- `prose-clarity-reviewer` agent

- `codex-review` は著者が明示的に求めた場合のみ（opt-in）

2 round 目以降は CRITICAL と変更部分の regression のみ blocking。

### Phase 3 — 著者の内容 GO（通読）→ タイトル

`headline-craft` で候補生成 → `title-reviewer` の findings → 著者が選択。
Zenn は原則 50 字以内、正確さに必要なら 60 字まで。

### Phase 4 — 受け入れと公開

1. `npm run validate`
2. `npm run evidence -- articles/<slug>.md`（deviations 0。公開直前は `--online` も）
3. `/quality-gate articles/<slug>.md`
4. 著者の公開 GO
5. `published_at` を設定して `/publish-article`
6. `npm run generate:index` → `npm run validate` && `npm run check:index`
7. **push を促す**（未 push commit は Zenn の予約に届かない）
